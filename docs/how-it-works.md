# How it works

cigcompile is a Rust command line that reads a CigScript script, checks
it the way `cig check` does, and writes it as a program that runs with
nothing installed. This page is the map, for contributors; the design
decision is in [the backend record](decisions/0001-backend.md).

## Stage A: runtime, payload, trailer

Stage A (every release today) makes a program by appending:

```
+-------------------+-----------+-----------+
|    cig runtime    |  payload  |  trailer  |
+-------------------+-----------+-----------+
     cig's binary     a record    a few bytes
     for the target    (script +   that say
                      checked AST) where the
                                   payload is
```

The payload is CigScript's own `program` record: the script's text and
name, a sha256 of each, the cig version it was compiled for, the
cigcompile version that made it, and a trailer whose last bytes say
where the record started. See CigScript's
[docs/PROGRAMS.md](https://github.com/otmof-ops/cig-script/blob/main/docs/PROGRAMS.md)
for the layout.

At start, cig looks at itself: when it finds the trailer at its end, it
is a compiled program, so it reads the record and runs the script
through the same run as `cig run`. When it doesn't, it's just cig.
That's it.

Why this is the first stage, and what comes after (a bytecode VM, then
Cranelift) is in [the backend decision](decisions/0001-backend.md).

## The runtime search

`--runtime`, or `CIGCOMPILE_RUNTIME`, names the cig a build is
appended to. With neither, the search for this machine is:

1. `cig-runtime` beside this compiler (the one `cargo build` writes
   alongside `cigcompile`).
2. `cig` on `PATH`, when its `--version` is the one this compiler was
   built with.
3. cig's own release for this machine, fetched once and held to the
   sha256 this compiler pins.

For another machine (`--target` names one that isn't this one), the
search is always cig's release asset for it, fetched once.

A static Linux target asks for a static runtime: cig's Linux releases
are static musl builds, and a runtime found here that is dynamically
linked would tie its programs to this machine's glibc. Such a runtime
is passed over for step 3. With step 3 out of reach (offline,
`CIGCOMPILE_OFFLINE=1`) the build is refused with `E1008`.

A dynamic runtime named with `--runtime` is used, and the build warns,
naming what the program needs:

```
warning: /usr/bin/cig is dynamically linked, so its programs need glibc 2.39 to start
  and will not run on most Linux machines; cig's release for x86_64-unknown-linux-musl
  needs nothing (build without --runtime, or cigcompile fetch first)
```

## Pinned digests

`src/digests.rs` carries the sha256 of every runtime cigcompile will
accept from a release: cig's assets, as its release published them,
for the cig version `Cargo.toml` pins. The file is generated by
`ci/digests.sh v<tag>`, which calls
`gh release download -R otmof-ops/cig-script -p 'cig-*.sha256'` and
writes the Rust table.

A test holds the file's version to `cigscript::VERSION`, the one
cigcompile is compiled against, so a release that forgets to run
`ci/digests.sh` fails `cargo test`.

A checksum fetched beside the asset would prove nothing against a
tampered release; one built into the compiler does. `--runtime` names
a runtime by hand (a cig built from source); cigcompile checks that
it is cig of the pinned version and that its format matches the
target (an ELF for Linux, a Mach-O for macOS, a PE for Windows). It
does not check that it is cig's release build.

## The build index

`<cig home>/cache/compile/index.json` remembers what each program
was built from: its script's size, mtime and inode; the runtime's
file id; the pass settings; the sha256 of what was written. A build
that would write the same bytes reads neither the runtime nor the
program, runs no check, and touches nothing — not even the file's
mtime. A no-op rebuild of hello takes about a millisecond.

The index is a shortcut. Lost or damaged, the next build does the
work and writes it again. It is not needed to run a program, and it
is not needed to verify one.

## Writing an output

Every write is a temp file beside the final path, renamed over it.
A build that stops halfway, or whose signer fails, leaves the old
program there, or none — never half of a new one.

A build that writes more than one thing (`--sign`, `--sbom`,
`--emit oci`, `--emit deb`) writes to a staging folder beside the
`--out` first and moves them into place only when every step has
succeeded. See [shipping](shipping.md#all-or-nothing-staging).

## The IR and the passes

`--emit cir` prints the IR ([#3](https://github.com/otmof-ops/cig-compile/issues/3)): CigScript lowered to an SSA-like
form that each pass verifies before the next runs.

The IR carries the step budget (`--max-steps`, `CIG_MAX_STEPS`) the
way the interpreter counts it. A `step` opens every statement except
a `pull`, and a `step.iter` opens every loop body: one mark for each
tick of the interpreter's counter, at the same span. The verifier
holds them in place. A mark never moves, a loop body always opens
with its `step.iter` (V11), and a pass removes a mark only together
with everything else in its block (T3). A compiled program stops on
the same step, at the same line, as the interpreter.

Errors come out where the interpreter puts them. A map literal is
lowered in the interpreter's order: each computed key, then its
`key` check, then the entry's value. A key that is not a string or
an int raises before a later value can. An index, an indexed store, a
member store and a map's computed keys carry the spans of their own
operands
(`--emit cir` prints them beside the instruction's span, as
`idx@3:10`). A wrong index type is reported at the index, and a
value that cannot be indexed at the object, even after a pass has
replaced either operand with a value made somewhere else. The
verifier checks every such span lies inside its instruction (V2).

The passes today are
`fold-consts`, `copy-prop`, `fold-consts`, `sccp`, `dead-pure`, in
that order. Each is read as:

- **fold-consts** replaces constant expressions with their value.
- **copy-prop** replaces `stick a = b; use a` with `use b`, through
  slots that are neither mutable nor captured.
- **sccp** empties the dead side of an `if` whose condition is a
  known boolean constant, unless an effect in the dead branch means
  emptying it would delete work (T3 catches that shape).
- **dead-pure** prunes pure expressions whose result is unused.

Each instruction has a class, read from its kind and the types of its
operands. A **pure** one (a constant, a fresh list, `==`, float
arithmetic, a read of a `stick` where it lives) may move, merge or
vanish. One that **may raise** (integer arithmetic that can overflow,
`/`, an index, a member that can be missing, a float ordered against
a NaN) keeps its place and its order, and goes only where the
verifier proves it cannot raise: its operands are constants that the
interpreter's arithmetic folds, and the constant left in its place is
that result (T4). **Effects** (slot writes, calls, `exhale`, burn
ops) and step marks keep their place and order and are never lost
(T1 to T3), except with a whole `if` arm that a constant condition
never takes. Each pass is its own module, with a golden folder under
`tests/cir/` and a deliberately broken twin that the verifier must
catch.

`--passes-diff` adds a unified diff of what each pass changed, or a
line that says it did not; `--remarks` says the same thing in
prose. Neither changes what a program does: the verifier re-reads
the IR after each pass, and a program's bytes at stage A come from
the script, not from the IR. The level shapes `--emit` only.

Stage B is where `-O1` and `-O2` will start to differ: the passes
there will shape the bytecode a program runs.

### The bytecode lowering

`src/bc` lowers verified IR to the register bytecode of
[#31](https://github.com/otmof-ops/cig-compile/issues/31), the format cig-script's `docs/BYTECODE.md` sets out, and
runs the format crate's verifier on every module it makes (a module
that does not verify is the compiler's bug). A slot is a register for
the whole function; a value has a register from its definition to its
last use. A call moves its callee and arguments into consecutive
registers. `a > b` is `le a, b` then `not`, so the operands keep the
order the interpreter's errors name. A step mark is one `steps`
instruction, a loop sets its nesting before its condition and back
after it, and the line table keeps the IR's span for every instruction.
A slot a closure captures lives in a cell: a fresh one each time its
block runs (each turn of a loop), so a closure made in a turn keeps
that turn's value, and a pull calls itself or a sibling through the
cell its closure was declared into. `for` over `a..b` counts with
`forprep`/`forloop`, and over a list, a map or a string walks the
interpreter's snapshot with `iterprep`/`iternext`; the item is fresh
each turn. An index read or store checks the types of its operands
first, so a wrong index type is reported at the index and a value
that cannot be indexed at the object, as the interpreter reports them,
taking those positions from the spans the IR stores, and an `exhale`
part or interpolation piece is turned to text where the interpreter
shows it, before a later part can change it. A computed map key is
checked by its own `key` instruction, before the entry's value runs.
A `try` is laid out as the format sets out: `try.enter`, the body
(the handler's range), the `ashtray` block, then the `finally` block,
each ending with `try.leave`; `break`, `continue` and `snuff` leave
every `try` they cross first, so each `finally` runs, and a snuffed
value waits in a register no `finally` writes. `cough` is `throw`, and
a builtin, a module or `args` used as a value is `loadg`, read from
the prelude by name. Burns, `pack` and chains are refused with their
construct and position. `tests/bc.rs` runs what it lowers in the
VM and holds its output, errors, positions and step count to the
tree-walker's.

## The box is Linux's

cig's box is the copy-on-write layer and namespaces it uses on Linux
to keep a burn from touching the file system until the whole burn is
ready. Elsewhere it is not available: a boxed hop falls back to the
tin, or is refused.

A compiled program is cig for its target, so a program for a
non-Linux target has no box either. `cigcompile targets` says so in
the "missing" column: `no box (E777, E763)`.

## The differential suite

`tests/differential/` is cigcompile's correctness floor: every
CigScript script in the pinned CigScript checkout is run under `cig
run`, then as a compiled program, and the plan, the output, the exit
code and the files left behind must agree. It fails on any
difference.

```sh
CIGSCRIPT_SRC=../cig-script cargo test --release --test differential
```

It covers CigScript's examples and error corpus, its `tests/scripts`,
and the `cig` fences in its docs. It also holds every `cig explain`
page a program shows to `cig explain`'s, in every output mode, and
runs CigScript's portability probe through cig and with every script
built into a program (`ci/cig-compiled.sh`).

Beyond the pinned scripts, the suite reads a generator: `DIFF_RANDOM=
<seed>:<count>` makes that many programs (functions, declarations,
loops, `try`/`ashtray`/`finally`, pipelines, and burns under `out/`
that cough and roll back), runs each one, and shrinks a differ to the
fewest statements that still differ. Every pull request runs 100 from
a fixed seed; nightly runs a thousand on Linux, macOS and Windows.

## Fuzzing

The compiler is the first reader of code that may come from someone
else, so its front end is fuzzed ([#16](https://github.com/otmof-ops/cig-compile/issues/16)). The four targets live in
`src/fuzz.rs`:

- `parse` — any text into the parser.
- `check` — a parsed program into the checker.
- `lower` — a program the checker accepts lowers to IR that verifies
  through every pass.
- `program` — any bytes as a program's trailer.

`fuzz/` holds them for cargo-fuzz, and `.github/workflows/fuzz.yml`
runs each for five minutes a night, seeded with CigScript's own
scripts. `tests/fuzz_smoke.rs` drives the same bodies on stable over
a fixed sample on every test run.

Every target runs on the same 256 MB stack the compiler's main thread
is given, so a script nested deeper than the parser allows is refused
(`E208`), never a stack overflow.

## Pinning a new cig

cigcompile pins exactly one cig version (`Cargo.toml`'s `cigscript`
tag). Bumping it is three steps and a run:

1. **`Cargo.toml`** — change the `cigscript` tag to the new one and
   run `cargo update` so the lockfile picks the new hashes.
2. **`ci/digests.sh`** — run `bash ci/digests.sh v<new tag> >
   src/digests.rs`. The script reads the release's `.sha256` files
   through `gh release download` and writes the Rust table. The test
   `the_digests_are_for_the_pinned_cig` holds the file's version to
   `cigscript::VERSION`, so a mismatch fails `cargo test`.
3. **`ci/gen-third-party.py`** — regenerate `THIRD-PARTY-NOTICES.md`
   from the lockfile.
4. **The differential suite** — run it against a checkout of the new
   tag:
   ```sh
   CIGSCRIPT_SRC=../cig-script cargo test --release --test differential
   ```
   A single byte of difference anywhere fails the build.

Then CI builds for five machines and runs the whole suite there too.
A release goes out only when every machine and the differential
suite agree.

## The crates

Today cigcompile depends on `cigscript` as a git dependency, pinned
to a tag. That brings the parser, the checker, the kernel, the
diagnostics and the standard library in as one crate, which keeps the
compiler simple at the cost of linking all of cig into the output.
[#1](https://github.com/otmof-ops/cig-compile/issues/1) is the crate split that lets stage B's runtime be only what a
program uses — the smaller runtime #36 and #14 are aiming at.

The `vm` feature turns on the bytecode lowering, `--emit bc` and their
tests. It needs a cigscript that carries the bytecode VM and re-exports
its format crate, which no cig release does yet, so it is off by
default and the compiler builds at its pinned tag without it.

## The launcher

There is no launcher: `cigcompile` and `cig-runtime` are both built
as `[[bin]]` targets of the same crate, so `cargo build --release`
produces both. `cig-runtime` is `cig` of the pinned version, linked
the way cargo links it on this machine; a build that wants to ship
cig-runtime beside cigcompile as a static Linux runtime builds it
for the musl target, as the README says.

## The tests

`tests/` holds the end-to-end suite as ordinary Rust tests, plus the
differential one that reports itself (`harness = false` in
`Cargo.toml`). A unit test for any passes, writers and readers lives
beside its module in `src/`.

## Where a start goes

A program is cig, so its start is cig's start plus a payload lookup:
the tail of the file read, the trailer parsed, the record found. On
Linux the whole thing is about 5 ms for `hello` on this machine; the
first 1.6 ms is spawning the process, the rest is cig starting and
the script's one line of work. The budget tracked in [#14](https://github.com/otmof-ops/cig-compile/issues/14) is 5 ms at
stage A, 3 ms at stage C and 2 ms at stage D.

The size today is cig's: about 13 MB on Linux, 8 MB on macOS, with
the payload a few hundred bytes. Stage B and the crate split ([#1](https://github.com/otmof-ops/cig-compile/issues/1))
are what take size and start-up down together; see the
[roadmap](roadmap.md).
