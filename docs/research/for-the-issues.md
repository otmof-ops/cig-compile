## From: Cranelift: its IR and its acyclic e-graph mid-end

[studies/01-cranelift-ir-and-mid-end.md](studies/01-cranelift-ir-and-mid-end.md)

- **cig-compile#32 (stage C).** Lowering targets CLIF with block parameters, not phi, and keeps CIR's spans on every CLIF instruction through `SourceLoc` and debug tags (entries 1, 3, 17). Slots go through `SSABuilder`, following the Braun-et-al. construction; captured slots stay boxed, and exceptions ride the result-convention path, with `try_call`'s exception table reserved for the handler shape only when it earns its complexity (entries 4, 17). The lowering emits `cig_rt_burn_enter`/`cig_rt_burn_leave` and the burn-op calls as opaque skeleton calls so Cranelift never reorders across them (entry 13, entry 6). Stage C passes `opt_level=none` when `-O0` is requested, `speed` for `-O1` and `-O2`, `speed_and_size` for `-Os` (entry 15), and calls `Context::compile_with_cache` for a per-function cache keyed by the function stencil (entry 16). Nothing cig hands Cranelift needs the inliner's trait on the back-end side: all inlining happens on CIR before lowering, for the backtrace, class and burn-boundary reasons entry 14 names.
- **cig-compile#33 (the optimizer).** The pass list splits by what only CIR knows. cig's `cig-script/src/lower/cir/pass/` holds four passes today: `fold-consts`, `copy-prop`, `sccp`, `dead-pure` (`cig-script/src/lower/cir/pass/mod.rs` `NAMES`). #33 plans nine more on the CIR side, none yet in the clone: `inline`, `closure-elide`, `rc elision`, `tail calls`, `string builder`, `burn coalescing`, `unswitch`, `escape`, `scalar-replace`. Every one of those nine stays on the CIR side when it lands, because only CIR knows burn class, step marks, `MayRaise`, captures, backtrace identity, ordered maps and IEEE-exact floats. On the CLIF side, Cranelift's mid-end does the heavy lifting: GVN and LICM fall out of elaboration, rematerialization of constants and add-with-immediate ops is one rule, and bounds, overflow, strength-reduction and small-branch rewrites are rules in `arithmetic.isle`, `icmp.isle`, `cprop.isle`, `skeleton.isle` and `spectre.isle` (entry 18, entries 7-9, 13). Cranelift's rule set is the directional shape cig's rules take when they land: `subsume` whenever a rule drops a value-use, no rewrite to worse code, no bare commutativity (entries 10, 11). Each rule is pinned by a filecheck test; the broken-twin negative test cig already has for its four existing passes (`cig-script/src/lower/cir/pass/broken.rs`) is kept (entry 12).
- **cig-compile#37 (build speed).** The egraph pass is the one large pass in Cranelift's pipeline; it only runs at `opt_level != None`, so `-O0` and stage B get out quickly (entry 15). Per-function parallel codegen over Cranelift means the loss cost of stage C is wall-clock per hot function (which is short) rather than a serial pass list (entry 15, entry 2). The incremental cache cuts rebuilds of unchanged functions to a byte-blob read (entry 16): a cache key covers the `FunctionStencil` and the ISA, and `apply_params` patches the per-call-site data on a hit, so the output bytes stay reproducible. cig's own build cache in `cig-compile/src/cache.rs` wraps this on the module side.
- **cig-compile#39 (correctness at scale).** Chaos-mode shuffling (entry 20) is the shape cig's differential suite adopts to prove pass correctness does not accidentally depend on the default ordering of equally-good rewrites. The filecheck test convention (entry 12) composes with cig's existing goldens and the broken-twin negative tests under `cig-script/src/lower/cir/pass/broken.rs`. For large-scale correctness, Cranelift's fuzzgen (`cranelift/fuzzgen`) is a model for `cig-smith`; stage C can be plumbed into it once the lowering has a stable shape.
- **cig-compile#35 (values and memory).** Alias analysis (entry 13) is the Cranelift mechanism that depends on the memory-region tagging cig attaches to lowered loads and stores. cig's own value representation (24 bytes today, moving towards 16 or an 8-byte NaN-box at decision (a)) decides what the alias regions look like, because an `Rc<RefCell<...>>` list and a refcounted string are not the same region. The stage C writer picks regions when the runtime library's ABI stabilizes in #4.

## From: Cranelift's back end and regalloc2

[studies/02-cranelift-back-end-and-regalloc2.md](studies/02-cranelift-back-end-and-regalloc2.md)

- **cig-compile#32 (stage C):** the back end would be used whole, with the knobs in the table above. cig has no Cranelift dependency today and no native code path. Decision (a)'s value size settles which convention fits in registers: a planned 16-byte value (two words) fits under `SystemV` with `enable_llvm_abi_extensions` (three return regs) or `Tail` (eight); today's 24-byte value needs `Tail` on x86-64; a one-word NaN-boxed value fits under plain `SystemV` (entry 7). The result convention for `MayRaise` (the raise is a thrown exception through `try_call`) would map to `ExceptionTableData` with one tag per cig error class (entry 9). Tail calls would land on `return_call` when caller and callee are both CIR functions (entry 8). The one knob cig would add at stage C that Cranelift does not already have is `cig_rt_budget_exhausted(span)`, an opaque skeleton call the lowering would emit per `StepSite` from CIR (entry 1).
- **cig-compile#37 (build speed):** the pass list Cranelift runs (names in `timing.rs`, entry 20) would be the ceiling cig pays per function at stage C, and `opt_level=none` with `Algorithm::Fastalloc` the floor (entry 13). Incremental compilation at the function level would be the lever: a change to one function invalidates only its stencil (the IR of the other functions, module-level relocations unchanged), and Cranelift's incremental cache (entry 16 of the first study, `incremental_cache.rs`) is the mechanism. `-O0` build time is entry 13's measurement.
- **cig-compile#39 (correctness at scale):** regalloc2's symbolic checker would be the one in-allocator gate (entry 14). The differential suite would stay at zero differences by re-running the oracle on the stage-C output and comparing per-program outputs; the checker would be an extra guard that catches an allocator bug before the differential does.
- **cig-compile#40 (hardening):** every flag cig would turn on is a setting Cranelift already defines (entry 19); none are custom, which would keep the gate narrow and cig's attack surface small.
- **cig-compile#41 (targets):** the trait abstraction (`ABIMachineSpec` and `MachineEnv`, entry 6) covers x86-64 and aarch64 without a per-target code change above the ISA layer; a riscv64 build would re-use the same shape (Cranelift already ships `isa/riscv64/`). The target triple selects the unwind format (entry 15), the ABI, and the register environment. cig's cross-build matrix would be the product of (`x86_64-linux`, `x86_64-windows`, `aarch64-linux`, `aarch64-darwin`) and (`speed`, `speed_and_size`), with the ISA-specific hardening flags set per target.

## From: Wasmtime as an ahead-of-time embedder of Cranelift, and Winch

[studies/03-wasmtime-ahead-of-time-and-winch.md](studies/03-wasmtime-ahead-of-time-and-winch.md)

- **cig-compile#32 (stage C).** Entries 1 to 6 cover the image, its sections and the load-time guarantee of no writable-and-executable memory. Entry 3 argues for resolving all cross-pull calls at build time and routing every runtime call through a per-vmctx table; entry 12 makes that concrete. Entries 7 to 9 argue against adopting Wasmtime's buffered fuel for cig's step budget: buffered is not exact, so cig charges per `Step` mark instead, keeping the register-plus-check shape. Entries 10 and 11 give the two trap paths; cig starts with the libcall path. Entry 13 is the address map that turns a trap pc into a source position. Entry 14 argues for keeping cig's result convention for `throw`, with Wasmtime's exception-table layout as the measured fallback.
- **cig-compile#36 (start-up and size).** Entries 1, 2, 4 and 13 are where the size budget is spent: the sections are small per-byte, the address map and the stack maps dominate. The pre-compile docs' own strip-down (entry 1's `examples-minimal-cwasm.md`) is the model for `cigcompile size <program>`: an address-map opt-out and a symbols opt-out are the two biggest knobs.
- **cig-compile#37 (build speed).** Entries 4 and 16 are the two ways compile time is reduced: a per-function incremental cache and a Winch-style baseline. Both shrink the critical path for a one-line change.
- **cig-compile#40 (hardening).** Entry 5 (the publish sequence) and entry 11 (libcall traps, no signals) together bound cig's exposure: W^X on every mapping, trap handling without a signal handler for first-class embedders.
- **cig-script#256 (cig-cherry).** Entry 16 (the cache worker) is the model for cherry's cache. Entry 17 (Winch) is tier 2's compiler. Entry 15 (stack maps) is what the cycle collector needs so a specialised native frame does not hide a cycle. Entry 12 (builtin table) is how cherry code reaches the runtime without a relocation at map time. Entry 14 is the one place cherry may need an exception-table-style side-exit, on the day guarded code starts throwing from deep inside an inlined call.

## From: SpiderMonkey's CacheIR and Warp: one inline-cache language for four tiers

[studies/04-spidermonkey-cacheir-and-warp.md](studies/04-spidermonkey-cacheir-and-warp.md)

- **cig-compile#32** (stage C: native code, guards). Entries 2, 3, 7, 8, 16, 17, 18 and 19 together give what the issue's new comment (2026-11-15) names in four points: a shared crate with one op-table and one lowering (entries 2, 7, 19), a function as a unit with guards that exit (entries 16, 17), snapshots and recover for the step count and the open tries and burns and the journal (entry 17 is explicit about the cig-specific fields decision (d) needs), and `InvalidateIfFrequent`/`DisableIfFrequent` as the shape of recompile-then-blacklist (entry 18). The comment's "ahead of time, not a JIT" is kept: nothing in CacheIR or its transpiler needs writable-and-executable memory. Fuses (entry 20) are an orthogonal add-on and belong to the second pass of #32.
- **cig-compile#33** (the optimizer and PGO). Entries 5, 9, 11, 12, 13, 14, 15, 18 and 20 feed this: five-to-six specialized stubs per site (entry 11), folded shape guards (entry 12), op-level cost and per-site happiness (entry 13), one profile that drives the next tier (entry 14), trial inlining as the vehicle for per-caller specialization (entry 15), and fuses as a way to remove guards from hot loops without losing correctness (entry 20). The IR-as-table discipline of entry 2 means a new pass on the stubs' IR is a new consumer, not a new generator.
- **cig-compile#34** (types for speed). Entries 4 and 5: typed operand ids and per-generator value-driven attach decide which specialization the compiler sees; entry 6 is where decision (h) would reduce lookups to a slot index.
- **cig-script#256** (cig-cherry, tiers, guards, fallback). Entries 9, 10, 14, 15, 16, 17 and 18 are the map: cig-cherry drives the same code generator per function from a snapshot taken on the main thread (entry 16), recompiles or blacklists on repeated bailouts (entry 18), falls back to the VM at the matching PC with a cig-specific snapshot (entry 17), and shares the same CacheIR corpus as the VM (entries 9 and 14). The AOT corpus (entry 10) is the shape of `cig cherry warm` and of `cig tin`'s cache.
- **cig-script#243** (A8, B7). Entry 14 answers A8: ICScript's `warmUpCount_` plus per-stub `enteredCount_` is the design the single counting mechanism should carry (one counter per function and one per cache entry). Entry 17 answers B7: a snapshot is cig's job to get exactly right, and the recover-plus-bailout split is the mechanism. The step budget's ticks remain on the CIR's `Step` marks (`cig-script/docs/BYTECODE.md`, `steps`); the snapshot copies the current count into the rebuilt baseline frame.
- **Decisions (b), (c), (d) and (h).** (b) one inline-cache format: the YAML table of entry 2 is where cig writes its ops. (c) one counter and profile format: `ICScript` with per-function warmup and per-stub enteredCount (entry 14). (d) guards, snapshots, exits that keep the step count, the open tries and burns and the journal: entry 17's cig-specific snapshot shape. (h) shapes for records: entry 6 says what a cig shape would be, and its census says whether to pay for it.

## From: Lean 4, Koka and Lobster: reference counting made cheap

[studies/05-reference-counting-lean-koka-lobster.md](studies/05-reference-counting-lean-koka-lobster.md)

**cig-compile#33 (the optimizer, section `rc elision`).** Stage C's `rc elision` is three things, done in order: a liveness-driven dec placement at scope end or earlier when the value is dead (entry 1, Lean's shape; entry 2, Koka's shape, which places drops sharper by one or two sites), borrow inference on function parameters (entry 4, by fixed-point) backed by a per-module borrow table (entry 5), and the derived-borrow graph that keeps a projection from needing its own inc/dec (entry 17). Reset-reuse and reuse analysis (entries 6-9) are not taken, by rule 6. The "unique at run time" check is a small but valuable fragment (entry 15), moved to the builtin layer. Per-block coalescing (entry 18) is a cheap post-pass that reduces residual traffic; dead-pure (entry 19) already exists in cig's pass list and is the prerequisite.

**cig-compile#35 (values and memory).** The header and count encoding Lean and Koka use fit a shape-bound value kind (entry 11); for cig's existing `Value`, Rust's `Rc` gives the inline dec fast path (entry 13) and a safe uniqueness check (entry 15). The deep-free worklist (entry 12) is one afternoon's work in safe Rust and removes a real failure mode measured on cig 1.25.0: fine at 4.0 million levels, aborts at 4.5 million levels (`thread 'cig' has overflowed its stack`, exit 134 on both engines), within the default step budget. The "freed cell reused for the next same-shape allocation" idea does not apply to cig's `Vec`-backed `List` or `IndexMap`-backed `Map` (entry 16); if stage D adds record values, the mechanism from entries 8 and 9 becomes relevant then, and Lorenzen and Leijen's drop-guided variant of the analysis is the better starting point. The `thread-shared` transition in both runtimes is a design cross-reference, not taken, because cig is single-threaded.

**cig-script#243, Part 2 trick 3 (Perceus).** The precise dup/drop placement is one CIR pass (entry 2); the uniqueness-driven `drop_special` (entry 10) is a second, smaller pass, but its full form (hot path reuse of a freed cell) is not for cig. The two together are what the Perceus paper calls garbage-free; the one of them without the other is what cig gets. Borrow annotations on cig's hottest builtins (entry 5) are the complement to the pass: without them, dup/drop placement still dup's every argument into every call.

## From: Swift's SIL and its ARC optimizer, and Roc's reference counting: ownership written into the IR

[studies/06-swift-ownership-and-arc-roc.md](studies/06-swift-ownership-and-arc-roc.md)

- **cig-compile#33 (the optimizer, including `rc elision`):** the three passes this study recommends for the planned `rc elision` are (a) a signature pass `owned-to-borrowed` (entry 8), (b) a clone-elision pass `clone-elide` (entry 5), and (c) a drop-canonicalize pass (entry 7). All three run on a CIR extended with the vocabulary of entry 14 (Clone, Drop, Borrow, `Ownership` on each value). The design-point reject is the older pairing dataflow (entry 6): it is the shape cig would have to build without ownership in the IR, and it is specifically rejected under rule 5 for its extra ordering burden. A separate `uniq-hoist` pass (entry 10) belongs under `licm` rather than `rc elision`, but comes from the same mechanism. The level table in cig-compile#33 should carry `clone-elide` at `-O2` and the signature pass at `-O3`, matching Swift's own layering where OSSACanonicalizeOwned runs at `-O` but the function-signature pass is a late inter-procedural step.
- **cig-compile#35 (values and memory):** the CoW uniqueness primitive (entries 9, 16) is the biggest single win for cig's `Rc<RefCell<Vec<Value>>>` and `Rc<RefCell<IndexMap<String, Value>>>` data structures. Two new opcodes and the matching branch at `SetIndex`/`SetMember` sites would unlock the mutate-in-place path and shrink `nbody`, `fannkuch`, `strbuild` and `maps`. Reuse and drop specialization (entry 12), the deeper Perceus techniques, are rejected for cig by rule 6 and by the structural absence of static constructor shapes; the issue should not count them as available wins. The issue's plan to "typed list storage with widening" (bitset for a list of booleans, packed i64 for a list of ints) does not interact with ownership: the uniqueness check works the same whether the inner storage is tagged `Value` or a packed homogeneous array.
- **cig-script#243 (the VM's study list, including Part 2 trick 3 on Perceus):** this study's entries 11 and 13 are the applicable pieces (borrow-signature inference and `UpdateModeId`-driven in-place updates). Entries 12 (reset/reuse, drop specialization) are not applicable to cig for the reasons the study names. The study should carry entries 5, 7 and 8 into cig-script#243 as the shape the VM's planned Perceus pass takes on OSSA-style CIR, not on the paper's immutable-value model. A design note worth adding to cig-script#243: the VM and stage C share the code generator, so an ownership annotation on CIR is one design, not two; the signature pass of entry 8 lands once, and both the VM and stage C read its output.

## From: LLVM's optimization pipeline, and Alive2's translation validation

[studies/07-llvm-pipeline-and-alive2.md](studies/07-llvm-pipeline-and-alive2.md)

- **#33 (the optimizer).** The pass order at `-O1` is `fold-consts, copy-prop, fold-consts, sccp, dead-pure` already (five entries in `cig-script/src/lower/cir/pass/mod.rs`'s `level(1)`, not four; `fold-consts` runs twice so `copy-prop`'s exposed constants are folded). At `-O2`, the carry-away above adds a scoped CSE (entry 7), the two-LICM pattern around a planned loop-rotate (entry 8), a peephole combiner with the "strictly simpler" rule (entry 9), a bottom-up inliner with a CIR-size threshold (entries 2, 10), and bounds/overflow-check elimination as a `MayRaise`-aware pass (entry 8). The census (`data/census/README.md`) settles the inline-site shape (28 of 29 compute call sites are single-callee, 97.7% of arithmetic executions at one type pair) and the pin on step marks (a quarter of executed instructions in compute programs). `bisect` is one global counter in `run_passes`, incremented on each transform pass invocation, with `--opt-bisect-limit=N` as the knob (entry 12). The levels `-O0` through `-O3` and `-Os` map to inline thresholds taken from `InlineCost.h` but measured, not copied: 225 default, 250 at `-O3`, 50 at `-Os`, 5 at a future `-Oz` (entries 4, 10). The two-stage pipeline (simplification then optimization) is where `-Os` stops before the late aggressive passes to stay under the 4 MB budget (entries 1, 5).

- **#37 (build speed).** The analysis manager with a `PreservedAnalyses` return type is the lever (entry 11); when `fold-consts`, `copy-prop`, `sccp` and `dead-pure` do not change the call graph or the CFG, the analyses they would invalidate are kept. Entry 1's two-stage shape trades a second pass of the function pipeline for simpler late passes. The InstCombine discipline of one sweep per invocation (entry 9) keeps the per-pass cost bounded.

- **#39 (correctness at scale).** TV lands as a new module in `cig-compile/src/` that calls into the CIR passes and the SMT solver; it uses the three refinement checks CIR actually needs (entries 14, 15), skips interprocedural passes as Alive2 does (entry 16), and runs on each PR as part of the fuzz corpus (entry 17). The byte-equal shortcut (entry 17) keeps the budget realistic: most pass applications produce no change. The `broken.rs` discipline cig already has for each pass (`cig-script/src/lower/cir/pass/broken.rs`: a hand-broken twin the verifier must catch) is the structural half; TV is the value half (entry 17). The 99 LLVM bugs in `alive2-v21.0/BugList.md` set the expectation: an optimizer, once wired up with TV, will shed miscompiles that structural rules alone would not have caught. Alive2's own §8 report of 121 refinement violations in the LLVM unit tests, of which 47 were reported upstream, is the shape #39's `a_planted_miscompile_is_found_by_the_pr_fuzz` is aiming for.

## From: Go's compiler: a short pass list, rewrites as data, a linker that drops what the program never uses, and a profiler the program carries

[studies/08-go-a-small-fast-compiler.md](studies/08-go-a-small-fast-compiler.md)

**cig-compile#33 (the optimizer).** The 60-pass table and its 42-constraint order check (entry 1) is the first lesson: a single file, a single `Pass` record per pass, a single boolean per Func for optimize on/off, and 26 required passes that run even at `-N`. cig's `cig-script/src/lower/cir/pass/mod.rs` already has the shape; it should scale from 4 passes to 20 with the same discipline. The rule-driven rewrite layer (entries 3, 5, 6) is what Go uses for most of its optimizations: a `.rules` file, a Rust generator, a `rewrite.go`-shaped fixed-point loop, with CIR's `Class` as the rule's safety boundary. `prove` (entry 7) is the pass that gives cig bounds-check elimination, which the comparison with LuaJIT in `cig-script/docs/research/luajit.md` (38 against 15 instructions for an indexed read) names as the gap to close; a prove-shaped pass needs `len` values in CIR, per-value integer limits, and a `T4`-protected `RaiseFreeIndex` opcode. The inliner budget (entry 10) is cheap to adopt once CIR has an inliner at all; the pragmas map to `requires_burn` and a user `no_inline`. Devirtualization (entry 11) does not apply to cig; the CacheIR study (file 04) is the right pattern. Walk's separation (entry 15) is what CIR already enjoys, and the lesson is the cleanness, not a port.

**cig-compile#36 (start-up and size).** Linker dead-code elimination (entry 16) is the biggest finding: any reachable `light`, `CallBuiltin` by dynamic name, or `CallMethod` on `Ty::Dynamic` is cig's equivalent of `REFLECTMETHOD`, and the moment one is reached the payload cannot drop any builtin by name. The design question for stage b is which of the 21 benchmark programs' reachable builtins are provably by static name, which only through a dynamic reference, and whether a payload shrink pays at all. The pc-ln table (entry 17) is the other half of start-up size: Go's figure for the table is under 20 percent of code size; for cig, the span-per-instruction already in CIR is the data, so carrying it as a pc-map for cig-cherry is close to free.

**cig-compile#37 (build speed).** The build cache (entry 13) is already in cig's `cache.rs`; the method Go has right is the salt from the compiler version so a bug in one build does not read another build's output. `Subkey(parent, desc)` is a small primitive that pays off in three places (signed module id, stage-b payload id, carton-cover id). The parallel function compilation (entry 14) with longest-first ordering is a small win that costs nothing to adopt; the unified export format and the versioning discipline on the writer is more directly relevant to cig's stage-b payload, which already carries a version field but needs the "writer writes version N+1 guarded, readers on N stay oblivious" rule written down.

**cig-compile#38 (debugging and profiling).** The built-in CPU profiler (entry 18) is the design decision (c) for cig: a sampling profiler that writes the same pprof file that `--profile-use` reads (entry 12). The buffer sizing (1 MiB for 19 seconds at 100 Hz, 64 max stack depth) is a sensible starting point. The pc-ln table (entry 17) is what the profiler's stack walker reads; cig-cherry, when it lands, also reads it.

**cig-compile#17 (self-hosting).** `cmd/dist/buildtool.go` (entry 20) is the right discipline for a self-hosted compiler: a named older version builds the current one, with a convergence pass that re-builds and checks for bit-identical output (rule 8). cig-compile is in Rust and will remain so; the lesson is the naming and the convergence, not the mechanism.

## From: Types for speed: Julia's abstract interpretation, .NET's shared generics and guarded devirtualization, and rustc's monomorphization

[studies/09-types-julia-dotnet-rustc.md](studies/09-types-julia-dotnet-rustc.md)

- **cig-compile#34 (stage D).** The lattice this study proposes for CIR is three refinements adjoined to today's `Ty`: constants (already present in `Kind::Const`, lifted into the lattice so a `copy-prop` of a `Const` carries forward), partial records (a `ShapeId` per `Map` of fixed string keys; demoted on a dynamic key, as the issue already requires), and a two-element union (the only width the census justifies; `Union2(A, B)`). The inference pass is intraprocedural first (entry 1), interprocedural at a fixed point over SCCs (entry 1 again), with signature widening at specialization (entries 6, 7). The specialization cap this study proposes is 2 to 3 distinct inferred argument-type rows per function, falling back to `Dynamic` on exceedance (entry 3): less than Julia's `max_methods = 3` because the census says 15 of 20 compute programs are at one row and cigo is at 2 or 3 rows for the hot functions. The result-type table for builtins is the prerequisite (entry 4), and per-builtin effects (`terminates`, `consistent`, `nothrow`) come from the same table (entry 5). Union splitting at a call site with a `Union2` receiver is the one new pass (entry 8).
- **cig-compile#35 (values and memory).** The .NET split of "share for layout, specialize for layout" (entry 12) is the shape for cig's refcounted versus unboxed kinds; first-class structs (entry 14) is the shape for cig's records when the shape is known.
