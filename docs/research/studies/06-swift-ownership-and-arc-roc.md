## What cig should carry away

- Swift's model is that **ownership is in the IR itself**, not in a side table: every SIL value carries an `OwnershipKind` of `None`, `Owned`, `Guaranteed` or `Unowned`, and the verifier rejects any program whose uses do not line up with that value's rules (`copy_value` makes a new `Owned`; `begin_borrow` makes a `Guaranteed` whose scope is a matched `end_borrow`; `destroy_value` ends an `Owned` value's single lifetime). The verifier runs after every pass. That is the model cig's `verify.rs` already has the shape for: one rule set, re-checked between passes (entries 1, 2, 14).
- The ARC optimization that matters is not the old retain/release-pair dataflow (entry 6); it is **what ownership kinds make free**. A `copy_value` of a value already `Guaranteed` by its definition can simply vanish, no dataflow required: the uses are already "non-consuming" by their operand constraint (entry 5, `CopyValueOpts.cpp` and `OSSACanonicalizeOwned.cpp`). This is the design lesson for cig's planned `rc elision`: the pass is small when the IR carries ownership, and the pass is a dataflow when it does not.
- A **lexical lifetime** is the "cleanup that can be observed" case cig's rule 6 names. Swift marks the SIL values that come from source-level `let`/`var` as lexical (`begin_borrow [lexical]`, `move_value [lexical]`, lexical arguments, `alloc_stack [lexical]`), and defines three "deinit barriers" (synchronization points, weak/unowned loads, pointer accesses) across which a destroy may never move. cig's burns, chains, file handles and `Burn` regions are the direct analogue: an attribute on the owning value and a short list of barriers is enough to say "this value's destroy stays where it is" (entry 4).
- **Function parameter convention is where the biggest wins are.** Swift's `OwnedToGuaranteedTransform` changes an owned parameter to guaranteed when every path through the callee has a matching release at the epilogue, lifting that release and the caller-side retain out of the call pair entirely (entry 8). cig's `Value` derives `Clone` and the tree-walker (`interp/`) uses that clone; the census's measurement of the VM shows the median compute program spends 50.0% of its register moves copying a counted value (`data/census/README.md`, "Half the moves copy a counted value"). A signature analogue on CIR functions (an `owned`/`borrowed` bit per parameter) is the direct port and feeds decision (g).
- Roc's design, measured against the paper it cites in its own source: Roc inserts `inc`/`dec` using a **borrow-signature analysis** (fixed-point dataflow over SCCs of the call graph; parameters start `Owned` and get marked `Borrowed` only when safe) and then places `inc` at first use and `dec` at last use (entry 11). The analysis is in `crates/compiler/mono/src/borrow.rs`, the placement in `inc_dec.rs`; both run on `mono` IR after specialization. For cig, `borrow.rs`'s shape is the one to adopt: a one-bit-per-parameter signature set by fixed-point over the call graph, computed between lowering and the back end (entries 11, 14).
- Roc's deeper passes (**reset/reuse** and **drop specialization**, both direct from Perceus) depend on a static constructor shape (the memory about to be freed has a known layout, so the next allocation of that layout reuses it). cig's lists and maps have no such shape: they are hash maps and growable arrays, not constructors (entry 12). The practical thing cig takes from Perceus is the shape of the insertion pass, not the reuse (entry 11). Entry 12 is a reject by rule 6 as to reuse; entry 11 is a straightforward adapt.
- The **copy-on-write uniqueness primitive is the real win for cig's lists and maps.** Swift's `is_unique` / `begin_cow_mutation` tests the strong reference count at a single word and returns 1 only when the count is 1; the compiler then knows a mutation can happen in place (entries 9, 10). cig's `List = Rc<RefCell<Vec<Value>>>` and `Map = Rc<RefCell<IndexMap<String, Value>>>` already carry the count and the cell; a VM opcode that tests `Rc::strong_count == 1` on a receiver and chooses between the mutate-in-place and clone-first paths is a small change against a large speedup for `push`, `set`, `+=` and `insert` (entry 16).
- Roc's rewrite in `src/` (the Zig compiler) **has not yet reached reference counting**: `src/README.md`'s status table shows the "Reference Counting" row empty for every column at this pin. The Rust compiler under `crates/compiler/` is the one to study (entries 11, 12, 13). This is a measured observation about the pin, not a prediction (`src/README.md`).
- The **hoisting of uniqueness checks out of loops** (Swift's `COWArrayOpt`) is the rule-6-safe way to get in-place mutation working inside a loop: the original `make_mutable` stays in the loop (cig's rule 6 would forbid removing it), a copy is hoisted to the pre-header so the in-loop uniqueness check folds to a constant on later iterations (entry 10). This is the shape of the pass cig's planned LICM would use for `push` in a loop.
- **Stack promotion** is the other primitive cig takes from Swift directly (entry 18): a `List` or `Map` that does not escape its function can be arena-allocated and skip the reference count entirely. The escape analysis Swift uses (summarized function-effects) is a reasonable shape for CIR; the win is in the same places as entry 16's uniqueness-mutate, but through a different mechanism.
- **The pipeline is a stack of local rewrites**, not a global dataflow: entry 5's `clone-elide`, entry 7's `drop-canonicalize`, entry 8's `owned-to-borrowed`, entry 10's `uniq-hoist`. Each is a pass over CIR, each is verified by T1 to T7 between, and each has a negative test (a hand-broken twin) in the style of cig-compile#33's existing `broken.rs`. The order across them is: signature first (entry 8 changes signatures, so every call site reads the new signature), then elision (entry 5 removes redundant clones), then drop-canonicalize (entry 7 shortens live ranges), then uniqueness hoisting (entry 10 lifts a check out of a loop).

## Design points

### 1. The ownership kinds and the instructions that carry them

- **What it does, and why.** SIL (Swift's intermediate language) marks every value with a static `OwnershipKind` (`None`, `Owned`, `Guaranteed`, `Unowned`; a fifth value `Any` is the empty constraint for operands) and every operand of every instruction with an "ownership constraint" (`docs/SIL/Ownership.md` §Ownership Kind; `include/swift/SIL/SILValue.h` `struct OwnershipKind`). A value's uses are partitioned into "non-lifetime-ending" and "lifetime-ending": the lifetime-ending uses jointly post-dominate every other use, and there is exactly one lifetime-ending use on every reachable path (prevents leaks and use-after-frees). The instructions that carry ownership are then small and few: `copy_value` produces a new `Owned` (+1), `destroy_value` consumes an `Owned` (-1), `begin_borrow` makes a scoped `Guaranteed` whose only valid ending is a matched `end_borrow`, `move_value` ends an `Owned` lifetime and starts a new one (`docs/SIL/Instructions.md` §copy_value, destroy_value, begin_borrow, end_borrow, move_value). A function in "OSSA" has the `[ossa]` attribute; the optimizer runs on OSSA, then lowers away to non-OSSA for IRGen. The lattice carries: `None` is top, `Any` is bottom, and the three middle kinds each sit between the two. Trivial types (`Int`, `Float`, a non-payloaded enum case) are `None`: they need no management.
- **Owned, Guaranteed and Unowned in detail.** An **Owned** value is "move-only" in the SSA sense: it is consumed exactly once along every path, either by a `destroy_value` (actual destruction) or by a "forwarding" instruction like `upcast`, `switch_enum`, `checked_cast_br` that transforms the value, consuming it and producing a new `@owned` result. A **Guaranteed** value is scoped: its liveness depends on an enclosing `@owned` or `@guaranteed` value that is statically known to be live over the whole borrow region; the scope is bounded by an `end_borrow` (or by the function exit for a `@guaranteed` function argument). An **Unowned** value is instantaneously valid only; before it is used in any `@owned` or `@guaranteed` context it must be copied with `copy_value`. This is the model for ObjC unsafe-unowned arguments and for bitcasts of trivial-to-non-trivial types; it is never consumed. The join operation on the lattice is used when values from two control-flow paths meet at a phi: `Owned join Guaranteed = None`, which means "the joined value is unmanageable" (`docs/SIL/Ownership.md` §Ownership Kind).
- **Value Ownership Kind versus Ownership Constraint.** The same lattice names a value's static kind and an operand's constraint, and the verifier's rule is: given `op(i)` an operand of instruction `i` and `v` the value it refers to, the join of `OwnershipConstraint(op)` with `ValueOwnershipKind(v)` must equal `ValueOwnershipKind(v)` (`docs/SIL/Ownership.md`, from the "join" rule). Operationally: a value's kind does not change at an operand, and an operand with constraint `Any` accepts any kind without changing it. This is why many instructions declare their operands `Any`: they do not care about ownership, they take whatever comes.
- **For cig: adapt.** By rule 5 (identical behavior on every engine) and rule 1 (burns never move): the ownership vocabulary is the right shape for cig's optimizer, but only four of the five kinds are relevant and the vocabulary is coarser. cig has no weak references and no Objective-C bridge, so `Unowned` and `None` of the Swift sense collapse: cig's analogue is `Pure` (trivial) and `Counted` (participates in reference counting). cig's form: a new `enum Class` member beside `Pure`, `MayRaise`, `Effect`, `Step`, or a parallel `Ownership` enum on `ValueInfo` in `cig-script/src/lower/cir/ir.rs`. The instruction analogues are a `Clone(ValueId)` (Swift's `copy_value`) of class `Pure`, a `Drop(ValueId)` (Swift's `destroy_value`) of class `Effect` (chains, file handles are observable), a `Borrow(ValueId, scope)` (Swift's `begin_borrow`/`end_borrow` pair) that produces a shared reference with a scoped lifetime, and no `move_value` analogue at first (cig has no move-only types at the pin).
- **What would decide it.** The census measured the VM's share of counted-value register moves (`data/census/README.md`, item 5: "Half the moves copy a counted value", median 50.0% of moves in the median compute program, range 0% to 100%). The census counts only `mov` and `loadk`, not every clone, so copies made by arguments, results and builtins are not in that figure; still open is a hand-count of clones a Clone-Drop-Borrow CIR would emit for the hot loop of each of `nbody`, `trees` and `fannkuch`, measured against the census's per-site counts.

### 2. What the SIL ownership verifier proves, on every value, on every path

- **What it does, and why.** `SILOwnershipVerifier.cpp` runs after every pass and gives `SILValueOwnershipChecker` every value: the checker collects "lifetime-ending" and "non-lifetime-ending" uses from the use-list of the value, and hands them to the `LinearLifetimeChecker` which proves a value is **linear**: consuming exactly once along every reachable path, with all non-consuming uses post-dominated by the single consume. The checker understands "parallel operands" (`mark_dependence`, a `Reborrow` operand, a `GuaranteedForwarding` operand all let two operands of one instruction see the same value in a single step: `lib/SIL/Verifier/LinearLifetimeChecker.cpp` `isParallelOperand`). The verifier's errors are concrete: "found a leak" (a path reaches function exit with no consume), "found a use after consume" (a non-consuming use is not post-dominated by the consume), "operand ownership mismatch" (an operand whose constraint is `Owned` is passed a `Guaranteed` value). `GuaranteedPhiVerifier.cpp` adds: for every phi whose operands are `Guaranteed`, the borrow scopes dominate the phi and end strictly after all phi uses. `MemoryLifetimeVerifier.cpp` runs the corresponding check on addresses.
- **Dead-end blocks and unreachable program paths.** The verifier's linear-lifetime check has one exception: a block terminated by an `unreachable` is a "program terminating block", and a block post-dominated only by such blocks is a "dead-end block". An `@owned` value may **leak** along a dead-end block path: it does not need a consume there, because the system reclaims resources at process exit (`docs/SIL/Ownership.md` §Dead End Blocks). An `end_borrow` or `destroy_value` is legal but redundant in a dead-end block. This affects the verifier's definition of "jointly post-dominating": the consumes jointly post-dominate the def when every path from the def to a `return` or `throw` reaches a consume; paths to `unreachable` are excluded. cig has its own analogue in that a `Throw` ends a scope just as `Ret` does; cig's step budget `E515` also ends execution, but through the kernel and not through an unreachable terminator.
- **The verifier's interaction with pass order.** Because the verifier runs after every pass, a pass may **not** leave the IR in an intermediate state where ownership is temporarily inconsistent. This is the discipline that forces the shape of every pass: it rewrites a value's def-use chain atomically, in such a way that the post-state is linear. `LexicalLifetimeEliminator.cpp` (in `lib/SILOptimizer/Mandatory/`) is the one case where the verifier's rules change: after lexical-lifetime elimination, `begin_borrow [lexical]` loses its `[lexical]` flag and the barrier constraint goes away. Every pass that runs before this point must honor the lexical constraint; every pass after is free to move destroys more aggressively.
- **For cig: take.** By rule 5: a verifier that proves the invariant for every value on every path is exactly what cig's `verify.rs` is (V1 to V11, T1 to T4; `cig-script/src/lower/cir/verify.rs`). The three Swift error shapes are the shape cig's new rules would take. cig's form: three new verifier rules, V12 to V14, joining the existing set: V12 "every owned value is dropped exactly once on every path", V13 "every borrowed value's `end_borrow` post-dominates its uses within its scope", V14 "a consume post-dominates every other use of the consumed value". The linear-lifetime checker's shape in cig is a per-value backward walk from exits, cheap because cig's CIR is already structured (if, loop, burn, try own their nested blocks: `ir.rs` `Block`, `Kind`).
- **What would decide it.** Decided by rule 5. The verifier shape is the design; the only measured decision is the per-pass cost of running it, which is bounded by what T1 to T4 already cost.
- **Feeds.** cig-compile#33; decisions (e), (g).

### 3. Function parameter and result conventions

- **What it does, and why.** `ParameterConvention` has three direct variants, five indirect ones and three pack ones at this pin (`include/swift/SIL/SILFunctionConventions.h` lines 665-681): `Direct_Unowned`, `Direct_Guaranteed`, `Direct_Owned` for direct-value parameters; `Indirect_In`, `Indirect_In_Guaranteed`, `Indirect_In_CXX`, `Indirect_Inout`, `Indirect_InoutAliasable` for parameters passed by address; and `Pack_Inout`, `Pack_Owned`, `Pack_Guaranteed` for variadic packs. Eleven variants in all.
- **Semantics by name.** `Direct_Owned` means the callee owns the value and is responsible for consuming it; `Direct_Guaranteed` means the caller keeps it live across the call and the callee may not consume it; `Direct_Unowned` means the caller offers no lifetime guarantee past the call.
- **Indirect forms.** `Indirect_In` is the address form of `Direct_Owned`; `Indirect_In_Guaranteed` is the address form of `Direct_Guaranteed`; `Indirect_Inout` is a mutable reference with exclusive access the callee has for the duration of the call; `Indirect_InoutAliasable` relaxes the exclusivity for cases like `self` in a mutating method called from `withUnsafePointer`.
- **How the API hides the complexity.** `docs/SIL/SILFunctionConventions.md` says SILArgument indices depend on the SIL stage (Canonical vs Lowered), and the `SILFunctionConventions` abstraction manages the mapping. Every call site `apply` honors the same conventions, and the helper `getSILArgIndexOfFirstParam()` is the one way to translate.
- **For cig: adapt.** By rule 1 (burns never move) and rule 5: cig does not need Objective-C or variadic packs, so the vocabulary collapses to three: `Owned` (caller hands ownership to the callee: it drops), `Borrowed` (the callee may not drop or extend past the call), `Scalar` (no counting). The analogue of `Indirect_Inout` is "the callee may mutate, with exclusive access for the call's duration": cig's `SetIndex`, `SetMember` on a `List` or `Map` are the shape, but at the call boundary cig is strict single-threaded and never crosses a kernel boundary without a burn, so `Inout` reduces to `Owned` in practice. cig's form: a `convention: ParamConv` on `FnParam` in `cig-script/src/lower/cir/ir.rs`, with three variants, and a matching convention on the return value (`Owned` or `Scalar`). An `Owned` return by a function that never fails to drop its locals is the most common case; `Borrowed` returns are not supported at first because the lifetime relation at the call site is tricky to encode without `begin_borrow`.
- **What would decide it.** Not measured yet: the count of parameters that could be `Borrowed` on cig's benchmark set, measured by a trivial pass that counts "parameter is read but never dropped and never stored into a slot that outlives the call" over `nbody`, `trees`, `dispatch`.

### 4. Lexical lifetimes and deinit barriers: what may never move

- **What it does, and why.** Swift anchors the SIL-level lifetime of any value that comes from a source-level `let`, `var` or function argument to the variable's lexical scope (`docs/SIL/Ownership.md` §Variable Lifetimes). SILGen marks such values with `begin_borrow [lexical]`, `move_value [lexical]` or an argument carried as lexical by itself (an `alloc_stack [lexical]` is the address form). `ValueBase::isLexical` returns true for these.
- **The three deinit barriers.** A value's destroy may be moved only across instructions that are not **deinit barriers**. Three barriers are defined (`docs/SIL/Ownership.md` §Deinit Barriers, `Instruction::isDeinitBarrier`): synchronization points (locks, memory barriers, syscalls, etc.), loads of weak or unowned values, and accesses of pointers. The rationale is that a class deinit can have side effects a programmer sees: a file handle closed, a lock released, a weak reference it observed. The destroy's position decides whether those observed effects are preserved.
- **How the pass respects them.** `DestroyHoisting.swift` moves a destroy only when the walk from the destroy's old position to the proposed one crosses no barrier. The pass additionally has a 100,000-instruction cap on each function so its per-value lifetime search does not blow up on code generators and tables. Lexical lifetimes are stripped away by the mandatory `LexicalLifetimeEliminator` pass before IR lowering, so later passes can move destroys more aggressively; up to that point, every pass must honor the barrier list.
- **For cig: adapt.** By rule 1 (burns never move) and rule 6 (deterministic cleanup; cleanup that can be observed never moves): this is the rule, named. cig's lexical-lifetime values are: anything whose `Drop` has observable effect (a `Chain`, a value that owns a file handle, a `Func` whose capture environment points at a slot a closure still shares, a `Module`). cig's deinit barriers are: a burn's kernel call (`BurnOp`), any `CallBuiltin` or `CallValue` that the effect table marks non-pure (`cig-script/src/lower/cir/effects.rs`), a `Store` to a captured slot (another closure can read it before the drop). cig's form: a `lexical` bit on `VarInfo` in `cig-script/src/lower/cir/ir.rs`, set at lowering for every slot bound at the top of a function or a burn's body; a verifier rule that pins the drop of a lexical value in place against a defined barrier list (an effectful instruction, a `BurnOp`, a `Store` to a captured slot). The pass is simpler than Swift's because cig has no weak references.
- **What would decide it.** Decided by rule 6. The destroy of a `Chain`, a `Module` or a file-owning `Value` is observable; by rule 6 it never moves. The implementation is the enforcement, and the barrier list is the design decision the measurement cannot change.
- **Feeds.** cig-compile#33; decisions (g), (e).

### 5. OSSA-era copy elision: why a `copy_value` of a `Guaranteed` can just vanish

- **What it does, and why.** `CopyValueOpts.cpp`'s `performGuaranteedCopyValueOptimization` is the pass the OSSA design makes possible: given `%1 = copy_value %0` where `%0` is `@guaranteed` and every use of `%1` is non-consuming (plus a single `destroy_value %1`), the pass replaces the copy with `%0` and deletes the destroy.
- **Why it is sound.** The correctness argument is one line: `%0` is live across the whole region by virtue of its guaranteed status, so `%1` was never needed. The linear-lifetime check is not needed because `@guaranteed` already guarantees the region. The optimization is `+1` eliminated per site.
- **The newer pass that subsumes it.** The file's own comment flags that this pass is being subsumed by `OSSACanonicalizeOwned` (`lib/SILOptimizer/Utils/OSSACanonicalizeOwned.cpp`), which computes a pruned-liveness boundary for every `Owned` value, moves destroys to that boundary, and inserts the minimum number of copies needed to keep uses non-overlapping. The six-step algorithm is documented in the file's own header comment (pruned liveness, original boundary, extend at `-Onone`, extended boundary, insert destroys, rewrite copies).
- **The point for a reader.** When ownership is in the IR, the pass is small; when it is not, the pass is a full dataflow (entry 6). This is the design lesson: an ownership annotation turns a global analysis into a local rewrite.
- **For cig: adapt.** By rule 5 and rule 6: the same shape applies. Given CIR with an ownership annotation, a `Clone(%0)` whose source is a `Borrowed` (cig's analogue of `@guaranteed`) and all of whose uses are non-consuming (no `Drop`, no store, no return out of a smaller scope) can be replaced by `%0`, and the paired `Drop(%clone)` deleted. cig's form: a new CIR pass, `clone-elide`, after `dead-pure`, run between the verifier's T1 to T4 checks. Correctness proves itself: a borrowed value is live by definition over its scope, so the clone was never load-bearing.
- **What would decide it.** Not measured yet: the count of clones a naive CIR pass emits for `fannkuch`, `nbody` and `dispatch` that would disappear under `clone-elide`. The savings are the measurement the pass has to earn.
- **Feeds.** cig-compile#33, #35; decision (g).

### 6. The older ARC sequence dataflow, and why ownership replaced most of it

- **What it does, and why.** `lib/SILOptimizer/ARC/ARCSequenceOpts.cpp` is the pre-OSSA approach: it walks the control-flow graph, matches each `strong_retain` or `retain_value` with a dominating-free, post-dominating `strong_release` or `release_value` on the same RC-identical value (as defined by `RCIdentityAnalysis`: see `docs/SIL/ARCOptimization.md` §RC Identity), and deletes both.
- **The state machine.** It is in `RCStateTransition.def`: three kinds (`StrongEntrance`, `StrongIncrement`, `StrongDecrement`) with two abstract groups (`EndPoint`, `Mutator`). `RefCountState.cpp` tracks per-block live retains and releases; `GlobalARCSequenceDataflow.cpp` runs a bottom-up and a top-down dataflow; `ARCMatchingSet.cpp` pairs them.
- **Loop extensions.** `ARCLoopOpts.cpp` extends this to loops: a retain at loop-head and a release in the loop body can cancel across iterations if nothing in between observes the reference count. The `ARCLoopHoisting` section of `docs/SIL/ARCOptimization.md` is the long walk-through, with `is_unique` as the hard case: a retain hoisted across it changes its result.
- **Why OSSA replaced it.** Without ownership in the IR, every pair's safety requires a flow-sensitive proof that nothing in between depends on the reference count (a `release` that could run an observable deinit, an `is_unique` whose answer depends on the exact count). With OSSA (entry 5), most pairs vanish without any dataflow because the ownership annotation already proves the invariant. The older pass is kept at the pin for the cases OSSA does not yet subsume.
- **For cig: reject.** By rule 5 and rule 1: this older pass is the shape of what cig would have to build if CIR did not carry ownership. The design choice is between adding ownership to CIR (entries 1 and 2, cheap) and building a Swift-sized ARC sequence dataflow (this entry, expensive). The direct cost of the older design, from the source: eleven .cpp files in `lib/SILOptimizer/ARC/` (`ARCBBState.cpp`, `ARCLoopOpts.cpp`, `ARCMatchingSet.cpp`, `ARCRegionState.cpp`, `ARCSequenceOpts.cpp`, `ARCSequenceOptUtils.cpp`, `GlobalARCSequenceDataflow.cpp`, `GlobalLoopARCSequenceDataflow.cpp`, `RCStateTransition.cpp`, `RCStateTransitionVisitors.cpp`, `RefCountState.cpp`), plus `RCIdentityAnalysis.cpp`, `AliasAnalysis.cpp`, `LoopRegionAnalysis.cpp`, `EpilogueARCAnalysis.cpp`, `ProgramTerminationAnalysis.cpp` as analyses it depends on. cig's form in reject: cig does not build this. The equivalent correctness story in cig is entry 2's verifier plus entry 5's elision pass.
- **What would decide it.** Decided by rule 5. The design choice is made against rule 5 and rule 1: a dataflow-based ARC that reorders retain/release pairs would require a second ordering discipline on top of T1 to T3, and that is a cost the design does not take.
- **Feeds.** cig-compile#33; decisions (g), (e).

### 7. Shortening a lifetime to its last use, and what forbids it

- **What it does, and why.** `OSSACanonicalizeOwned.cpp`'s `canonicalizeValueLifetime(SILValue def)` is the canonical lifetime-shortening routine. Six steps per value: compute pruned liveness of `def` and its copies ignoring original destroys, find the original boundary with `PrunedLiveness::computeBoundary`, extend at `-Onone` toward the original extent only where doing so does not add copies, find the extended boundary, insert `destroy_value` at it, then rewrite the old copies and destroys. The algorithm is documented in the file's own header (lines 12-37).
- **The hoisting pass.** `DestroyHoisting.swift` moves a `destroy_value` later when a copy or in-memory copy keeps the referenced object alive across the current destroy's position, up to but not past a deinit barrier. The pass has a 100,000-instruction limit to avoid quadratic cost on very large functions. Both `alloc_box` and `alloc_stack` destinations are considered as alternate live-copies.
- **The borrow shrink.** `ShrinkBorrowScope.cpp` is the dual: `end_borrow` moves earlier, up to a deinit barrier, so that a following `destroy_value` of an underlying owned value can be hoisted up to the new `end_borrow`. The file's one-line summary states the goal: shrink borrow scopes by hoisting end_borrows to deinit barriers, so OSSACanonicalizeOwned can then hoist the owned value's destroys up to the new end_borrow and preserve the lexical lifetime of the guaranteed value.
- **What forbids both.** The deinit-barrier list from entry 4 (synchronization, weak/unowned loads, pointer accesses), plus for `OSSACanonicalizeOwned` any `OperandOwnership::PointerEscape` on a use. The file's TODO at line 40 says the latter is the remaining obstruction: when `project_box` is protected by a borrow scope and `mark_dependence` is associated with an `end_dependence`, those will no longer be pointer-escapes and canonicalization will work universally.
- **For cig: adapt.** By rule 6 (cleanup that can be observed never moves) and rule 1: shortening a `Drop` to the value's last use is the shape, but the barrier list is cig's barrier list (entry 4). cig's form: a `drop-canonicalize` CIR pass, after `rc-insert`, that walks from each `Drop(%v)` upward through the block in reverse looking for the last non-drop use of `%v`, and places the `Drop` immediately after that use, stopping at the first barrier. The pass is a per-value backward walk, bounded by the block's size; cig's structured CIR lets it stay a single pass without a dominator tree.
- **What would decide it.** Not measured yet: the size (in CIR instructions) by which the live range of each `rc`-counted value shrinks over the benchmark set, before and after `drop-canonicalize`.

### 8. Changing an owned parameter to guaranteed, lifting a retain/release out of the call pair

- **What it does, and why.** `FunctionSignatureTransform::OwnedToGuaranteedAnalyzeParameters()` in `lib/SILOptimizer/FunctionSignatureTransforms/OwnedToGuaranteedTransform.cpp` looks at each `Direct_Owned` or `Indirect_In` parameter of a function and asks: is there a matching `strong_release` or `destroy_addr` at every return block (and, if the function can throw, at every throw block)?
- **If yes, the transform.** The parameter is changed to `Direct_Guaranteed` (or `Indirect_In_Guaranteed`), the release in each return/throw block is deleted (`A.CalleeRelease` and `A.CalleeReleaseInThrowBlock`), and every caller is rewritten to retain-before-call plus borrow-across-call instead of consume-at-call.
- **The net effect.** One retain and one release move out of the callee (where they ran unconditionally) into the callers (where some callers may already have an owned copy and can skip both). The optimization is large because the callee sees every call, but each call site often has a local owned copy that cancels the retain the caller was going to emit.
- **How the epilogue is found.** `ConsumedArgToEpilogueReleaseMatcher` (in `lib/SILOptimizer/Analysis/ARCAnalysis.cpp`) finds the matching epilogue releases; it uses `RCIdentityAnalysis` to see through struct-of-reference projections (a struct with one reference-counted field is RC-identical to that field). The analysis returns a set of releases per argument, which the transform then deletes together as a batch.
- **Reader's note.** `FSODisableOwnedToGuaranteed` is a command-line flag for testing (`sil-fso-disable-owned-to-guaranteed`); when set, the pass runs but makes no change. It is a test hook, not a production tuning knob.
- **For cig: adapt.** By rule 5 and decision (g): this is the exact shape of cig's "signature" pass. cig has no throw-and-rethrow outside a `try`, so the equivalent is: look at each `Owned` parameter, find the `Drop(%p)` that dominates every return of the function; if present, change the parameter to `Borrowed` and delete the drop; update every call site to take a `Borrowed` reference. The epilogue matcher in cig is trivial because cig's CIR is structured: a function has one or more `Ret` terminators, and `Drop(%p)` is at the end of the function's top-level block. cig's form: a signature pass `owned-to-borrowed`, run between `rc-insert` and `drop-canonicalize`, outputs a new signature per function and rewrites each call site. For a recursive function in an SCC, the pass runs to a fixed point (it is an ordinary dataflow over the call graph).
- **What would decide it.** Not measured yet: the count of functions in the benchmark set whose `Owned` parameters all have a dominating `Drop` at every return. The expected answer is "most", from Swift's own experience, but cig's dynamic calls through `CallValue` and `CallMethod` are harder to analyze.

### 9. Copy on write and the uniqueness primitive

- **What it does, and why.** `is_unique` takes the address of a reference-counted object's reference and returns 1 if the strong count is exactly 1, 0 otherwise (`docs/SIL/Instructions.md` §is_unique: lines 2097-2111). It is the SIL-level primitive by which an owning type, such as `Array` or `Set`, decides whether a mutation may happen in place.
- **`begin_cow_mutation` is the higher-level primitive.** It consumes an owned reference, returns a boolean `isUnique` and a new reference; the returned reference is semantically the same bits as the operand but SSA-distinct, so the optimizer treats it as a fresh value for alias purposes. The whole trick: `ref_element_addr [immutable]` on the operand is not valid on the result, so no stale read of the buffer's fields survives the mutation.
- **`end_cow_mutation` is the opposite.** It consumes the mutable reference, returns a reference the compiler may treat as uniquely owned; if the `[keep_unique]` attribute is set, the optimizer must not replace that result with a non-unique reference (`docs/SIL/Instructions.md` lines 2142-2165; `end_cow_mutation_addr` follows at line 2166).
- **The LLVM-level wrinkle.** From `docs/SIL/ARCOptimization.md` §Copy-On-Write Considerations: the LLVM-level ARC optimizer must model `_swift_isUniquelyReferenced` as a function that may release X, use X, and exit the program; without this, LLVM can incorrectly cancel a `retain X; retain X; _swift_isUniquelyReferenced(X); release X; release X` sequence because the outer retain/release pair looks redundant, but the pass-off to `_swift_isUniquelyReferenced` itself might change the count. The uniqueness check is a trust boundary for the optimizer.
- **For cig: adapt.** By rule 6 and decision (g): cig's `List` is `Rc<RefCell<Vec<Value>>>` and `Map` is `Rc<RefCell<IndexMap<String, Value>>>` (`cig-script/src/value.rs` lines 19-20). `Rc::strong_count(&l) == 1` is the direct analogue of `is_unique`. The design: a new VM opcode `IS_UNIQUE_LIST` (and `IS_UNIQUE_MAP`), the receiver in R(A), a boolean out in R(B); the bytecode's existing `SETINDEX`, `SETFIELD` and the list/map append builtins branch on it. cig's form: a bytecode pass that, at a `SetIndex`/`SetMember` or an append whose receiver's class is `List` or `Map`, emits `IS_UNIQUE_*` and a conditional clone-first path. The uniqueness check does not move (rule 1: it is a `Class::Effect` because the mutation that follows depends on its result).
- **What would decide it.** Not measured yet: the hit rate of `strong_count == 1` on a `List` or `Map` at `SetIndex`/`push` sites, over `fannkuch`, `sieve`, `strbuild` and `maps`. A hit rate below 50 percent would say the uniqueness path is not worth the branch; above 80 percent would say it is a significant win.
- **Feeds.** cig-compile#35, #33; decisions (g), (a).
- **Read.** `swift-swift-6.4.3-RELEASE/docs/SIL/Instructions.md` (`is_unique`, `begin_cow_mutation`, `end_cow_mutation`, `end_cow_mutation_addr`); `swift-swift-6.4.3-RELEASE/docs/SIL/ARCOptimization.md` (`Copy-On-Write Considerations`, `Builtin.isUnique`); `cig-script/src/value.rs` (`Value`, `List`, `Map`).

### 10. Hoisting a uniqueness check out of a loop: COWArrayOpt

- **What it does, and why.** `lib/SILOptimizer/LoopTransforms/COWArrayOpt.cpp` targets the pattern where a mutating array operation inside a loop performs a uniqueness check every iteration. The pass's job is to lift a copy of the `make_mutable` call to the loop pre-header so that, after inlining, the in-loop `begin_cow_mutation`'s uniqueness check folds to a known-unique result.
- **The in-loop call is not removed.** The original in-loop `make_mutable` is left in place; removing it would violate COW's representation rules (file comment, lines 907-914). The optimization is to let constant folding of the uniqueness check short-circuit the in-loop path, without removing the primitive that guards the mutation.
- **The three safety checks.** `hoistMakeMutable` uses `checkUniqueArrayContainer` to establish the array is not aliased, then `hasLoopOnlyDestructorSafeArrayOperations` to prove no path through the loop releases a reference the hoisted mutation would see as still live, and finally requires that the original make-mutable call dominates all exits of the loop (parameter `dominatesExits`), so hoisting a copy to the pre-header cannot cause an extra retain along an exit path.
- **The alias collector.** The pass depends on an alias collector specialized for the Array-value shape (`StructUseCollector` in the same file), which knows the Array buffer is reached through a specific field projection pattern.
- **For cig: adapt.** By rule 1 (burns never move; a uniqueness-check Pass is `Class::Effect`, pinned) and rule 6: the pattern is `push`, `set` or `+=` inside a loop with a receiver defined outside. cig's form: a loop pass that, at a `SetIndex`/`push` site whose receiver is defined outside the loop, inserts an `IS_UNIQUE_*` check in the pre-header and a local flag in the loop that skips the in-loop check when the pre-header check proved unique and no other in-loop operation escaped the receiver. The pass respects T1 to T3: the in-loop `IS_UNIQUE_*` is not removed, only short-circuited by the pre-header's flag, so no burn or step mark moves. This mirrors Swift's design of leaving the in-loop `make_mutable` in place: representational safety trumps the optimization.
- **What would decide it.** Not measured yet: the ratio of in-loop uniqueness-check hits to total loop iterations, for a representative set of `push`-in-loop scripts. The expected answer: in the common case, a receiver not stored elsewhere stays unique for the whole loop, so the hoisted check catches every iteration.

- **Read.** `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/LoopTransforms/COWArrayOpt.cpp` (`COWArrayOpt`, `hoistMakeMutable`, `checkUniqueArrayContainer`, `hasLoopOnlyDestructorSafeArrayOperations`); `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/LoopTransforms/ArrayPropertyOpt.cpp`; `swift-swift-6.4.3-RELEASE/docs/SIL/ARCOptimization.md` (`ARC Loop Hoisting`); `cig-script/src/lower/cir/ir.rs` (`Kind::SetIndex`, `Kind::SetMember`, `Kind::Loop`).

### 11. Roc's reference-count insertion with borrow inference

- **What it does, and why.** `crates/compiler/mono/src/inc_dec.rs` carries the file-level comment that the implementation follows the Perceus paper (`papers/reinking-2021-perceus.pdf`) and a Utrecht University thesis by Jelle Teeuwissen. The pass runs on `mono` IR (`Proc`, `Stmt`), after specialization.
- **The two-phase structure.** First `insert_inc_dec_operations` calls `infer_borrow_signatures` from `crates/compiler/mono/src/borrow.rs`, which constructs a `BorrowSignature` per `(Symbol, ProcLayout)`: one bit per parameter (`Owned` or `Borrowed`), 55 parameters max. The signature is a `u64` (`borrow.rs` line 15): the low 8 bits hold the length (line 50: `(self.0 & 0xFF) as usize`) and the constructor asserts `len < 64 - 8` (line 31), leaving 56 bits for ownership flags and capping the usable parameter count at 55. Initially every parameter of a function whose layout is "may be borrowed" (`Str`, `List`, lambda-set wrapping one of those: `layout_to_ownership`) starts `Borrowed`; a per-SCC fixed-point walk marks a parameter `Owned` on evidence that the function keeps it past the call. The walk topologically-sorts the call graph's SCCs (`matrix.strongly_connected_components_all()`) and converges per SCC before moving on.
- **The forward-walk insertion.** Then `insert_inc_dec_operations_proc` walks the function body in forward order with an `Ownership` state per symbol: `consume_rc_symbol` marks a symbol consumed (owned at its first use, borrowed thereafter), `Inc(sym, n)` is emitted when a symbol is used `n+1` times along a branch, `Dec(sym)` when the live range ends without a consume. The walk honors the borrow signatures: a symbol passed to a `Borrowed` parameter of a call is not consumed; a symbol passed to an `Owned` parameter is consumed (and an `Inc` is emitted if it must stay live for a later use).
- **`ModifyRc`'s three cases.** `ModifyRc` has three cases: `Inc(Symbol, u64)` (reference-count increment with a count), `Dec(Symbol)` (recursive decrement that walks into the value's contents), `DecRef(Symbol)` (non-recursive decrement of the outer container only, used when a derived value is dropped but the container is still shared). The `DecRef` case is important for a container that is uniquely held but whose contents are still shared from elsewhere: freeing just the outer is cheaper than a recursive free that walks into values already borrowed by another path.
- **Reader's note.** `crates/compiler/mono/src/expand_rc.rs` is at this pin marked `UNUSED` but kept; it would have expanded `Inc/Dec` to lower-level operations closer to Perceus's paper form. The passes that are actually wired in at this pin are `inc_dec.rs`, `borrow.rs`, `reset_reuse.rs` and `drop_specialization.rs`.
- **For cig: adapt.** By rule 5, rule 1 and decision (g): the two-phase structure (borrow signatures first, then per-function insertion) is the correct shape. cig's form: a signature pass (entry 8's `owned-to-borrowed`), then an insertion pass (`rc-insert` for cig) that walks CIR forward and emits `Inc`/`Dec`. The `DecRef` distinction is the direct analogue of what cig would need for `List` of `List`: dropping the outer list without recursively dropping the inner lists when the outer is known uniquely held and the inner lists are still shared from elsewhere. cig has no such split today (`Rc::drop` is always recursive through `Value`); a `DecRef` opcode or a bytecode path that marks the drop non-recursive is a small addition that matters for `trees`-style programs.
- **What would decide it.** Not measured yet: the count of `Inc`/`Dec` pairs that would be `DecRef` instead on `trees` and `fannkuch`, each counted as a saved recursive descent.
- **Feeds.** cig-compile#33, #35; cig-script#243; decisions (g), (a).
- **Read.** `roc-alpha4-rolling/crates/compiler/mono/src/inc_dec.rs` (`insert_inc_dec_operations`, `SymbolRcTypes`, `VarRcType`, `Ownership`, `RefcountEnvironment`, `consume_symbol`); `roc-alpha4-rolling/crates/compiler/mono/src/borrow.rs` (`BorrowSignature`, `infer_borrow_signatures`, `State`, `layout_to_ownership`); `roc-alpha4-rolling/crates/compiler/mono/src/ir.rs` (`ModifyRc`, `Inc`, `Dec`, `DecRef`); `roc-alpha4-rolling/crates/compiler/mono/src/expand_rc.rs`; `papers/reinking-2021-perceus.pdf`.

### 12. Roc's reset/reuse and drop specialization: Perceus's deeper passes

- **What it does, and why.** `crates/compiler/mono/src/reset_reuse.rs` states its implementation follows "Reference Counting with Frame Limited Reuse" (`papers/compilers/lorenzen-2022-frame-limited-reuse.pdf`) and the file-level comment links back to Perceus. The pass rewrites a `Dec(x)` followed by an allocation of a value whose layout matches `x`'s into a `reset(x)` followed by a `Reuse(token, ...)` of the reset token for the new allocation.
- **The environment.** `insert_reset_reuse_operations` walks each `Proc` with a `ReuseEnvironment` that carries `reuse_tokens: MutMap<...>` per layout, and a `non_unique_symbols: MutSet<Symbol>` of symbols known not to be uniquely referenced (so a reuse that targets one of them would be unsound). The pass can decline to reuse when the symbol's uniqueness is not statically clear.
- **Drop specialization.** `crates/compiler/mono/src/drop_specialization.rs` (file comment: "Drop Specialization from Perceus") searches for an `Inc(child)` followed by a `Dec(parent)`, where `child` was indexed out of `parent`, and rewrites the pair out: when the outer drop recursively decrements, it already has the child's increment to cancel; the specialization inlines the decrement to find the match. The pass runs after `reset_reuse` and rewrites per `Proc`.
- **Why both depend on a static shape.** Both passes depend on the layout being a tagged union with a fixed shape (`UnionLayout`): the reset-reuse's correctness proof is "this memory about to be freed is exactly the size and shape the new allocation needs", and without a static shape the proof does not hold. Drop specialization has the same dependence: the "child indexed out of parent" is a shape-bound projection, not a dynamic lookup.
- **For cig: reject.** By rule 6 (deterministic cleanup; observable effects never move) and the structural mismatch: cig's `List` is a `Rc<RefCell<Vec<Value>>>` and cig's `Map` is a `Rc<RefCell<IndexMap<String, Value>>>`. Neither has a static shape in Roc's sense: a cig list's element count is dynamic, a cig map's key set is dynamic. The reset primitive needs a layout-bound "this memory is the right size for the next allocation of layout L"; cig's `Vec` capacity is grown and shrunk by `push`/`pop`, and reusing it for a different layout would mean re-reading the length and clearing the capacity, which is more expensive than a fresh allocation. Drop specialization has the same difficulty: cig has no constructors and no projection operator that returns a shape-bound child; `list[0]` is a `Value` of dynamic kind, not an "inc of a projected child". cig's form: nothing from reset/reuse or drop specialization lands directly. The companion reject-case for cig-compile#35: the issue's "arenas for short-lived temporaries" (`-O3` option) is a different mechanism (stack allocation for non-escaping values), which is not a reject and lands under entry 15's stack promotion.
- **What would decide it.** Decided by rule 6 and by the layout mismatch. The reuse primitive is unsound without a static layout.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `roc-alpha4-rolling/crates/compiler/mono/src/reset_reuse.rs` (`insert_reset_reuse_operations`, `ReuseEnvironment`, `reuse_tokens`, `non_unique_symbols`); `roc-alpha4-rolling/crates/compiler/mono/src/drop_specialization.rs` (`specialize_drops`, `DropSpecializationEnvironment`); `roc-alpha4-rolling/crates/compiler/mono/src/ir.rs` (`ReuseToken`, `Stmt`); `papers/reinking-2021-perceus.pdf`; `papers/compilers/lorenzen-2022-frame-limited-reuse.pdf`.

### 13. Roc's alias analysis and in-place list updates

- **What it does, and why.** `crates/compiler/alias_analysis/src/lib.rs` is the third of Roc's reference-counting passes: it hands `morphic_lib` (an external library linked here) a specification of the program's heap behavior and gets back an `UpdateMode` per site that says whether a list operation may update in place.

- **What would decide it.** Not measured yet: the fraction of `SetIndex` and append sites that a one-block local analysis can mark `InPlace` on cig's benchmark set; above 30 percent would make the compile-time slot worth the bytecode variant, below 10 percent would make a run-time `IS_UNIQUE_*` branch the only mechanism cig needs.

### 14. The smallest ownership vocabulary that would let a CIR pass remove a clone/drop pair, with the verifier able to prove it

- **What it does, and why.** Synthesizing entries 1, 2, 5 and 11: the smallest useful extension to CIR is three new instruction kinds and a two-bit ownership annotation on every value.
- **The three new kinds.** `Clone(ValueId)` (Swift's `copy_value`, class `Pure`: a counted value is cloned into a new one, incrementing the count); `Drop(ValueId)` (Swift's `destroy_value`, class `Effect`: the value's refcount is decremented and recursive drop may run); `Borrow(ValueId, scope: BlockId)` (Swift's `begin_borrow`/`end_borrow` pair, class `Pure` but with a scope the verifier checks: the value is passed as a borrowed reference inside `scope`, no drop may run inside `scope`).
- **The annotation.** On every `ValueInfo`, an `Ownership: { None, Owned, Borrowed }`. cig has no weak references so `Unowned` is omitted; a fifth kind (`MoveOnly`) is reserved for the future case of entry 17.
- **The three new verifier rules.** T5: "every `Clone(%v)` whose `%v` is `Borrowed` and whose result's uses are non-consuming may be replaced by `%v`" (entry 5's elision). T6: "the drop of a value whose class is `Effect` never moves across a `BurnOp`, a `Store` to a captured slot, or a non-pure `CallBuiltin`/`CallValue`" (entry 4's barriers). T7: "every `Owned` value has exactly one `Drop` on every path to a `Ret`, `Throw` or `Break`" (entry 2's linear lifetime).
- **What the vocabulary unlocks.** The elision pass of entry 5 (replace a `Clone` of a `Borrowed` with the original), the drop-canonicalize pass of entry 7 (shorten a `Drop`'s range), and the signature pass of entry 8 (change an `Owned` parameter to `Borrowed` when the matching drop is at the epilogue). The three fit naturally beside T1 to T4, and the verifier's existing structural rules (V1 to V11) are unchanged.
- **For cig: adapt.** By rule 5, rule 6 and decision (g): this is the design, and it is in reach of cig's existing verifier. cig's form: add the three new `Kind` variants to `cig-script/src/lower/cir/ir.rs`; add `Ownership` to `ValueInfo`; add T5-T7 to `cig-script/src/lower/cir/verify.rs`. The elision pass joins `pass/` as a new entry `clone-elide` in `NAMES`; `rc-insert` is a separate pass that runs before, emitting the initial `Clone`/`Drop`/`Borrow` sequence from the lowering's "move always copies" model.
- **What would decide it.** Not measured yet: the end-to-end measurement of this design against today's naive clone-on-copy model, over the compute benchmark set at stage B. The hypothesis is that `clone-elide` alone recovers most of the lost ground.

### 15. Where cig's shared slots defeat the Swift model, and what Swift does about the same problem

- **What it does, and why.** Swift keeps mutable state in two places: a local variable (an `alloc_stack` address; mutations are `store` through that address) and a class's property (a reference to a class, mutations through `ref_element_addr`).
- **Access enforcement.** The variable case is governed by access enforcement (`docs/SIL/SILMemoryAccess.md`: the Law of Exclusivity says a mutable access to a variable may not overlap with another access to the same variable on any path through the program; dynamic enforcement uses `begin_access`/`end_access` to assert this at run time). This is the mechanism that keeps a `Store` and a `Load` through the same address from racing within one function.
- **Boxing captures.** The closure-capture case is governed by boxing: a heap-allocated `Box<T>` wraps a shared cell when a closure captures a `var`, and `project_box` returns its address under a borrow scope. `Mandatory/CapturePromotion.cpp` tries to promote a boxed capture back to a stack slot when the closure cannot escape; when it cannot, the box stays on the heap and reference-count traffic follows every assignment.
- **Where this hits cig.** cig's `roll`/`stick`/`var` slots are shared cells that closures capture (`cig-script/src/lower/cir/ir.rs` `VarInfo::captured`), and the current lowering boxes them into `Rc<RefCell<...>>` at run time. The problem for an ownership model: a value loaded from a captured slot has no single lifetime-ending use the verifier can prove linear; another closure can overwrite the slot under the current function's feet, and the compiler cannot see the writer.
- **For cig: adapt.** By rule 5 and rule 1: the Swift answer is to treat a captured slot as `inout` for the duration of the access, and to insert `begin_access [modify]`/`end_access` pairs around every write. cig's form: treat `Load(VarId)` of a captured slot as a `Borrow` of class `MayRaise` (it may raise if a concurrent write overlaps; cig is single-threaded so this reduces to "a function called during the load's live range may rebind the slot"), and treat `Store(VarId, ...)` of a captured slot as `Class::Effect` (already so). The verifier's new rule: a `Clone` of a value loaded from a captured slot is **not** eligible for entry 5's elision, because the borrow's scope can be invalidated by a `Store` the compiler cannot see. This is a direct reject for a slice of the elision pass, on a well-defined criterion: captured slots are a reject by rule 5.
- **What would decide it.** Not measured yet: the fraction of `Clone` sites in the benchmark set whose source is a captured slot (as opposed to a temporary or a parameter). The hypothesis is that most are non-captured, so the elision is mostly safe.
- **Feeds.** cig-compile#33, #35; decisions (g), (e), (i).
- **Read.** `swift-swift-6.4.3-RELEASE/docs/SIL/SILMemoryAccess.md`; `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/Mandatory/AccessEnforcementSelection.cpp`; `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/Mandatory/CapturePromotion.cpp`; `cig-script/src/lower/cir/ir.rs` (`VarInfo`, `Kind::Load`, `Kind::Store`).

### 16. Copy-on-write uniqueness as a VM primitive for cig's lists and maps

- **What it does, and why.** Synthesizing entries 9 and 10, grounded in cig's `value.rs`: cig's `List` type is `Rc<RefCell<Vec<Value>>>`; `Map` is `Rc<RefCell<IndexMap<String, Value>>>`. At each mutation site (`SetIndex`, `SetMember`, the append builtins, the `+=` on a `Str` that is ropes-materialized in the future), the VM can check `Rc::strong_count(&self.0) == 1` to decide between the mutate-in-place path and the clone-first path.
- **The primitive.** This is the same word the uniqueness check in Swift's `is_unique` reads. The branch is predictable in a scripted program: a list built in a function and mutated immediately in the same function is unique; a list stored into a slot shared across closures is not.
- **Opcode shape.** The implementation shape in cig: two new opcodes in the `Op` enum of `cig-script/crates/cig-bytecode/src/opcode.rs`, each reading a receiver slot and writing a boolean to a result slot. The bytecode pass that lowers CIR to bytecode (`cig-script/src/lower/bc/mod.rs`) emits them at every `SetIndex`/`SetMember` whose receiver's class is `List` or `Map`.
- **CIR parallel.** At the CIR level a matching `Kind` variant is a `Class::MayRaise` instruction that is `Pure` for the result but `Effect` for its position (not moved across a mutation). The verifier T6 of entry 14 pins it to its position.
- **String special case.** For `+=` on a `Str`, the primitive is `Rc::get_mut(&mut self.0)`: returns `Some(&mut str)` only when the count is one, otherwise `None` and the caller clones first. The behavior is identical to the `is_unique`+mutate path for lists and maps, exposed through a different Rust primitive.
- **For cig: adapt.** By rule 5, rule 1 and decision (g): this is the design, and it is the primitive that unlocks the win. The design matches entry 9's `is_unique` and entry 10's loop hoisting. cig's form: add two new opcodes to the `Op` enum in `cig-script/crates/cig-bytecode/src/opcode.rs`, one for `List` receivers and one for `Map` receivers; add the lowering in `cig-script/src/lower/bc/mod.rs`; add a new `Kind` variant in `cig-script/src/lower/cir/ir.rs` for the CIR-level uniqueness check; and add a verifier rule that pins the instruction to its position (it may not move across a mutation of its operand). The loop hoisting is a separate CIR pass (entry 10's `uniq-hoist`) that short-circuits the in-loop check with a pre-header flag.
- **What would decide it.** The census (`data/census/README.md`) counted method calls and list/map operations per site but did not measure the dynamic hit rate of `Rc::strong_count == 1` at those sites. From the census's compute tables, `fannkuch` spends 1,321,062 instructions on `getindex` and 1,060,163 on `setindex` out of 12,416,903 total; `sieve` spends 607,827 on `setindex` and 608,473 on `lej` over 7,612,450 total; `strbuild` runs 10,000 `addk` in a loop over 40,033 total. Still open: the dynamic hit rate at each `setindex`/`push` site, which needs a second instrument that reads the receiver's `Rc::strong_count`.
- **Feeds.** cig-compile#35, #33; cig-script#243; decisions (g), (a).
- **Read.** `cig-script/src/value.rs` (`Value`, `List`, `Map`); `cig-script/src/lower/cir/ir.rs` (`Kind::SetIndex`, `Kind::SetMember`, `Class::MayRaise`); `cig-script/src/lower/bc/mod.rs`; `swift-swift-6.4.3-RELEASE/docs/SIL/Instructions.md` (`is_unique`, `begin_cow_mutation`); `swift-swift-6.4.3-RELEASE/docs/SIL/ARCOptimization.md` (`Copy-On-Write Considerations`).

### 17. Move-only values and `drop_deinit`

- **What it does, and why.** Swift's experimental move-only types (`@_moveOnly`, `@noImplicitCopy`) are modeled in SIL with a `move_value` instruction and a mandatory `MoveOnlyChecker` pass (`lib/SILOptimizer/Mandatory/MoveOnlyChecker.cpp`, `MoveOnlyObjectCheckerUtils.cpp`, `MoveOnlyAddressCheckerUtils.cpp`).
- **`move_value`.** A `move_value [lexical]` ends an `@owned` lifetime and begins a new one; the resulting value is move-only (`docs/SIL/Instructions.md` §move_value). The `[lexical]` flag carries the source-level variable's lifetime constraint into the new lifetime, so a destroy of the result still respects deinit barriers.
- **`explicit_copy_value`.** It is the escape hatch: when a programmer writes an explicit copy on a `@noImplicitCopy` type, the checker treats it as intentional and lets the copy stand. This is needed because the move-only type opts out of the compiler's default of inserting copies on demand.
- **`drop_deinit`.** The counterpart (`docs/SIL/Instructions.md` §drop_deinit): it marks the following `destroy_value` or `destructure_struct` so that the move-only type's user-defined deinit is not called; only the fields are released. This is the operator for "I have consumed the user-visible semantics; release only the memory".
- **What the checker proves.** The checker emits a diagnostic for every path that fails to consume a move-only value or that consumes it twice; the move-only type's deinitializer runs on exactly one of the paths through the function.
- **For cig: reject.** By rule 6 (deterministic cleanup; observable cleanup never moves): cig's values are mutable and shared by design; the move-only kind is a static restriction a language puts on a type to let the compiler reason about moves without an escape analysis, and cig has no such type in the language. The one case where cig might use it in the future is a `Chain` or a `Module`: both have a deinit observable to the kernel (a chain's open steps, a module's imports), and both are candidates for a move-only annotation that the verifier could enforce. At this pin, however, cig has no annotation, and a port would be a language change. cig's form: nothing from this entry lands directly. The design note: if cig ever ships a move-only kind for a `Chain` or a file handle, the shape is this: a new `Ownership::MoveOnly` on `VarInfo`, a new verifier rule that forbids `Clone` on a MoveOnly value and requires exactly one `Drop` per path (entry 2's T7 strengthened), and a `drop_deinit`-equivalent for the case where the kernel has already observed the resource and the drop should only release the Rust-side memory.
- **What would decide it.** Decided by rule 6 at the pin: cig has no move-only type, so the mechanism has nothing to attach to.
- **Feeds.** cig-compile#33; decisions (g), (i).
- **Read.** `swift-swift-6.4.3-RELEASE/docs/SIL/Instructions.md` (`move_value`, `drop_deinit`, `explicit_copy_value`); `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/Mandatory/MoveOnlyChecker.cpp` (`MoveOnlyChecker`); `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/Mandatory/MoveOnlyObjectCheckerUtils.cpp`; `swift-swift-6.4.3-RELEASE/lib/SILOptimizer/Mandatory/MoveOnlyAddressCheckerUtils.cpp`; `cig-script/src/lower/cir/ir.rs` (`VarInfo`).

### 18. Stack promotion of non-escaping allocations

- **What it does, and why.** `StackPromotion.swift` (`SwiftCompilerSources/Sources/Optimizer/FunctionPasses/StackPromotion.swift`) promotes a heap-allocated object (`alloc_ref` or `alloc_ref_dynamic`) to the stack when an escape analysis proves the value does not escape its function. If promoted, the allocation gets the `[stack]` attribute and a `dealloc_stack_ref` is inserted at the end of the value's extended lifetime.
- **The escape analysis.** The pass uses `ComputeEscapeEffects.swift` and `ComputeSideEffects.swift` to summarize what each callee does with its parameters; a callee that stores a parameter to a non-local location escapes it. Both effect summaries are cached per function, so the escape analysis amortizes across uses of the same callee.
- **The box variant.** `AllocBoxToStack.swift` is the related pass on captured variables: a `var` captured into an `alloc_box` is promoted to an `alloc_stack` when the box does not escape, so the captured mutable state moves from the heap to the stack. This pass runs before stack promotion in the pipeline.
- **The dual win.** Stack promotion reduces allocation overhead and reference-count traffic in the same step: an on-stack allocation has no reference count. For a hot allocation site in a benchmark, this halves two costs at once.
- **For cig: adapt.** By rule 5 and decision (g): cig allocates `List` and `Map` on the heap through `Rc<RefCell<...>>` even for a value that lives only inside a function. An escape analysis of the same shape as Swift's can place such a `List`/`Map` on a per-function arena (see cig-compile#35's "arenas for short-lived temporaries at `-O3`"). The analysis has three inputs: whether the value escapes through a return, a store to a slot the caller can see, or a call that is not known to not escape its argument. cig's form: a CIR pass `escape-analyze` that computes per-function escape sets, plus a lowering that, for a `MakeList` or `MakeMap` whose result does not escape, emits an `ARENA_LIST`/`ARENA_MAP` opcode variant that allocates into a bump-allocated per-function arena and skips the drop at scope end. The arena is freed at function exit, so the drop is not needed. Rule 6 does not block this because the arena-allocated value has no deinit observable to the kernel (no file handle, no chain).
- **What would decide it.** Not measured yet: the fraction of `MakeList`/`MakeMap` sites whose result does not escape on `nbody`, `trees` and `dispatch`; and the saved allocation count per second at those sites.
- **Feeds.** cig-compile#33, #35; decisions (g), (a).
- **Read.** `swift-swift-6.4.3-RELEASE/SwiftCompilerSources/Sources/Optimizer/FunctionPasses/StackPromotion.swift` (`stackPromotion`, `FunctionPass`); `swift-swift-6.4.3-RELEASE/SwiftCompilerSources/Sources/Optimizer/FunctionPasses/AllocBoxToStack.swift`; `swift-swift-6.4.3-RELEASE/SwiftCompilerSources/Sources/Optimizer/FunctionPasses/ComputeEscapeEffects.swift`; `swift-swift-6.4.3-RELEASE/SwiftCompilerSources/Sources/Optimizer/FunctionPasses/ComputeSideEffects.swift`; `cig-script/src/lower/cir/ir.rs` (`Kind::MakeList`, `Kind::MakeMap`).

## For the issues

- **cig-compile#33 (the optimizer, including `rc elision`):** the three passes this study recommends for the planned `rc elision` are (a) a signature pass `owned-to-borrowed` (entry 8), (b) a clone-elision pass `clone-elide` (entry 5), and (c) a drop-canonicalize pass (entry 7). All three run on a CIR extended with the vocabulary of entry 14 (Clone, Drop, Borrow, `Ownership` on each value). The design-point reject is the older pairing dataflow (entry 6): it is the shape cig would have to build without ownership in the IR, and it is specifically rejected under rule 5 for its extra ordering burden. A separate `uniq-hoist` pass (entry 10) belongs under `licm` rather than `rc elision`, but comes from the same mechanism. The level table in cig-compile#33 should carry `clone-elide` at `-O2` and the signature pass at `-O3`, matching Swift's own layering where OSSACanonicalizeOwned runs at `-O` but the function-signature pass is a late inter-procedural step.
- **cig-compile#35 (values and memory):** the CoW uniqueness primitive (entries 9, 16) is the biggest single win for cig's `Rc<RefCell<Vec<Value>>>` and `Rc<RefCell<IndexMap<String, Value>>>` data structures. Two new opcodes and the matching branch at `SetIndex`/`SetMember` sites would unlock the mutate-in-place path and shrink `nbody`, `fannkuch`, `strbuild` and `maps`. Reuse and drop specialization (entry 12), the deeper Perceus techniques, are rejected for cig by rule 6 and by the structural absence of static constructor shapes; the issue should not count them as available wins. The issue's plan to "typed list storage with widening" (bitset for a list of booleans, packed i64 for a list of ints) does not interact with ownership: the uniqueness check works the same whether the inner storage is tagged `Value` or a packed homogeneous array.
- **cig-script#243 (the VM's study list, including Part 2 trick 3 on Perceus):** this study's entries 11 and 13 are the applicable pieces (borrow-signature inference and `UpdateModeId`-driven in-place updates). Entries 12 (reset/reuse, drop specialization) are not applicable to cig for the reasons the study names. The study should carry entries 5, 7 and 8 into cig-script#243 as the shape the VM's planned Perceus pass takes on OSSA-style CIR, not on the paper's immutable-value model. A design note worth adding to cig-script#243: the VM and stage C share the code generator, so an ownership annotation on CIR is one design, not two; the signature pass of entry 8 lands once, and both the VM and stage C read its output.

## Not settled

- Whether cig's `Ty::Dynamic` (the type of a value whose compile-time kind is unknown) plays the role of Swift's `OwnershipKind::Any` (the empty constraint) or needs its own class: Swift's `Any` is a constraint, never a value's kind, and cig's `Dynamic` is a value's kind. The two are not aligned, and a mechanical port would conflate them. A run-time branch on the value's tag is the only sound way to pick between the Owned and Borrowed paths for a `Dynamic` value; whether the branch is worth the two code paths is a measurement, not a design.
- Whether the `DecRef` distinction (entry 11) is worth a separate bytecode opcode in cig or should be an inline branch in the single `DEC` path: Roc has three distinct cases at IR level, but the bytecode is one path with a shallow/deep flag in Rust's `Drop`. The source does not say which is faster on cig's test machine.
- Whether a weak-reference primitive is needed for `Chain` steps that reference each other (a step naming a label of an earlier step by weak reference): cig today has no weak reference and no cycle collector; the only cycle-forming pattern the source shows is a self-referential chain, which rule 6 does not resolve. The question returns when the cycle collector lands (cig-compile#35's "cycles_are_freed" test).
- Whether the elision pass should run before or after cig's existing `dead-pure`: a clone whose result is never read is already removed by `dead-pure`, but the drop that pairs it is not (it is `Class::Effect`); the elision pass should run first so the drop pairing is seen. Not settled against the pass-order measurement in cig-compile#33's level table.
- Whether `move_value`'s cig analogue (a `Move` instruction with no reference-count change) is useful at cig's pin: cig has no move-only types and no eager-move annotations, so a `Move` kind has nothing to say that `Clone`+`Drop` cannot. The question returns if cig ever ships a move-only kind for a file handle or a chain.
- Whether the alias-analysis mechanism in Roc's `morphic_lib` (entry 13) is implementable within cig's single-crate rule 9: `morphic_lib` is a separate Rust crate with its own build; cig would have to either depend on a new crate (adding build time and binary size) or reimplement a local alias analysis for the one-block case. The source at the pin does not say which Roc chose for its Zig rewrite; at this pin the Zig side has no RC pass at all (entry 13). Measurement decides which approach is cheaper for cig.
- Whether cig's `Burn` regions should be treated as a single lifetime-ending use for every value they consume, or whether the destroy's position inside a burn can move. The current reading of rule 1 says they cannot move inside a burn (every effect is pinned), but a value that is dropped on the burn's exit is a slightly different case: the drop could in principle move to the burn's compensation block without crossing a burn op. The study does not settle this; a design review of `cig-script/src/lower/cir/ir.rs`'s `BurnNode` is owed.
