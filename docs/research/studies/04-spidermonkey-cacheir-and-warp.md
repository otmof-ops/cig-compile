# SpiderMonkey's CacheIR and Warp: one inline-cache language for four tiers

- **Serves.** cig-compile#32 (guards that can exit to the VM), #33 (profile-guided passes), #34 (observed types); cig-script#256 (cig-cherry, fallback to the VM at a snapshot), #243 (A8, B7); decisions (b), (c), (d), (h).
- **Pins.** `spidermonkey-FIREFOX_160_0_1_RELEASE` (MPL-2.0): `js/src/jit/` (sparse), `js/src/vm/`, `js/public/`, `js/src/doc/`. Short name follows the brief.
- **License rule.** MPL-2.0. Ideas freely; reimplement, never adapt a file. Names and shapes in words only; no code is lifted.
- **Read with.** `papers/compilers/demooij-2023-cacheir.pdf` (de Mooij 2023, MPLR, "The CacheIR Compiler Framework"), `papers/compilers/hacks-warp-improved-js-firefox-83.html` (Mozilla's Warp post), and the tree's own `js/src/doc/cacheir.md` and `js/src/doc/how-we-optimize.md`.

## What cig should carry away

- **A CacheIR-shaped IR is the strongest candidate for how cig's VM caches and its native tiers share what they learned,** which is what cig-compile#98 area 5 names as the question. The study's verdict is: adapt the YAML-driven, typed-operand, three-op-kind design. Reject the Ion habit of baking per-site constants into native code (the newer comment on cig-compile#32 already does). The key is that four readers consume the same IR: the baseline compiler, the optimizing-tier IC compiler, the transpiler into optimizer IR, and the interpreter of stubs with no code generation. (entries 1, 2, 7, 8, 9)
- **One IR for the caches is the right level.** Writers produce it from runtime values; several readers consume it: a baseline compiler, an optimizing-tier IC compiler, a transpiler into the optimizer's IR, and an interpreter with no code generation. The last is cig's situation, and it works. (entries 1, 7, 8)
- **Stub data separate from stub code is what lets one piece of code serve many sites.** A baseline stub's shapes and slot offsets live in the `ICStub` struct; the generated code reads them by offset. A baseline weak map `CacheIRStubInfo*` to `JitCode*` keyed by bytes plus `(kind, engine)` shares the code zone-wide. (entries 2, 3)
- **A site progresses through three modes with a hard stub count.** Specialized up to six stubs, Megamorphic for the generic cases, Generic when no more stubs should be attached. Failures and attaches both move the site. (entry 11)
- **The optimizer compiles from a snapshot of plain data,** taken on the main thread, built off-thread. No live stub pointers are followed in the compiler. This is directly what cig-cherry decision (b) and `cig-script#256` need: the bytecode and the stub bytes are the whole input. (entries 15, 16)
- **Guards are failures, bailouts are exits.** A CacheIR guard that fails just stops the stub; the chain's next stub tries. The optimizer's guards are MIR, and their failure becomes a bailout: the frame is rebuilt at the matching bytecode position with snapshot plus recover instructions. This split is what decision (d) is asking for. (entries 17, 18)
- **Shapes earn their keep as a one-word guard,** and they are what the stubs and the transpiler read; their absence in cig today is a measurement-owed decision (h). The generators emit `GuardShape` rather than name lookups, and the baseline stub holds the `Shape*` as one stub field. (entries 4, 6, 12)
- **Ahead-of-time stubs are a cache the tin can carry.** The AOT corpus is a C array of bytes, built from captured stubs, installed on start; no runtime pointers, no live state. It is what `cig cherry warm` would write. (entry 10)
- **The handful of cig operations that would get caches first:** the three the VM's `Proto::hints` already reaches for (`GETFIELD`, `SETFIELD`, `CALLM`; the `callm` hint already holds the receiver's kind and the method's row), then the ones the census shows are settled but have no cache today: binary arithmetic (97.7% of executions at a one-pair site), index ops (one container-and-index kind every compute site), and the user call (one function per site in the compute set). A guard tests a type tag (`Int`, `Float`, `Str`, `Map`, `List`), a key's position (an `IndexMap` slot index), and a shape if decision (h) lands. The first reader cig needs is the interpreter: it is what every tier shares. (entries 1, 5, 6, 9; `data/census/README.md`)

## Design points

### 1. CacheIR is a linear bytecode of guards, idempotent loads and one result op

- **What it does, and why.** A stub is a sequence with three kinds of op: guards that check a property (`GuardToObject`, `GuardShape`), idempotent loads and stores without side effects (`LoadObject`, `LoadFixedSlot`), and exactly one result op at the end that may have side effects. Reading top-down makes a stub a straight-line program: no branches, no loops. The `[SMDOC] CacheIR` comment in `CacheIR.h` states this contract, and `CacheIROps.yaml` declares every op. There are 468 ops at this pin; 80 start with `Guard`, 287 end in `Result`.

  Operands come in three kinds: `Id` (a 16-bit operand number encoded as a single byte in the stream), field (the value is in the stub's data; the stream carries only the offset), immediate (the value is baked into the op bytes). A stub is written through a `CompactBufferWriter` and read through a `CompactBufferReader`; the opcode itself is a fixed 16-bit tag, and the writer records, per operand id, which instruction used it last (`operandLastUsed_` in `CacheIRWriter.h`) so the register allocator in the compilers can free a slot the moment it is no longer live. A stub that has run once shares its code (see entry 3) but not its data, and the compact-buffer encoding keeps the common per-site overhead small: on `JS_64BIT` an operand id is one byte and a stub field offset is one byte.
- **For cig: adapt.** cig's VM today stores one 32-bit cell per bytecode PC (`Proto::hints`), read only at `GETFIELD`, `SETFIELD` and `CALLM` (three sites, not four): the getfield and setfield cache remembers the key's position in the `IndexMap`, the callm cache packs the receiver's kind in the high half and the method's table row in the low half (`cig-script/src/stdlib/mod.rs`, `method_slot` and `method_at`, with the test `slot >> 16 != kind`). The arithmetic opcodes read no `hints`. Replace this with a small CacheIR-shaped IR: an input operand id, a guard operand, a result that writes a register. Keep rule 7 by verifying the IR when it is built, and rule 1 by forbidding a `burn` op from a stub's body. **cig's form:** a new cache module beside `cig-script/src/vm/mod.rs`, with an op enum and a per-site stub chain replacing the `hints: Vec<Cell<u32>>` field of `Proto`.
- **What would decide it.** Measured: the census counted exactly this (`data/census/README.md`). In the 21 compute programs, every field site saw one shape at one key position and every method site one receiver type; 28 of 29 call sites called one function. In `orchestrate.cig` (cigo's script) 66% to 100% of field reads were at a two-shape site, the key sat at one position for 50% to 84% of them, and no function saw more than three rows of argument types. A chain length of two covers every site measured; a cap of three leaves room for the caller cases the census did not run. What is still open: the per-site time cost on the test machine; the tree-walker was not instrumented.
- **Feeds.** cig-compile#32, cig-script#256; decisions (b), (h).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIR.h` (`CacheOp`, `OperandId`, `CACHE_IR_KINDS`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIROps.yaml` (`GuardToObject`, `LoadFixedSlotResult`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/doc/cacheir.md`; `cig-script/src/vm/mod.rs` (`Proto`, `hints`); `cig-script/src/stdlib/mod.rs` (`method_slot`, `method_at`).

### 2. Each op declares itself in a YAML table that drives code generation

- **What it does, and why.** Every op in `CacheIROps.yaml` carries `name`, `shared` (whether one piece of generated code serves both baseline and the optimizer's own caches), `transpile` (whether the Warp transpiler can turn it into MIR), `cost_estimate` (a score from 0 to 6 where 0 is no machine code and 5 is a call into the VM), and `args` broken into three argument kinds: `Id` (an operand defined earlier in the stub), field (a value in the stub's own data), immediate (a byte written into the op itself). A Python script, `GenerateCacheIRFiles.py`, turns the table into header macros that the writer, the reader, the compilers, the transpiler, the cloner and the health spewer all consume. 390 ops are `shared: true` at this pin; 460 are `transpile: true`. Two optional attributes complete the table: `custom_writer` (the generated writer is private, with a trailing underscore, so the generator can wrap it in handwritten pre-checks) and `inlining_candidate` (the writer sets the `TrialInliningState` to `Candidate` when this op is emitted). Only four ops carry `inlining_candidate` at this pin: the scripted-call and scripted-getter/setter ops that trial inlining looks for.
- **For cig: take.** This is what rule 2 ("errors at the same place with the same code") needs for cig: a single table where each op's definition, cost and permission to be transpiled is declared once and read by every tier. **cig's form:** a `cache-ops.toml` under `cig-script/crates/cig-bytecode/` with the same four columns, read by a `build.rs` that emits the op enum, the writer trait and the interpreter's dispatch table.
- **What would decide it.** Decided by rule 2 and rule 5 (identical behavior on every engine). One definition is the only way to keep three engines in step.
- **Feeds.** cig-compile#32, cig-compile#33; decisions (b), (c).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIROps.yaml` (`shared`, `transpile`, `cost_estimate`, `args`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/GenerateCacheIRFiles.py` (`CACHE_IR_TRANSPILER_OPS`); `cig-script/crates/cig-bytecode/src/opcode.rs` (`Op`).

### 3. Stub data lives apart from stub code, so one piece of code serves many sites

- **What it does, and why.** A baseline stub has three parts: the generated jitcode (shared), a `CacheIRStubInfo` (shared: holds the IR bytes plus a map of stub-field offsets for the GC), and the stub's own data appended to the `ICCacheIRStub` struct (shapes, slot indexes, `JSObject*` fields). The jitcode reads every stub-field by offset from the stub pointer.

  The sharing is enforced by `CacheIRStubKey`: its `Lookup` hashes the bytes with `kind` and `engine`, so any two stubs with the same IR bytes end up in the same slot of the zone's weak map `CacheIRStubInfo*` to `JitCode*`. Ion stubs, by contrast, bake stub fields directly into code; the `[SMDOC] CacheIR` comment calls that "probably a mistake" and says Ion ICs should be shared the same way as baseline's one day. `CacheIRWriter::addStubField` deduplicates fields within one stub (scanning existing fields for the same `(value, type)` pair) and caps the stub's data at `MaxStubDataSizeInBytes = 20 * sizeof(uintptr_t)` and the operand ids at `MaxOperandIds = 20`, which is what keeps every offset in a single byte.
- **For cig: adapt.** Rule 8 ("programs stay reproducible, the same bytes from the same input") lands cleanly on the baseline design: the per-site data is small, the per-code stream is content-addressed, and nothing in a program's bytecode ever changes because of a stub. The Ion design, which bakes constants into machine code, is a dead end under rule 7 ("verified bytecode, never rewritten"): cig's native tier must never carry a pointer that can be relocated per-site. **cig's form:** a `CacheStubInfo` type in the new cache module with the IR bytes, a stub-data-offset table, and the per-site data appended; the stub map is on `cig-script/src/vm/mod.rs`'s `Proto` as a slice indexed by PC.
- **What would decide it.** Decided by rule 8.
- **Feeds.** cig-compile#32, cig-compile#36 (size and start-up); decisions (b), (f).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIR.h` (`StubField`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRStubKey.h` (`CacheIRStubKey`, `Lookup`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineIC.h` (`ICCacheIRStub`, `CacheIRStubInfo`); `cig-script/src/vm/mod.rs` (`Proto`).

### 4. OperandId types carry the type that a guard has already proved

- **What it does, and why.** `OperandId` is a 16-bit index; its subclasses (`ValOperandId`, `ObjOperandId`, `StringOperandId`, `Int32OperandId`, and so on) carry, at the type level, what a prior guard already showed. `GuardToObject` returns an `ObjOperandId`; later ops that take an `ObjOperandId` can skip the tag check. This is how a stub's sequence stays single-guard-per-property.

  The writer in `CacheIRWriter.h` has typed methods; the reader in `CacheIRReader.h` decodes a typed byte stream; the interpreter in `PortableBaselineInterpret.cpp` stores `uint64_t` virtual registers and relies on the writer's types to keep the bits interpretable (there is no runtime type check inside the IC interpreter). A `TypedOperandId` carries a `JSValueType` alongside the operand index; it has implicit conversions from `ObjOperandId`, `StringOperandId`, `SymbolOperandId`, `BigIntOperandId`, `BooleanOperandId` and `Int32OperandId` that fix the tag to the matching `JSVAL_TYPE_*`, and an explicit `(ValOperandId, JSValueType)` constructor. The register allocator uses it in `CacheIRCompiler::useRegister` to decide whether an operand needs unboxing.
- **For cig: adapt.** cig's values are 24 bytes with a plain Rust `enum Value`; a check is a `match` on the variant and is not cheap when repeated. A typed operand id would let a stub say once that a register holds a `Map`, and later ops read the inner `Rc<RefCell<IndexMap<String, Value>>>` directly. **cig's form:** a `TypedId` with `Val`, `Obj` (a `Map` or `List` or object-like value), `Int`, `Str`, `Float` in the op's Rust type.
- **What would decide it.** Partly measured: the census (`data/census/README.md`) reports 97.7% of arithmetic executions at a one-pair site, and 15 of 20 arithmetic programs ran every arithmetic instruction on two integers. Typed ids save work where the same variant is read twice; the census shows the second read is at the same tag in nearly every case. What is still open: the per-read time the tree-walker's `match` on `Value` costs; the census counted instructions, not milliseconds.
- **Feeds.** cig-compile#34 (types for speed), cig-compile#35 (values); decisions (b), (i).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIR.h` (`OperandId`, `ObjOperandId`, `Int32OperandId`, `TypedOperandId`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRWriter.h` (`CacheIRWriter`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRCompiler.cpp` (`useRegister`); `cig-script/src/value.rs` (`Value`, `Map`).

### 5. The generators look at actual values and emit guards then an action

- **What it does, and why.** Each generator (`GetPropIRGenerator`, `SetPropIRGenerator`, `BinaryArithIRGenerator`, `CallIRGenerator`, and so on) is given the actual values that the fallback stub saw. Its `tryAttachStub` runs a sequence of `tryAttach*` helpers (`tryAttachNative`, `tryAttachDenseElement`, `tryAttachProxy`, `tryAttachInt32`, `tryAttachDouble`), each of which either returns `AttachDecision::NoAction` or writes a short IR sequence and returns `Attach`. A `TRY_ATTACH` macro returns the first that attaches. The baseline fallback keeps the operation working; the IR only has to handle the case it saw. 20+ generator classes exist in `CacheIRGenerator.h`.

  The decision enum has four values: `NoAction`, `Attach`, `TemporarilyUnoptimizable` (do not count this as a failure so the site stays in Specialized), and `Deferred` (the stub needs a shape the operation itself will produce, so attach after the fallback runs). The first stub at a site can be more optimistic than later stubs: generators consult `isFirstStub()` to emit a tighter IR before polymorphism forces a widening. A generator never does the work itself: it writes IR that, when run, would do the work; the fallback does the work for this one call. This separation is what lets the generator be a pure function of the inputs, with no observable side effects, which is what rule 3 (step budget exact) requires.
- **For cig: adapt.** cig's VM at `GETFIELD` and `SETFIELD` remembers only a slot position; at `CALLM` the cache already keys on the receiver's kind (`str`, `list`, `map`) and the method's table row (`cig-script/src/stdlib/mod.rs`, `method_slot`, `method_at`), so no `callm` generator is new work. The sites with no cache today are arithmetic (`ADD`, `ADDK`, `SUB`, `SUBK`, `MUL`, `MULK`, ...; see `cig-script/src/interp/ops.rs` `fast_binary`), the index ops, and the user call. Lacking today: a shape-aware `getfield` that would hold a slot valid across calls, a binary-arith generator that remembers the operand-type pair, an index-op generator that remembers container-and-index kinds. **cig's form:** one generator per CIR instruction kind that gets a cache (`get_field`, `set_field`, `binary`, `index`, `call_user`), living under a `gen` submodule of the new cache module; `callm` keeps its existing two-field cache for now.
- **What would decide it.** Measured: the census (`data/census/README.md`) counted operand-type pairs at every arithmetic site (97.7% of executions were at a one-pair site; 15 of 20 programs had every arithmetic instruction run on two integers) and shapes at every field site (one shape and one key position in every compute program). A one-stub generator would attach once and stay attached for the whole run on every compute program. What is still open: the generator-would-attach rate on larger scripts than cigo's and the cost of the attach itself (time on the test machine).
- **Feeds.** cig-compile#32, cig-compile#34; decisions (b), (c).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRGenerator.h` (`GetPropIRGenerator`, `BinaryArithIRGenerator`, `CallIRGenerator`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIR.cpp` (`tryAttachNative`, `tryAttachInt32`, `TRY_ATTACH`); `cig-script/src/vm/mod.rs` (`Proto`, `hints`); `cig-script/src/stdlib/mod.rs` (`method_slot`, `method_at`); `cig-script/src/interp/ops.rs` (`fast_binary`).

### 6. A shape is a one-word summary of a map's layout that guards can check

- **What it does, and why.** Every native object carries a `Shape*`; two objects with the same `(class, realm, prototype, property list, fixed-slot count)` share a `SharedShape`. A `GuardShape` op in the stub does one pointer compare; if it passes, the stub can load `fixed slot N` by offset without a hash lookup on the key. The `SMDOC Shapes` comment in `Shape.h` names the hierarchy (`Shape` -> `NativeShape` -> `SharedShape`/`DictionaryShape`, `ProxyShape`, `WasmGCShape`).

  The shape is immutable in the shared case: a field write that adds a key makes a new shape, which is why `GuardShape` is a stable test. A `DictionaryShape` is unshared, private to one object, created when the heuristics in `NativeObject::maybeConvertToDictionaryForAdd` decide the object is too dynamic to keep a shared shape (many property adds, flag changes on non-last properties, deletes of non-last properties). A `GuardShape` against a dictionary shape is still a valid guard but the shape is replaced any time the dictionary mutates, so stubs for a dictionary object rarely stay attached.
- **For cig: adapt.** cig has no shapes today: `Map` is `Rc<RefCell<IndexMap<String, Value>>>`, insertion-ordered, string-keyed (`cig-script/src/value.rs`). Rule 4 (maps keep insertion order) is already met by `IndexMap`; a shape would be a second layer that remembers which keys have appeared together. A cig shape is the pair `(class marker, Vec<String>)` plus the fixed-slot count, built lazily when a map is first used at a cached site; shape changes would happen only on key insert, which is a plain write, so rule 1 (burns never move) is untouched. The census makes the case: in the 21 compute programs every field site saw one shape, so a `GuardShape` that reads one word is strictly cheaper than the `IndexMap` lookup cig does today; in cigo's script 66% to 100% of field accesses are at a two-shape site, so a two-stub chain with two `GuardShape` ops covers the measured polymorphism. Decision (h) is answered by the counts.
- **What would decide it.** Measured: `data/census/README.md` (one shape a site in the compute set; two shapes a site in cigo, key at one position for 50% to 84% of accesses). What is still open: the per-write cost of maintaining a shape as keys are inserted, and how the shape interacts with `IndexMap`'s rehash on grow; neither was timed.
- **Feeds.** cig-compile#35 (values, shapes), cig-compile#34; decision (h).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/vm/Shape.h` (`Shape`, `SharedShape`, `DictionaryShape`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/vm/PropMap.h` (`PropMap`); `cig-script/src/value.rs` (`Map`, `IndexMap`); `data/census/README.md`.

### 7. Shared code for baseline, Ion's own caches and the macro assembler

- **What it does, and why.** `CacheIRCompiler.cpp` implements every `shared: true` op (390 of 468) once, in terms of a macro assembler that both the baseline compiler and the Ion IC compiler drive. `BaselineCacheIRCompiler.cpp` extends it for ops whose baseline implementation cannot share (the `shared: false` ops): call setup, bound functions, create-this, and the arguments-object paths. `IonCacheIRCompiler.cpp` does the same on the Ion side and also bakes stub-field values directly into the code. The split keeps the mechanical guards in one place and the tier-specific scaffolding in two.

  The register allocator is a shared service too (entry 19 covers it): it keeps track of which operand id lives in which register and spills when a `callVM` or `callWithABI` demands a specific register. The cost table from entry 2 (`cost_estimate 0..6`) is scaled on this allocator's work: 0 is "no code", 5 is "a call into the VM", 6 is "more than one such call", and the per-op scores in the YAML say which of those is the right one.
- **For cig: adapt.** cig has two native tiers planned (stage C whole-program, cig-cherry per-function) and they both lower CIR to Cranelift. A shared-ops crate, read by both, is exactly the right shape. **cig's form:** a new crate (name provisional: `cig-cache-compile`) under `cig-script/crates/`, holding the per-op lowering from CacheIR to Cranelift IR, called by stage C's lowering and by the cig-cherry executable.
- **What would decide it.** Decided by rule 2 and by `docs/decisions/0001-backend.md`'s single-code-generator commitment, which the newer comment on cig-compile#32 extends to cig-cherry.
- **Feeds.** cig-compile#32, cig-script#256; decisions (b), (e).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRCompiler.h` (`CacheIRCompiler`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineCacheIRCompiler.h` (`BaselineCacheIRCompiler`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/IonCacheIRCompiler.h` (`IonCacheIRCompiler`); `cig-compile/docs/decisions/0001-backend.md`.

### 8. Warp turns baseline's IR into optimizer IR with a transpiler

- **What it does, and why.** `WarpCacheIRTranspiler` reads the bytes of one baseline stub and emits MIR through `CACHE_IR_TRANSPILER_OPS` (a macro produced from the YAML column `transpile`). A `GuardShape` op in the stub becomes `MGuardShape` in MIR; a `LoadFixedSlotResult` becomes an `MLoadFixedSlot`. `TranspileCacheIRToMIR` in `WarpCacheIRTranspiler.cpp` is what every call site in `WarpBuilder.cpp` uses. The transpiler's input is a `WarpCacheIR` snapshot, which already contains the bytes; MIR bailouts for transpiled guards get `BailoutKind::TranspiledCacheIR`.

  460 of 468 ops are transpilable at this pin; an untranspilable op in a stub (see `maybeInlineIC` in `WarpOracle.cpp`) stops the snapshot being created for that site, which falls back to an Ion IC instead. The one-result-op rule from entry 1 pays off here: every stub has exactly one point where an effectful MIR instruction is emitted, and the `effectful_` debug field in the transpiler asserts it.
- **For cig: adapt.** Decision (b) asks for "one inline-cache and feedback format for the VM, stage C and cig-cherry". The transpiler shows how: the same op reader fed into a function that emits whatever the optimizer wants (MIR in Warp's case, Cranelift IR in cig's). **cig's form:** a `transpile_cacheir(reader, builder)` function in the shared ops crate, called by cig-compile's stage C where today it would emit a runtime call, and by cig-cherry when it compiles a hot function.
- **What would decide it.** Not measured yet: a comparison between (i) inlining the cached fast path into the compiled code and (ii) always calling into `cig_rt_getfield` after a cheap guard, on fib and mandel.
- **Feeds.** cig-compile#32, cig-compile#33, cig-script#256; decisions (b), (c).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/WarpCacheIRTranspiler.cpp` (`WarpCacheIRTranspiler`, `transpile`, `TranspileCacheIRToMIR`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/WarpBuilder.h` (`buildIC`); `papers/compilers/hacks-warp-improved-js-firefox-83.html`.

### 9. The interpreter reads stubs with no native code: this is cig's situation

- **What it does, and why.** `PortableBaselineInterpret.cpp` is a C++ interpreter that runs the IC stubs by interpreting the IR, with no jitcode. Its `[SMDOC] Portable Baseline Interpreter` in `PortableBaselineInterpret.h` is the design document. It keeps an auxiliary stack separate from the C++ stack, an array of `uint64_t` virtual registers (`ICCtx::icregs`), and a dispatch table built from `CacheIROps.yaml`. A "hybrid IC" mode (`kHybridICsInterp`) skips the chain for common opcodes and uses static fast paths, which is what cig's VM does today. Unimplemented ops act as a failed guard and fall through to the next stub, so fallback keeps the engine correct even when PBL implements only part of CacheIR.

  The dispatcher is computed-goto where the compiler supports it and a `switch` otherwise; `ICInterpretOps` saves and restores the first N operand-id virtual registers (where N is the arity of the IC kind) across each stub so that an op that mutates its input in place (for example `GuardToObject` strips the tag from a Value) does not corrupt the next stub in the chain. The hybrid-IC split is explicit in the SMDOC: "calls and property accesses use ICs" because property access is slow (shape lookup) and calls can inline intrinsics; everything else uses a static fast path in the JSOp interpreter. The IC interpreter is the one PBL inlines into every IC site to save a native call.
- **For cig: take.** This is the closest existing design to cig's rule 8 (no writable-and-executable memory) and to cig-os's Fortress profile (cherry off). cig's VM already is a bytecode interpreter; it just needs stubs that it can walk. **cig's form:** the VM in `cig-script/src/vm/mod.rs` gets a per-op handler for the new cache ops, and a per-site chain walker that tries each stub, falling back to the current slow path when every stub fails.
- **What would decide it.** Decided by rule 8 for CIG.OS Fortress; measured for Standard: `cig-script/docs/research/luajit.md` "Status" gives a field read at 88 instructions in cig's VM against 21 in LuaJIT's interpreter, and a map read by key at 97 against 29. The overhead the IC interpreter adds must be balanced against the slots it saves; the census already shows one shape and one key position per site on every compute program (`data/census/README.md`), so the maximum per-site win is close to the VM's baseline count on those programs.
- **Feeds.** cig-compile#36, cig-script#256; decisions (b), (c).

### 10. Ahead-of-time stubs: a corpus baked into the runtime

- **What it does, and why.** Under `ENABLE_JS_AOT_ICS`, `CacheIRAOT.cpp` compiles a captured set of stubs into the runtime itself, as C arrays of bytes plus a `CacheIRAOTStub` header per stub carrying the kind, operand counts, instruction counts, stub-data size and the field-type table (`AOTStubFieldData`). `FillAOTICs` installs them into a `JitZone` on start. Native pointers are serialized as null (the comment: "an AOT-loaded stub should not bake in an arbitrary pointer observed from a previous execution"), which is why the AOT corpus is restricted to baseline-shaped stubs that do not need runtime pointers.

  The reconstructed `CacheIRWriter` copies the stub-fields vector from the AOT struct and writes the IR bytes directly through `buffer_.writeBytes`; the existing baseline compiler then compiles the stub exactly as if the writer had just emitted it live. The macros `OP`, `ID`, `OFFSET`, `INT32`, `GUARDCLASSKIND` and so on in `CacheIRAOT.cpp` match the writer's encoding byte-for-byte, so an AOT stub and a freshly-written one of the same shape are indistinguishable once installed.
- **For cig: take.** This is a straight fit for cig's tin: a program's cache for its own hot sites, keyed by the function's bytecode hash, lives signed in the tin exactly like cig-cherry's native code does (cig-script#256 §4). The format carries bytes, not code. A program can ship with a trained corpus: `cig cherry warm` runs it, the IC chains are dumped as AOT stubs, the next run starts with them already in place.
- **What would decide it.** Not measured yet: compare a first run of a short script with and without a trained corpus for `getfield` and `callm`, on the compute set.
- **Feeds.** cig-compile#36 (start-up and size), cig-script#256 §4; decisions (b), (f).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRAOT.h` (`CacheIRAOTStub`, `AOTStubFieldData`, `GetAOTStubs`, `FillAOTICs`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRAOT.cpp` (`JS_AOT_IC_DATA`); `cig-script/src/burn/modcache.rs`.

### 11. A site has three modes and a hard stub count

- **What it does, and why.** `ICState` (`ICState.h`) is the per-fallback-stub state: `Mode::Specialized`, `Mode::Megamorphic`, `Mode::Generic`, plus `numOptimizedStubs_` and `numFailures_`. The site attaches up to `MaxOptimizedStubs = 6` specialized stubs; the 7th attach forces a transition through `shouldTransition()`. The failure budget is `5 + 40 * numOptimizedStubs_`, so an attached stub buys the site more tries before it falls out of Specialized.

  Megamorphic uses more general IR (for example a hash-based slot lookup rather than a shape guard); Generic stops attaching and always runs the fallback. `forceTransition` moves from Specialized to Megamorphic when the stub count is at the cap, and from Megamorphic to Generic when the failure count exceeds `maxFailures` (or immediately from Specialized to Generic if the failure count is already high enough). `trackAttached` caps the failure count at 1 after a successful attach (`numFailures_ = std::min(numFailures_, 1)` at `ICState.h`) so that an attach with a transient bad pattern before it does not force the site into Generic unnecessarily; a count already at 0 stays at 0.
- **For cig: adapt.** Rule 2 (errors happen at the same place) and rule 5 (identical behavior on every engine) are untouched: a site that falls to Generic still calls the oracle path, which is the tree-walker's logic in the fallback. **cig's form:** a `SiteState` type in the cache module with the three modes, a stub-count cap, and a failure counter. The census (`data/census/README.md`) says the cap can be small: one stub serves every site in the compute set, and two stubs serve 66% to 100% of field accesses in cigo. A cap of three is enough for every site the measurement saw; four to five leaves slack. The 6-stub cap is SpiderMonkey's, and the Megamorphic mode is kept as a safety net for scripts larger than cigo's.
- **What would decide it.** Measured for the compute set and for cigo: one and two shapes a site, one and three rows of argument types a function, 28 of 29 compute call sites with one callee (`data/census/README.md`). What is still open: sites in scripts larger than cigo's, which the census has none of; the Megamorphic threshold stays a conservative choice until a larger corpus exists.
- **Feeds.** cig-compile#33, cig-compile#34; decisions (b), (c).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/ICState.h` (`ICState`, `Mode`, `MaxOptimizedStubs`, `maxFailures`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineIC.h` (`ICFallbackStub`, `state`); `cig-script/src/vm/mod.rs` (`Proto`, `hints`).

### 12. Stub folding: several shape guards become one

- **What it does, and why.** `StubFolding.cpp` detects IC chains whose stubs share code and differ only in a single `GuardShape` stub field (and the consecutive slot offset it reads). When the first `firstStub` has been overtaken in entered-count by another stub, `TryFoldingGuardShapes` rewrites the chain into a single stub whose `GuardShape` is replaced with `GuardMultipleShapes` (or `GuardMultipleShapesToOffset` when the offset also varies), and whose shape list is kept in a tracing map on the stub. This turns a polymorphic site back into a one-stub site that the transpiler can inline.

  The conditions are explicit (comment at the top of `TryFoldingGuardShapes`): (a) all stubs in the chain have the exact same code, (b) their stub-field data differs only in a single `GuardShape` field (and possibly a consecutive `RawInt32` offset), (c) at least one stub after the first has been entered, (d) every shape in the resulting list is in the same realm. If any condition fails, the fold is abandoned and the chain keeps its original stubs. `ICState::mayHaveFoldedStub` is a hint set at attach time to try folding again when the next stub arrives.
- **For cig: adapt.** It is the counterpart to Specialized mode's cap: fold before the 6th stub forces the site into Megamorphic. **cig's form:** a `fold_shape_guards` pass on the stub chain, called from the site's "about to attach a new stub" path, using cig's shape (entry 6) once it exists.
- **What would decide it.** Not measured yet: the fraction of cig's sites that would fit a 2-to-4-shape GuardMultipleShapes on the compute set.
- **Feeds.** cig-compile#33, cig-script#256; decisions (b), (h).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/StubFolding.cpp` (`TryFoldingGuardShapes`, `GuardMultipleShapes`, `GuardMultipleShapesToOffset`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/StubFolding.h`; `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineIC.h` (`ICFallbackStub`).

### 13. Health scoring: a per-op cost that reads out a site's happiness

- **What it does, and why.** Each op in `CacheIROps.yaml` has a `cost_estimate` (0 to 6). `CacheIRHealth.cpp` walks a stub's IR and sums the costs; a site is `Happy` under 10, `MediumHappy` under 20, `MediumSad` under 30, `Sad` above. The spewer also records whether the fallback was ever entered, the trial-inlining state, and the final warm-up count, into a structured-spew channel.

  The cost table is a per-op uint32 vector `CacheIROpHealth[]` declared in `CacheIR.h`; it is filled by the Python generator from the YAML cost column. `spewICEntryHealth` reports per-site the opcode, the line and column, the fallback count, the IC mode (an unspecialized fallback mode drops the entry straight to `Sad`), and each stub's health. The spewer is only built when `JS_CACHEIR_SPEW` is defined; in release builds the cost table is still present but unused.
- **For cig: adapt.** cig has no counters beyond the step budget; this gives a cheap way to decide which sites are worth specializing further and which have gone bad. **cig's form:** a `cost_estimate` column in the `cache-ops.toml` from entry 2, a per-site score computed at attach time, and a spew channel for the `cig run --log-cache` diagnostic.
- **What would decide it.** Decided by rule 3 (step budget is exact, so counters do not drift) and by cig's logging policy; the thresholds 10/20/30 are read in place from `CacheIRHealth.cpp` and may differ after measurement.
- **Feeds.** cig-compile#33, cig-compile#38 (debugging); decisions (b), (c).

### 14. Counters and the next tier live together in ICScript

- **What it does, and why.** A `JitScript` owns one `ICScript` as its last field; the `ICScript` holds an array of `ICEntry` and one `ICFallbackStub` per entry, plus `warmUpCount_` (an atomic uint32) and `ionThreshold_` (the warm-up value at which the script tiers up). Each `ICStub` has its own `enteredCount_` so a chain tells you both "how many times this site fired" and "how many times each stub fired". The `[SMDOC] ICScript Lifetimes` and `[SMDOC] JitScript` in `JitScript.h` state the ownership. The warm-up counter drives the four tiers' tier-up thresholds from `how-we-optimize.md`: 10 for blinterp, 100 for baseline-compile, 1500 for Ion.

  Trial inlining allocates a free-standing `ICScript` per inlined site; the comment "Each ICStub is owned by an ICScript and, indirectly, a JitScript" is literal: a stub's `CacheIRStubInfo` is a zone-level object, but its stub-data and its position in a chain belong to one `ICScript`. An IC chain's first stub is its most recently attached; the fallback is its tail. `BaselineIC.h`'s ASCII diagram at the head of the file is the picture to keep in mind. The `WarpOracle` uses "second stub has entered count 0" as the test that the most recently attached stub handles every case the site has seen since it was attached, which is the condition for transpiling the stub into MIR instead of leaving an Ion IC in place (`cacheir.md` names this as the design's "single source of truth" principle).
- **For cig: adapt.** Rule 3 (step budget, one tick per statement) is the oracle for step counting; cig-cherry decision (c) is "one counter and profile format". cig-script#243 A8 already decided a single counting mechanism. **cig's form:** a `CacheScript` on `Proto` with the per-site chain, a 32-bit warm-up counter per function, and a per-stub entered-count. Thresholds are cig's to choose from measurement.
- **What would decide it.** Not measured yet: the warm-up thresholds for cig-cherry are the subject of its own experiment; SpiderMonkey's 10/100/1500 are read in place here, not taken.
- **Feeds.** cig-compile#33, cig-script#256, cig-script#243 (A8); decisions (b), (c).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/JitScript.h` (`ICScript`, `warmUpCount_`, `ionThreshold_`, SMDOC); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineIC.h` (`ICStub`, `enteredCount_`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/doc/how-we-optimize.md`.

### 15. Trial inlining gives a call site its own copy of the callee's caches

- **What it does, and why.** `TrialInlining.cpp` runs on top of the baseline interpreter: at each call IC site, `TrialInliner::maybeInlineCall` decides whether to make a fresh, inlined `ICScript` for the callee's bytecode (`createInlinedICScript`), rewrite the caller's stub to point at it, and let the callee's caches specialize to this particular caller. `cloneSharedPrefix` copies the shared prefix of the caller's stub into the new `CacheIRWriter` (through `CacheIRCloner`), keeping the guards but swapping the call's target. `tryInlining` walks the caller's IC entries and decides for every scripted call and property IC separately. The depth is capped at 4 by `MaxICScriptDepth`.

  The trial-inlining state is a 3-bit field on the `ICState` (`TrialInliningState`): `Initial`, `Candidate`, `Inlined`, `MonomorphicInlined`, `Failure`. Transitions are checked in debug builds to ensure each site goes through trial inlining at most once; `Failure` can be reached at any time but is terminal. The `JitHints` cache in `WarpOracle.cpp` lets a next-page-load remember which sites were monomorphically inlined, so the second load skips the trial. For getters and setters, `maybeInlineGetter` and `maybeInlineSetter` do the same for property ICs, cloning the shape-guard prefix and then rewriting the "call the scripted accessor" tail with the accessor's own bytecode.
- **For cig: adapt.** Decision (c) asks for one profile format for the VM, stage C and cig-cherry; trial inlining shows how the same caches can be reused at depth without re-recording. **cig's form:** per-call-site cloned `CacheScript` entries, built on the back of entry 14's `CacheScript`, in an `inline` submodule of the cache module.
- **What would decide it.** Measured: the census (`data/census/README.md`) counted that in the compute programs 28 of 29 `call` sites called one function and every function was called with one row of argument types, so a caller-local copy would not change the hit rate there. In cigo's script, no function saw more than three rows of argument types, so one copy per caller would already cover the observed polymorphism. What is still open: whether the extra `ICScript` per inlined site fits the memory budget of `cig-compile#36`.
- **Feeds.** cig-compile#33, cig-script#256; decisions (b), (c).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/TrialInlining.cpp` (`TrialInliner::tryInlining`, `maybeInlineCall`, `maybeInlineGetter`, `maybeInlineSetter`, `cloneSharedPrefix`, `createInlinedICScript`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRCloner.h` (`CacheIRCloner`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/JitScript.h` (`ICScript`).

### 16. The snapshot is taken on the main thread, from plain data

- **What it does, and why.** `WarpOracle::createSnapshot` in `WarpOracle.cpp` is the main-thread half of Ion compilation: it walks the bytecode of the script (and its trial-inlined callees), and for each IC site decides what to carry. If a single stub handles all cases, it copies the stub's IR bytes and its data into a `WarpCacheIR` (a `WarpOpSnapshot` of kind `WarpCacheIR`). If the site is cold, a `WarpBailout` is recorded instead so the off-thread build can insert a bailout. If an IC's call target is known and the callee's bytecode fits, trial inlining attaches the callee's own stubs. The result is a `WarpSnapshot` that contains only bytes, lists and offthread GC pointers: `WarpBuilder.cpp` runs off-thread on the snapshot alone.

  The op-snapshot kinds are `WARP_OP_SNAPSHOT_LIST` in `WarpSnapshot.h`: sixteen kinds including `WarpArguments`, `WarpRegExp`, `WarpBuiltinObject`, `WarpGetIntrinsic`, `WarpGetImport`, `WarpRest`, `WarpBindUnqualifiedGName`, `WarpVarEnvironment`, `WarpLexicalEnvironment`, `WarpClassBodyEnvironment`, `WarpBailout`, `WarpCacheIR`, `WarpCacheIRWithShapeList`, `WarpCacheIRWithShapeListAndOffsets`, `WarpInlinedCall` and `WarpPolymorphicTypes`. The two "with shape list" variants carry a folded stub's shapes (entry 12) explicitly into the snapshot so the off-thread compiler does not race a GC that could remove shapes from the stub's tracing list. The "polymorphic types" snapshot records multiple observed operand-type pairs for sites that did not fit a single stub but whose polymorphism is still regular enough to specialize against.
- **For cig: take.** Rule 2 and rule 1 both need this: an off-thread compile never looks at the VM's live state. cig's values are `Rc` and can never cross a thread boundary; the snapshot's bytes can. **cig's form:** a `cherry::snapshot(func, caches)` call on the main thread, written to the staging folder in the tin as plain bytes; the `cig-cherry` executable reads the bytes and emits native code, as cig-script#256 §5 specifies.
- **What would decide it.** Decided by rule 1 (burns never move: a compile thread must not touch `Rc` counts) and by cig-script#256's requirement that compile run in its own process.
- **Feeds.** cig-compile#32, cig-script#256; decisions (b), (e).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/WarpOracle.cpp` (`WarpOracle::createSnapshot`, `maybeInlineIC`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/WarpSnapshot.h` (`WarpSnapshot`, `WarpCacheIR`, `WarpBailout`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/WarpBuilder.cpp` (`TranspileCacheIRToMIR`).

### 17. Bailouts rebuild the lower tier's frame from snapshot plus recover instructions

- **What it does, and why.** Each Ion guard carries a snapshot (see `Snapshots.h` for the encoding `RValueAllocation`: `TYPED_REG`, `TYPED_STACK`, `RECOVER_INSTRUCTION`, `RECOVER_SIDE_EFFECT_MASK`, `CONSTANT`) that says, for each baseline-frame slot, where the live value is in the Ion frame. On a failed guard, `Bailouts.cpp` and `BaselineBailouts.cpp` walk the snapshot and build a fresh baseline frame; recover instructions (`Recover.h`'s `RECOVER_OPCODE_LIST`, documented in `[SMDOC] IonMonkey Recover Instructions`) are the pieces of work that Ion optimized away and have to be redone before the baseline frame can run. The baseline interpreter then takes over at the matching bytecode PC.

  A recover instruction has the same name as the MIR instruction it mirrors (`RBitAnd`, `RBitOr` and so on); its operands come from the snapshot through the `SnapshotIterator`, and its result goes back into the frame slot that would have held the MIR instruction's output. When the stack is introspected from the outside (a debugger reading an Ion frame, say), running a recover instruction invalidates the code, because the allocation that `RECOVER_SIDE_EFFECT_MASK` marks may have observable state.
- **For cig: adapt.** cig-compile#32's new comment and decision (d) both say stage C and cig-cherry need guards that exit to the VM, with the step count, the open tries, the open burns and the journal's position all rebuilt. SpiderMonkey's snapshots cover the register-and-stack half; the tries/burns/journal half is cig-specific. **cig's form:** a `CigSnapshot` with (i) per-slot `RValueAlloc` for registers and stack, (ii) a step-count field, (iii) a try-depth and the pc/base of each open `try`, (iv) a burn-depth and the journal position at each open `burn`. The off-thread compiler writes this snapshot next to each guard's MIR; a failed guard calls `cig_rt_exit(snapshot_id)` which rebuilds the VM state.
- **What would decide it.** Decided by rules 1, 2, 3 (burns never move, errors at the same place, step budget exact).
- **Feeds.** cig-compile#32, cig-script#256, cig-script#243 (B7); decisions (b), (d).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/Snapshots.h` (`RValueAllocation`, `RECOVER_INSTRUCTION`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/Recover.h` (`RECOVER_OPCODE_LIST`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/Bailouts.cpp` (`BailoutFrameInfo`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineBailouts.cpp` (`BailoutKind::TranspiledCacheIR`).

### 18. Invalidation keeps a function from bailing forever

- **What it does, and why.** The `BailoutKind` enum lives in `js/src/jit/IonTypes.h` (`enum class BailoutKind : uint8_t` at line 96, with `TranspiledCacheIR`, `StubFoldingGuardMultipleShapes`, `LICM`, `InstructionReordering`, `HoistBoundsCheck`, `EagerTruncation`, `UnboxFolding`, `SpeculativePhi`, `TooManyArguments`, `FirstExecution` and a dozen others). `BaselineBailouts.cpp` consumes the enum and, in its `BailoutAction` enum (declared in the same file), picks an action: `InvalidateImmediately`, `InvalidateIfFrequent`, `DisableIfFrequent`, or `NoAction`. `IfFrequent` increments a counter on the `IonScript` and only trips `InvalidateAfterBailout` when the counter crosses `shouldInvalidate`'s threshold; `Disable` sets a per-script flag that keeps Ion off until a reset. `Invalidation.h` carries the `IonScriptKey` set that tracks pending invalidations and `Invalidate` walks the stack.

  Repeated-bailout detection stores a hash of the CacheIR that produced the last compile to catch bailout loops. `LICM` is a worked example: the first time an LICM-hoisted guard bails, the IonScript's LICM state moves from `NeverBailed` to `Bailed`; if the baseline fallback for that guard is then entered, the state moves to `BailedAndHitFallback` and future bailouts are treated as regular CacheIR bailouts; if not, the next bailout invalidates the script and disables LICM for it.
- **For cig: adapt.** cig-script#256's §3 says a function that keeps falling back is recompiled with wider types, then blacklisted (`E2383`). The design maps on: `InvalidateIfFrequent` is "recompile with wider types"; `DisableIfFrequent` is "blacklist". **cig's form:** a `cherry::BailoutKind` with the same four actions and a `recompile_or_blacklist(func, reason)` entry point. The step budget is untouched: a bailout is a transfer back to the VM, not a replay. Rule 2 is held because every bailout goes back to the matching bytecode PC (entry 17); rule 5 by the differential suite (cig-script#256 "Phase 3 onwards", cherry forced on, zero differences).
- **What would decide it.** Decided by rules 2 and 5 for correctness; the frequency thresholds are chosen from measurement on the compute set.
- **Feeds.** cig-compile#32, cig-compile#33, cig-script#256; decisions (b), (d).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/IonTypes.h` (`BailoutKind`, `TranspiledCacheIR`, `StubFoldingGuardMultipleShapes`, `FirstExecution`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/BaselineBailouts.cpp` (`BailoutAction`, `InvalidateAfterBailout`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/Invalidation.h` (`IonScriptKey`, `Invalidate`); `cig-script/src/vm/mod.rs` (`Proto`).

### 19. CacheIRCompiler's register allocator is a stub-wide SSA scheme

- **What it does, and why.** The `[SMDOC] CacheIR Value Representation and Tracking` in `CacheIRCompiler.h` describes how a stub's physical registers are assigned: each `OperandId` gets an `OperandLocation` (register, stack slot, or constant), and the allocator keeps track of whether each location holds a boxed `Value`, an unboxed pointer, or an `Int32`. A register is freed the instruction after the writer's `operandLastUsed_` says it was last consumed.

  Because a stub's IR is straight-line, the allocator is linear: no joins, no live-range overlap analysis. On a guard failure the stub's exit code restores the original input location so that the next stub in the chain sees a clean slate; this is what the "intra-op register allocation" paragraph of the SMDOC calls "ensuring we are able to restore the input state so that a subsequent stub can attempt to provide a value."
- **For cig: adapt.** cig-cherry runs a per-function compile. A stub is smaller than a function, but the allocator's property (single pass, linear in operands) is a fit. **cig's form:** inside the `transpile_cacheir` function of entry 8, a per-stub operand-id-to-Cranelift-value map, built in one walk, with a register-restore sequence at each guard's failure edge.
- **What would decide it.** Decided by rule 7 (verified bytecode, never rewritten at run time): a stub's code is produced once, consumed read-only. The allocator cannot introduce mutation.
- **Feeds.** cig-compile#32, cig-script#256; decisions (b), (e).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRCompiler.h` (`CacheIR Value Representation and Tracking`, `OperandLocation`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIRWriter.h` (`operandLastUsed_`); `cig-compile/docs/decisions/0001-backend.md`.

### 20. Fuses let a hot guard leave the IR, then invalidate the code if it ever pops

- **What it does, and why.** A fuse is a runtime bit that stands for a composite property ("all iterator prototypes still have their default `next`", "no array subclass overrides `push`"). `GuardFuse` in a stub checks one byte; `Realm::realmFuses` and `JSRuntime::runtimeFuses` in `vm/RealmFuses.h` and `vm/RuntimeFuses.h` are where fuses live. When Warp transpiles a `GuardFuse` that guards an invalidating fuse, it does not emit the guard: it registers a compilation dependency on the fuse, and if the fuse pops later, the whole Ion script is invalidated instead of each guard having to fire.

  `how-we-optimize.md` and `WarpOracle.cpp`'s fuse-handling branch state the mechanism; the hot-loop win is that guards vanish from the compiled code at the cost of one invalidation at pop time. Fuses are organized into trees so that one top-level fuse can depend on many smaller ones: if any of them pops, the top-level one pops too, and both the IC-level check and the Ion-script dependency reduce to a single byte at the top of the tree.
- **For cig: adapt.** cig's equivalent is a cached fact "this map's shape list has never changed" or "this builtin method is still the one the stdlib defined". A fuse-shaped design would let compiled code skip the shape guard altogether, and the pop-invalidates-code policy keeps rule 5 intact: an invalidated function falls back to the VM and the differential suite catches any drift. **cig's form:** a `Fuses` module beside the cache module, holding per-realm bits for the stdlib invariants cig today proves through `effects.rs` and the name-resolution pass (`names.rs`).
- **What would decide it.** Not measured yet: the frequency of `GuardShape` hits in `orchestrate.cig` against the frequency of shape changes to the same map. If a map's shape changes rarely, a fuse pays.
- **Feeds.** cig-compile#33, cig-script#256; decisions (b), (c), (h).
- **Read.** `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/doc/how-we-optimize.md` (`Fuses`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/WarpOracle.cpp` (`GuardFuse`, `GuardRuntimeFuse`); `spidermonkey-FIREFOX_160_0_1_RELEASE/js/src/jit/CacheIROps.yaml` (`GuardFuse`).

The AOT corpus (entry 10) is the shape of `cig cherry warm` and of `cig tin`'s cache.

## Measurements owed

- The site census the earlier draft asked for is done: `data/census/README.md` counted shapes per field site, receiver types per method site, callees per call site, operand-type pairs per arithmetic site, and rows of argument types per function, in the 21 compute programs and in cigo's `orchestrate.cig`. Entries 1, 4, 5, 6, 11 and 15 cite its findings; the shape-and-type counts answer the chain-cap, Megamorphic-threshold and shape-scheme questions the earlier draft left open.
- Per-op overhead of an interpreted stub against cig's hand-coded fast path, timed on fib, loop, sieve, mandel, a map-heavy and a `callm`-heavy workload. The census counted instructions only, not milliseconds. Decides entry 9: the kHybridICs split between interpreted ICs and static fast paths for cig's VM.
- Instruction count per field read and per `callm` with and without a shape-guarded stub, measured as `cig-script/docs/research/luajit.md` measures it (its run `w32-ljcount-j1`). Decides entry 6 against the status quo: the VM today takes 88 instructions per field read against 21 in LuaJIT's interpreter, and 97 per map read by key against 29.
- Startup cost of a trained AOT corpus against cold start, on a 500-line script. Decides entry 10: how much the tin should cache.
- Bailout frequency per function in a run with cherry forced on, for the differential suite. Decides entry 18's thresholds.
- Per-write cost of maintaining a cig shape as keys are inserted, and the shape's interaction with `IndexMap`'s rehash on grow. The census did not measure this. Decides entry 6's cost half against the already-measured win half.
- Memory per site for a cig stub against the current `Cell<u32>` in `Proto::hints`. Decides entries 1, 3 and 11: whether the per-site overhead fits the memory budget of `cig-compile#36`.
- Time per turn of a hot loop with and without an interpreted-IC chain, on fib, mandel and sieve. Decides entry 9: the point at which cig's VM gains more from a stub chain than it loses to the dispatch overhead.

For each measurement the entry format sets what is recorded and where. The compute set is the 21 programs under `cig-script/bench/compute/`; `orchestrate.cig` is the cigo workflow script that the census runs seven cases of. Every timed measurement is run on the test machine, with the step budget on and the differential suite checking that outputs match the tree-walker's.

## Not settled

- The cost of an off-thread compile in cig terms. `Rc` cannot cross threads, so the snapshot contains no live cig values; whether the `cig-cherry` executable can nevertheless re-materialise constants without them is a small design item for entry 16.
- The fold's realm/compartment check (`StubFolding.cpp` only folds same-realm shapes, since cross-realm shape pointers would complicate tracing). cig has no realms today; this constraint does not translate, but if cig grows modules with separate loaders (ADR 0004 payload) the question returns.
- The interpreter's register lifetime: PBL's virtual registers are `uint64_t` and no register allocator reclaims them; a cig interpreter that stores `Value` (24 bytes) per operand id will pay more. Decided by measurement, not by rule.
- Shapes for records: the census settles that two shapes a site cover cigo's field accesses and one shape covers every compute site, so decision (h) is to adopt shapes; what remains open is the per-write cost and the `IndexMap`-grow interaction (entry 6).
- Whether cig's per-op `cost_estimate` should be read in machine instructions (the cig unit, by rule 3) or in abstract score (the SpiderMonkey choice). The two scale differently as hardware moves; a cig-specific table is likely, with the thresholds in entry 13 recomputed from measurement.
- Whether every cig stub should terminate in a single "result" op as SpiderMonkey's does. cig's effect boundary (rule 1: burns never move) means a stub must never contain a `burn.op`; the one-result-op rule is a stricter version of that constraint, and the interaction with cig's `MayRaise` instruction class (CIR §2) is a design item for the first entry's measurement.
- Whether the AOT corpus (entry 10) belongs in `cig-script` (the runtime) or `cig-compile` (the program-build tool). SpiderMonkey keeps it in the runtime because the browser ships one runtime for many pages; cig ships one runtime per program (per `cigcompile build`), so either location would work. The location also decides whether the training run is `cig cherry warm` (runtime) or an invocation of `cigcompile` (build-time).
- Whether cig's `callm` cache (receiver kind + method row) should become a full CacheIR site right away or stay as a specialized two-field cache alongside new CacheIR sites for `getfield` and `setfield`. The question is whether to keep the existing hot path during the migration or replace it in one change.
