## What cig should carry away

- Julia's whole design is one trade: pay specialization cost to make a dynamic language read fast. Stage D makes the same trade for cig, and the three compilers in this study show the three places the cost lands (inference time, code size, cache size) and the mechanisms that bound each. The findings below are ordered by the stage-D decisions they feed.
- Julia proves type stability by inferring the callees of every call, not by looking at each function alone: `abstract_call_gf_by_type` finds applicable methods for the argument types, infers each, and the join of their return types is the call's result (entry 1). cig's VM census says every arithmetic and comparison site in a compute program saw one operand-type pair, every field site one shape, and every function one row of argument types (`data/census/README.md`), so a purely intraprocedural pass over CIR's SSA values would already settle those sites; what Julia adds is the mechanism for letting a call site's result refine the caller, which stage D needs to propagate a typed return (entries 1, 6).
- The lattice is not one type: it is seven layers Julia composes, each layer adjoining a kind of refinement to the lattice beneath it (`JLTypeLattice` < `ConstsLattice` < `PartialsLattice` < `ConditionalsLattice` < `InterConditionalsLattice` < `MustAliasesLattice` and `InterMustAliasesLattice` < `InferenceLattice`), and a widening step calls the parent lattice with `widenlattice` when a refinement does not apply (entry 2). cig's CIR has `Ty::Dynamic`, `Null`, `Bool`, `Int`, `Float`, `Str`, `List`, `Map`, `Func`: one enum, no refinements. The three refinements worth adopting first are constants (cig has `Kind::Const` already, so the lattice should carry it through), partial records (shapes: cig's `IndexMap<String, Value>` has insertion-ordered string keys, a shape is a list of keys), and conditionals (a comparison result refines the branches), each as its own layer that widens to a plain `Ty` (entries 2, 6, 15).
- Inference ends because Julia caps everything that could grow unboundedly with named constants and widens the moment one is exceeded. `MAX_TYPEUNION_COMPLEXITY = 3`, `MAX_TYPEUNION_LENGTH = 3` in `Compiler/src/typelimits.jl`; `max_methods = 3`, `max_union_splitting = 4`, `max_apply_union_enum = 8`, `max_tuple_splat = 32`, `tuple_complexity_limit_depth = 3` in `Compiler/src/types.jl`'s `InferenceParams`, with five Boolean flags (`ipo_constant_propagation`, `aggressive_constant_propagation`, `assume_bindings_static`, `ignore_recursion_hardlimit`, `force_enable_inference`). Beyond these, `limit_type_size` widens a type that is "more complex than" the caller's recorded comparison before a recursive call is taken (entry 3). A recursion that would run forever is caught by walking the inference stack with `AbsIntStackUnwind` in `abstract_call_method` and widening the signature when a call to the same method with a bigger signature is found. cig-cherry and stage D share a monomorphization budget; the candidate for cig is a single cap per method and a `Ty::Dynamic` fallback on exceedance, which is what `limit_type_size` does inside Julia (entries 3, 6).
- Builtins' result types live in one table, not in the builtin's own code. `Compiler/src/tfuncs.jl` registers each intrinsic and builtin with `add_tfunc(name, minarg, maxarg, tfunc, cost)`; the IR interpreter looks up the result type and the cost from this table, and inference's cost model (`inline_worthy`, `statement_cost`) uses the same costs. cig's stdlib has no result-type field on `Builtin` (`cig-script/src/value.rs`'s `Builtin` struct has `effect`, `min_args`, `max_args`, `func`, `calls_back` and no `ty`): adding one table of result types, keyed by name, is a prerequisite for stage D's inference (entry 4). The census says cigo's hot work is in builtins and methods (each hook call: about 1,600 script-function calls, 3,400 builtin calls, 1,600 method calls, 175 arithmetic instructions; `type_of` 3,149 times, `.push()` 1,282 times, `data/census/README.md` observation 10), not arithmetic, so the table is where most of the information in a cigo run lives.
- Julia records nine effects per method (`consistent`, `effect_free`, `nothrow`, `terminates`, `notaskstate`, `inaccessiblememonly`, `noub`, `nonoverlayed`, `nortcall` in `Compiler/src/effects.jl`), inferred upward from statements and callees. cig's `Class` has four coarse buckets (`Pure`, `MayRaise`, `Effect`, `Step`) and burns are a separate axis; the mapping to Julia's effects is close ("may it throw" is `MayRaise`, "may it move" is `Pure` against `Effect` or `Step`), and the lesson for cig is per-builtin effect summaries that stage D's optimizer reads instead of walking the body (entry 5).
- Specialization in Julia makes one compiled copy per argument-type combination (`jl_specializations_get_linfo` in `src/gf.c`), and the signature is widened by `jl_compilation_sig` before the key is formed, so that an argument that is a function not called and declared with a general type is cached under `Function`, a `@nospecialize` argument is cached under its declared type, and a trailing vararg is folded. The design that stops bloat is the widening of the key, not a cap on the count of keys (entry 6). cig today has no specialization and no call-site cache a stage-C or cig-cherry copy could key on; the census says 28 of 29 call sites in the 21 compute programs call one function and every function there was called with one row of argument types, so the first copy would catch the hot path for those (`data/census/README.md`). The two rules worth adopting outright are: do not specialize on an argument that is only passed through, and fold a vararg below a measured fixed length (entries 6, 7).
- rustc caps monomorphization with two defaults a user can raise, `recursion_limit = 128` and `type_length_limit = 2**24 = 16777216`, applied respectively in the collector and in `Instance::try_resolve`; a type beyond the length limit stops resolution, and a recursion depth beyond the limit is a fatal error (`rust-1.100.0/compiler/rustc_interface/src/limits.rs`, `rust-1.100.0/compiler/rustc_middle/src/ty/instance.rs`). The cost of specialization is paid at link time, not inference time, and the user sees it as code size (entry 13). A cig specialization limit should fail soft (fall back to `Dynamic`) rather than hard, because cig's engines must stay equal and a failed specialization is still a correct program; rustc's hard limit is a design choice that only a build system can tolerate (entries 6, 13, 15).
- .NET shares one compiled body for all reference-type instantiations (`__Canon`) and makes a fresh copy per value type, and a shared body reads types out of a per-instantiation generic dictionary through a chain of three dependent loads (`docs/design/coreclr/botr/shared-generics.md`): this is the shape "monomorphize for things where layout differs, share for things where layout does not". cig's analogue of "reference" is the counted payload (`Str`, `List`, `Map`, `Func`), which is already one layout across the four; the analogue of "value type" is `Int`, `Float`, `Bool`, which is where stage D's flat typed arrays and unboxed loops live (entry 12). A shared compiled body for the four refcounted kinds, keyed by a small token the dictionary resolves, is a design candidate for cig-cherry where the live code count is the bottleneck.
- Guarded devirtualization is the shape cig-cherry's guards already need (cig-script#256): .NET measures that on a two-class call site, guessing the more likely class correctly even half the time improves performance, and a guess right only 10 percent of the time still breaks even for a mixture of three classes (`docs/design/coreclr/jit/GuardedDevirtualization.md`). The relative size cost in .NET is 5 percent over all methods, and about 33 percent for methods where the optimization applied. cig's VM census says 28 of 29 call sites in the compute programs call one function and 72 percent of calls in `cigo list` go to a function that only ever saw one row of argument types: a single-guess guard is cheap and would hit on the overwhelming majority of sites (entry 13).
- The widening of a signature before specialization and the limits on inference have the same purpose: make inference end and make the compiled-code set finite. They are the mechanism behind "one monomorphization limit, shared" in cig-script#256's new comment. The entries say what each knob does today in each compiler; the stage-D design has to pick numbers (a candidate: `MAX_UNION = 2`, `MAX_METHODS = 2`, no deep tuple widening since cig has no tuples, and a vararg widening whose length is still to be measured), and the rule (1) **burns never move** forces a widening that would move or fold an effect to abstain (entries 3, 6, 7).

## Design points

### 1. Inference is abstract interpretation of the call graph, not of a function alone

- **What it does, and why.** Julia's inference runs `abstract_call_gf_by_type` on each call: given the argument types, `find_method_matches` asks the method table for the applicable methods (up to `max_methods`, default 3); for each match, `abstract_call_method` invokes `typeinf_edge` to infer that callee with the match's argument types, and `abstract_call_gf_by_type` joins their return types with the lattice's `tmerge`. Inference finishes at a call only when every applicable callee has been inferred at the types the call hands it, so the callee's type stability propagates upward: if `vsum([1])`'s inner call to `+(::Int64, ::Int64)` returns `Int64`, `vsum` returns `Int64` (`papers/compilers/bezanson-2018-julia-dynamism.pdf`'s §2 on type stability). The opposite is what Julia names "type instability": a call whose callees return different types widens to the join and takes dynamic dispatch at run time. Union splitting at an inlining site (next design point) is how a small union of return types is still compiled fast.

  The driver is in `Compiler/src/typeinfer.jl`: `typeinf_edge` starts a fresh inference for the callee if the cache does not already hold a `CodeInstance`, caching results keyed by `(MethodInstance, world range)` (`Compiler/src/cicache.jl`'s `InternalCodeCache`). The abstract interpreter processes basic blocks in a worklist (not a standard CFG; `Compiler/src/ssair/ir.jl` names the structure), joining the lattice state at merges with `smerge`, running `abstract_call_known` or `abstract_call_unknown` at each call, and asking `typeinf_edge` at the first call whose result is not already in the cache. Cycles in the call graph are detected by `is_edge_recursed` (`Compiler/src/abstractinterpretation.jl`) walking the active frames; a cycle is resolved to a fixed point over the strongly connected component, with widenings in `typelimits.jl` guaranteeing the fixed point is reached (entry 3).
- **For cig: adapt.** Decided by the census (`data/census/README.md`): compute programs are already type-stable at every site, and the mechanism that lets cig prove it is the propagation of the callee's return type into the caller. cig today has no interprocedural pass: `cig-script/src/lower/cir/ir.rs`'s `ValueInfo::ty` is set once in `lower.rs` and never changes. cig's form is a per-function inference that treats a `CallUser` instruction's result as the callee's inferred return `Ty` when the callee has one row of argument types, falling back to `Dynamic` when it has more than the cig limit (see entry 3). The oracle is the tree-walker, so stage D cannot change what a program prints; the inference is a hint stage C uses to pick the typed path, and a wrong guess at inference time stays correct because cig has no speculative runtime path yet.
- **What would decide it.** Not measured yet: for each program in the 21 compute benchmarks, how many of its CIR functions have one row of inferred argument types once the pass is run in order over the call graph's strongly connected components. The census counts observed rows, not inferred ones.
- **Feeds.** cig-compile#34; decision (i).
- **Read.** `julia-v1.13.4/Compiler/src/abstractinterpretation.jl` (`abstract_call_gf_by_type`, `find_method_matches`, `abstract_call_method`, `typeinf_edge`); `julia-v1.13.4/Compiler/src/typeinfer.jl` (`typeinf_edge`, `typeinf_frame`); `julia-v1.13.4/doc/src/devdocs/inference.md`; `papers/compilers/bezanson-2018-julia-dynamism.pdf`; `data/census/README.md`; `cig-script/src/lower/cir/ir.rs` (`ValueInfo`, `Ty`, `Kind`); `cig-script/src/lower/cir/lower.rs`.

### 2. The lattice is seven layers composed, each adjoining one kind of refinement

- **What it does, and why.** Julia's inference lattice is built by adjoining structures to `JLTypeLattice` one level at a time, in `Compiler/src/abstractlattice.jl`. `ConstsLattice` adds `Const` (a value known) and `PartialTypeVar`. `PartialsLattice` adds `PartialStruct` (a struct whose fields are each their own lattice element) and `PartialOpaque`. `ConditionalsLattice` and `InterConditionalsLattice` add `Conditional` and `InterConditional`, which refine a slot's type under the then or else branch of a `Bool` test (`Compiler/src/typelattice.jl`'s `Conditional` has fields `slot`, `thentype`, `elsetype`). `MustAliasesLattice` and `InterMustAliasesLattice` add `MustAlias` and `InterMustAlias`, which propagate a constraint on a field access when the parent slot is proven not to be re-assigned. `InferenceLattice` wraps the whole with `LimitedAccuracy`, a marker that the result is approximate because a widening fired.

  Each layer defines `widenlattice`, which returns the parent lattice element; a lattice function that does not handle a refinement calls `widenlattice` and defers to the layer below. The design keeps the outer lattice element in the inner result when it would not fit, so a refinement lost here never becomes a wrong answer, only a wider one.

  The three named compositions in `abstractlattice.jl` are `SimpleInferenceLattice = typeof(PartialsLattice(ConstsLattice()))`, `BaseInferenceLattice = typeof(ConditionalsLattice(SimpleInferenceLattice.instance))` (what runs locally inside a function), and `IPOResultLattice = typeof(InterConditionalsLattice(SimpleInferenceLattice.instance))` (what crosses a function call: conditionals are `inter` because the slot they refine is in the caller, not the callee). The split keeps the heavy lattice elements inside a function and sends a lighter encoding across the function boundary.
- **For cig: adapt.** cig's `Ty` is a single enum of nine flat types; stage D wants constants (for folding), partial structs (for cig's record shapes, which are `IndexMap<String, Value>` today), and element types for lists (which cig does not have). Decided by rule 5 (identical behavior on every engine): a lattice element that a pass drops must widen to `Dynamic`, never rewrite the value. cig's form: a `TyRef` that is either a `Ty` (today's enum) or a refinement (constant, shape, list element type), with a `widen` method that returns the plain `Ty`. A conditionals layer costs little in cig because the comparison sites the census measured are already settled: in `data/census/README.md`'s report.md, the compute programs' arithmetic-and-comparison sites are at one operand-type pair for 100 percent of executions in 20 of 21 programs, 74.9 percent in `trees`, and comparison sites specifically are overwhelmingly integer with integer (100 percent in most compute programs; `mandel` 51 percent integer with integer against 49 percent float with float; `words` 94.4 percent integer with integer). That means a conditional refinement proved from a comparison hits almost every site. The seven-layer stack is more than cig needs; three layers (constants, partial records, conditionals) is the design to carry.
- **What would decide it.** Not measured yet: on the 21 compute programs, how often a record is read or written by only its static keys (the condition cig-compile#34 names for a record demoting to `Map`). The census counts every field site at one shape and one position, which is necessary but not sufficient for demotion.
- **Feeds.** cig-compile#34; decision (i); cig-script#256.
- **Read.** `julia-v1.13.4/Compiler/src/abstractlattice.jl` (`JLTypeLattice`, `ConstsLattice`, `PartialsLattice`, `ConditionalsLattice`, `InterConditionalsLattice`, `MustAliasesLattice`, `InterMustAliasesLattice`, `InferenceLattice`, `widenlattice`); `julia-v1.13.4/Compiler/src/typelattice.jl` (`Conditional`, `MustAlias`, `PartialStruct`, `LimitedAccuracy`); `data/census/README.md`; `cig-script/src/lower/cir/ir.rs` (`Ty`, `ValueInfo`).

### 3. Widening makes inference terminate: named constants and `limit_type_size`

- **What it does, and why.** Julia bounds the growth of every object inference can enlarge, and when a bound is hit the offender is widened to a supertype. The named caps are in `Compiler/src/typelimits.jl`: `MAX_TYPEUNION_COMPLEXITY = 3` and `MAX_TYPEUNION_LENGTH = 3`. The default inference parameters are in `Compiler/src/types.jl`'s `InferenceParams` struct (lines 199 to 236): `max_methods = 3` (the method match list is cut), `max_union_splitting = 4` (a tuple whose arguments are small unions is split into separate signatures), `max_apply_union_enum = 8` (a `_apply_iterate` call splits up to this many), `max_tuple_splat = 32` (unrolling a splat stops here), `tuple_complexity_limit_depth = 3` (recursion on a tuple whose depth exceeds this triggers widening), plus five Boolean flags (`ipo_constant_propagation`, `aggressive_constant_propagation`, `assume_bindings_static`, `ignore_recursion_hardlimit`, `force_enable_inference`).

  The widening machinery is `limit_type_size(t, compare, source, allowed_tupledepth, allowed_tuplelen)`: it returns a supertype of `t` that is simpler than `compare` by walking the two in parallel, pairing their parameters element-wise and widening any element that is `type_more_complex`. The result is a type that is not wider than needed, so inference loses as little precision as the bound allows.

  The second mechanism is call-stack widening in `abstract_call_method`: `AbsIntStackUnwind(sv)` walks the pending inference frames, and if a frame is already inferring the same method with a signature `edge_matches_sv` judges "wider than the callee's", the callee's signature is widened and `RECURSION_MSG` recorded. Two modes exist: a hard limit (the usual case), and a soft limit that is relaxed when a parent frame will see both call stacks (`InferenceParams.ignore_recursion_hardlimit = false`). The result that comes out of a widened call is marked `LimitedAccuracy` (`Compiler/src/typelattice.jl`), which the caller treats as a type but does not cache for anyone else to use.

  Together these mechanisms make inference end on any input. A cycle in the call graph at the same signature is caught by equality (`sv'.specTypes == sig`, which triggers `edgecycle` in `abstract_call_method`); a cycle whose signature is growing is caught by `limit_type_size` flattening the growth to a bound; a recursion that keeps the signature small but uses up the hard limit returns `Any`. The RECURSION_MSG variants (`RECURSION_MSG`, `RECURSION_MSG_HARDLIMIT`, `RECURSION_UNUSED_MSG`) tag which case fired, so `--trace-compile` and `@code_typed` can report it.
- **For cig: adapt.** Decided by rule 5 (identical behavior on every engine) and rule 6 (deterministic cleanup): a widening in cig has to fall back to `Dynamic`, and the fallback runs on the same path the tree-walker takes, so the program still prints the right thing. cig's form is one cap per method on the number of distinct argument-type rows ever specialized (the "one monomorphization limit, shared" of cig-script#256's new comment), and one cap on the depth of a recursive specialization. The census says functions see at most 3 rows today (`data/census/README.md`), so a cap of 4 would never fire; a safer candidate is a cap of 2 to 3 paired with a `Dynamic` fallback, measured. `limit_type_size`'s element-wise widening is not transferable (cig has no parametric types and no tuples), but the mechanism of recording a comparison signature per method and widening a callee that grows against it is the general shape and does transfer. cig does not need `LimitedAccuracy` because it has no inter-method cache a limited result could poison; a limited result is simply not cached.
- **What would decide it.** Not measured yet: on `orchestrate.cig` and the compute programs, the maximum number of distinct argument-type rows any function would ever be specialized for, if the pass ran to a fixed point over the call graph.
- **Feeds.** cig-compile#34; cig-script#256; decisions (i), (b).
- **Read.** `julia-v1.13.4/Compiler/src/typelimits.jl` (`MAX_TYPEUNION_COMPLEXITY`, `MAX_TYPEUNION_LENGTH`, `limit_type_size`, `_limit_type_size`, `is_derived_type`, `type_more_complex`); `julia-v1.13.4/Compiler/src/types.jl` (`InferenceParams`, `max_methods`, `max_union_splitting`, `max_apply_union_enum`, `max_tuple_splat`, `tuple_complexity_limit_depth`); `julia-v1.13.4/Compiler/src/abstractinterpretation.jl` (`abstract_call_method`, `RECURSION_MSG`, `RECURSION_MSG_HARDLIMIT`, `edge_matches_sv`, `AbsIntStackUnwind`); `julia-v1.13.4/Compiler/src/typelattice.jl` (`LimitedAccuracy`); `data/census/README.md`.

### 4. One table of built-in result types and costs

- **What it does, and why.** Julia records a transfer function per built-in and per intrinsic in `Compiler/src/tfuncs.jl`. The registration is `add_tfunc(f, minarg, maxarg, tfunc, cost)`, where `tfunc` is a function from the argument lattice elements to the result lattice element and `cost` is a cycle estimate.

  Three tables hold the registrations: `T_IFUNC` for intrinsics (`add_int`, `sub_int`, `mul_int`, `sdiv_int`, `udiv_int`, `srem_int`, `urem_int`, `neg_int`, `neg_float`, `add_float`, `mul_float`, `div_float`, `min_float`, `max_float`, `fma_float`, and so on), `T_FFUNC_KEY` and `T_FFUNC_VAL` for builtins (`throw`, `Core.throw_methoderror`, `bitcast`, `sext_int`, `zext_int`, `trunc_int`, `fptoui`, `fptosi`, `uitofp`, `sitofp`, `fptrunc`, `fpext`, and so on), with a parallel `T_FFUNC_COST`. A caller uses `find_tfunc` to look up a registration by the built-in's identity.

  The costs are also fixed in the table: an integer `add`, `sub` is 1 cycle; `mul_int` is 3; an integer division or remainder is 20; `mul_float` is 8; `div_float` is 10; a bit cast is 0. An `:invoke` expression (a call whose input and output types are inferred) is assigned 20 cycles; a `:call` (a dynamic dispatch) is `inline_nonleaf_penalty = 1000`, a signal that dynamic dispatch dwarfs the per-instruction cost.

  The two uses are: (1) in inference, to compute the result type of a call to a built-in from the types of its arguments, without recursing into the built-in's body; (2) in inlining's cost model (`inline_worthy` in `doc/src/devdocs/inference.md`'s "inlining algorithm"), to estimate a block's cost from the costs of its instructions.
- **For cig: take.** Decided by rule 1 (burns never move) paired with the census (`data/census/README.md`): in cigo's hook cases, each hook call makes about 1,600 calls to script functions, 3,400 to builtins (`type_of` 3,149 times), and 1,600 method calls (`.push()` 1,282 times) against 175 arithmetic instructions (README observation 10), so builtins and methods dominate the hot work; stage D cannot infer a return type for a builtin without a table because cig's stdlib has no result-type field. cig's `Builtin` struct in `cig-script/src/value.rs` has `name`, `effect`, `min_args`, `max_args`, `func` and `calls_back`: adding a transfer function (a function from a slice of `Ty` to a `Ty`) and a `cost` is what Julia carries. cig's form: a new field `ty: fn(&[Ty]) -> Ty` on `Builtin` (and the parallel field in `cig-script/src/stdlib/methods.rs` for methods), populated for every entry in the stdlib (`cig-script/src/stdlib/math.rs`, `cig-script/src/stdlib/text.rs` and the rest), with a default of `Ty::Dynamic`. The effect is already recorded on each builtin (`Effect`), so the two axes (effect, result type) line up with Julia's (effect, tfunc) and feed the same inliner. Cost in cycles is secondary; a flat high cost for a builtin that "calls back" (`calls_back`) matches Julia's `inline_nonleaf_penalty` and keeps the inliner from inlining through a callback.
- **What would decide it.** Decided by rule 1: a builtin's effect is already its class, and a result-type table is a pure extension that does not change what any engine runs. No measurement is needed to write the table.
- **Feeds.** cig-compile#34, #37; decision (i).
- **Read.** `julia-v1.13.4/Compiler/src/tfuncs.jl` (`add_tfunc`, `T_IFUNC`, `T_FFUNC_KEY`, `T_FFUNC_VAL`, `T_IFUNC_COST`, `find_tfunc`); `julia-v1.13.4/doc/src/devdocs/inference.md`; `cig-script/src/value.rs` (`Builtin`, `BuiltinFn`); `cig-script/src/stdlib/mod.rs` (`builtin_catalogue`, `catalogue`); `cig-script/src/stdlib/` (`math.rs`, `text.rs`); `data/census/README.md`.

### 5. Nine inferred effects per method, read at call sites

- **What it does, and why.** `Compiler/src/effects.jl` defines `Effects`, a struct of nine fields a method is tagged with after inference. `consistent` says the method gives the same return for the same arguments (with sub-states `CONSISTENT_IF_NOTRETURNED` and `CONSISTENT_IF_INACCESSIBLEMEMONLY`); `effect_free` says it has no externally visible side effect (sub-state `EFFECT_FREE_IF_INACCESSIBLEMEMONLY`); `nothrow` says it cannot throw a user-visible exception; `terminates` says it halts; `notaskstate` says it does not read or write the current task's state; `inaccessiblememonly` says it does not access externally visible memory (sub-state `INACCESSIBLEMEM_OR_ARGMEMONLY`); `noub` says it is free of undefined behavior (`NOUB_IF_NOINBOUNDS` when inbounds elision may introduce one); `nonoverlayed` says it does not call a method from an overlay table (`CONSISTENT_OVERLAY` when it does but the overlay is consistent); `nortcall` says it does not call `Core.Compiler.return_type`. Three constant tuples name the common cases: `EFFECTS_TOTAL` (all `ALWAYS_TRUE` or `true`), `EFFECTS_THROWS` (as total except `nothrow = false`), `EFFECTS_UNKNOWN` (the pessimistic merge). `merge_effects!` combines a statement's effects into the method's, dropping each field to the weaker state when any statement weakens it. An `:invoke` at a cached, totally-effect-free method is constant-folded by `concrete_eval_call` (`Compiler/src/abstractinterpretation.jl`); a call to one not proven effect-free stays.
- **For cig: adapt.** cig has `Class::Pure`, `MayRaise`, `Effect`, `Step` in `cig-script/src/lower/cir/ir.rs`, and a separate burn classification per builtin (`Effect` in `cig-script/src/value.rs`). The coarse axes line up: `Pure` is Julia's `effect_free + nothrow`, `MayRaise` is not `nothrow` only, `Effect` is not `effect_free`. `Step` has no Julia analogue because Julia does not guarantee a step budget's exactness; this is cig's own axis (rule 3). Decided by rule 1: cig cannot drop `Step` from a pass just because a method is `effect_free`. cig's form: adopt `terminates` (useful for proving a loop ends), `consistent` (proves two calls can be folded to one) and `nothrow` (lets stage C drop a guard around a call); do not adopt `notaskstate` (no tasks) or `noub` (`forbid(unsafe_code)` holds, except for one audited crate). The three lines up with what cig would need to prove a `CallBuiltin` is foldable and what it would need to prove `copy-prop` can look through a call. Record these as summaries on the stdlib's builtins, same table as entry 4, next to the existing `Effect` field in `cig-script/src/value.rs`.
- **What would decide it.** Not measured yet: on the compute programs, how many `CallBuiltin` sites would qualify for constant folding under `effect_free + nothrow + terminates`.

### 6. One compiled copy per argument-type combination, keyed after signature widening

- **What it does, and why.** Julia compiles each generic function's method once per combination of concrete argument types it is called with. `jl_specializations_get_linfo` in `src/gf.c` is the entry point: given a method and a tuple of argument types, it returns the method instance (a `MethodInstance`) that is the key under which the compiled code is cached.

  Two functions decide the key before the lookup: `jl_compilation_sig` and `jl_isa_compileable_sig`. `jl_compilation_sig` walks the actual argument tuple and the method's declared signature in parallel and emits a widened tuple that is the actual key. The rules it applies are:

  - A `Type{T}` with a general declared type widens to `Type{T}` by default so that every `Type` argument does not get its own copy, unless the argument is called (`iscalled = definition->called & (1 << (i_arg - 1))`).
  - A `nospecialize` argument (`definition->nospecialize & (1 << (i_arg - 1))`) widens to its declared type.
  - A `Function`-subtype argument whose declared type is a supertype of `Function` and that is not called widens to `Function` (`notcalled_func`).
  - A vararg tail is folded into a single `Vararg{T}` when every tail element is a subtype of a common `T`, else into `Vararg{Any}` capped at `max_varargs + nargs` elements.

  The result is a dispatch cache that fuses "called with `MyType`" and "called with `OtherType`" when the method does not depend on the actual type. `jl_isa_compileable_sig` is the inverse test, used to decide whether a type already in hand is a possible output of `jl_compilation_sig` (so a cache lookup can shortcut the widening). The paper's phrase for this is "method specialization" (`papers/compilers/bezanson-2018-julia-dynamism.pdf`'s §1, §2).
- **For cig: take.** Decided by rule 5 (identical behavior on every engine): a specialized copy compiled by stage D runs a program the same way the tree-walker runs it, so no guard is needed when inference proved the signature. cig's form: a per-function cache `HashMap<SignatureKey, CompiledCode>` keyed by the inferred argument tuple, after a widening step that follows the three Julia rules. The three rules worth taking in cig:
  1. Do not specialize on an argument that is only passed through (Julia's `notcalled_func`): cig's lowering can record which parameters are called (an argument that appears in the head position of a `CallValue`), and a parameter not called is widened to `Dynamic`. The census says 28 of 29 `call` sites in the 21 compute programs call one function (`data/census/README.md` observation 4), so most parameters in those programs are called; higher-order code (`.map`, a chain's step, a pass's work) has one or two call-through parameters per function, which the compute benchmarks under-represent.
  2. Fold a vararg below a fixed length: cig uses `max_args: Option<usize>` on `Builtin` already (`None` means variadic). The vararg widening gives an explicit bound at which variadic specialization stops; a candidate for cig is a small constant chosen from a measurement of how many distinct argument counts a variadic builtin is called with, which the census does not measure (it records receiver types and operand types, not arg-count distributions). The bound belongs with the measurement in "measurements owed".
  3. Specialize on constant inputs only when a `@constprop`-like annotation says so. Julia's `concrete_eval_call` uses `const_prop_profitable` heuristics; cig's `Kind::Const` already carries the constant, and the policy can be "fold at the call site when every argument is const".
- **What would decide it.** Not measured yet: on `orchestrate.cig` and the compute programs, the count of distinct inferred signatures per function under the three rules, compared with the census's observed rows. The census records up to 16 rows a function as its own storage cap (`data/census/README.md` line 18); the maximum actually observed is 3 (line 48, observation 9), so inferred-row counts would have to exceed that to be interesting.
- **Feeds.** cig-compile#34; cig-script#256; decisions (i), (f).
- **Read.** `julia-v1.13.4/src/gf.c` (`jl_specializations_get_linfo`, `jl_compilation_sig`, `jl_isa_compileable_sig`, `jl_type_intersection`, `very_general_type`, `iscalled`, `notcalled_func`); `papers/compilers/bezanson-2018-julia-dynamism.pdf`; `cig-script/src/value.rs` (`Builtin`, `BuiltinFn`); `cig-script/src/lower/cir/ir.rs` (`Kind`, `CallUser`, `CallValue`, `Const`); `data/census/README.md`.

### 7. The front-end widens too: a type the programmer never has to pay for

- **What it does, and why.** Julia's front end pre-sets two of the widening flags `jl_compilation_sig` reads. The `analyze-variables` pass, named in `doc/src/devdocs/functions.md`'s "compiler efficiency issues", records which parameters are called in the head position of a call: that is what sets the `called` bit mask on `definition` that `jl_compilation_sig` reads as `iscalled`. The paragraph says the heuristic is "extremely effective" in practice because many higher-order functions (`map`) actually call their argument, so they are still specialized, and many pass-through functions do not, so they are not.

  The other flag, `nospecialize`, is a per-argument annotation a programmer writes (as `@nospecialize`) and it is stored in `m->nospecialize` (`src/gf.c`); a `~m->nospecialize` sets the opposite (the `@specialize` escape). The outcome is a specialization policy that does the right thing by default and lets a programmer override it when the default is wrong.

  The `called` bit mask has width 8 (`i_arg <= 8` in `jl_compilation_sig`'s check), which means the heuristic only applies to the first eight positional parameters. A function with more than eight is specialized on every parameter by default; a parameter past position 8 can still be `@nospecialize`'d by the programmer.
- **For cig: adapt.** Decided by rule 5: a widening has to keep the output the same. cig's form is a one-pass analysis over CIR before stage D infers, computing for each parameter whether it appears in the head of a `CallValue` or `CallUser` ("called"), is the receiver of `CallMethod` ("called"), is stored into a map or list ("escapes"), or is only read by some number of `Load` and `Member` (neither). A parameter that is neither called nor escapes is a candidate for widening to its declared type (or to `Dynamic` when it has none). cig has no `@nospecialize`, and CigarScript's "medium" strength (cig-compile#34) is the escape hatch: a parameter declared with a general type stays general. cig has no `kwcall` sorter to worry about.
- **What would decide it.** Not measured yet: on the compute programs, the fraction of parameters that are "called" against those that are "escapes" against those that are neither.
- **Feeds.** cig-compile#34; decision (i).
- **Read.** `julia-v1.13.4/doc/src/devdocs/functions.md`; `julia-v1.13.4/src/gf.c` (`nospecialize`, `called`, `jl_compilation_sig`); `cig-script/src/lower/cir/ir.rs` (`Kind`, `CallUser`, `CallValue`, `CallMethod`).

### 8. Union splitting at inlining sites

- **What it does, and why.** When inference's result for a call is a small union of types (not a single concrete type), Julia's inliner does not fall back to dynamic dispatch: it splits the call into a cascaded `if-else` that tests the dispatched type and inlines the right body on each branch. `Compiler/src/ssair/inlining.jl` holds the mechanism. `UnionSplit` is a struct of `handled_all_cases` (every applicable dispatch has a case), `fully_covered` (the cases together cover the whole union), `atype` (the signature), and `cases: Vector{InliningCase}` with one entry per concrete type.

  `cfg_inline_unionsplit!` builds the CFG for the split; `assemble_inline_todo!` is where a call is decided to be a split, a single-case inline, or a dynamic call. The split is bounded by `max_union_splitting = 4` (`Compiler/src/types.jl`'s `InferenceParams`): a call whose argument union has more than four tag-combinations stays a dynamic dispatch. The split's cost is one tag test per case, but each case is a direct call (an `invoke` in Julia terms) that can be inlined, so the run-time cost of a small union is not a dispatch; it is a predictable branch.

  The complement to `UnionSplit` is `InliningCase` (a signature paired with the item to inline: an `InliningTodo`, an `InvokeCase`, or a `ConstantCase`). A `ConstantCase` is when the result of inference says the call always returns the same constant: inlining substitutes the constant and drops the call entirely. The split is thus not only a devirtualization; it is also a constant-propagation vehicle at each case.
- **For cig: adapt.** cig has no unions in its lattice today (`cig-script/src/lower/cir/ir.rs`'s `Ty` is a flat enum). Decided by the census and rule 5: compute programs are at one type per site, cigo's hooks are at one or two types per site (`data/census/README.md`'s observation 8 says 66 to 100 percent of field reads were at a two-shape site), so a two-element union is the only shape stage D would gain from. cig's form: a `Ty::Union2(A, B)` layer (the second layer of the lattice, between `Ty` and the partial-struct layer of entry 2), and a lowering that, at a `CallMethod` or `CallBuiltin` whose receiver's type is `Ty::Union2(A, B)`, emits an `If` with a tag test (cig's `Kind::Binary` of `==` plus a new tag op) and the two branches inlined. The branch keeps the same step budget charge (rule 3: `STEPS` goes with the whole block, so a split counts as one step by cig's rule, not two). A `Union2` of a counted and an uncounted type (say `Str` and `Int`) still has to generate a reference-count op on the `Str` branch and no op on the `Int` branch; this is exactly the shape of cig's `Class::Effect` marker.
- **What would decide it.** Not measured yet: on cigo's hook cases, the number of sites a two-element union would convert from dynamic to direct, measured as the hit rate of the second tag test.
- **Feeds.** cig-compile#33, #34; decision (i); cig-script#256.
- **Read.** `julia-v1.13.4/Compiler/src/ssair/inlining.jl` (`UnionSplit`, `handle_single_case!`, `cfg_inline_unionsplit!`, `assemble_inline_todo!`, `InliningCase`, `InliningEdgeTracker`, `batch_inline!`); `julia-v1.13.4/Compiler/src/types.jl` (`max_union_splitting`); `data/census/README.md`; `cig-script/src/lower/cir/ir.rs` (`Ty`, `Kind`, `If`).

### 9. The method cache: one per method instance, keyed by world range

- **What it does, and why.** Each `MethodInstance` in Julia carries a cache of `CodeInstance`s, stratified by world age (`Compiler/src/cicache.jl`). `InternalCodeCache` holds an `owner` whose equality (`jl_egal`) selects which cache is read; `setindex!` inserts a new `CodeInstance` through `ccall(:jl_mi_cache_insert, ...)`, and `ccall(:jl_push_newly_inferred, ...)` records the new instance in a global list. Lookup goes through `WorldView` (`WorldRange` with a `min_world` and `max_world`): `get` calls `ccall(:jl_rettype_inferred, Any, (Any, Any, UInt, UInt), owner, mi, min, max)` and returns the one `CodeInstance` whose world range covers the view, or nothing. `WorldRange`s compose by `intersect` and `union`. The design keeps every historical specialization visible to every caller that is bound to a world where it was valid: a redefinition of a method bumps the current world, old `CodeInstance`s stay in the cache keyed by the earlier range, and only code bound to the new world misses. A compile running in one inference pass holds a `WorldView` and only reads instances that match.

  World ages are the mechanism that lets Julia redefine any method at the REPL, add a new method to a generic function, or load a package after the base image is already running, all without breaking any compiled code. Each change bumps the global world counter; every `CodeInstance` has a `min_world`/`max_world` range that says "I was inferred correctly between these two worlds"; a caller that started before the bump still sees the old instance, a caller bound to a later world misses, re-infers, and the new instance is inserted. The caller's `WorldView` is decided once (at the call to `typeinf_edge`) and is not raised mid-inference; this gives atomicity to one inference pass's cache reads.
- **For cig: adapt.** cig has no redefinition at run time: `cig-script/docs/LOWERING.md` and the lowering refuse a function that reads a declaration it does not yet see (`cig-script/src/lower/cir/mod.rs`'s `LowerError::Refused`, raised through `cig-script/src/lower/cir/lower.rs`'s `Fail::Refused`). This removes the world-age axis entirely. Decided by rule 7 (verified bytecode, never rewritten) and rule 8 (reproducible bytes from the same input): cig's cache is keyed by the module's content hash plus the inferred signature, not by a world. The per-`MethodInstance` structure still transfers: one `HashMap<SignatureKey, CompiledCode>` per cig function, under the function's id. The cache is flat because it does not have to version.
- **What would decide it.** Decided by rule 7: cig cannot redefine a function at run time, so the world axis does not exist. The sizing of the per-function cache is set by entry 6's measurement, not here.
- **Feeds.** cig-compile#36; cig-script#256; decision (f).
- **Read.** `julia-v1.13.4/Compiler/src/cicache.jl` (`InternalCodeCache`, `WorldRange`, `WorldView`, `haskey`, `get`, `getindex`, `setindex!`); `cig-script/src/lower/cir/mod.rs` (`LowerError`, `Refused`); `cig-script/src/lower/cir/lower.rs` (`Refused`); `cig-script/docs/LOWERING.md`.

### 10. Cached native code between runs: package images, not a separate format

- **What it does, and why.** Julia caches compiled code between runs as a shared library per package (`doc/src/devdocs/pkgimg.md`, `doc/src/devdocs/aot.md`). The build writes an archive that contains both the serialized global data (types, method tables, bindings) and the native object files; a linker runs on the object files (`lld` shipped with Julia, `-flavor gnu` on Windows, `-undefined dynamic_lookup` on macOS) and the result is a `.so`, `.dll` or `.dylib` that Julia loads. The data format is the same as the system image, and the system image is the base against which the package image is built.

  Four flags make an image unusable when they do not match the loader's: `-g` (`--debug-info`), `--check-bounds`, `--inline`, and `-O` (the loader will accept an image compiled at a higher optimization level than its own, not a lower one). The environment variable `JULIA_MAX_NUM_PRECOMPILE_FILES` caps how many variants Julia keeps per package.

  The method-instance validation at load is in `doc/src/devdocs/aot.md`'s "Loading Code Images": for a package image, every method is checked against the global method table and invalidated if the state has moved. System images skip the check because the method table is empty at load.

  The build itself traces compiled methods when `--trace-compile=filename` is set, producing a precompile script for the AOT run (`doc/src/devdocs/aot.md`'s "Tracing Compiled Methods"), and `jl_dump_native` multithreads optimization and codegen (`JULIA_IMAGE_THREADS` controls the count, default half the system threads). Multi-architecture builds are supported through the `JULIA_CPU_TARGET` string: a `clone_all` target makes the loader clone every function for the target's ISA; a `base(n)` target builds on another target's cloned functions; `opt_size` and `min_size` select `-Os` or `-Oz` code for the clone (`doc/src/devdocs/sysimg.md`). cig has no analogue of multi-architecture yet; the pattern is a design candidate for cig-compile#41 (targets) rather than for stage D.
- **For cig: adapt.** cig's stage `b` is already an ahead-of-time payload: a lowered module in its final form, verified, kept next to the pinned runtime. What cig does not have yet is native code in the payload. Decided by rule 7 (verified bytecode, never rewritten) and rule 8 (no WX memory, signable): a package-image-like scheme fits cig-cherry's cache (decision (f)), not stage `b`. The design that transfers is the compilation-flag check at load: cig-compile should reject a cached native blob whose flags differ from the loader's (level, debug info, `check-bounds` equivalent, `inline` policy), the same shape as Julia's four. The method-instance validation is unnecessary for cig (rule 7: a module's bytes never change at run time), and so is the trace step (cig's lowering runs once and can emit a native blob for every function at compile time, not after). The LLD-shipped linker is a decision cig does not have to make (Cranelift emits object files; the OS linker is used once at `cig-compile` time).
- **What would decide it.** Not measured yet: the native-code size per cig function, under the cig-cherry tier, and the proportion that justifies caching between runs for the `orchestrate.cig` case (where the census says 13 to 80 of 1,038 functions are entered per command).
- **Feeds.** cig-compile#36, #41; cig-script#256; decision (f).
- **Read.** `julia-v1.13.4/doc/src/devdocs/aot.md`; `julia-v1.13.4/doc/src/devdocs/pkgimg.md`; `julia-v1.13.4/doc/src/devdocs/sysimg.md`; `julia-v1.13.4/src/aotcompile.cpp`; `data/census/README.md`.

### 11. Invalidation: backedges and binding partitions

- **What it does, and why.** A `CodeInstance` in Julia is cached under the world range in which it is valid: when a method is redefined or a global binding changes, `ccall(:jl_invalidate_code_instance, ...)` moves the instance's `max_world` to the point of change, so any caller bound to a later world will miss the cache. The binding path is in `Compiler/src/bindinginvalidations.jl`: `invalidate_method_for_globalref!` is the entry point.

  It walks every `CodeInstance` of every specialization of the affected method, and for each instance, decides whether to invalidate by two checks. First, a quick path: if the method's source refers to the binding anywhere (`should_invalidate_code_for_globalref`, which walks the `CodeInfo`'s statements with `foreachgr`/`anygr`), the whole method is invalidated. Second, a precise path: `scan_edge_list` reads the `CodeInstance.edges` (its backedges), and invalidates only when the binding is listed as an edge. `ccall(:jl_maybe_log_binding_invalidation, ...)` logs the event when an invalidation fires.

  The design records a backedge per binding and per method dependency at inference time (the `edges` field is populated during `abstract_call_gf_by_type` and `abstract_call_method`), so invalidation is linear in the edges, not in the cache. The two-level check is the key trade-off: the method-source scan is coarse (one bit per method) and the precise edge list is fine (one entry per callee or binding), and the coarse path lets Julia skip the precise scan when the method's own source does not mention the binding at all.
- **For cig: reject.** Decided by rule 7 (verified bytecode, never rewritten at run time) and rule 5 (identical behavior on every engine): cig has no redefinition at run time. A function that would be redefined at run time is declined by the lowering already (`cig-script/src/lower/cir/names.rs`'s `LowerError::Refused`). cig's analogue of a binding change is a module loaded again from a different source, and the whole module is rebuilt and reverified then; the per-method backedge list has no reason to exist. The one piece that does transfer is the backedge *concept* for cig-cherry's inline caches (cig-script#256): a speculative compiled copy that observed a receiver type must invalidate when the method table it depended on changes, but cig's method table does not change, so this too reduces to "do nothing".
- **What would decide it.** Decided by rule 7.
- **Feeds.** cig-compile#34; cig-script#256; decision (f).
- **Read.** `julia-v1.13.4/Compiler/src/bindinginvalidations.jl` (`invalidate_method_for_globalref!`, `scan_edge_list`, `should_invalidate_code_for_globalref`, `foreachgr`, `anygr`); `julia-v1.13.4/Compiler/src/abstractinterpretation.jl`; `cig-script/src/lower/cir/names.rs`.

### 12. .NET shared generics: one body per reference, a copy per value type, a dictionary

- **What it does, and why.** .NET compiles the body of a generic method once for all reference-type instantiations (`__Canon` in the design document), and separately for each value-type instantiation. A shared body reads any type-specific value (a type handle, a method handle, a field offset) out of a per-instantiation *generic dictionary*, and the dictionary layout is shared across all compatible instantiations (`docs/design/coreclr/botr/shared-generics.md`).

  The dictionary is pointed to by `m_pPerInstInfo` on a method's `InstantiatedMethodDesc` (direct) or a type's `MethodTable` (through a table of dictionaries, one per base type: a derived generic type inherits its base's dictionary, and accesses at depth `n` read `dictionaryTable[n]`). A shared body's load of a type handle is a chain of three dependent reads: load the method descriptor, load the dictionary pointer from `m_pPerInstInfo`, load the slot. A slot is unassigned at type-load time and populated on first use by a helper (`JIT_GenericHandleClass` for a type dictionary, `JIT_GenericHandleMethod` for a method dictionary), through `Dictionary::PopulateEntry`.

  The layout grows dynamically when a tiered recompile demands more slots than the original layout had room for: `DictionaryLayout::FindToken` resizes the layout, `Dictionary::GetTypeDictionaryWithSizeCheck` and `GetMethodDictionaryWithSizeCheck` resize the per-instantiation dictionaries, and a size check (`pDictionary[sizeOffset] <= requiredOffset`) is emitted at any access past the original number of slots so the shared code sees a correct bound. Reference types all share a body because they all have the same runtime layout: a pointer. Value types each get a body because their layouts differ (size, alignment, how they are passed in registers).

  The design has a visible cost: a `typeof(List<T>)` inside a shared generic method is three dependent loads, against one register move in a non-generic function. .NET makes the trade because the alternative (a copy per reference type) explodes code size: `List<object>`, `List<string>`, `List<Stream>` would each be a full compilation. The dynamic expansion is what lets ReadyToRun, which pre-allocates fewer slots, still work beside tiered re-compilation, which may discover a slot the AOT build did not emit.
- **For cig: adapt.** cig has no generics and no inheritance, so `__Canon` versus "each value type" does not map one-to-one. The closer mapping is cig's own split of representation: `Int`, `Float`, `Bool` fit in a machine register (stage D's "unboxed `i64`, `f64`, `u8`"), and `Str`, `List`, `Map`, `Func` are a refcounted pointer each. A shared compiled body could serve the four refcounted kinds (they all have the same layout at the dispatch point), with a small token read from a per-receiver word steering a few type-specific operations; a per-kind body is needed for `Int`, `Float`, `Bool`. Decided by rule 1 (burns never move): the token read is a regular load, not a burn, and no effect is reordered. The dictionary-of-tokens shape is heavier than cig needs because cig has at most a few dozen methods per kind, so a direct jump table keyed by `(kind, method-slot)` is enough. The lesson that transfers is the split "share one body where layout is one, specialize where it differs", not the dictionary layout itself.
- **What would decide it.** Not measured yet: the native-code size per method under one unified body for the four refcounted kinds, against four separate bodies, on the compute programs.
- **Feeds.** cig-compile#32, #35, #36; cig-script#256; decisions (a), (i).
- **Read.** `dotnet-runtime-v11.0.0/docs/design/coreclr/botr/shared-generics.md` (`__Canon`, `m_pPerInstInfo`, `DictionaryLayout`, `Dictionary::PopulateEntry`, `DictionaryLayout::FindToken`, `GetTypeDictionaryWithSizeCheck`, `GetMethodDictionaryWithSizeCheck`, `JIT_GenericHandleClass`, `JIT_GenericHandleMethod`, `JIT_GenericHandleWorker`); `dotnet-runtime-v11.0.0/docs/design/coreclr/botr/type-system.md`; `cig-script/src/value.rs` (`Value`).

### 13. Guarded devirtualization: a guess and a guard, with a fallback

- **What it does, and why.** When .NET's JIT cannot prove the exact method a virtual or interface call will reach, it inserts an `if-then-else` with a runtime type test: on a match the direct (and inlinable) call runs; on a miss the original virtual call runs. The document reports that regular devirtualization naturally succeeds at about 15 percent of virtual sites and 5 percent of interface sites, which is a lower bound on what a guarded guess can add.

  The measurement on a two-class site (an array of two types, class `B` with probability `p`) says: a correctly predicted virtual call costs about 19 time units, a mispredicted one about 55; with guarded devirtualization and a single guess, performance matches or beats the unguarded case over the whole range of `p`, because even a wrong guess leaves the fallback with one type to dispatch against and the hardware's indirect branch predictor finds it. The three-class case breaks even at about 10 percent correct guess and wins outright above 30 percent.

  The relative code-size cost is about 5 percent over all methods, and about 33 percent for methods where guarded devirtualization applied (the document notes that guarded devirtualization kicks in for about 15 percent of methods, so the average relative size increase in a method where it fires is about 33 percent): the optimization is restricted to Tier 1 for that reason. Interface calls on .NET use a virtual stub dispatch (VSD) with a monomorphic dispatch stub that tests one method table and tail-calls; guarded devirtualization sits above that and filters one method table before the VSD runs, which helps with two-class sites. The design records: `impDevirtualizeCall` marks a candidate during importation; the actual split happens later, between the importer and the inliner, because the importer cannot introduce control flow.
- **For cig: adapt.** Decided by the census (`data/census/README.md`) and rule 5 (identical behavior on every engine): the compute programs' 28 of 29 call sites call one function, and in `cigo-list` 72 percent of calls go to a function that only ever saw one row of argument types (`data/census/README.md` observation 9). One guess is enough for most sites; the fallback is the VM's dynamic dispatch, which cig has. cig's form: a stage-C or cig-cherry call site has a guard that compares the receiver's `kind` tag (or the callee's `Func` identity for a plain call) against the inferred value, and falls through to the VM on a miss (cig-script#256's side exit). The side exit is where cig has to pay attention to rule 1 (burns never move): a guard may only be placed where no burn op has run since the region's entry, or right after one, which is already what cig-compile#34 says. The 5 percent size cost is comparable to the tier-1 cost in .NET, so cig-cherry should restrict guarded dispatch to "hot" sites (decision (c)): a counter per site, a threshold, a compile. The design candidate for a threshold is the lower bound where the census says the site has run more than a few hundred times.
- **What would decide it.** Not measured yet: on cigo's hook and guard-line cases, the hit rate of a single-guess guard per site, and the code-size growth of guarding every site that ran more than 100 times.
- **Feeds.** cig-compile#32, #33; cig-script#256; decisions (b), (c), (d).

### 14. First-class structs in registers

- **What it does, and why.** RyuJIT treats a struct that fits a register as a first-class value. `docs/design/coreclr/jit/first-class-structs.md` names four new types `TYP_SIMD8`, `TYP_SIMD12`, `TYP_SIMD16` and `TYP_SIMD32` for vector values, used both for platform-independent types (`Vector2`, `Vector3`, `Vector4`, `Vector<T>`) and for the intrinsic hardware types (`Vector64<T>`, `Vector128<T>`, `Vector256<T>`).

  A generic struct carries a `ClassLayout` (its size and GC layout) attached to every struct-typed node; the `ClassLayoutTable` on the `Compiler` object interns layouts so the attachment is one word per node. Struct values can appear on the right-hand side of an assignment, as a call argument, or as an operand of a hardware intrinsic. Struct promotion turns a struct's fields into separate scalar variables, each eligible for register allocation; promotion is all-or-nothing today and bounded by a field count (the document proposes to relax this). A promoted struct that has to be passed by reference becomes "dependently promoted" and stays on the stack.

  The design separates "what a struct is" (shape, in `ClassLayout`) from "how a node uses it" (a `GT_LCL_VAR`, `GT_LCL_FLD`, `GT_OBJ`, `GT_BLK` or `GT_FIELD_LIST`), so the back end can choose register placement without the front end knowing: `GT_FIELD_LIST` is an exploded struct whose fields are already separate values; `GT_OBJ` keeps the struct opaque with its layout; `GT_LCL_VAR` is the enregistered form. Lowering and register allocation choose between these; the importer does not.
- **For cig: adapt.** cig's value is 24 bytes today (`cig-script/src/value.rs`'s `Value` enum), too big to live in a register pair without a different representation. Stage D's "tagged 16 bytes, or NaN-boxed 8" (decision (a)) is the first thing to decide; the mechanism that makes the choice pay is a struct-promotion-like pass at stage C that turns a cig record (a `Map` of fixed keys, cig-compile#34's record type) into separate scalars. cig has no SIMD type and does not need one here; the `TYP_SIMDn` lesson is that a small, fixed-layout struct earns its own IR type, not an opaque blob. For cig, a record of two `Float`s is `{Float, Float}` as two values in the IR, not one list of two values behind an `Rc<RefCell>`. Decided by rule 4 (floats are IEEE-exact, maps keep insertion order): the promotion must preserve the order of the record's keys (cig's `IndexMap<String, Value>` orders by insertion), so a promoted record's fields have the same iteration order as the map it came from. `ClassLayout` is heavier than cig needs; one `ShapeId` per record (the ordered keys interned into a slot, cig-compile#34's "shape") is enough.
- **What would decide it.** Not measured yet: on `nbody` (seven-float records), the throughput of the arithmetic loop under a promoted-record representation against the current `Map`-of-value representation.
- **Feeds.** cig-compile#34, #35; decisions (a), (h), (i).
- **Read.** `dotnet-runtime-v11.0.0/docs/design/coreclr/jit/first-class-structs.md` (`TYP_SIMD8`, `TYP_SIMD12`, `TYP_SIMD16`, `TYP_SIMD32`, `ClassLayout`, `ClassLayoutTable`, `GT_OBJ`, `GT_FIELD_LIST`, `fgMarkAddressExposedLocals`, `fgMorphField`, `GT_LCL_VAR`, `GT_LCL_FLD`); `dotnet-runtime-v11.0.0/docs/design/coreclr/jit/object-stack-allocation.md`; `cig-script/src/value.rs` (`Value`).

### 15. rustc monomorphization: a collector, a partitioner and two limits

- **What it does, and why.** rustc compiles each generic function once per combination of concrete type arguments, like .NET for value types but for every type. The mechanism has two phases. `compiler/rustc_monomorphize/src/collector.rs` walks the crate's HIR to find roots (every public non-generic function, every `#[no_mangle]` function, every function called by an inlinable one), and then walks each root's MIR to find uses (every call, every reference, every drop glue, every unsizing cast that builds a vtable, every constant it evaluates). Each use is a new mono item, keyed by `(DefId, GenericArgsRef)`; the collector memoizes seen items. `collect_items_root` and `MirUsedCollector::visit_rvalue` are the heart.

  The collector has two strategies, named `Lazy` (only items actually used) and `Eager` (used for incremental compilation, where a stable set of items matters more than a minimal one: drop glue for every drop-able type, default implementations of trait methods, every function). "Mentioned" items are a middle layer: items that syntactically appear in the code but may be dead-code-eliminated after optimization; the collector forces constant evaluation of every mentioned item so the build does not become dependent on the optimization level.

  `compiler/rustc_monomorphize/src/partitioning.rs` groups the mono items into codegen units: two per source module, "stable" (non-generic code) and "volatile" (monomorphized instances), merged if there are too many, then internalized so LLVM can optimize across what will stay in one unit. The guide (`src/doc/rustc-dev-guide/src/backend/monomorph.md`) explains why: codegen units are the granularity of incremental recompilation and of LLVM's optimization boundary, so the two-per-module heuristic trades inlining against invalidation.

  Two numeric limits are the stop: `recursion_limit` (default 128) in `compiler/rustc_interface/src/limits.rs` caps how deep a chain of instantiations can go (checked in `check_recursion_limit`, a fatal error at the limit); `type_length_limit` (default `2usize.pow(24)`, i.e. 16,777,216) caps the total number of type-tree nodes in an instantiated signature (checked in `Instance::try_resolve`: beyond the limit, resolution returns `None`, and `expect_resolve` emits `TypeLengthLimit`). Both can be raised with a crate attribute (`#![recursion_limit = "..."]`). `drop_glue` has a divide-by-4 escape hatch on the recursion count, because drop glue naturally creates tight monomorphization loops (`check_recursion_limit` in `collector.rs`).
- **For cig: adapt.** cig has no generics, no incremental compilation and no codegen units today; the partitioner and the limits still have an analogue. Decided by rule 8 (programs stay reproducible and signable): cig's stage-b payload is one artifact and does not need partitioning. The lesson for cig is the collector's shape: a two-pass walk (CIR roots to CIR uses, memoized) is exactly what a stage-D specialization worklist is. The two limits also transfer: a per-function cap on the depth of a specialization chain (candidate: 32, lower than rustc's 128, because cig has no templates and a depth of 32 is already alarming), and a cap on the total number of specialized copies in the module (candidate: a few times the function count, the number from the census). rustc's hard fatal on exceedance does not fit cig (rule 5: identical behavior on every engine): cig falls back to `Dynamic`. The `#[inline]` escape hatch does not transfer; cig has no inlining pass today.
- **What would decide it.** Not measured yet: on `orchestrate.cig`, the size of the collected mono-item set at a fixed point under the three widening rules of entry 6, and the fraction of roots whose MIR walk reaches a cap.
- **Feeds.** cig-compile#33, #34, #37; cig-script#256; decisions (i), (f).
- **Read.** `rust-1.100.0/compiler/rustc_monomorphize/src/collector.rs` (`collect_crate_mono_items`, `MirUsedCollector`, `check_recursion_limit`, `collect_items_root`, `visit_rvalue`); `rust-1.100.0/compiler/rustc_monomorphize/src/partitioning.rs` (`partition`, `place_mono_items`, `merge_codegen_units`, `internalize_symbols`); `rust-1.100.0/compiler/rustc_middle/src/ty/instance.rs` (`enforce_type_length_limit`, `expect_resolve`, `TypeLengthLimit`); `rust-1.100.0/compiler/rustc_interface/src/limits.rs` (`get_recursion_limit`, `RecursionLimit`, `TypeLengthLimit`); `rust-1.100.0/src/doc/rustc-dev-guide/src/backend/monomorph.md`; `data/census/README.md`.

## For the issues

- **cig-compile#34 (stage D).** The lattice this study proposes for CIR is three refinements adjoined to today's `Ty`: constants (already present in `Kind::Const`, lifted into the lattice so a `copy-prop` of a `Const` carries forward), partial records (a `ShapeId` per `Map` of fixed string keys; demoted on a dynamic key, as the issue already requires), and a two-element union (the only width the census justifies; `Union2(A, B)`). The inference pass is intraprocedural first (entry 1), interprocedural at a fixed point over SCCs (entry 1 again), with signature widening at specialization (entries 6, 7). The specialization cap this study proposes is 2 to 3 distinct inferred argument-type rows per function, falling back to `Dynamic` on exceedance (entry 3): less than Julia's `max_methods = 3` because the census says 15 of 20 compute programs are at one row and cigo is at 2 or 3 rows for the hot functions. The result-type table for builtins is the prerequisite (entry 4), and per-builtin effects (`terminates`, `consistent`, `nothrow`) come from the same table (entry 5). Union splitting at a call site with a `Union2` receiver is the one new pass (entry 8).
- **cig-compile#35 (values and memory).** The .NET split of "share for layout, specialize for layout" (entry 12) is the shape for cig's refcounted versus unboxed kinds; first-class structs (entry 14) is the shape for cig's records when the shape is known.
- **cig-compile#37 (build speed).** The one table of builtin transfer functions (entry 4) is cheap (a constant table at Rust compile time, no runtime data); the specialization cap (entry 3) is the main cost gate on compile time, and a cap of 2 to 3 bounds stage D's work to a small constant per function.

## Not settled

- The right value for cig's monomorphization cap: Julia uses 3 for `max_methods` and 3 for the tuple-complexity limit; rustc uses 128 for recursion and 2**24 for type length (a different axis). The census justifies a cap of 2 to 3, but the choice is a stage-D decision pending the measurements in entry 3.
- Whether cig's `Union2` layer should be bounded at two elements or at three. Julia uses four (`max_union_splitting`); the census says up to two shapes at a cigo field site and never more. A measured answer waits on entry 8.
- The exact `cost` to assign to a cig builtin that "calls back". Julia uses `inline_nonleaf_penalty = 1000`, a signal rather than a real cycle estimate. cig has no inliner yet, so the field can be added and populated with the same signal, then tuned when an inliner lands.
- Whether cig-cherry's cached native blob should match Julia's four-flag reject (level, debug info, bounds, inline) or a smaller set. Entry 10 suggests the same four; the final list has to wait on cig-cherry's actual flags (decision (f)).
- Whether a `Ty::Union2(A, B)` layer has to be ordered (`A` then `B` is different from `B` then `A`): Julia's `tmerge` is commutative on the lattice; a `Union2` in cig could be stored as a sorted pair without losing precision, which simplifies the equality test at a call cache. Pending the choice of union representation (entry 2).
- Whether cig's specialization cache should have a world axis at all. Rule 7 (verified bytecode, never rewritten) says no, but a module reloaded from a different source has a different hash and so lives in a different cache entry already. Pending a decision on (f).
- Whether cig should adopt Julia's `nortcall` effect (a method that does not call `Core.Compiler.return_type`). cig has no equivalent of `return_type`; the effect would always be true, so it does not need to be tracked. The general question is which of Julia's nine effects collapse to a constant in cig: `notaskstate` (no tasks), `noub` (`forbid(unsafe_code)`), `nonoverlayed` (no overlay tables) and `nortcall` all do. The five that remain are `consistent`, `effect_free`, `nothrow`, `terminates`, `inaccessiblememonly`.
- Whether cig's cig-cherry guards should test one type at a time (the .NET design) or fail over to a two-type polymorphic inline cache (SpiderMonkey's design, another study). The census says one type is enough in the compute programs and two in cigo; either shape matches. Pending the study on CacheIR.
