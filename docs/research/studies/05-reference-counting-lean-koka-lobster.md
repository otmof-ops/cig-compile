## What cig should carry away

- cig's values are mutable, shared containers (`Rc<RefCell<Vec<Value>>>`, `Rc<RefCell<IndexMap<String, Value>>>`); the passes Lean and Koka build on assume an immutable value whose freed memory can be reused in place for the next value of the same shape. That optimization is not available to cig's lists and maps as they stand (entry 16). The ones that survive are last-use dup/drop placement (entries 1, 2), borrow inference (entries 4, 5), the inline fast path for dec (entry 13), and a "count is one" check that turns a write into in-place mutation (entry 15).
- Borrowing cuts refcount traffic when a value is passed down a call chain without being stored: Lean infers it by fixed-point dataflow over an SCC, with a correctness core (reset-reuse, tail calls, exports) and a performance heuristic layer; Koka reads a per-module `([ParamInfo], Fip)` table out of Core (entries 4, 5). cig has no such annotation, no such pass; a `borrow` bit on CIR parameters is a small change against a measurable gain (entry 17).
- The inlined dec is: "if `rc > 1`, `rc -= 1`; else call the cold path" (Lean) or "if `rc > 0`, `rc -= 1`; else call the cold path" (Koka). Cold handles sharing, sticky overflow, and deep free (entries 11, 12, 13). cig's standard-library `Rc` aborts the process on count overflow rather than freezing to a sticky value: the only observable difference from the two runtimes is in catastrophic-overflow behavior.
- Deep structures are freed without recursion by rewriting the object's header during deletion into a worklist "next" pointer: `object.cpp`'s `set_next`/`get_next` for Lean, `kk_block_drop_free_recx` with the stack of parents in the first field for Koka (entry 12). Measured on cig 1.25.0 on 2026-11-23: a list nested by `xs = [xs]` is built and dropped without error at 4,000,000 levels on both engines, and at 4,500,000 levels the drop aborts the process (`thread 'cig' has overflowed its stack`, exit 134) on both engines, on the default 256 MiB stack. Because 4,500,000 iterations cost 9,000,000 steps, inside the default step budget of 10,000,000, a script reaches the abort without raising any limit. The cause is that the drop the compiler derives for `Value` recurses into its inner `Rc` children; `Value` has no `Drop` of its own in `cig-script/src/value.rs`. A worklist-based drop for `Value::List` and `Value::Map` is cheap to add and removes a real failure mode (entry 12, measurement owed).
- Per-block coalescing of multiple inc/dec operations is a cheap pass that runs after dup/drop placement: multiple `inc x` with no observing write between can be summed at the first occurrence, multiple `dec x` at the last (entry 18). It is a small post-pass on CIR that stays correct under cig's `T1`-`T3` because incs and decs within a block are `Class::Effect` only against each other.
- Dead-code elimination of pure values keeps `inc`/`dec` honest by removing a let-binding whose result nobody reads (entry 19); cig's existing `dead-pure` pass does the same for CIR values, so the Lean pass is a design cross-reference, not something to port.
- Rules that decide against the deeper Perceus reuses by rule 6: `reset_reuse` (entry 6), `expandResetReuse` (entry 7), reuse analysis (entry 8), reuse specialization (entry 9) all require the freed cell to be shape-bound; cig's dynamic collection kinds don't give that guarantee, and a closure or `Chain` can still reach the cell through a captured `VarInfo`.
- The two measured sources for how much reference counting matters as a fraction of program time: Ullrich and de Moura (Lean's paper) report the explicit-RC overhead on a synthetic benchmark of tree rebuilds at under 10 percent after reset-reuse and borrow inference; Reinking, Xie, de Moura and Leijen (Perceus paper) report Koka within 10-30 percent of OCaml and Haskell on the same fp benchmarks after drop specialization. Neither number is directly applicable to cig, because cig's values are not immutable and Ullrich's and Reinking's wins come largely from reuse, which cig cannot take. The applicable number is the count of inc/dec a cig program runs today, measured against a design that places dup/drop precisely at last use and declares borrows on hot builtins.
- A final design note: the three languages differ most sharply in what the user sees. Lean and Koka are pure functional languages whose user writes constructors; the RC passes are invisible and the user's only tool is the borrow annotation. Lobster is partly imperative; the user sees occasional errors and must know the ownership model to resolve them. cig, dynamic and mutable, is closer to Lobster in user experience but cannot ship Lobster's errors; the passes that reduce RC traffic have to be fully invisible to the user, which is why entries 6 through 9 are rejected and entries 1, 2, 4, 5, 10, 15, 17 and 18 are the ones that survive.
- The structural observation worth carrying away for the next stage: the three places refcounting touches a compiler are the IR pass (entries 1, 2, 10, 17, 18), the per-function signature (entries 4, 5, 20), and the runtime's inline fast path (entries 11, 12, 13, 15). All three must agree on what "owned" and "borrowed" mean, and all three must honor the same observation rule (cig's rule 6). A design that puts the pass first and the signature as a late addition is an easier staging than the reverse: a signature that changes after the pass has run invalidates its result.

## Design points

### 1. Lean's explicit reference-counting pass, inserted after a liveness analysis over owned and borrowed variables

- **What it does, and why.** `ExplicitRC.lean` traverses an LCNF module with `inc` and `dec` already absent, walks the code and runs a backward liveness analysis, and inserts a `dec` at the first position a possible reference is no longer alive and an `inc` wherever an owned use would otherwise free a value still needed later. Live variables are split into two sets: `vars` (possibly killable) and `borrows` (kept alive by a borrowed parameter, never killed here). A separate pre-pass, `CollectDerivedValInfo`, builds a dependency graph: a projection (`oproj`, `uproj`, `sproj`, or the array-get primitives) records which parent its result derives from, so when the parent is borrowed the derived value counts as borrowed too ("derived borrows"). The decrement is emitted at the join-point boundary: for each alternative of a `cases`, the pass computes its own live set and emits decrements for variables live in the discriminant but dead in that alternative, incrementing derived values that would otherwise lose their parent. The paper this follows is Ullrich and de Moura (`papers/ullrich-2019-counting-immutable-beans.pdf`).

  The concrete rules the module encodes: `addIncBefore` inserts `inc` at the first occurrence of each argument, as many times as the argument is consumed; if the argument is still live after, or is also passed as a borrow in the same call, the number of incs equals the number of consumptions, otherwise one is subtracted. `addDecAfterFullApp` emits a `dec` for a borrowed argument only when five conditions hold together: `info.isPossibleRef` (the argument is a possible reference), `isFirstOcc args i` (this is the first occurrence of the fvar among the call's arguments, so a value repeated in several positions is dec'd once), `isBorrowParam fvarId args ps` (the argument is in a borrow position in this call), `!(← isLive fvarId)` (the argument is not live after the call), and `!(← isBorrowed fvarId)` (the caller is not itself holding the argument as a borrow). `addPrologForAlt` increments derived values whose parent is no longer in the arm's live set and decrements values that were live in the cases but not in this arm, in a fixed sort order over the variables' introduction indices (`info.idx`) so the pass's output is stable across renamings.
- **For cig: adapt.** By rule 1 (burns never move): a liveness-driven dec placement is the correct shape for cig, but the pass has to run on CIR after cig's `Class::Effect`, `Class::MayRaise` and `Class::Step` are honored. The analogue of a "possible reference" is `Ty::List`, `Ty::Map`, `Ty::Str`, `Ty::Func` and `Ty::Dynamic`; the rest is scalar. cig's form: a new CIR pass, `rc-insert`, run after `dead-pure`, inserting an `Instr` of a new kind, `Dec(ValueId)` (or on `VarId` for slots), of `Class::Effect` so the verifier pins it. A `cases`-equivalent in cig is `If` and the short-circuit ops; the `jp` role is played by cig's lowering to a fresh block for each arm.
- **What would decide it.** Not measured yet: the count of inc/dec a liveness-driven placement emits for `nbody`, `trees`, `closures` and `dispatch`, compared to the naive "clone on move, drop at scope end" the VM has today.
- **Feeds.** cig-compile#33, #35; decisions (g), (a).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/ExplicitRC.lean` (`DerivedValInfo`, `CollectDerivedValInfo`, `LiveVars`, `addInc`, `addDec`, `addPrologForAlt`, `useVar`, `explicitRc`); `papers/ullrich-2019-counting-immutable-beans.pdf`; `cig-script/src/lower/cir/ir.rs` (`Kind`, `Class`, `Ty`); `cig-script/src/lower/cir/verify.rs`.

### 2. Koka's Perceus pass, with dup and drop placed precisely at last use, walked in reverse

- **What it does, and why.** `Parc.hs` walks the Core in reverse: expressions are visited right-to-left, so the `live` state after visiting a sub-expression is the live set that matters at that program point. The monad carries `Owned` and `Borrowed` environments (multisets, like the paper) and a live-variable state. For an application, `parcExpr` reverses the argument list before recursing, so the right-most use is seen first; `useTName` looks up a name, and if it is not yet live emits a `dup`. At let binders, the body is visited first, then the binding, and any value whose last use is in the binding gets a `drop` at its end. For a `cases`, the branches are visited independently, each returning its own live set, then reconciled: the union of lives becomes the outer live set and variables dropped on only one arm get a drop prepended to the others, as the paper's `D` and `S` functions do. Function parameters marked `Borrow` are not dup'd at the entry; each remaining captured free variable is dup'd once at `parcLam`. The paper is `papers/reinking-2021-perceus.pdf`.

  The difference between "dec at death" (Lean) and "dup at first reverse-walk use and drop where unused" (Koka) is this: Koka can place a drop inside the arm of a case that makes a variable dead, where Lean emits an alternative prolog that decrements it. For a program with few `cases`, the two placements converge; for a program with deep pattern matching, Koka's placement is closer to the value's actual last touch. The paper calls this placement "garbage-free" because at any program point every dead reference has already been dropped.
- **For cig: adapt.** By rule 5 (identical behavior on every engine): dup/drop at last use is sharper than Lean's dec-only-at-death placement in that an unused value gets a drop in the same lexical scope it was bound. cig's CIR is forward-ordered and structured, so a reverse walk is natural; the pass is a map over blocks visited in reverse order, with a live-set accumulated as a state. cig's form: a single CIR pass, replacing a naive "move always copies" model with a precise "last use moves, earlier uses dup". A drop is `Class::Effect` for lists, maps and strings that may own file handles or chains; for `Ty::Str` alone a drop is `Class::Pure` because dropping a shared string cannot be observed.
- **What would decide it.** Not measured yet: the count of dup/drop operations against the "liveness dec-at-death" of entry 1, on the same programs. The expected difference is drop placement in arms, not total.
- **Feeds.** cig-compile#33, #35; cig-script#243 (Part 2 trick 3); decisions (g), (a).
- **Read.** `koka-v3.2.9/src/Backend/C/Parc.hs` (`parcCore`, `parcExpr`, `parcLam`, `useTName`, `parcDefGroup`, `genDup`, `genDrop`); `papers/reinking-2021-perceus.pdf`; `cig-script/src/lower/cir/ir.rs` (`Kind`, `Class`).

### 3. Lobster's compile-time lifetimes: LT_BORROW, LT_KEEP, LT_ANY on every AST node

- **What it does, and why.** Lobster carries a `Lifetime` on every AST node, matched against what its recipient wants: `LT_BORROW` (value, "do not hold on"), `LT_KEEP` (value, "you are responsible"), `LT_ANY` (non-reference, either side is fine), `LT_MULTIPLE` (per-tuple, stored on the type), `LT_UNDEF`. Positive values are indices into a per-function table of currently borrowed `SpecIdent`s. Type checking interleaves with the lifetime assignment because specialization is by ownership as well as by type. `AdjustLifetime` matches a node's lifetime against its recipient's and emits inc or dec per tuple component: a borrowed value given to a keep recipient takes an `incref`; a kept value given to a borrow recipient takes a `decref` (deferred to after the recipient). `LifetimeUnion` reconciles two branches at an `if` or `and`/`or`: equal, agreed with any, both borrows (in an `and`), or default to `LT_KEEP`. The algorithm is described as removing "around 95% of runtime reference count operations" in `docs/source/memory_management.md`.

  Lobster's errors are what makes the design incompatible with cig: "cannot modify x while y borrows it", "cannot assign to borrowed argument: x", and the two aliasing errors the author admits he has never seen trigger. Each of these is a compile-time refusal for a program that would be legal in cig's dynamic language. The underlying analysis, though, is a good model for the shape of a heuristic: initial borrow, promotion to keep on specific triggers, union at joins. That model informs entry 4 and entry 5's reading of the Lean and Koka passes.
- **For cig: reject.** As a whole design: by rule 5 and the differential suite, Lobster trades errors ("cannot modify x while y borrows it") for compile-time count removal, which cig's dynamic language cannot: a cig program that fails Lobster's analysis has to still run and produce the same output. The useful part is the shape of the heuristic: a value defaulting to borrow when it is an L-value's reference, to keep when it is a fresh allocation, and reconciled at control-flow joins; this lives in the design of entries 4 and 5 for cig, not as a separate analysis.
- **What would decide it.** Decided by rule 5 (every program must run; an error that only Lobster's analysis finds cannot be a cig compile error).
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `lobster-v2026.8/docs/source/memory_management.md` (`Ownership Analysis`, `AST ownership matching`); `lobster-v2026.8/dev/src/lobster/type.h` (`Lifetime`, `LT_BORROW`, `LT_KEEP`, `LT_ANY`, `LT_MULTIPLE`); `lobster-v2026.8/dev/src/lobster/typecheck_base.h` (`AdjustLifetime`); `lobster-v2026.8/dev/src/lobster/typecheck_flow.h` (`LifetimeUnion`).

### 4. Lean's borrow inference by fixed-point dataflow over an SCC

- **What it does, and why.** `InferBorrow.lean` starts every reference-typed parameter as `borrow := true` and runs a fixed-point that marks a parameter owned when any of the reasons in `OwnReason` fires: a value stored in a constructor, passed to an owned parameter of another function, used as the source or target of `reset`/`reuse`, returned, passed to a self-tail call that would otherwise break the tail position, or passed as the callee of an fvar or pap call. Reasons are split into "forced" (correctness) and "not-forced" (heuristic): reset-reuse, tail-call preservation and exports are forced; constructor-arg, function-call-arg, fvar-call, partial-application and jp-arg-propagation are heuristic. When a parameter already carries a user-annotated borrow, the pass respects it for non-forced reasons and overrides it for forced ones. `PropagateBorrow.lean` is a smaller pass that then threads the borrow information through projections and constructor fields. The pass iterates until the `modified` flag stays false.

  The pass is careful about exports. An `@[export]`-annotated declaration starts with every parameter owned (`initParamsIfNotExported` returns `{ p with borrow := false }` when the def is exported), because a C caller is the stable ABI: a borrow annotation would require every consumer to agree. Inside a module, borrow is the aggressive default and owned is the fallback. `getParamInfo` falls back to `getImpureSignature?` for a call into a declaration that is not in the current SCC, so cross-SCC borrow information is read, never re-derived.
- **For cig: adapt.** By rule 5 and rule 6: cig's parameters have no borrow bit today, and the whole VM calling convention is "argument is a clone" (every `clone()` on a `Value::List` or `Value::Map` bumps the inner `Rc`). A borrow bit on `Func::params` (the existing `cig-script/src/lower/cir/ir.rs` type is the place to add it) marks arguments the callee will not drop. A forced reason for cig: a value stored in a `MakeList`, `MakeMap` or closure capture is owned, by the same reasoning as Lean's `resetReuse` / `constructorResult`. A heuristic reason: an argument of a `CallBuiltin` whose builtin signature is declared borrowing (e.g. `len`, `str.contains`). The fixed-point is at module scope, not the function scope.
- **What would decide it.** Not measured yet: the count of `.clone()` calls in `cig-script/src/vm/mod.rs`'s call setup for `dispatch`, before and after a simple borrow-infer pass on arguments of `CallBuiltin` only.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/InferBorrow.lean` (`ParamMap`, `OwnReason`, `isForced`, `collectDecl`, `ownArgsUsingParams`, `ownParamsUsingArgs`, `preserveTailCall`, `infer`); `lean4-v4.35.0/src/Lean/Compiler/LCNF/PropagateBorrow.lean`; `cig-script/src/lower/cir/ir.rs` (`Func`, `VarInfo`).

### 5. Koka's borrow signatures carried with the module, consulted at every call

- **What it does, and why.** `Core/Borrowed.hs` holds a map from `Name` to `([ParamInfo], Fip)`: each exported definition's parameter borrow flags and its FIP annotation. `extractBorrowed` walks a Core module and lifts every `DefFun pinfos fip` into the map; `borrowedLookup` is what `Parc.hs`'s `parcBorrowApp` consults to decide whether an argument is passed as `Own` or `Borrow`. When an argument is borrowed, `parcBorrowApp` names its result (so a later drop can refer to the let-bound temporary), moves the dups before the call, and emits any drops the call owes after. If the function is not in the table, no arguments are treated as borrowed. Borrow signatures cross module boundaries through the interface Core file; the borrow pass itself (`Parc.hs`) is a single top-down walk over the current module's defs, with the imported borrow table in the reader environment.

  The split between Lean's inferred borrows and Koka's declared borrows is a useful one for cig. Lean's inference is a whole-SCC fixed point that is sensitive to call chains; Koka's declaration is per-function and never changes. cig's pack and pull declarations are a stable ABI inside a module (no ABI mismatch concern between modules because there is no linking), so a declared borrow on a cig signature is cheap to add, cheap to read, and the inference from entry 4 can fill in the rest.
- **For cig: adapt.** By rule 6 and rule 5: a declared borrow signature on `pull` and `pack` (cig's function kinds) lets the lowering and the VM skip the clone on a borrowed argument. cig's form: `Func::params` grows a per-parameter `Mode::Owned | Mode::Borrowed`; cig-compile's pass fills them from the signature annotation (a new `borrow` keyword on parameters, or an inferred value from entry 4); CIR's `CallUser` and `CallBuiltin` read them. The split that matters is that a builtin's signature is written down (dozens of them, once, in `cig-script/src/lower/cir/effects.rs`'s neighborhood), not inferred: `len`, `str.contains`, `list.get`, `map.has` are all borrowed on their receiver and arguments.
- **What would decide it.** Not measured yet: with a static borrow signature on the five hottest builtins (`len`, `.contains`, `.get`, `.has`, `.keys`), count the clones removed on the benchmark set.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `koka-v3.2.9/src/Core/Borrowed.hs` (`Borrowed`, `borrowedLookup`, `extractBorrowed`); `koka-v3.2.9/src/Backend/C/Parc.hs` (`parcBorrowApp`, `parcBorrowArg`, `getParamInfos`); `cig-script/src/lower/cir/ir.rs` (`Func`, `Kind`); `cig-script/src/lower/cir/effects.rs`.

### 6. Lean's reset-reuse: the freed cell of a matched constructor fed to the next same-shape allocation

- **What it does, and why.** `ResetReuse.lean` implements the paper's `R`, `D` and `S` functions. `R` picks candidates among variables whose last use is a `cases` match; for each, `D` finds a code region in which the variable is dead, and calls `S`. `S` searches for the next constructor allocation whose shape (size, `usize`, `ssize`) matches the freed constructor's; if one is found, it inserts a `reset size x` before the dead region, giving a fresh `w`, and rewrites the allocation into `reuse w info' updateNecessary ys`. `mayReuse` governs whether two constructors are shape-compatible; without `relaxedReuse`, the two must share the type's prefix (`c₁.name.getPrefix == c₂.name.getPrefix`), which keeps a `Prod.mk` from being reused to allocate a `PSigma.mk`. The pass is run twice: once without `relaxedReuse` (more conservative), then once with it enabled, so straightforward reuse is preferred.

  The `updateNecessary` flag in the emitted `reuse` records whether the constructor tag changed and therefore whether the runtime needs to overwrite it; if the two constructors share a tag, the tag byte is not rewritten. The pass is careful not to feed the same reused slot twice: `alreadyFound` tracks the FVar ids already picked for a reuse, which is how a nested `cases` on the same discriminant avoids a double-reset.
- **For cig: reject.** By rule 6, and by what cig's values are: cig's lists and maps are not immutable constructors of a known shape; they are heap-allocated `Vec` and `IndexMap`, and the "freed cell" model does not apply. The only cig allocation whose shape is fixed enough to reuse is a map that has become a record (cig-compile#35's shape work), and even there the reused cell would be a shape-bound record allocation, not a general map. If stage D brings records as a separate value kind, this pass becomes relevant then; it is not relevant to the general `MakeList` / `MakeMap`. cig's form: not planned at stage C.
- **What would decide it.** Decided by rule 6 (cleanup that can be observed, including file handles held by a `Chain` or by a closure, cannot be moved by a reset-reuse pair; and for lists and maps the shapes are not fixed).
- **Feeds.** cig-compile#35; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/ResetReuse.lean` (`mayReuse`, `insertResetReuse`, `UseClassification`, `relaxedReuse`); `papers/ullrich-2019-counting-immutable-beans.pdf`; `cig-script/src/value.rs` (`List`, `Map`).

### 7. Lean's reset-reuse expansion into hot and cold paths with dynamic derived borrows

- **What it does, and why.** `ExpandResetReuse.lean` turns every `let token := reset nfields orig` into a `cases` on `isShared orig`: the hot branch (unique) jumps to a join point with `token := orig` and a flag saying "we may reuse"; the cold branch jumps to the same join point with `token := box(0)` and the flag cleared, so the subsequent `reuse` behaves as an ordinary allocation when the cell was shared. Inside the join point, `dec` on `token` becomes `del` (free the cell now), and a `reuse` is itself expanded into another `cases` on the flag: hot path writes the fields into the freed cell, cold path allocates afresh. On the hot path, the pass erases projection-driven increments: `let x_0 := proj[0] orig; inc x_0` is removed because on the hot path `orig` is not freed and the projections stay alive through it (a "dynamic derived borrow"). It also skips self-stores where the field written back is the same projection that was read: `eraseProjIncFor` is the helper.

  The hot-path self-store elision ("if the new field value is the same projection that was read") is one of the paper's most quietly consequential moves: it means an immutable update of a record that keeps most fields and changes a few costs only the touched fields' stores, not the full copy. For cig, where the "update" of a map happens through `SetMember` and the map itself is mutable, the self-store check does not apply; the operation is already an in-place write.
- **For cig: reject.** As entry 6: without constructor-shaped reusable allocations, the hot path has nothing to reuse. The one valuable idea is the branch on uniqueness (entry 15, "count is one"), which is useful on its own for cig's `push`, `+=` and `set` on a sole-reference list or string; the expansion that wraps a `reuse` in a hot/cold `cases` has no cig analogue today.
- **What would decide it.** Decided by rule 6.
- **Feeds.** cig-compile#35; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/ExpandResetReuse.lean` (`eraseProjIncFor`, `partitionSelfSets`, `remapSets`, `Mask`); `cig-script/src/value.rs` (`List`, `Map`).

### 8. Koka's reuse analysis: a dropped allocation of size N feeds the next same-size allocation

- **What it does, and why.** `ParcReuse.hs` runs after Perceus. It carries an `Available` map from constructor allocation size (`conReprAllocSize`) to the list of `ReuseInfo` reuse tokens live at this point; a dropped constructor's cell is added to the map at its drop site via `ruMakeAvailable`, where the `Available` map updates are keyed by size, not by shape. When a constructor allocation is next encountered, `ruTryReuseCon` looks up the matching size, picks the first available slot and rewrites the allocation to `alloc_at(reuseName, con(..))`. Branches reconcile their `Available` and `Reused` sets by intersection. The reuse token, when the match fails, is a `NULL` pointer the runtime recognizes (which lowers to `kk_likely(#1!=NULL)`). `ruIsReusable` disqualifies value types (`size == 0`), `Just`-like optimizing constructors (where one arm has no block), and names ending in `_noreuse` (a benchmark switch). The `drop_special` wrapper from Perceus (entry 10) is the entry point `ruLet'` looks at.

  The size-keyed rather than shape-keyed design is useful to know: two constructors of different tags but the same byte size can feed each other, which widens the pool of reusable cells beyond what Lean's prefix check (`c.name.getPrefix`) allows. The FIP mode enables an additional "pick a good match: for now we prefer the same constructor" rule in the `pick` helper (currently disabled in the shipped pass, left as a `let (rinfo,rinfos) = pick ..` comment), signalling the design space is still being measured.

  Lorenzen and Leijen's "Reference Counting with Frame Limited Reuse" (`papers/compilers/lorenzen-2022-frame-limited-reuse.pdf`, ICFP 2022) revises this exact pass: the published reuse analysis is "fragile with respect to small program transformations" and "can cause an arbitrary increase in the peak heap usage"; the paper's drop-guided reuse runs after Perceus inserts dup and drop, is simpler to reason about, and is proven frame-limited (a function uses at most a constant factor more memory than its garbage-free optimum). For cig the verdict does not change by rule 6; the useful note is that any future shape-bound-record reuse should follow the drop-guided discipline, not the size-keyed analysis of `ParcReuse.hs`.
- **For cig: reject.** For lists and maps; the pass would become relevant only if a record value kind lands. By rule 6 and rule 4 (maps keep insertion order): a reused cell makes sense only when the next allocation has a known shape and the stored values are set from values the caller already has; cig's `MakeMap` with dynamic keys does not. If cig-compile#35's shapes land as a separate value kind (a shape-bound record), the mechanism is a drop-in: the shape's byte size is the key, and the token is at the record value. Not planned for stage C.
- **What would decide it.** Decided by rule 6 for general lists and maps.
- **Feeds.** cig-compile#35, #33; decision (g).

### 9. Koka's reuse specialization: skip the field store when the value written matches the pattern

- **What it does, and why.** `ParcReuseSpec.hs` is a second pass after reuse analysis. For every `alloc_at(reuseName, con(args))`, it reads the pattern that gave `reuseName` its slot, zips the constructor's arguments against the pattern, and calls `tryMatch` on each pair. A match is one of: the argument is the exact variable the pattern bound; the argument is `dup(x)` where `x` is that variable; the argument is a unit constructor that was also in the pattern. A non-match keeps the store. The decision whether to specialize is: `oldTagBenefit + length (filter isMatch matches) >= 1 + ((1 + length args) `div` 4)` (save at least a quarter of the stores, counting a saved tag-write as one if the old tag already matches). The lowered form is `if (kk_likely(reuse != NULL)) { set only the non-matching fields } else { allocate afresh }`.

  The pass is a small but telling example of how much of Perceus is about not doing work: the fully-general reuse cell is still a sound target, but a specialized reuse that skips stores is sounder when the shape matches. The quarter-of-stores threshold is what prevents the specialization from turning into a branch that costs more than it saves. For cig's shape-bound records, the threshold is likely to need its own measurement; a conservative starting value is "specialize only when at least half of the stores can be skipped".
- **For cig: reject.** By rule 6 and entry 8: the specialization requires a reusable cell in the first place, which cig's lists and maps do not have. The one takeaway is the quarter-of-stores threshold as a useful rule of thumb when reuse does land for shape-bound records.
- **What would decide it.** Decided by rule 6.
- **Feeds.** cig-compile#35; decision (g).
- **Read.** `koka-v3.2.9/src/Backend/C/ParcReuseSpec.hs` (`ruSpecialize`, `ruSpecCon`, `tryMatch`, `Match`, `genConFieldsAssign`, `genReuseIsValid`); `cig-script/src/value.rs` (`List`, `Map`).

### 10. Koka's drop specialization: a dropped value, branched on uniqueness, with children dup'd on the shared path

- **What it does, and why.** `specializeDrop` in `Parc.hs` turns a plain `drop v` into `makeDropSpecial v xUnique xShared xDecRef`, which lowers to a branch on `kk_is_unique`: the unique arm runs the specialized code and frees the cell, the shared arm runs the shared code and decrements the count. The unique arm drops the direct children in place (`optimizeDupDrops shapes dups (childrenOf shapes v)`), which is how a long list is freed without recursion; the shared arm dup's any descendent of `v` already in the live-dup set, then decrements the parent. `optimizeDisjoint` reconciles `(dups, drops)` in the tree of a candidate, so a dup of a child whose parent is being dropped can be fused: `fuseDupDrops` cancels pairs where the same name appears in both. The pass only runs with specialization enabled (`enableSpecialize`), guarded at module-opt level; the paper documents it as "drop specialization". `forwardingChild` is the helper that recognizes a newtype or a box whose drop forwards straight to a single child.

  The pass refuses to specialize in a few recorded cases: value types with mixed box forms (`getBoxForm` returns anything other than `BoxIdentity`), function types (`isFun`), bare integer types, and types the pass could not identify as a known data constructor (`mchildrenOf` returned `Nothing`). The guard makes drop specialization strictly a hot-path optimization: it only fires where the compiler knows the full shape and can name the children's drops at the call site.
- **For cig: adapt.** By rule 6 and rule 4: the branch on uniqueness is the valuable idea; it does not require shape-bound children. cig's `push`, `+=` on `Value::Str`, and `set` on `Value::List` can take an in-place path when the inner `Rc::strong_count(&r) == 1` (what Rust gives us). cig's form: three builtins on the mutation path check uniqueness and either append in place or clone-then-append. No new pass is needed for this, just a small shim in the VM and in the builtin layer.
- **What would decide it.** Not measured yet: `strbuild`, `fannkuch` and the `maps` benchmark at stage B with the uniqueness check on, against the current clone-every-time path.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `koka-v3.2.9/src/Backend/C/Parc.hs` (`specializeDrop`, `optimizeDupDrops`, `optimizeDisjoint`, `fuseDupDrops`, `forwardingChild`, `makeDropSpecial`); `koka-v3.2.9/kklib/include/kklib.h` (`kk_block_is_unique`); `cig-script/src/value.rs` (`Value`, `List`, `Str`).

### 11. The object header: Lean's 32-bit count with sticky bands, Koka's 32-bit count with unique = 0

- **What it does, and why.** Lean's header is 64 bits total: `int m_rc; unsigned m_cs_sz:16; unsigned m_other:8; unsigned m_tag:8`. `m_rc > 0` is single-threaded; `m_rc < 0` is thread-shared (atomic, counts down toward `INT_MIN`); `m_rc == 0` is persistent (never counted). The sticky mechanism uses two thresholds, not one: once `rc <= LEAN_RC_STICKY_DROP` (`INT_MIN + 0x20000000`), drops stop adjusting the count, and once `rc <= LEAN_RC_STICKY` (`INT_MIN + 0x10000000`), increments stop as well. The wider band `[INT_MIN, LEAN_RC_STICKY_DROP]` is where drops are already frozen but increments can still fire; the narrower `[INT_MIN, LEAN_RC_STICKY]` is where both are frozen; the gap between them is the margin that bounds how far a stale-read race on another thread can lift the count back out. A single-threaded count that overflows past `INT_MAX` wraps straight into the stuck-ST sub-range `[INT_MIN, INT_MIN + 0x10000)`, and a shared count descending toward `INT_MIN` is caught by the drop threshold first. `LEAN_RC_INC_MAX` (`0x10000`) bounds the per-call increment the inline path can apply. Koka's header is 64 bits with scan size (8), context path (8), tag (16) and refcount (atomic 32). Koka inverts the sign convention: unique = 0 (so a `drop` on a unique object is a single compare against zero), rc > 0 is single-threaded shared count, rc < 0 is thread-shared. Static objects start at `INT32_MIN` (sticky); the cold path handles sticky checks. Lean never shrinks its RC to 0 for a live heap object; Koka does.

  The difference in sign convention has one practical consequence: Koka's "is this unique" test is one instruction (a compare against zero), Lean's is a compare against one that also has to fall through to a `rc != 0` check for the persistent case. For cig's fast path the Koka convention is tighter, but Rust's `Rc` places the count at offset 0 of the heap node and makes neither unique nor persistent cheaper to test than the other: both go through `Rc::strong_count` and a compare.
- **For cig: adapt.** By rule 9 (`forbid(unsafe_code)`): cig's `Rc` is Rust's stdlib `Rc` today, with `strong` and `weak` counts of pointer width. The one-compare unique check (Koka's "rc == 0" or Rust's `Rc::strong_count(&r) == 1`) is available to cig in safe code. The sticky-overflow freezing in both runtimes is a defensive trade: a 32-bit count is small enough to overflow under pathological sharing, so an unbounded leak is preferred to a safety bug. cig's `Rc` aborts the process on count overflow (Rust's stdlib behavior: an abort on count wrap, with a usize count that would need pointer-width increments to reach the limit); the design trade is already more conservative than a 32-bit sticky freeze. If stage C ships a custom header (for shapes, from entry 15 of the values study), cig keeps the pointer-width count rather than tightening to 32 bits.
- **What would decide it.** Decided by rule 9 and rule 5 (the encoding has no observable semantics, but the freezing behavior under overflow has to be the same on both engines: for cig, simplest is Rust's panic, already there).
- **Feeds.** cig-compile#35, #40; decisions (a), (g).
- **Read.** `lean4-v4.35.0/src/include/lean/lean.h` (`lean_object`, `m_rc`, `LEAN_RC_STICKY`, `LEAN_RC_STICKY_DROP`, `LEAN_RC_INC_MAX`, `lean_inc_ref_n`, `lean_dec_ref`, `lean_is_exclusive`, `lean_is_never_freed`); `koka-v3.2.9/kklib/include/kklib.h` (`kk_header_t`, `kk_refcount_t`, `kk_block_is_unique`, `kk_refcount_is_thread_shared`, `kk_refcount_inc`, `KK_HEADER_STATIC`); `cig-script/src/value.rs` (`Value`).

### 12. Freeing a deep structure without deep recursion: the header rewritten into a worklist pointer

- **What it does, and why.** When Lean frees an object whose children are heap-allocated, it must drop each child, which may recursively free its children. Naïve recursion stack-overflows on a long linked list. Lean's solution: during `lean_dec_ref_cold`, when the count reaches zero, the first field of a child whose count also reaches zero is overwritten with the current `todo` head (`set_next`, `push_back`), and the loop continues with the next `todo`. `get_next` reads it back by masking the high two bytes of the object's header word. This is not compatible with ARM MTE or HWASAN (the top byte is in use for pointer tags) and is asserted at compile time. Koka's `kk_block_drop_free_recx` in `refcount.c` uses the same technique: the parent is stashed in the first field of the child being visited, and the `_field_idx` byte records which field index to resume at. A separate `kk_block_drop_free_large_rec` handles vectors whose scan size exceeds `KK_SCAN_FSIZE_MAX` (255) by iterating fields recursively (the recursion depth is bounded by nesting of large vectors).

  Both designs trade memory layout tricks for stack bounds, which is a cost cig does not have to pay: safe Rust can push `Value`s onto a `Vec` and drain it, and a hand-written `Drop` on `Value` (replacing the one the compiler derives) is the one place to install the worklist. The order of visitation is still the same (the children of a block are drained before the block is freed), and no field mutation of a still-live object happens. The one implementation question is whether to install the worklist drop at `Drop for Value` directly, at a wrapper around `List` (applies to any `Rc<RefCell<Vec<Value>>>`), or at a top-level `drop_value` helper the VM calls at register-move boundaries.
- **For cig: adapt.** By rule 6 and rule 9: `Value` in `cig-script/src/value.rs` has no `Drop` of its own; the drop the compiler derives for `Value::List(Rc<RefCell<Vec<Value>>>)` recurses into its inner `Rc` children. Measured on cig 1.25.0 on 2026-11-23, a list nested by `xs = [xs]` in a loop is built and dropped without error at 4,000,000 levels on both engines, and at 4,500,000 levels the drop aborts the process (`thread 'cig' has overflowed its stack`, exit 134) on both engines, on the default 256 MiB stack. 4,500,000 iterations cost 9,000,000 steps, inside the default step budget of 10,000,000, so a script reaches the abort without raising any limit. A worklist-based drop for `List` and `Map` (and `Function`/`Chain`) lives outside `forbid(unsafe_code)` and does not need the header trick, because cig's values are a Rust enum, not a tagged heap block: a `Vec<Value>` worklist of pending drops is safe, allocates only once per deep tree, and can be installed at the derived drop boundary. The `set_next`/`get_next` byte-stealing is not cig's path.
- **What would decide it.** Not measured yet: on the test machine, a program that builds a 1,000,000-deep nested list and lets it go out of scope, before and after the worklist `Drop`, against the stack-overflow crash the current path produces.
- **Feeds.** cig-compile#35, #40; decisions (a), (g).
- **Read.** `lean4-v4.35.0/src/runtime/object.cpp` (`lean_dec_ref_cold`, `lean_del_core`, `lean_del_core_other`, `set_next`, `get_next`, `push_back`, `pop_back`); `koka-v3.2.9/kklib/src/refcount.c` (`kk_block_drop_free_recx`, `kk_block_drop_free_large_rec`, `kk_block_field_should_free`); `cig-script/src/value.rs` (`Value`, `List`).

### 13. The fast path of a decrement is: "if count > 1, decrement and return; else cold path"

- **What it does, and why.** Lean's `lean_dec_ref` is a two-line inline: a count above one is decremented in place; a count of zero does nothing; any other count calls the cold path (`lean_dec_ref_cold`). The common case is three machine instructions: load, compare, store. `rc == 0` is persistent (no count kept), caught by the second branch; `rc == 1` and `rc < 0` (shared) fall into the cold path. Koka's `kk_block_drop` is one comparison of the count against zero: at zero or below it calls the cold path (`kk_block_check_drop`), otherwise it decrements in place. Koka's "unique" is zero, so the cold path handles unique-and-free, shared, and sticky, in three cases, decided on the sign of the count. In both runtimes the hot path is inlined at every call site; the cold path is a function call. The inc fast path is symmetric for Lean (`rc += n` unconditionally in the single-threaded case; the shared-or-sticky check is outside a `LEAN_UNLIKELY` guard); for Koka `kk_block_dup` is inlined inc with a fall-through to `kk_block_check_dup` when the count is thread-shared or sticky.

  cig's analogue is Rust's `Clone::clone` on `Rc`, which is one load, one compare (against the overflow check) and one store on the non-atomic count; and `Drop::drop`, which is one load, one compare and either a store or a call into the destructor. The two are already as cheap as the C runtimes' fast paths, modulo one difference: Rust's `Rc` uses a non-atomic usize count (pointer-wide on 64-bit targets), whereas Lean and Koka's counts are 32-bit. The wider count is friendlier to overflow but may share cache lines with the data less tightly; for cig's `Value::List` and `Value::Map` this does not matter because the header is already cache-local to the `Vec`'s or `IndexMap`'s own pointer.
- **For cig: take.** By rule 9: cig's `Rc::clone` and `Rc::drop` in Rust's standard library are of this shape: a non-atomic increment on `strong` and a cold `Drop` call when the count reaches zero. The one difference is that Rust's `Rc` aborts on count overflow rather than freezing to a sticky value; cig does not need a custom `Rc` for this entry. If stage D ships a shape-bound record with a custom header (entry 11), the inlined dec stays the same shape.
- **What would decide it.** Decided by rule 9.
- **Feeds.** cig-compile#35; decisions (a), (g).
- **Read.** `lean4-v4.35.0/src/include/lean/lean.h` (`lean_dec_ref`, `lean_inc_ref`, `lean_inc_ref_n`, `LEAN_LIKELY`, `LEAN_UNLIKELY`); `koka-v3.2.9/kklib/include/kklib.h` (`kk_block_drop`, `kk_block_dup`, `kk_block_decref`, `kk_block_check_drop`); `cig-script/src/value.rs` (`Value`).

### 14. Koka's fip and fbip checks: static guarantees of in-place functional programming

- **What it does, and why.** `CheckFBIP.hs` enforces the `fip` and `fbip` annotations on a declaration. `fip` (fully in-place) requires that every allocation of the function is matched one-for-one by a drop earlier in the function: `chkAllocation` consults `fipAlloc` and enforces `AllocAtMost n` or `AllocUnlimited`. `fbip` is weaker: no new heap allocation at all in the function body; a value can be built only from reused cells. The check also propagates through calls: a `fip` function calling a non-`fip` function emits a warning. The useful part is not the check itself but what the check guarantees: with `fip`, the compiler can lower a recursive descent into a loop that reuses its own structure (the Koka papers' morris traversal, the tree-rebalance examples). The annotations are language-level and opt-in.

  The one piece of the design that is worth cross-referencing even for cig is the per-function "allocation budget" idea: a function marked as `AllocAtMost n` has a static count of fresh allocations the compiler may perform; if the count is exceeded, an error is emitted. For cig, this is not a check but a diagnostic: `--remarks` (cig-compile#33's optimization remarks facility) could report, per function, the number of allocations the lowering emits, which is a useful number for the operator to see without being a correctness gate.

  Lorenzen, Leijen and Swierstra's "FP2: Fully in-Place Functional Programming" (`papers/compilers/lorenzen-2023-fp2-fully-in-place.pdf`, Technical Report MSR-TR-2023-19, 2023) formalizes the FIP calculus the `fip` keyword rests on: a linear fragment of the language in which function parameters are owned and unique and may be used once, so the compiler can safely reuse a matched constructor's memory. The paper proves that an FIP function uses no (de)allocation and constant stack space and shows how splay trees, merge sort and quick sort can be written FIP. The verdict for cig does not change: the linearity required by FIP is incompatible with cig's dynamic sharing of lists and maps. The paper does not propose a mechanism cig could take without a type lattice (cig-compile#34).
- **For cig: reject.** By rule 5 and rule 6: cig is dynamically typed and has no annotation like `fip`; even if a function could be proven in-place at compile time, its arguments at run time are not shape-bound, so the proof does not carry into the generated code. The ideas feed entry 10 (uniqueness-driven in-place mutation at the builtin level) but not a static check.
- **What would decide it.** Decided by rule 5.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `koka-v3.2.9/src/Core/CheckFBIP.hs` (`checkFBIP`, `chkAllocation`, `mayAlloc`, `writeCallAllocation`, `getFip`); `cig-script/src/lower/cir/ir.rs` (`Func`).

### 15. The "count is one" check as the gate for in-place writes to strings, lists and maps

- **What it does, and why.** Lean's `lean_is_exclusive` is `rc > 0 && rc == 1`; Koka's `kk_block_is_unique` is `rc == 0`. Both are a single compare. Lean uses it in every in-place operation the standard library offers: `lean_array_set` has an exclusive path that writes to the array in place and a shared path that copies; the same split for `lean_string_push`, `lean_sarray_push`, every mutator. Koka uses it inside `kk_block_dropi` (the "drop with inlined dropping of children") at line 827 of `kklib.h`: if the block is unique, the children are dropped in place and the block is freed, without touching the atomic path. `drop_special` from entry 10 is the general form of a unique-dispatched operation. Cost: one load, one compare, one branch. When the count is one, the operation is a direct write; when not, it is a `clone` followed by a write.

  The subtlety for cig is that `Rc<RefCell<T>>` holds a `RefCell` of borrow state alongside the data. A `Rc::get_mut` tests both strong and weak counts and is the right primitive if cig can be sure no `Weak` is ever issued. The crate `std::rc` offers that guarantee by never exposing a `Weak` factory from cig's code; a cheaper alternative is `Rc::make_mut`, which already does the clone-then-mutate fallback internally (but requires `T: Clone`, which `Vec<Value>` and `IndexMap<String, Value>` satisfy via `#[derive(Clone)]` paths in cig's existing code). The three-line builtin shim does not require any `unsafe`.
- **For cig: take.** By rule 6: every cig builtin that mutates (`list.push`, `list.set`, `map.insert`, `str +=`) can wrap its RefCell borrow in a `Rc::get_mut` (safe in Rust's stdlib) and fall back to a clone-then-write when the count is above one. The RefCell makes this slightly delicate: `Rc::get_mut` requires both strong and weak counts to be 1. For cig's values today, weak references are never issued, so the check is on the strong count alone. This changes no CIR: the lowering of `push` lowers to the same `CallMethod`; only the method's implementation changes.
- **What would decide it.** Not measured yet: `strbuild` and `fannkuch` at stage B with and without the unique-write fast path, on the test machine. The expected gain is removing the per-iteration allocation when a loop builds a string or list from scratch.
- **Feeds.** cig-compile#35, cig-script#235 (if string builder is tracked there); decision (g).
- **Read.** `lean4-v4.35.0/src/include/lean/lean.h` (`lean_is_exclusive`, `lean_is_exclusive_obj`); `koka-v3.2.9/kklib/include/kklib.h` (`kk_block_is_unique`, `kk_block_dropi`); `cig-script/src/value.rs` (`Value`, `List`, `Map`); `cig-script/src/vm/mod.rs`.

### 16. What cig's mutable, shared `Rc<RefCell<..>>` containers change: most reuse is gone

- **What it does, and why.** Lean and Koka build on *immutable* values: a constructor allocation holds a fixed set of fields, and when the only reference is being consumed the compiler proves the cell is about to be freed and the next allocation of the same shape can land in it. cig's lists and maps are not shaped: `Vec<Value>` and `IndexMap<String, Value>` resize, and the fields are set and unset at run time through mutation (`push`, `pop`, `insert`, `remove`). cig's `Rc<RefCell<..>>` has two consequences at this level. First: a "reuse" of the cell for the next constructor of the same shape is not a well-defined operation; the next `MakeList` allocates a fresh `Vec` because the capacity, the length and the contents are not a static shape. Second: the insertion-order map is implemented as `IndexMap`, which keeps a backing hash table alongside the ordered-key vector; reusing a freed map's buffer would require preserving or clearing both. The pieces that still fit are the three in entry 15: strings, lists and maps can append in place when the count is one (and in the case of `IndexMap`, the stdlib's `Rc::get_mut` gives the exclusive access the standard `push` on the inner `Vec` needs). Lobster's "append in place" on `s += x` (where `s` is the only reference) is the shape of what cig's string concatenation can do (`docs/source/memory_management.md`).

  A second consideration is observability: cig's `Chain` holds live references to values a hook may still read when a burn enters it (`cig-script/src/burn/`); a closure capture (`VarInfo::captured`) holds a slot that lives as long as the closure. Freeing or moving memory held by either is observable to the kernel or to a user script. The rule from the contract (rule 6) states cleanup that can be observed never moves; this rules out the reset-reuse family for any value a `Chain` or closure can reach. For a strictly local temporary (a `MakeList` consumed by a `CallBuiltin` and never stored), the observation argument does not fire, and the uniqueness check still applies.
- **For cig: adapt.** Only the uniqueness-driven in-place write from entry 15 is taken, not the shape-bound reuse. By rule 6: reuse of a general list or map cell would move memory a user's `Chain` or closure may still observe through a captured slot; the uniqueness check in entry 15 is the only safe and useful fragment.
- **What would decide it.** Decided by rule 6 (cleanup that can be observed, closures that reach a list through a captured `VarInfo::captured`, maps a `Chain` has in scope, all stop any free-and-reuse that is not strictly counted).
- **Feeds.** cig-compile#35; decision (g).
- **Read.** `cig-script/src/value.rs` (`List`, `Map`, `Value`); `cig-script/src/lower/cir/ir.rs` (`Kind`, `VarInfo`); `lobster-v2026.8/docs/source/memory_management.md` (`s += x`); `koka-v3.2.9/kklib/include/kklib.h` (`kk_block_is_unique`).

### 17. Derived borrows: a projection of a borrowed value is itself borrowed

- **What it does, and why.** Lean's `ExplicitRC.lean` builds a derived-value tree in `CollectDerivedValInfo`: when `let y := oproj i x` or an `Array.getInternal x i` runs, `y` is recorded as derived from `x`. When `x` is borrowed, the pass can treat `y` as borrowed too, because the borrowed lender keeps `x` alive and therefore the slot `y` points to. The payoff is a dec not emitted on `y` and an inc not emitted when `y` is passed on in a borrow position. `addDescendants` walks the transitive closure of the derived map so a borrow of an array keeps every element known to be derived from it in the live-borrow set. The pass is careful about `Array.get!Internal` returning either the element or the `Inhabited` default on panic, so both parents are recorded.

  cig's version of this analysis must also handle the mutable-list case: a borrowed `List` can be indexed to produce a derived value, but a subsequent `list.push` or `list.set` on that same list may invalidate the derivation (if the push reallocates the backing `Vec`, or the set replaces the element). The analysis that survives is: a derived value is borrowed only until the next mutation of the parent. Within a straight-line code path with no intervening mutation, the derivation holds; across a mutation, it is withdrawn and the derived value needs a fresh dup. The CIR class system (`Class::Effect` for mutations through `SetIndex`, `SetMember`) gives the pass the fence it needs.
- **For cig: adapt.** By rule 5 and rule 6: cig's analogue of `oproj` is `Member`, `Index`, `CallMethod` on a getter. If a parameter is borrowed (entry 4), the values read from it (`b.vx`, `xs[i]`) can be borrowed themselves: no inc on the fetch, no dec at scope end. The implementation is a small graph on CIR built during a forward walk: each `Member`/`Index` records its source. The CIR pass that uses it is the one from entry 4. There is a caveat cig has to honor: a `List` or `Map` can be mutated under the borrow by the same function (`xs.push(x)` while holding a borrowed element reference), which Lean's immutable arrays do not face; a borrowed derived value must be treated as live until the parent is written to, not past.
- **What would decide it.** Not measured yet: the count of inc/dec removed by derived borrows for `nbody` (field reads of a borrowed body record) and `fannkuch` (repeated indexing of a borrowed list) against entry 4's pass without the derived-value graph.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/ExplicitRC.lean` (`DerivedValInfo`, `CollectDerivedValInfo`, `addDerivedValue`, `addDescendants`, `useVar`); `cig-script/src/lower/cir/ir.rs` (`Kind`, `Member`, `Index`).

### 18. Coalescing inc and dec operations within a basic block

- **What it does, and why.** `CoalesceRC.lean` collapses a sequence of `inc x` with no intermediate observation into one `inc x n` at the first site, and a sequence of `dec x` into one `dec x n` at the last site. The module's own comment states the two moves and their correctness argument: an intermediate operation cannot observe `rc == 1` between two `inc`s because the later `inc` would not fire if the count had reached one in between, and a value is alive at least until its last `dec` regardless of where the earlier ones sit. The pass is purely syntactic on a basic block, implemented with a forward-and-backward accumulator (`incTotal`, `incAccum`, `decTotal`, `decPlaced`) that ensures the coalesced op is emitted at the first `inc` and the last `dec`. The module's docstring also notes this pass must run after `expandResetReuse`, because that earlier pass pattern-matches on the exact placement of `inc`s on projections.

  The correctness argument generalizes: within a basic block, inc operations commute (each is an ordinary memory write to the count, and the count is private to the single thread at that point), and dec operations commute up to their last site (every earlier dec is matched by a later inc that keeps the count above one). The pass's forward+backward accumulator is one data structure that plays both roles; the simpler but less compact implementation would be two linear scans.
- **For cig: adapt.** By rule 1 and rule 5: once a dec-insertion pass (entry 1 or entry 2) emits one inc and one dec per consumption, consecutive incs or decs on the same value inside a basic block can be coalesced into a single operation with a count. cig's form: a CIR pass, `rc-coalesce`, run after `rc-insert`; the `Inc(ValueId, n)` and `Dec(ValueId, n)` instruction kinds carry an `n` for this. The pass is `Class::Effect` on each coalesced instruction (so verifier `T1`-`T3` hold); the coalesced inc stays at the first site, the coalesced dec at the last, which keeps the "cleanup at observable point" rule honest.
- **What would decide it.** Not measured yet: the count of inc/dec after entry 1's pass, before and after coalescing, on `nbody`, `trees`, `closures`.
- **Feeds.** cig-compile#33; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/CoalesceRC.lean` (`coalesceRC`, `incTotal`, `incAccum`, `decTotal`, `decPlaced`); `cig-script/src/lower/cir/ir.rs` (`Kind`, `Class`).

### 19. Dead-code elimination of pure let-bindings as a prerequisite for counts

- **What it does, and why.** `ElimDead.lean` walks LCNF forward, collects used free variables of every let, jp and fun binding, and removes the binding when its result is not used. The module's own docstring says the pass is "syntactic" (no proof of effect-freedom beyond what LCNF already states about let values) and is careful in the impure phase: a `let` whose value is a potentially-raising operation or a side-effecting primitive is not removed, because the effect it represents must still happen. `collectLocalDeclsLetValue` is the walk; `oproj`, `uproj`, `sproj`, `reset`, `box`, `unbox` and `isShared` register their source as used, so an unreferenced projection vanishes with its parent still live if the parent is used elsewhere. The pass runs before `ExplicitRC` so that counts are not inserted around a value that is about to be deleted.

  The order-of-passes observation is useful for cig: cig's `dead-pure` deletes an unreferenced pure value (`Class::Pure` instructions whose result nobody reads), which is the right prerequisite before any new `rc-insert` pass; otherwise a value that a later `dead-pure` would delete still gets its inc and dec threaded through. In practice this means `rc-insert` should run after `dead-pure`, which cig's `run_passes` order already places at the end of its level-2 list.
- **For cig: take.** By rule 5: cig's `dead-pure` pass in `pass/mod.rs` already does the same for CIR's `Pure` class; `Effect`, `MayRaise` and `Step` are kept by the verifier. The entry is a design cross-reference: Lean's order of passes (dead first, then RC insertion) is also the order cig should run them, so that counts are not threaded through a let that `dead-pure` would have removed next. Current CIR order ("level" in `pass/mod.rs`) already has `dead-pure` at the end; moving a hypothetical `rc-insert` after it is the natural slot.
- **What would decide it.** Decided by rule 5 (correctness) and already done for cig's `Pure` class by `dead-pure`.
- **Feeds.** cig-compile#33; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/ElimDead.lean` (`UsedLocalDecls`, `collectLocalDeclsArg`, `collectLocalDeclsLetValue`); `cig-script/src/lower/cir/pass/mod.rs` (`NAMES`, `run_passes`); `cig-script/src/lower/cir/ir.rs` (`Class`).

### 20. Propagating user-annotated borrows forward with a four-point lattice

- **What it does, and why.** `PropagateBorrow.lean` is the pass that carries a user's borrow annotation on a parameter forward through the function body, so that `ResetReuse` does not pick a value the user asked to keep borrowed. The lattice is four-point: `bot` (unknown), `borrow` (always borrowed), `own` (always owned), `top` (mixed). `Ownedness.join` is the lattice's meet: `bot` is identity, `borrow+borrow` is `borrow`, `own+own` is `own`, everything else is `top`. The pass initializes each parameter to `borrow` if the user annotated it, otherwise `top`, and fixed-points over the function body, joining per fvar. The payoff: `ResetReuse` consults the propagated ownedness and refuses to pick a value whose ownedness is not `own` at the match site.
- **For cig: adapt.** Taken as a model of the analysis, not as code to copy. By rule 5 and rule 6: the join-per-variable fixed-point with a four-point lattice is a compact representation of what the entry 4 inference emits at the function boundary, and the forward propagation inside the body is what cig's CIR pass needs to make a borrow on a parameter useful at a later use. The useful idea is the `top` state: a value whose ownedness is mixed across branches should be treated as owned (safe default), which Lean's pass encodes in a one-line `join` function. cig's form: a small CIR analysis that runs after entry 4 and threads a per-value ownedness through the body, consulted by entry 15's uniqueness-write to decide whether a borrow hint even applies.
- **What would decide it.** Not measured yet: the count of ambiguous (`top`) sites in cig's benchmark set, which tells whether a four-point lattice is the right shape or a simpler three-point (owned, borrowed, mixed) would do.
- **Feeds.** cig-compile#33, #35; decision (g).
- **Read.** `lean4-v4.35.0/src/Lean/Compiler/LCNF/PropagateBorrow.lean` (`Ownedness`, `join`, `analyzePropagatedBorrows`, `initializeDecl`); `cig-script/src/lower/cir/ir.rs` (`VarInfo`, `Func`).

## For the issues

**cig-compile#33 (the optimizer, section `rc elision`).** Stage C's `rc elision` is three things, done in order: a liveness-driven dec placement at scope end or earlier when the value is dead (entry 1, Lean's shape; entry 2, Koka's shape, which places drops sharper by one or two sites), borrow inference on function parameters (entry 4, by fixed-point) backed by a per-module borrow table (entry 5), and the derived-borrow graph that keeps a projection from needing its own inc/dec (entry 17). Reset-reuse and reuse analysis (entries 6-9) are not taken, by rule 6. The "unique at run time" check is a small but valuable fragment (entry 15), moved to the builtin layer. Per-block coalescing (entry 18) is a cheap post-pass that reduces residual traffic; dead-pure (entry 19) already exists in cig's pass list and is the prerequisite.

**cig-compile#35 (values and memory).** The header and count encoding Lean and Koka use fit a shape-bound value kind (entry 11); for cig's existing `Value`, Rust's `Rc` gives the inline dec fast path (entry 13) and a safe uniqueness check (entry 15). The deep-free worklist (entry 12) is one afternoon's work in safe Rust and removes a real failure mode measured on cig 1.25.0: fine at 4.0 million levels, aborts at 4.5 million levels (`thread 'cig' has overflowed its stack`, exit 134 on both engines), within the default step budget. The "freed cell reused for the next same-shape allocation" idea does not apply to cig's `Vec`-backed `List` or `IndexMap`-backed `Map` (entry 16); if stage D adds record values, the mechanism from entries 8 and 9 becomes relevant then, and Lorenzen and Leijen's drop-guided variant of the analysis is the better starting point. The `thread-shared` transition in both runtimes is a design cross-reference, not taken, because cig is single-threaded.

**cig-script#243, Part 2 trick 3 (Perceus).** The precise dup/drop placement is one CIR pass (entry 2); the uniqueness-driven `drop_special` (entry 10) is a second, smaller pass, but its full form (hot path reuse of a freed cell) is not for cig. The two together are what the Perceus paper calls garbage-free; the one of them without the other is what cig gets. Borrow annotations on cig's hottest builtins (entry 5) are the complement to the pass: without them, dup/drop placement still dup's every argument into every call.

## Not settled


- Whether cig's `MayRaise` instructions on a value path (`Index`, `Member`) force the dec-placement pass to fence like Lean's `cases` prolog does, or whether a backward walk alone suffices: Lean's immutable arrays raise on out-of-range in a way that does not re-emit the exact prior state, so the two-phase placement is a conservatism Koka also adopts; cig's semantic rule 2 (errors happen at the same place) may demand the same two-phase structure, but the source at the pin does not say what it costs.
- Whether a `Chain`'s step list should be treated as shape-bound (entry 8's mechanism becomes relevant) or as a plain `Vec<ChainStep>`: `cig-script/src/value.rs`'s `Chain` is a `struct` with a fixed `steps: Vec<ChainStep>`, not a constructor, so the shape-bound interpretation has no direct Perceus analogue; the question is open until the stage D record design lands.
- Whether `FBIP` could ever apply to a `pack` (cig's pure function kind), given cig values are untyped at compile time: the source is clear that Koka's check is static and per-signature, which cig cannot reproduce without a lattice (cig-compile#34); outside the type lattice, the check has nothing to anchor to.
- Whether Lean's and Koka's `thread-shared` transition (promotion of a block from single-threaded to atomically counted) is worth any cost on cig today: cig is single-threaded by design, and `Rc` (not `Arc`) is the primitive in the VM; the thread-shared machinery in both runtimes is a design cross-reference, not a design cig takes. The question returns if cig ever ships a work-stealing scheduler.
- Whether entry 15's uniqueness-write should be opt-in per builtin or on by default: a surprising case is `list.push` under iteration (a user iterates a list and pushes to it in the loop), where the uniqueness check still correctly distinguishes a borrowed (read-only) iteration from an owning one, but the behavior should be measured first against the differential suite at zero differences before it is turned on everywhere.
- Whether entry 20's four-point lattice should be the pass's output on its own or a late reconciliation of entry 4's and entry 17's results: the two previous passes already compute a two-point (owned/borrow) decision; `top` from entry 20 only arises when control flow merges disagreeing decisions. A design that merges the three passes into one is tempting but gives up the modular test surface each pass currently affords.
