## What cig should carry away

- **The embedded linker is small because the input is small.** mold runs about forty passes across input files that may hold thousands of objects and millions of mergeable strings (entry 3); a stage C program has one object cigcompile wrote and one runtime archive cig's own release built, so of that pipeline it needs symbol resolution, relocation and writing, with optional section garbage collection. The rest (merged strings, version scripts, ICF, `.eh_frame` reconstruction across archives, `-z relro` shaping around shared objects) is either empty for cig's inputs or a direct fit from one shape of `object` writer (entries 3, 5). Entries 3, 5.
- **Writing a linked executable from Rust is what has to be built.** `object`'s unified `write::Object` emits relocatable object files only; its lower-level `write::elf::writer` and `write::pe::Writer` write a linked ELF or PE in a two-phase reserve-then-write shape, and its Mach-O side writes linkable objects (entry 5). cig-compile wants an executable per target, so stage C writes relocatables with `object`'s unified API and either shells out to the host linker (what rustc_codegen_cranelift does, entry 2) or carries its own ELF and PE writer wired to a resolution pass over cig's one archive (entry 8). Decision (e) picks between them. Entries 2, 5, 8.
- **A per-program runtime pays its weight.** The command line is 2.0 MB and the keyring 1.4 MB of the 12.3 MB of code today (`data/size/README.md`); gating each stdlib module behind a feature cig-compile#4 names, then letting the host linker's section garbage collection cut what no code reaches, is the first cut; LLVM's ThinLTO is the pattern for cutting across cig's crates with parallel backends (entries 10, 11). mold's ICF would save a few percent more on identical read-only sections (entry 4). A script that reaches a builtin through a computed name defeats the cut and has to be seen as calling every builtin in that module. Entries 4, 9, 10, 11.
- **DWARF written from Rust is already a solved piece.** gimli writes `.debug_line`, `.debug_info`, `.debug_frame` and `.eh_frame` (entries 12, 13); rustc_codegen_cranelift turns Cranelift's `MachSrcLoc` into DWARF line rows and builds frame-description entries from each ISA's `create_systemv_cie` (entries 1, 12, 13). cig needs the span from CIR to native address on stage C; cig-cherry needs perf's jitdump for a profiler to see run-time native code by its CigScript function name (entry 14). Entries 1, 12, 13, 14.
- **Hardening costs little once Cranelift exposes it.** Cranelift's shared settings carry `enable_probestack`, `preserve_frame_pointers` and heap/table Spectre mitigation; its arm64 ISA settings carry `sign_return_address` for PAC and `use_bti` for Branch Target Identification (entry 15). `-fsanitize=cfi-vcall` reports less than 1 percent on Dromaeo and up to 15 percent larger binaries on Chromium (entry 16); SafeStack reports less than 0.1 percent (entry 16); PIE and full RELRO are the linker's, not the code generator's, and mold's `-z relro`/`-z now` write the RELRO segment and a `.relro_padding` chunk to align it to a page (entry 17). Entries 15, 16, 17.
- **The bootstrap is what makes self-hosting checkable.** Zig builds a WebAssembly image of its own compiler (`zig1.wasm`), translates it to C with a `wasm2c` interpreter in C, and compiles the result with any C compiler to get a bootstrap, from which the real compiler builds (entry 19). rustc runs three stages (stage 0 downloaded, stage 1 built with stage 0, stage 2 built with stage 1); the invariant "stage 2 equals stage 3" rules out carry-over from stage 0, and Wheeler's diverse double-compiling turns that invariant into a check against the trusting-trust attack by building the second stage with a second, independent toolchain (entry 20). Entries 19, 20.
- **A cig program is one object plus one archive, measured.** The one-object-per-program shape rustc_codegen_cranelift uses (entry 1) matches cig because stage A is already "one runtime plus one appended payload" (`cig-script/docs/PROGRAMS.md`, format 2). Stage C is the same shape with the payload replaced by a real object section. That has three consequences cig can carry forward today: `-ffunction-sections -fdata-sections` on the runtime's build is a release-side change (not a cigcompile change), with a measurable size cost and a measurable gc-sections win; the pin by hash in `cig-compile/src/digests.rs` for cig 1.25.0 already works and only needs the runtime asset to be augmented with an archive sidecar per target; and the per-program runtime measurement (entry 9) is a `cigcompile size <program>` command cig-compile#36 names and can land before stage C does.
- **Signatures cover the whole file, or they do not cover anything.** `cig-compile/docs/decisions/0001-backend.md` (line 64, "Signing appended data") states that macOS code signatures and Windows Authenticode do not cover bytes appended after signing, and names the planned routes: the payload goes in a Mach-O section (where the signature then covers it), and on Windows it is appended before Authenticode signs (so it is inside the signed image's content range). cig today works around appended-bytes signing by writing an SSH-style detached signature over the whole program with `ssh-keygen -Y sign` in the `cigcompile-program` namespace (`cig-compile/src/sign.rs: NAMESPACE`). Stage C's reserved-section shape (entry 8) generalises the Mach-O route to a real section of the ELF, Mach-O or PE image, so the operating system's signature covers it the way it covers any other section. That is a stage-C-only win; stage A cannot get it.

## Design points

### 1. One object per codegen unit through `cranelift-object`; units compiled in parallel, functions serial inside a unit

- **What it does, and why.** `rustc_codegen_cranelift` wraps Cranelift in `UnwindModule<ObjectModule>` and writes one object file per codegen unit (`compiler/rustc_codegen_cranelift/src/driver/aot.rs: AotModule`, 390 lines). `make_module` builds an `ObjectBuilder` with the target ISA, sets `builder.per_function_section(...)` so every function lands in its own section (disabled by default on Windows because of `link.exe` slowdowns), and wraps `ObjectModule::new(builder)` in `UnwindModule::new(..., true)` to collect exception frame information alongside the code. Each codegen unit's items are walked by `codegen_cgu`: `MonoItem::Fn` goes through `base::codegen_fn` and is appended to `module.codegened_functions`, `MonoItem::Static` is lowered by `constant::codegen_static`, `MonoItem::GlobalAsm` is routed through `codegen_global_asm`, and a naked assembly function is lowered by `naked_asm::codegen_naked_asm`. `compile_cgu` then walks `aot_module.codegened_functions` and compiles each one with `base::compile_fn` against a single `cached_context: Context` reused across every function in that unit, serially within the unit; `cranelift_codegen::timing::set_thread_profiler` is set per thread so per-function time is measurable. The parallelism is at the codegen-unit level: `ExtraBackendMethods::compile_codegen_unit` returns one module at a time to the layer above (`rustc_codegen_ssa::back::write`) which dispatches units across threads. The main shim is created once per primary codegen unit by `main_shim::maybe_create_entry_wrapper`. `emit_module` finishes by adding a `.comment` section carrying the producer string ("`rustc version <v> with cranelift <v>`" from `src/debuginfo/mod.rs: producer`) on ELF, then writing the object to a temp file with `product.object.write_stream`.
- **For cig: take.** Decided by rule 7 (verified bytecode, never rewritten) and rule 9 (`forbid(unsafe_code)` everywhere but one small crate): the shape "one object per unit, written through `object`, units in parallel" has no unsafe code of its own, and the `object` crate is `unsafe` in its parsing side but not in its writing side (`object/src/write/mod.rs` has no `unsafe` block in the writer types read). cig's form: a cig program is one program per build, so the parallelism for cig lives inside one unit, across its functions. `cranelift_object::ObjectModule` (`wasmtime-v50.0.1/cranelift/object/src/backend.rs: ObjectModule`) is a plain struct, not internally synchronised, so stage C runs Cranelift's per-function `compile_fn` through a rayon pool with one `cranelift_codegen::Context` per worker and the `ObjectModule` behind a cig-side lock; each function passes cig's existing verifier (`cig-script/src/lower/cir/verify.rs`, `V1` to `V11`, `T1` to `T4`) before lowering. A naked-asm item has no CIR analogue; a static item maps to a CIR constant interned during lowering (`cig-script/src/lower/mod.rs`). Today `cig-compile/src/build.rs` just appends a payload to a pinned runtime (`program::append2`, the trailer in `cig-script/docs/PROGRAMS.md`); stage C grows a second mode that writes an object instead.
- **What would decide it.** Not measured yet: the wall time of lowering all CIR functions in cigo (1,038 functions) in serial against rayon-parallel through Cranelift, on the test machine, against the VM lowering time at the same level (`cig-script/src/lower/mod.rs: DEFAULT_LEVEL`).
- **Feeds.** cig-compile#32, #4; decisions (e), (f).
- **Read.** `rust-1.100.0/compiler/rustc_codegen_cranelift/src/driver/aot.rs` (`AotModule`, `make_module`, `emit_module`, `codegen_cgu`, `compile_cgu`, `AotDriver`, `cached_context`); `rust-1.100.0/compiler/rustc_codegen_cranelift/src/main_shim.rs` (`maybe_create_entry_wrapper`, `create_entry_fn`); `rust-1.100.0/compiler/rustc_codegen_cranelift/src/linkage.rs` (`get_clif_linkage`, `get_static_linkage`); `rust-1.100.0/compiler/rustc_codegen_cranelift/src/debuginfo/mod.rs` (`DebugContext`, `producer`); `rust-1.100.0/compiler/rustc_codegen_cranelift/src/unwind_module.rs` (`UnwindModule`); `object-v0.41.0/src/write/mod.rs` (`Object`); `wasmtime-v50.0.1/cranelift/object/src/backend.rs` (`ObjectModule`); `cig-script/src/lower/cir/verify.rs`; `cig-script/crates/cig-bytecode/src/verify.rs`; `cig-compile/src/build.rs` (`DEFAULT_STAGE`, `append2`); `cig-compile/docs/decisions/0001-backend.md`.

### 2. What rustc_codegen_cranelift delegates to the system linker

- **What it does, and why.** `src/driver/aot.rs` emits one object per codegen unit and nothing else: no archive is built here, no executable is written.
- **No LTO at all.** `WriteBackendMethods::optimize_and_codegen_fat_lto`, `run_thin_lto` and `optimize_and_codegen_thin` all `unreachable!()`. Fat and thin LTO are LLVM's; this backend turns them off upstream of its own entry.
- **No optimize pass.** `WriteBackendMethods::optimize` is empty (`_module: &mut ModuleCodegen<Self::Module>, _config: &ModuleConfig`): Cranelift's own egraph-based optimizer runs inside `compile_fn` through `cranelift_codegen::Context::compile`, not through this trait.
- **The linker runs higher up.** The linker is invoked by the layer above (`rustc_codegen_ssa::back::link`) after all objects are on disk; the backend's only post-codegen step inside this crate is `emit_module` adding a `.comment` section on ELF with the producer string.
- **Not yet supported.** The `Readme.md` lists SIMD and unwinding on panics (outside `-Cpanic=abort`) as not supported, and the "Not yet supported" section notes "`-Cpanic=abort` is enabled by default". The platform support table marks AIX not supported ("XCOFF object file format is not supported").
- **For cig: adapt.** Decided by rule 8 (no memory both writable and executable; reproducible, signable): a system linker invocation is a dependency on the host, which breaks "any machine builds for any other with nothing installed" (cig-compile#41). cig's form: keep the one-object-per-program shape from entry 1 but bring the linker inside (entries 5, 8), so the only thing stage C may need from the host is a C compiler for the system start files on musl Linux (optional, when the runtime archive is built without its own start code).
- **What would decide it.** Decided by rule 8 and cig-compile#41's "any machine builds a program for any other with nothing installed". A measurement is not what the rule turns on.
- **Feeds.** cig-compile#32, #41; decisions (e).
- **Read.** `rust-1.100.0/compiler/rustc_codegen_cranelift/src/driver/aot.rs` (`WriteBackendMethods`, `optimize_and_codegen_fat_lto`, `run_thin_lto`, `optimize_and_codegen_thin`, `optimize`); `rust-1.100.0/compiler/rustc_codegen_cranelift/Readme.md` (`Not yet supported`, `XCOFF`, `Cpanic=abort`); `cig-compile/src/runtime.rs` (`Target`, `Format`, `TARGETS`).

### 3. mold's pipeline, and what a cig program needs of it

- **What it does, and why.** `papers/compilers/mold-design.md` names the design in a line: "fix the layout of an output file as quickly as possible, so that we can start copying actual data from input object files to an output file as soon as possible", with symbol resolution lifted into the preload phase through string interning and `_exit(2)` latency paid in a child while the parent returns. The size-of-the-problem table reports 30,723 object files, 1,428,149 public undefined symbols, 1,579,996 mergeable strings and 9,914,510 comdat groups for a Chrome link; ICF on Chromium is five times faster than lld (5 s to 1 s). The pipeline is in `mold-v3.0.0/src/driver.rs: link`, roughly forty passes through `src/passes.rs` (4,547 lines) and side modules, in order: expand response files, parse non-positional args, read input files, `apply_exclude_libs`, `create_internal_file`, `resolve_symbols`, optional `do_lto`, `remove_unreachable_files`, prepare `.gdb_index` inputs, `parse_eh_frame_sections`, `parse_sframe_sections`, `create_merged_sections`, `convert_common_symbols`, `apply_version_script`, `parse_symbol_version`, `compute_import_export`, `check_duplicate_symbols`, optionally `convert_zero_to_bss`, `compute_address_significance`, section garbage collection if `-gc-sections`, identical-code folding if `-icf`, `create_synthetic_sections`, `check_shlib_undefined`, `check_symbol_types`, `create_output_sections`, `add_synthetic_symbols`, `claim_unresolved_symbols`, `sort_init_fini`, `sort_ctor_dtor`, `fixup_ctors_in_init_array`, `add_dynamic_strings`, `scan_relocations`, `sort_output_sections`, `compute_section_sizes`, optional RELR packing (`chunks/reldyn.rs: construct_relr`), `sort_dynsyms`, `sort_debug_info_sections`, `compute_section_headers`, `set_osec_offsets`, and only then `OutputFile::open` and `copy_chunks`.
- **For cig: adapt.** Decided by rules 1 (burns never move), 8 (reproducible, signable) and 9 (`forbid(unsafe_code)` everywhere but one small crate): mold uses `memmap2` and raw file descriptors which belong in the one audited crate or not at all, and the preload-across-30,000-objects shape is for problems cig does not have. A cig stage C program has two inputs: cig's one runtime archive built once per target and one object cigcompile wrote. Of mold's forty passes it needs symbol resolution across those two, a `create_output_sections` that collects the archive's sections, `scan_relocations`, `compute_section_sizes`, `set_osec_offsets`, `copy_chunks` with relocations applied, and the ELF program header written. Optional: `gc_sections` (entry 4), ICF (entry 4), and `.eh_frame_hdr` (`chunks/eh_frame_hdr.rs`, 57 lines) when stack unwinding is used. Not needed: comdat groups, version scripts, dynamic symbols, `.plt`/`.got` for a statically linked executable, shared-library undefineds, mergeable-string merging across many objects.
- **What would decide it.** Not measured yet: the serial wall time for one object plus the pinned runtime archive to be linked by mold against a prototype embedded linker, on the test machine, on each format.
- **Feeds.** cig-compile#32, #36, #41; decisions (e).
- **Read.** `mold-v3.0.0/src/driver.rs` (`link`, `main`, `apply_exclude_libs`, `resolve_symbols`, `gc_sections`, `icf`, `create_output_sections`, `scan_relocations`, `set_osec_offsets`, `copy_chunks`); `mold-v3.0.0/src/passes.rs` (`create_internal_file`, `create_synthetic_sections`, `add_synthetic_symbols`, `claim_unresolved_symbols`, `scan_relocations`, `compute_section_sizes`, `set_osec_offsets`); `mold-v3.0.0/src/output_file.rs` (`TMPFILE`, `OutputFile`); `mold-v3.0.0/README.md`; `papers/compilers/mold-design.md`; `cig-compile/src/build.rs` (`append2`, `Built`).

### 4. Section garbage collection and identical code folding

- **What it does, and why.** mold's `--gc-sections` (`src/gc_sections.rs`, 312 lines) runs a mark-sweep in parallel: a section is live if it is reached by a relocation from a root. Roots are the entry symbol (named by `--entry`), every section with `SHF_GNU_RETAIN`, every section whose type is `SHT_NOTE`, `SHT_INIT_ARRAY`, `SHT_FINI_ARRAY` or `SHT_PREINIT_ARRAY`, and every section whose name starts with `.ctors`, `.dtors`, `.init` or `.fini` (`src/gc_sections.rs: should_keep`). Sections named as valid C identifiers can be referenced through the linker-synthesized `__start_<name>`/`__stop_<name>` symbols: a reference from live code to those symbols pulls every section of that name into the live set (`build_start_stop_map`, `start_stop_name`). The sweep happens in parallel over files (`sweep`). `--icf` (`src/icf.rs`, 679 lines, "Identical Code Folding") finds pairs of read-only input sections whose contents, flags, exception records and relocations agree, with relocations compared by the identity of their target section under the same equivalence (the file's top comment gives the "A calls C, B calls D" example on lines 20 to 33: A and B are mergeable if and only if C and D are, so the problem is graph isomorphism over labeled graphs); the design document (`papers/compilers/mold-design.md`) reports ICF on Chromium five times faster than lld (5 s to 1 s).
- **For cig: take.** Decided by rule 8 (reproducible, signable: a determined section layout is in the rule's spirit) and cig-compile#36. cig's form: the pinned runtime archive built from cig's crates is compiled with `-ffunction-sections -fdata-sections` (`-Csplit-debuginfo=unpacked -Cembed-bitcode=no` on the rustc side) so every function and every static has its own section; the embedded linker's gc pass marks only what cig-compile's own object reaches. cig's measured per-program needs (`data/size/README.md`): never the command line (2.0 MB), rarely the keyring (1.4 MB), rarely zstd (0.8 MB), rarely the regex engine (0.6 MB), rarely `zbus`/`zvariant`/`secret_service` (1.33 MB together); these are three sections' worth of top-level crate code. ICF is a smaller win because rustc already folds vtables across generics at compile time, but a few functions duplicated across `cig-script/src/vm/` and `cig-script/src/interp/` would fold (both engines together are 223 KB of code: `data/size/report.md`). A dynamic call through a function kept in a map (CIR's `CallValue`) is a root the gc pass must honor, so every stdlib builtin reachable by name must be kept unless cig's lowering proves the name is never computed; this is the "defeats the cut" case.
- **What would decide it.** Not measured yet: the size of `hello` built with the host linker and `--gc-sections` against a cig release that passes `-Clink-arg=-Wl,--gc-sections -Clink-arg=-Wl,--icf=safe` at release time; the 2 MB budget (cig-compile#36) is the threshold.
- **Feeds.** cig-compile#36, #4, #1; decisions (e), (f).
- **Read.** `mold-v3.0.0/src/gc_sections.rs` (`should_keep`, `build_start_stop_map`, `start_stop_name`, `collect_root_set`, `mark_section`, `visit_section`, `sweep`, `gc_sections`, `SHF_GNU_RETAIN`, `SHT_INIT_ARRAY`); `mold-v3.0.0/src/icf.rs` (`icf_sections`); `papers/compilers/mold-design.md`; `data/size/README.md`; `data/size/report.md`; `cig-script/src/lower/cir/ir.rs` (`Kind::CallValue`, `Kind::CallBuiltin`).

### 5. What `object` can write, and what it cannot

- **What it does, and why.** `object-v0.41.0/README.md` states the surface: raw structs for zero-copy reading; a unified `write::Object` for writing relocatable object files in COFF, ELF, Mach-O, XCOFF and GOFF; and low-level writers for ELF, PE and COFF that write both relocatable and executable files.
- **The unified model.** `src/write/mod.rs` (`Object`, 1,231 lines) carries it: `BinaryFormat`, `Architecture`, `sections: Vec<Section>`, `standard_sections: HashMap<StandardSection, SectionId>`, `symbols`, `symbol_map`, and `Object::write` which dispatches to the format writer; its module doc says "This does not support writing executable files."
- **PE.** `src/write/pe.rs` (`Writer`, 858 lines) is a two-phase approach: "reserves file ranges and virtual address ranges for everything in the order that they will be written", then "writes everything out in order". `NtHeaders`, `Section`, `SectionRange` and the DOS stub are all written through it. Executable PE is in scope.
- **ELF.** `src/write/elf/writer.rs` (`Writer`, `Mode`, `SinglePhase`, `TwoPhase`, 2,143 lines) exposes a sealed `Mode` trait for reserve-then-write or write-as-you-go. Both modes take the file-header type as an input (`Writer::write_file_header(&FileHeader)` at line 283), and the caller sets `FileHeader::e_type` to one of `ET_REL`, `ET_EXEC` or `ET_DYN`, so executable ELF is in scope under either mode.
- **Mach-O.** `src/write/macho/` is relocatable object only (925 lines of `object.rs` plus 1,003 lines of `encoder.rs`). An executable Mach-O load-command set is not written here.
- **COFF.** `src/write/coff/{object.rs, writer.rs}` (817 and 559 lines) covers relocatable COFF. An executable COFF is not what this writes; PE is where a linked image on Windows lives.
- **ELF rewriting.** The crate's own `README.md` advertises a "higher level builder for ELF (`crates/rewrite/src`)" for whole-ELF editing, useful for the reserved-section-in-a-PIE-runtime route entry 8 names.
- **For cig: adapt.** Decided by rule 9: writing bytes is where `object` is `safe`; cig's embedded linker uses `write::elf::writer::Writer` and `write::pe::Writer` for ELF and PE executables; for Mach-O it must write its own mach header and load commands, because `object` writes only relocatable Mach-O, or carry one small Mach-O writer in the same audited crate. The two-phase shape maps onto cig's shape: a reserve pass over the archive's live chunks fixes every file and virtual offset, then one copy pass writes the bytes. cig's form: a new crate cig-linker inside cig-compile (planned; decision (e)) owns the three writers over `object`.
- **What would decide it.** Not measured yet: on the test machine, the lines of code needed to make `cig-linker` write a 2 MB static ELF, a 2 MB PE and a 2 MB Mach-O from the archive-plus-object input, counted after the first working build.

### 6. Relocations across ELF, Mach-O and PE: what the generator emits

- **What it does, and why.** Cranelift emits relocations at a function-local resolution through `cranelift_module`: a function body refers to another function by `FuncRef` and to a static by `DataId`, and the `Module` (here `ObjectModule` under `UnwindModule`) turns those into object-file relocations when the function is "defined". On ELF and Mach-O the generator emits PC-relative relocations for call sites (`R_X86_64_PLT32` for x86_64 or the Mach-O equivalent `X86_64_RELOC_BRANCH`) and for data addresses a GOT-relative or direct form depending on `-Cmodel`; on PE the generator emits `IMAGE_REL_AMD64_REL32` for a call and `IMAGE_REL_AMD64_ADDR32NB` for a static. `rustc_codegen_cranelift/src/debuginfo/emit.rs: DebugReloc` and `DebugRelocName` (218 lines) collect the DWARF-side relocations needed because `.debug_line` and `.eh_frame` refer to code and data the same way. The object crate accepts these through its `RelocationEncoding`, `RelocationFlags` and `RelocationKind` enums (visible in `src/write/mod.rs`).
- **For cig: take.** Decided by rule 8: the three formats have different relocation types for the same meaning, and cig's embedded linker must know them to turn an object cigcompile wrote into a linked image. cig's form: cig's embedded linker carries a per-format table that maps Cranelift's `Reloc` to the format's constant and applies it on the output buffer: on ELF `R_X86_64_PC32`, `R_X86_64_PLT32`, `R_X86_64_GOTPCREL`, `R_AARCH64_CALL26`; on Mach-O `X86_64_RELOC_BRANCH`, `X86_64_RELOC_GOT_LOAD`, `ARM64_RELOC_BRANCH26`; on PE `IMAGE_REL_AMD64_REL32`, `IMAGE_REL_AMD64_ADDR32NB`, `IMAGE_REL_ARM64_BRANCH26`. mold's `src/passes.rs: scan_relocations` and the format-specific files under `src/chunks/reloc.rs` (185 lines) are the model for how a relocation is resolved (entry 3).
- **What would decide it.** Not measured yet: on the test machine, the number of distinct relocation types Cranelift emits for cigo lowered through stage C, by target format, counted from the generated object.

### 7. The alternative with no linker at all: Wasmtime's image

- **What it does, and why.** The shape: Wasmtime compiles a `.wasm` module to a native image that it maps and runs, not an executable object the operating system's loader reads.
- **How debuggers see it.** The "precompiled modules" shape (`wasmtime-v50.0.1/crates/jit-debug/src/gdb_jit_int.rs: JITDescriptor`, `JITCodeEntry`) uses GDB's JIT compilation interface to register the memory region as debug info, and a GDB-side reader parses the ELF-shaped blob there: this is one in-memory layout of a linked image, written at run time, not a file.
- **The analogue for a cig program.** Emit the native code and relocations into cig's payload as a signed section and let cig's runtime map them at start-up, so the operating system's linker never runs on the program itself. The code's memory is signed and mapped read-and-execute by the runtime after verification; writable-and-executable memory is never needed.
- **The cost.** The operating system's loader is what Developer ID and Authenticode cover, so a run-time map-and-execute image gives up the operating system's signature check in return for freeing stage C from writing a real ELF, Mach-O or PE; the memory the image uses must still obey rule 8 (read-and-execute after verification, never writable-and-executable).
- **For cig: reject.** Decided by rule 8 (no memory both writable and executable). A run-time map-and-execute is what this shape is for; a program that is not a file the loader can map is not a file the system can sign with Developer ID or Authenticode (`cig-compile/src/sign.rs` and PROGRAMS.md on signing: `--sign` needs a real file). cig's form: the stage C program stays a real ELF/Mach-O/PE executable the operating system maps, as entry 5's writers emit. What cig takes from this is nothing for stage C; for cig-cherry (cig-script#256), the gdb JIT interface and perf's jitdump (entry 14) register run-time code so a debugger or profiler sees it by name, and that is the shape it is for.
- **What would decide it.** Decided by rule 8.
- **Feeds.** cig-compile#32.
- **Read.** `wasmtime-v50.0.1/crates/jit-debug/src/gdb_jit_int.rs` (`JITDescriptor`, `JITCodeEntry`, `versioned_link`); `wasmtime-v50.0.1/crates/jit-debug/src/perf_jitdump.rs`; `cig-compile/src/sign.rs` (`NAMESPACE`, `path_for`, `precheck_signer`); `cig-script/docs/PROGRAMS.md`.

### 8. A third way: the runtime as a position-independent executable with a reserved code section

- **What it does, and why.** The runtime's shape: cig's stage A puts the whole runtime in the image and appends a payload (`cig-script/docs/PROGRAMS.md`, format 2). A natural extension at stage C is to keep the runtime as a position-independent executable, built with `-fPIE` and full RELRO (`mold-v3.0.0/src/cmdline.rs: pie`, `z_relro`, line 137 and 225 of the help text).
- **The reserved sections.** Reserve one `.text.cigprog` section big enough to hold the compiled code for the program's functions, plus a `.rodata.cigprog` for their constant pools, both in the ELF/Mach-O/PE image at release time.
- **The patch pass.** cigcompile writes the compiled object into that reserved section (one run over the pre-signed runtime: write the section bytes, apply the few relocations from the section into the runtime, record the section's SHA-256 in the trailer, sign), with no system linker involvement at build time. The runtime maps and verifies the signed sections at start-up through its loader (`cig-script/src/burn/modcache.rs` has the kept-modules model today).
- **For cig: adapt.** Decided by rule 7 (verified bytecode, never rewritten at run time) and rule 8: the reserved sections are read-only after the start-up check, so the rules hold. cig's form: `cig-compile/docs/decisions/0001-backend.md` (line 64, "Signing appended data") names the problem that macOS code signatures and Windows Authenticode do not cover bytes appended after signing, and records the plan: the Mach-O route puts the payload in a Mach-O section (so the signature covers it), while the PE route appends the payload before Authenticode signs (so the payload sits inside the signed image's content range). The reserved-section-in-a-PIE-runtime idea generalises the Mach-O route to a real section of the ELF, Mach-O or PE image, which the operating system's signature then covers end to end. The cost: a stage C program carries the runtime's full code image, so size is the runtime's size (entry 9). The gain: no system linker on any machine.
- **What would decide it.** Not measured yet: on the test machine, the smallest PIE runtime with reserved sections that holds cig's code and leaves room for 1 MB of compiled program code, compared with a from-scratch linked executable built by `object`'s ELF writer (entry 5).
- **Feeds.** cig-compile#32, #40, #41.
- **Read.** `cig-script/docs/PROGRAMS.md`; `cig-compile/docs/decisions/0001-backend.md`; `cig-compile/src/sign.rs` (`NAMESPACE`); `mold-v3.0.0/src/cmdline.rs` (`pie`, `z_now`, `z_relro`); `mold-v3.0.0/src/chunks/relro_padding.rs` (`new_header`, `is_relro`).

### 10. ThinLTO: whole-program optimization while modules still compile in parallel

- **What it does, and why.** `clang/docs/ThinLTO.md` describes the shape: in the compile phase, each translation unit emits LLVM bitcode plus a compact per-module summary; in the thin link phase, only the summaries are read and merged into a combined summary index that holds a cross-module function-location index for later importing; whole-program analysis (`WPA`) is performed on this combined summary without ever parsing or loading any IR; all transformations are deferred to parallel backends that each read their module and the functions imported into it. The paper (`papers/compilers/johnson-2017-thinlto.pdf`) says: "ThinLTO aims to be as scalable as a regular non-LTO build" and "CMO is applied during fully parallel optimization backends". `llvm/lib/LTO/LTO.cpp` (2,401 lines) is the implementation point; the "thin link" step reads a `BitcodeFileContents` plus summaries and emits a `ThinLTOCodeGenerator` plan.
- **What a module summary holds.** `llvm/include/llvm/IR/ModuleSummaryIndex.h` (2,186 lines) defines it: a `GlobalValueSummary` (`SummaryKind` of `AliasKind`, `FunctionKind` or `GlobalVarKind`) with `GVFlags` (linkage, visibility, `NotEligibleToImport`, live, DSO-local) and an `ImportKind` (`Definition` or `Declaration`). A `FunctionSummary` adds `InstCount` (an instruction count), `FFlags` (readnone, readonly, noRecurse, returnDoesNotAlias, etc.), `CallGraphEdgeList: SmallVector<EdgeTy>` where `EdgeTy = pair<ValueInfo, CalleeInfo>` and `CalleeInfo` carries a hotness value (`Unknown`, `Cold`, `None`, `Hot`, `Critical`), `TypeIdInfo` with `VFuncId { GUID, Offset }` and `ConstVCall { VFunc, Args }` for virtual-call promotion, and an optional parameter-access list. A `GlobalVarSummary` records constness and `WriteOnly`/`ReadOnly` summary bits. `TypeIdSummary` carries a `TypeTestResolution` and a `WPDRes` map from byte offset to whole-program-devirt resolution. A combined index also holds `TypeIdCompatibleVtableMap`, a `std::map<StringRef, TypeIdCompatibleVtableInfo>` where `TypeIdCompatibleVtableInfo = vector<TypeIdOffsetVtableInfo>` and each `TypeIdOffsetVtableInfo` is `{ Offset: u64, ValueInfo }`. Module paths are keyed by a `ModuleHash = array<uint32_t, 5>` (a 160-bit module hash). For cig, this is more structure than cig's own summaries need: cig has no virtual calls, no vtables and no C++-style type IDs; what cig would carry in a summary is the `CallGraphEdgeList` (CIR callees), an instruction count equivalent, and the `Pure`/`MayRaise`/`Effect`/`Step` class of each function, keyed by the lowered module's own hash.
- **For cig: adapt.** Decided by rule 5 and rule 7: cross-module inlining must preserve the step budget and the error span exactly, so what cig takes is the three-phase shape (compile with summary, thin link over summaries, parallel backends) and not the IR representation. cig's form: a module summary is a small per-function record emitted by cig's lowering (entry point, calls it makes, builtins it uses, whether it is `Pure`, sizes), and the thin link pass picks a few short functions to import across modules; the backend is Cranelift (entry 1). This matters more at cig-cherry (cig-script#256) than at stage C, because cig's programs are much smaller than a Chrome link (mold-design: 30,723 objects for Chrome; one object for a cig program): inlining is cheap in absolute terms, and a summary is a small file per module.
- **What would decide it.** Not measured yet: on the test machine, the size of a per-module summary for cigo's 1,038 functions (`data/census/README.md`) compared with the lowered-module bytes.
- **Feeds.** cig-compile#32, #33 (the optimiser), #37 (build speed).
- **Read.** `llvm-project-llvmorg-23.1.6/clang/docs/ThinLTO.md` (`Introduction`, `Current Status`, `Usage`, `Controlling Backend Parallelism`); `papers/compilers/johnson-2017-thinlto.pdf`; `llvm-project-llvmorg-23.1.6/llvm/lib/LTO/LTO.cpp`; `llvm-project-llvmorg-23.1.6/llvm/include/llvm/IR/ModuleSummaryIndex.h` (`GlobalValueSummary`, `GVFlags`, `ImportKind`, `FunctionSummary`, `EdgeTy`, `CalleeInfo`, `TypeIdInfo`, `GlobalVarSummary`, `AliasSummary`, `TypeIdSummary`, `TypeIdCompatibleVtableInfo`, `TypeIdOffsetVtableInfo`, `ModuleHash`, `ModuleSummaryIndex`).

### 14. perf maps and perf jitdump for code made at run time

- **What it does, and why.** `wasmtime-v50.0.1/crates/jit-debug/src/perf_jitdump.rs` implements the Linux kernel's jitdump format: a `RecordHeader { id, record_size, timestamp }` followed by one of five `RecordId` values: `JitCodeLoad = 0` (a new function's address, size, name, bytes), `JitCodeMove = 1` (a function relocated), `JitCodeDebugInfo = 2` (line table entries for a function, address to source), `JitCodeClose = 3` (the end of the run), `JitCodeUnwindingInfo = 4` (`.eh_frame` for a function). The kernel specification referenced from the file's top is `linux/tools/perf/Documentation/jitdump-specification.txt`; Wasmtime's `docs/examples-profiling-perf.md` describes the two levels: a simple perf map `/tmp/perf-<pid>.map` with one line per function (`<addr> <size> <symbol>`), which `perf` reads automatically when it encounters unresolved symbols, and the detailed jitdump a `perf inject -j -i perf.data -o perf.jit.data` consumes to resolve source positions and unwind JITted frames. `src/gdb_jit_int.rs` implements GDB's JIT interface with `JITCodeEntry` and `JITDescriptor` structs the debugger reads; the `__jit_debug_descriptor` symbol and `__jit_debug_register_code` function are what GDB's JIT reader looks for, with `JIT_NOACTION = 0`, `JIT_REGISTER_FN = 1`, `JIT_UNREGISTER_FN = 2` as the three actions, and a doubly linked list of `JITCodeEntry` structs each pointing at an ELF-shaped blob in memory.
- **For cig: take.** Decided by rule 8 (no memory both writable and executable) only in part: a stage C program is ahead-of-time and has no JIT, so its symbols are already in the ELF/Mach-O/PE symbol table and perf sees them without help. cig-cherry (cig-script#256) does make native code at run time and needs both the perf map (for `perf top`) and the jitdump (for `perf record -k 1 -j`); the memory is signed and mapped read-and-execute, so rule 8 holds. cig's form: cig-cherry writes `/tmp/perf-<pid>.map` with one line per compiled CigScript function, naming the function by its pull name (`<file>:<line>:<name>`), and when `CIG_JITDUMP=1` is set it opens a jitdump file and emits `JitCodeLoad` records for each function it compiles, with DWARF line info from the same `gimli` line program entry 12 builds, and `JitCodeUnwindingInfo` records from the same `gimli` frame table entry 13 builds. The GDB interface is left to a second step; the jitdump route serves `perf` and matches how a profiler already works.
- **What would decide it.** Not measured yet: on the test machine, the overhead of writing a jitdump record per compiled cig-cherry function against a bare native compile.
- **Feeds.** cig-compile#38, cig-script#256.

### 15. Cranelift's hardening settings

- **What it does, and why.** Shared settings: `wasmtime-v50.0.1/cranelift/codegen/meta/src/shared/settings.rs` defines what every ISA inherits.
- **`preserve_frame_pointers`.** Line 226: "Preserving frame pointers ... makes it easy to capture the stack of a running program ... Many sampling profilers and similar tools walk frame pointers to capture stacks." Off by default.
- **Stack probes.** `enable_probestack` (256, "Enable the use of stack probes for supported calling conventions"); `probestack_size_log2` (263, default 12, so the guard region is 4096 bytes); `probestack_strategy` (275, `outline` or `inline`). Rust uses these to defeat large-stack-frame overflows past the guard region.
- **Spectre mitigation.** `enable_heap_access_spectre_mitigation` (290, on by default: "Enable Spectre mitigation on heap bounds checks"; "This is a no-op for any heap that needs no bounds checks"); `enable_table_access_spectre_mitigation` (305, on by default: "This option uses a conditional move to ensure that when a table access index is bounds-checked and a conditional branch is used for the out-of-bounds case, a misspeculation of that conditional branch (falsely predicted in-bounds) will select an in-bounds index to load on the speculative path"). Both are on by default in Cranelift, so Wasmtime's embedder picks them up for free.
- **ARM64 settings.** `meta/src/isa/arm64.rs`: `has_pauth` (14, pointer authentication, off by default), `sign_return_address_all` (44), `sign_return_address` (51, "Use pointer authentication instructions to sign function return addresses; HINT-space instructions using the A key"), `sign_return_address_with_bkey` (60), `use_bti` (68, "Use Branch Target Identification (FEAT_BTI) instructions"), `use_csdb` (74, Spectre `csdb`).

### 16. CFI, SafeStack and ShadowCallStack: what each protects and what each costs

- **What it does, and why.** What CFI is: `clang/docs/ControlFlowIntegrity.rst` lists the schemes: `cfi-cast-strict`, `cfi-derived-cast`, `cfi-unrelated-cast`, `cfi-nvcall`, `cfi-vcall`, `cfi-icall`, `cfi-mfcall`. All except `kcfi` require LTO (`-flto` or `-flto=thin`), and the compiler produces a check for a class only when it can infer hidden LTO visibility.
- **What it costs.** On virtual calls, `-fsanitize=cfi-vcall` reports less than 1% overhead on the Dromaeo benchmark suite against an instrumented Chromium and "up to 15%" binary-size increase. Bad-cast checks and non-virtual call checks have similar performance characteristics.
- **SafeStack.** `clang/docs/SafeStack.md` separates the stack into a safe stack (return addresses, register spills, always-safely-accessed locals) and an unsafe stack (everything else); the stated overhead is less than 0.1% on average, "mostly because most small functions do not have any variables that require the unsafe stack". Linking a DSO with SafeStack is not currently supported.
- **ShadowCallStack.** `clang/docs/ShadowCallStack.md` saves a return address to a separately allocated stack in the prolog and loads it in the epilog; "currently only implemented for aarch64, RISC-V and Hexagon"; it uses `x18` on AArch64, `x3`/`gp` on RISC-V; the x86_64 implementation was removed in LLVM 9 for "critical performance and security deficiencies". A runtime is required and must be provided by the application or the operating system.
- **For cig: adapt.** Decided by rule 9 (`forbid(unsafe_code)` everywhere but one small crate) and the measured facts: cig's compiled code is Rust-shaped, so the unsafe-stack buffers CFI and SafeStack most strongly protect C code from do not apply to it in the same way. What cig takes is backward-edge CFI (PAC-RET on aarch64, entry 15; CET shadow stack on x86_64 from the operating system's hardware when the runtime opts in through the `GNU_PROPERTY` note), because it protects every function cig makes. SafeStack is not worth adding over Rust's stack probes (`enable_probestack`, entry 15), which already defeat stack-buffer-overflow writes beyond a guard region; and SafeStack's documentation says DSOs are not currently supported (`clang/docs/SafeStack.md: Compatibility`). ShadowCallStack is not applicable on x86_64 at all; on aarch64 it is subsumed by PAC-RET through `sign_return_address` (entry 15).
- **What would decide it.** Not measured yet: on the test machine and on an aarch64 machine, the `-fsanitize=cfi` and `-fsanitize=shadow-call-stack` overhead on cig's C dependencies (`zstd` is C: `data/size/README.md` names it 821,181 bytes of code).
- **Feeds.** cig-compile#40.
- **Read.** `llvm-project-llvmorg-23.1.6/clang/docs/ControlFlowIntegrity.rst` (`cfi-vcall`, `cfi-nvcall`, `cfi-icall`, `cfi-mfcall`, `Forward-Edge CFI for Virtual Calls`, `Performance`); `llvm-project-llvmorg-23.1.6/clang/docs/SafeStack.md` (`safe stack`, `unsafe stack`, `Compatibility`); `llvm-project-llvmorg-23.1.6/clang/docs/ShadowCallStack.md` (`shadow call stack`, `SCSReg`, `x18`, `Zicfiss`); `llvm-project-llvmorg-23.1.6/clang/docs/ControlFlowIntegrityDesign.rst`.

### 17. PIE and full RELRO: a linker-side hardening pair

- **What it does, and why.** What the flags are: `mold-v3.0.0/src/cmdline.rs` lists them: `--pie, --pic-executable` (136) to create a position-independent executable, `-z relro` (225) to make some sections read-only after relocation (default) and `-z norelro` to turn it off; `z_now` resolves all dynamic relocations at load (the struct field is declared on line 498 and the assignment `a.z_now = value;` is on line 1615).
- **What the defaults are.** `pic` and `pie` (603, 604) default to false, `z_now` defaults to false, `z_relro` defaults to true. Static-pie turns `z_now` on by necessity because there are no runtime-resolved dynamic relocations to defer.
- **Why `.relro_padding` exists.** `src/chunks/relro_padding.rs` is the chunk that pads the RELRO segment up to a page boundary (`is_relro = true`, `SHT_NOBITS`, `SHF_ALLOC | SHF_WRITE`), because `PT_GNU_RELRO` works on page granularity. Without it, the end of the RELRO region can straddle a page and part of the writable segment would be covered too.
- **Where the aarch64 flags come in.** On aarch64, mold's cmdline reads `use_bti` and `force-ibt`/`force-bti` through the `-z` family that `read_z_flag` parses (line 1637 for `relro`, 1639 for `norelro`).
- **For cig: take.** Decided by rule 8. cig's form: the pinned runtime is built as a static PIE (`-C relocation-model=pic`, `-C link-arg=-Wl,-z,relro -C link-arg=-Wl,-z,now`), and cigcompile applies the same to the executable it writes through its embedded linker (entry 5); the writer emits a `PT_GNU_RELRO` program header covering the segment that holds `.data.rel.ro`, `.got`, `.got.plt`, with one page of `.relro_padding` so the end aligns to a page. On static-pie the `z_now` default is on because there are no runtime-resolved dynamic relocations (the mold doc comment in `relro_padding.rs` names that case). cig-compile#40 names "PIE, full RELRO / bind-now, non-executable stack and data (`PT_GNU_STACK` RW)"; cig's embedded linker writes these as mold does.
- **What would decide it.** Not measured yet: on the test machine, the increase in `hello.cig`'s size and start-up with PIE and full RELRO against without; the figure in cig-compile#36 is the budget.

### 19. Zig's bootstrap: a WebAssembly image of the compiler translated to C

- **What it does, and why.** The path: `zig-0.17.1/bootstrap.c` (248 lines) is a plain C program that, when built with any C compiler, produces `zig-wasm2c` (a WebAssembly-to-C translator compiled from `stage1/wasm2c.c`), then runs it on the checked-in `stage1/zig1.wasm` to produce `zig1.c`, then compiles `zig1.c` with `stage1/wasi.c` as a WASI shim to a small `zig1` executable.
- **The self-compile.** `zig1` is then invoked as `./zig1 lib build-exe -ofmt=c -lc -OReleaseSmall --name zig2 -femit-bin=zig2.c -target <host_triple> --dep build_options -Mroot=src/main.zig -Mbuild_options=config.zig` (lines 198 to 206) to translate the real Zig compiler's source (`src/main.zig`) to C, which `cc` then compiles to the real `zig2`.
- **The translator.** `stage1/wasm2c.c` turns WebAssembly functions into C functions one at a time; the `#define EXTRA_BRACES 0` on line 1 gates structural braces around blocks.
- **GCC bug worked around in the bootstrap.** `bootstrap.c` carries workarounds for GCC bug 119085 (a miscompilation in GCC 10 to 15.1 that would relocate function calls incorrectly) and GCC bug 94081 (false-positive `-Waddress-of-packed-member` warnings), with `-fno-tree-sra` and `-Wno-address-of-packed-member` applied by the detected version of GCC. This is the cost of bootstrapping through C: every bug in every compiler used must be avoided or hidden.
- **For cig: adapt.** Decided by cig-compile#17 (self-hosting). cig's form: cig itself is written in Rust today, and the self-hosting plan (cig-compile#17) names "Stage 0: the Rust CigCompile (kept forever as the bootstrap). Stage 1: CigCompile rewritten in CigarScript, compiled by stage 0". What Zig gives cig is a route for a machine that does not have Rust: a checked-in "stage 1 of cig compiled by cigcompile to a stable form (a stored CIR module, or a stored program the Rust cig can run)". The analogue of `zig1.wasm` for cig is a stored, verified bytecode module of cigcompile itself (format 2's `bytecode` section, cig-script/docs/PROGRAMS.md), which a machine with only Rust can bootstrap from by running cig; a machine without Rust is not a cig target today (`cig-compile/src/runtime.rs: TARGETS`), so the problem is narrower than Zig's. The lesson is the invariant: a bootstrap is stored, checked, and reproduced, and the compiler it builds should rebuild the same checked form.
- **What would decide it.** Not measured yet: on the test machine, the size of a verified-bytecode form of cigcompile compared with `zig1.wasm` (which is in the tree, named by path `stage1/zig1.wasm`).

### 20. A staged bootstrap, and diverse double-compiling as its check

- **What it does, and why.** rustc's bootstrap paradox is written out in `src/doc/rustc-dev-guide/src/building/bootstrapping/intro.md` ("where did the first compiler come from? It must have been written in a different language. In Rust's case, it was written in OCaml ... However, it was abandoned long ago, and the only way to build a modern version of rustc is with a slightly less modern version"). `what-bootstrapping-does.md` gives the four stages: stage 0 is the pre-compiled compiler and standard library; stage 1 is current code built by stage 0; stage 2 is "the truly current compiler"; stage 3 is "the same-result test" (stage 3 is built from stage 2 and must match it byte for byte, so nothing of stage 0 leaks through). `src/bootstrap/README.md` describes the build system: "Each time bootstrap is invoked, it will iterate through the list of predefined steps and execute each serially in turn if it matches the paths passed or is a default rule"; the stage 0 compiler compiles the stage 1 compiler, which builds the stage 1 standard library, then the stage 2 compiler. The invariant "stage 2 equals stage 3" rules out any carry-over from stage 0, but it does not rule out a compiler whose stage 0 was itself maliciously built. `papers/compilers/wheeler-2009-ddc.pdf` (Wheeler's 2009 dissertation) names Ken Thompson's "Reflections on Trusting Trust" attack and turns the stage invariant into a check against it through Diverse Double-Compiling: build the source once with the compiler being checked and once with a second, independent compiler, then compile the first output with the first output and compare to the second output compiled with the first output; if they agree, the compiler produces an executable that corresponds to its source. Wheeler demonstrates this on a small C compiler, a small Lisp compiler and a small [third] compiler, and on GCC. Go's switch is in `papers/compilers/go-go15bootstrap.html`: Go 1.5 onwards requires Go 1.4 as the bootstrap compiler, and the invariant is the same (step 2 builds the Go 1.x compiler with Go 1.4, step 3 rebuilds it with itself).
- **For cig: take.** Decided by rule 8 (reproducible, signable). cig's form: cig-compile#17 names stage 0 (Rust cigcompile), stage 1 (cigcompile rewritten in CigarScript, compiled by stage 0), stage 2 (stage 1 compiling the same source), stage 3 (stage 2 compiling the same source), and "stage 2 and 3 must be byte-identical". cig-compile#17 also names DDC directly: "also build stage 1 with a second, independent path (stage 0 built by a different Rust toolchain version) and check the results converge to the same stage 2". On CI, that is two Rust toolchains (a stable and a MSRV, or two different stable releases) building stage 0, then each stage 0 building stage 1, then each stage 1 building stage 2; the two stage-2 binaries must match. Reproducibility (cig-compile#9) is the precondition. The bootstrap toolchain is one previous cig, not a downloaded binary of unknown provenance, because cig-compile fetches the runtime by hash (entry 18). The cost is CI time: two full toolchains build.
- **What would decide it.** Decided by rule 8 and cig-compile#17's "stage 2 and 3 must be byte-identical".
- **Feeds.** cig-compile#17, #9 (reproducible).
- **Read.** `rust-1.100.0/src/doc/rustc-dev-guide/src/building/bootstrapping/intro.md`; `rust-1.100.0/src/doc/rustc-dev-guide/src/building/bootstrapping/what-bootstrapping-does.md`; `rust-1.100.0/src/doc/rustc-dev-guide/src/building/bootstrapping/how-bootstrap-does-it.md`; `rust-1.100.0/src/bootstrap/README.md`; `rust-1.100.0/src/doc/rustc-dev-guide/src/building/bootstrapping/debugging-bootstrap.md`; `papers/compilers/wheeler-2009-ddc.pdf`; `papers/compilers/go-go15bootstrap.html`; `cig-script/docs/PROGRAMS.md`; `cig-compile/docs/decisions/0001-backend.md`.

## Not settled

- **Cranelift's `x64` CET IBT.** `cranelift/codegen/src/isa/x64/settings.rs` is one `include!` of the generated `settings-x86.rs` and no further x64 hardening settings are visible in the clone; whether current Cranelift emits `endbr64` landing pads at indirect-call targets, or leaves that to the host linker's `-z force-ibt`, is not visible from the files read. Settled by: reading `cranelift/codegen/src/isa/x64/inst/emit.rs` and the generated `settings-x86.rs` for a `use_cet_ibt` or an `endbr64` instruction encoding, or the Cranelift changelog at this pin.
- **Mach-O linked executable through `object`.** `object-v0.41.0/src/write/macho/` holds the relocatable-object writer; a linked Mach-O (segment-and-section layout, LC_LOAD_DYLINKER, LC_MAIN) is not visible in the Mach-O write side at this pin. Settled by: reading the full `src/write/macho/encoder.rs` for load-command emission, or finding one in another consumer's code at this pin.
- **PE Authenticode with an embedded payload.** `cig-compile/docs/decisions/0001-backend.md` (line 64) names the appended-bytes caveat and records its planned route for PE ("appends before Authenticode signs"); the reserved-section shape in entry 8 is a different shape, not a measurement at this pin. Settled by: a prototype PE built with the reserved-section layout and `signtool` output on it.
- **The LSDA format for cig's `Try`/`Throw` personality.** Entry 13 says `rust_eh_personality` is wrong and a `cig_eh_personality` with a cig-specific LSDA is needed; the exact encoding (what fields the LSDA carries for open burns and the step budget) is design work, not reading, and is left to cig-compile#38's implementation.
- **cig's analogue of `zig1.wasm`.** Entry 19's "a stored, verified bytecode form of cigcompile" is a route, not a specification; the question of whether it is a format-2 program carrying its own bytecode, or a free-standing bytecode module, is left to cig-compile#17's implementation.
- **Cranelift's PE image writer.** `object-v0.41.0/src/write/pe.rs` writes a linked PE in a two-phase reserve-then-write shape (entry 5), but how Cranelift's `cranelift-object` layer hands relocations to the PE writer specifically (as against ELF or Mach-O) is not visible in `rustc_codegen_cranelift/src/driver/aot.rs`, which uses the unified `ObjectBuilder` only. Settled by: reading `wasmtime-v50.0.1/cranelift/object/src/backend.rs` for the format-specific side of `ObjectModule::finish`; the file was read for entry 1 but only its `ObjectModule` shape was followed, not its relocation handoff per format.
- **Mach-O linked-executable load-command set.** Entry 5's "`object` writes only relocatable Mach-O" leaves open which load commands a stage C program's Mach-O carries (`LC_SEGMENT_64`, `LC_LOAD_DYLINKER`, `LC_MAIN`, `LC_CODE_SIGNATURE`, `LC_UUID`, `LC_BUILD_VERSION`, `LC_LOAD_DYLIB` for `libSystem.B.dylib`). Settled by: a hand-built minimal Mach-O against the one `codesign` and the loader require on macOS 15, cross-checked against the Darwin ABI reference.
