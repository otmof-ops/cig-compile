## What cig should carry away

- A whole-program compiler shifts work from the call to the compiler: in MLton the chain is five intermediate languages (XML, SXML, SSA, SSA2, RSSA), each dropping a feature (polymorphism, higher-order functions, high-level types); by the time optimization starts in SSA the program is first-order and simply typed and a traditional dataflow pass is enough (entries 1, 2). cig today compiles one script at a time: a cig program is one `.cig` file plus the pinned runtime, and imports of other `.cig` files are on the roadmap, not built (`cig-script/docs/DESIGN.md` lines 106 and 179 name cartons and imports as roadmap items). In that sense the lowering already sees every function the script defines, so a whole-program analysis is feasible today for one script; once imports land, the trade shifts. The lesson is that dropping polymorphism and closures *before* optimization is MLton's compile-time trade; cig has no polymorphism and only one open form of closure (an indirect call through a value), so entries 3, 4 and 5 are the three analogs.
- MLton represents a function as a value of a tagged sum, not as a code pointer and environment; a call is a case over the tag followed by a direct call per arm, so a call through a value stays direct whenever 0CFA identified a small set of functions it could be (entries 4, 5). cig's `V10` already says that a function is made at one place at most, which is stronger than MLton's analysis per creation site but weaker than MLton's analysis per call site: a function stored in a map, passed as a callback or carried by a `ForEach`'s iterator leaves `V10`'s guarantee and cig has no analog of 0CFA today (entry 5). A control-flow analysis over CIR that records the set of `FuncId`s each `CallValue` could reach is the shape cig would add to turn `Kind::CallValue` into `Kind::CallUser` where it can.
- MLton's first-order simplification is a long list of small passes named in `ssaPassesDefault`, each doing one thing to one invariant (contification, flattening in three variants, useless-component removal, packed representation, `simplifyTypes`) and each run in a defined order (entries 6, 7, 8, 9). cig's pass list has four passes today (`fold-consts`, `copy-prop`, `sccp`, `dead-pure` in `cig-script/src/lower/cir/pass/mod.rs`) and will need the scale MLton has; the sequence worth taking first is `useless` (dead-field removal through a dependence graph) and `flatten` (a tuple at every use site is passed flat), because together they close the record-of-fields path the census measures as dominant in compute code (entries 8, 9).
- Worker and wrapper (`compiler/GHC/Core/Opt/WorkWrap.hs`) is a *split*: a strict argument's `case` unwrapping moves into the wrapper and the worker takes the unboxed component; the wrapper is always inlined, so a caller reaches the worker directly whenever the argument is already evaluated (entries 10, 11). cig is a strict language already; the demand analysis GHC runs (`GHC/Core/Opt/DmdAnal.hs`) is what justifies the split in a lazy language and does *not* justify it in a strict one. In cig the split is justified by types: if an argument has `Ty::Int` at every call site the worker takes `i64`, the wrapper boxes for the one site that passes `Ty::Dynamic` (entry 11). CPR (`compiler/GHC/Core/Opt/CprAnal.hs`) is the symmetric split on results (entry 12).
- GHC unboxes a value into *multiple* machine values at STG time through `Unarise`: `(# Int, Int #)` becomes two arguments and a function like `Int -> (# Int, Int #)` returns two registers (entries 13, 14). cig's value is 24 bytes and `Ty::Int` is a boxed `i64` today; a stage-D worker returning `(Int, Status)` or a hot loop variable of type `Int` fits the unarisation idea exactly, and the census shows that 226 of 227 arithmetic-and-comparison sites in the 21 compute programs saw one operand-type pair (`data/census/README.md`: 28,190,255 of 28,864,733 executions, 97.7 percent), so the worker's domain is settled in practice; the arithmetic-only execution count (`data/census/README.md`: 23,984,719) sits inside that same figure.
- Specialization has two forms: `SpecConstr.hs` (specialize a loop for the data constructor it is called with, bounded by `-fspec-constr-recursive` and `-fspec-constr-count`) and `Specialise.hs` (specialize a polymorphic function per type-class dictionary); the second is the type-directed analog and maps directly to cig's planned monomorphization limit (entries 14, 15). The bounds on both are the discipline worth taking: a polynomial per site, a recursive limit, and a fall-back to the general version (entry 15).
- MLton's SSA simplifier runs a long sequence of passes in a *named order* kept in one file (`mlton/ssa/simplify.fun`'s `ssaPassesDefault`); `contify` is scheduled three times and `removeUnused` four, because other passes expose new opportunities (entry 6). The shape to carry into cig-compile#33 is MLton's and Go's shared one: a single-file pass table, each pass declared once with a doc comment stating what it must not do, with explicit reruns of the two passes that depend on iterated exposure.
- The local simplifier (MLton's shrinker, entry 16; GHC's `Simplify`, entry 17) is a single pass that cleans the output of every other pass. cig has two simplifier-like passes today (`fold-consts`, `dead-pure`) and runs them manually after every bigger pass; a named `Shrink` at the end of every larger pass is the shape to take.

## Design points

### 1. The intermediate-language chain: XML, SXML, SSA, SSA2, RSSA

- **What it does, and why.** MLton's `CompilerOverview.adoc` lays out the translation chain: a source module is elaborated to CoreML, Defunctorize produces XML, Monomorphise produces SXML, ClosureConvert produces SSA, ToSSA2 produces SSA2, ToRSSA produces RSSA, and ToMachine produces Machine code. Each language drops something, and the drop is what makes the next optimizer small. `XML.adoc` says XML is "polymorphic, higher-order, with flat patterns", every expression annotated with its type, polymorphic generalization explicit through type variables annotating `val` and `fun`, polymorphic instantiation explicit by specifying type arguments at variable references, and patterns that cannot be nested or carry wildcards. `SXML.adoc` names the two differences between XML and SXML: SXML `val`, `fun`, and `datatype` declarations always have an empty list of type variables, and SXML variable references always have an empty list of type arguments; a previous version of the compiler parameterized XML's signature to enforce this, but the software-engineering gains did not pay. `SSA.adoc` says SSA is "a first-order, simply-typed intermediate language" and that it is "the main intermediate language used for optimizations"; an SSA program consists of datatype declarations, a sequence of global statements, and a collection of functions, each a collection of basic blocks ending with some control transfer. `SSA2.adoc` adds mutable fields and n-ary vectors so later flattening passes can be expressed (`DeepFlatten`, `RefFlatten`). `RSSA.adoc` makes representation explicit through a packed type system with subtyping: a singleton type `0xFFFFEEBB` is a subtype of `Word32`. `WholeProgramOptimization.adoc` states the trade: MLton can perform defunctorization, monomorphization, higher-order control-flow analysis, inlining, unboxing, argument flattening, redundant-argument removal, constant folding and representation selection, because it has the whole program; and whole-program compilation is an integral part of the design and is not likely to change.
  The pass list that surrounds each language is in `*Simplify.adoc` and the `*Simplify.fun` files. `XMLSimplify.adoc` names two XML passes: `XMLSimplifyTypes` and `XMLShrink`. `SXMLSimplify.adoc` names `Polyvariance` and `SXMLShrink`, plus the implementation passes `ImplementExceptions` and `ImplementSuffix`; it also names `Uncurry` and `LambdaLift` as "optimization passes not implemented, but might prove useful". `SSASimplify.adoc` lists the 23 SSA passes (`CombineConversions`, `CommonArg`, `CommonBlock`, `CommonSubexp`, `ConstantPropagation`, `Contify`, `DuplicateGlobals`, `Flatten`, `Inline`, `IntroduceLoops`, `KnownCase`, `LocalFlatten`, `LocalRef`, `LoopInvariant`, `LoopUnroll`, `LoopUnswitch`, `Redundant`, `RedundantTests`, `RemoveUnused`, `ShareZeroVec`, `SimplifyTypes`, `SplitTypes`, `Useless`), plus implementation passes `PolyEqual` and `PolyHash`, plus analysis and rewrite passes `Multi`, `Restore` and `Shrink`. `SSA2Simplify.adoc` lists four passes: `DeepFlatten`, `RefFlatten`, `RemoveUnused`, `Zone`, plus `Restore` and `Shrink`.

- **For cig: adapt.** By rule 1 (burns never move) and rule 5 (identical behavior on every engine): the staged-language idea fits CIR as a succession of refinements, not as five languages, because cig's lowering already produces a structured SSA with Burn, Try, If, Loop and ForEach that MLton's SSA has unrolled into basic blocks (`cig-script/src/lower/cir/ir.rs`'s `Kind::Burn`, `Kind::Try`, `Kind::If`, `Kind::Loop`, `Kind::ForEach`). cig's form: three stages of CIR, kept as the same type with a `stage` field that the verifier reads. Stage 0 is today's CIR (what the lowering produces, with closures, dynamic calls and `Ty::Dynamic`). Stage 1 drops `Kind::CallValue` where a flow analysis proved a small callee set (entry 5). Stage 2 (for stage D in cig-compile#34) replaces `Ty::Dynamic` by the inferred `Ty` and introduces an unboxed representation. Each stage has a pass list; the verifier's `T1` to `T4` check the step, burn and error-attribution invariants between every pass of every stage.
- **What would decide it.** Decided by rule 1 and rule 5. The staging is a design question, not a measurement; a measurement that matters is the differential suite at zero differences for every stage boundary.

### 2. What whole-program compilation costs: time, memory, executable size

- **What it does, and why.** Weeks's 2006 report (`weeks-2006-mlton.pdf`) names the three drawbacks of MLton's approach on its slide 10: compile time, compiler memory usage, and executable size. The same report measures: the SSA optimizer during a self-compile of MLton itself starts with 26.2k functions and 719k statements at 101 MB, falls to 7.7k functions and 341k statements at 50 MB after inlining, and finishes at 1.8k functions and 365k statements at 52 MB. The compile-time envelope the report names is "less than 5 minutes for a self-compile" and "compile a 100k line program in minutes with 1G RAM". The `DeepFlatten.adoc` document is explicit that the deep-flatten pass has known cases where it exhausts memory and that users turn it off with `-disable-pass deepFlatten`.

  Weeks's report on "Performance: Large Programs" (slide 30) names specific wins and one specific loss: HOL at 120k lines is 10.3x faster than Moscow ML under MLton; MLton itself at 145k lines is 81x faster than SML/NJ; RML, SML.NET and others are 2x to 3x faster. The one "Large failure" named on the same slide is HOL (400k), where whole-program compilation fails to scale. For cig, where the "whole program" is one script plus a pinned runtime (not 400k lines of library code), the risk shape is inverted: cig's whole program is small by SML standards, but cig-cherry (cig-script#256) compiles at run time, so compile-time is a critical-path cost. The lesson is that a per-pass compile-time budget is read at the design level, not measured after.
- **For cig: adapt.** By rule 5 and rule 10 (ahead of time by default): cig today compiles one `.cig` file per script plus the pinned runtime and has no separate compilation, so a single-script compile is whole-program in MLton's sense today; imports of other `.cig` files are on the roadmap (`cig-script/docs/DESIGN.md` lines 106 and 179). The cost shape worth carrying is the honesty about memory and compile time: MLton's `deep-flatten` is turned off in practice because it is quadratic in a dimension the user did not bound. cig's form: every pass in `cig-script/src/lower/cir/pass/` carries a rough asymptotic in its doc comment, and a pass whose cost is not linear-ish in the module's size has a `cig-compile` flag that disables it, named in `--remarks` when it runs out. The SSA size table (26k to 7.7k to 1.8k functions over the compile) is the shape cig should expect as inlining and specialization land: the function count falls, the statement count moves, and memory follows.
- **What would decide it.** Not measured yet: compile-time and peak-RSS plots on the 21 compute programs, the lines-500 benchmark and cigo's own script as each pass is added. The measurement is on the test machine; the budget is a doubling of today's lowering time at `-O1` per pass added. Today the lowering is 3.14 times the tree-walker's time for a 500-line script (`cig-script/docs/ENGINES-1.25.0.md`).
- **Feeds.** cig-compile#34, #37 (build speed).
- **Read.** `papers/compilers/weeks-2006-mlton.pdf`; `mlton-on-20241230-release/doc/guide/src/DeepFlatten.adoc`; `cig-script/docs/ENGINES-1.25.0.md`.

### 3. Monomorphization: copy a polymorphic function per type at which it is used

- **What it does, and why.** `Monomorphise.adoc` and `mlton/xml/monomorphise.fun` describe the pass that turns XML into SXML. The monomorphizer makes one pass over the program; on the way down, it keeps a cache per variable declared in a polymorphic declaration that maps a vector of types to a new variable name, and at each variable reference it consults the cache. On the way up, it duplicates each variable declaration for each entry in the cache. The same idea applies to datatype declarations and constructors. `monomorphise.fun` names the `Cache` structure: `type 'a t`, `new`, `getOrAdd: 'a t * Stype.t vector * (unit -> 'a) -> 'a`, `toList: 'a t -> (Stype.t vector * 'a) list`. `Monomorphise.adoc` gives the worked example: `fun 'a f (x: 'a) = T x; val a = f 1; val b = f 2; val z = f (3, 4)` turns into `fun f1 (x: int) = T1 x; fun f2 (x: int * int) = T2 x; val a = f1 1; val b = f1 2; val z = f2 (3, 4)`. Weeks (`weeks-2006-mlton.pdf` slide 12) reports a maximum 30% code increase in MLton from monomorphization, and the paper names polymorphic recursion as the one SML feature that could in theory cause non-termination; the SML language's absence of polymorphic recursion makes the pass terminate for every well-typed program. `Monomorphise.adoc` works a pathological case: a datatype `'a t = A of 'a | B of ('a * 'a) t` with `val z : int t = B (B (A ((1, 2), (3, 4))))` would seem to need infinite types, but the monomorphizer drops unused constructors and ends with three monomorphic datatypes. This "drop unused constructors" is a liveness property the monomorphizer takes advantage of; without it the translation would not terminate.
- **For cig: adapt.** What is adapted into what: only the cache's shape (a map keyed by a row of types to a specialized copy) and the termination argument (a bounded set of keys). The mechanism itself (duplicating a polymorphic declaration per type variable instantiation) does not apply: cig is dynamically typed and has no polymorphism to instantiate. By rule 5: the lattice at stage D (cig-compile#34) has `Ty::Int`, `Ty::Float`, `Ty::Bool` already present in `cig-script/src/lower/cir/ir.rs`, and a function's argument may be `Ty::Dynamic` or a specific one. "Monomorphization" in cig is a different pass whose name coincides: specialization per inferred *signature* of a user-defined function, where a signature is a row of argument types. The census measures two separate facts here (`data/census/README.md`): 28 of 29 `call` sites in the 21 compute programs called one function for the whole run, and every function was only ever called with one row of argument types; in cigo's script 72% of calls in `list` and `audit` went to a function that only ever saw one row, and no function in the cigo cases saw more than three rows. The cache structure `getOrAdd(key -> Func)` transfers; the keys are rows of `Ty`. cig's form: a `monomorphize` pass over CIR that reads a call-site type profile from inference (entry 11) and emits a specialized copy of each `Func` per signature, keeping the original for the sites it could not prove. The termination rule MLton relies on (no polymorphic recursion) is cig's by construction: no polymorphism to recurse through; the limit is the bounded number of `Ty` combinations.

  The pass's placement in cig: *before* inlining, so the inliner sees specialized callees (as entry 15's late-specialise says of GHC's pipeline) and no polymorphism-adapter indirection is left for the inliner to pay through. The fallback at the bound is to `Ty::Dynamic` for the extra rows; the original `Func` remains as the fallback target. The named limit at stage D (cig-compile#34: "a pull called with 50 signatures falls back, and the size budget holds") is the same shape as MLton's implicit bound plus the user's `-disable-pass` escape hatch.
- **What would decide it.** Not measured yet: the code-size growth from signature-driven specialization on the 21 compute programs and on cigo's script, against a target of cig-compile#34's `code size growth from specialisation ≤ 1.5× -O2's`. MLton's 30% figure is the ceiling at which the lesson is the user's fallback (MLton prints a diagnostic and the user sets `-disable-pass`).

- **Read.** `mlton-on-20241230-release/doc/guide/src/Monomorphise.adoc`; `mlton-on-20241230-release/mlton/xml/monomorphise.fun` (`Cache`, `getOrAdd`, `monomorphise`); `papers/compilers/weeks-2006-mlton.pdf`; `cig-script/src/lower/cir/ir.rs` (`Ty`, `Func`).

### 4. Defunctionalization: a closure is a tagged sum, a call is a case over the tag

- **What it does, and why.** `ClosureConvert.adoc` and `mlton/closure-convert/closure-convert.fun` describe MLton's conversion of SXML (higher-order) to SSA (first-order). `Closure.adoc` states the representation: a function is not a code pointer plus an environment, but a value of a sum type whose variant indicates which function it is and carries the free variables as arguments. A call is a case expression over the variants, with one direct call per arm. `closure-convert.fun`'s header comment states that all local variables are renamed because an SXML variable may be bound in SSA once for each lambda it occurs in, and the main trickiness is that properties are used to implement the renamer so a binding must be visited with `newVar` or `newScope` before being looked up with `getNewVar`. The pass uses `Globalize` (which free variables are top-level and need no closure capture) and `LambdaFree` (which variables are free in each lambda), and its heart is the control-flow analysis implemented by `AbstractValue`, `Lambda` and `Lambdas`: a lambda has a hash, two lambdas are equal when their hash and SXML term are equal, and `Lambdas` is a set of such things with a cache size and bit count. The underlying idea is credited in `ClosureConvert.adoc` to Cejtin, Jagannathan and Weeks (ESOP 2000); the paper is `papers/compilers/cejtin-2000-flow-directed-closure.ps.gz`.
- **For cig: adapt.** By rule 1 and `V10`: a closure in cig today is already made at one site (`Kind::Closure(FuncId)` in `cig-script/src/lower/cir/ir.rs`); a closure value is `Value::Func(Rc<Function>)` in `cig-script/src/value.rs`. A `Kind::CallUser` already names its callee, so no defunctionalization is needed there; the open question is `Kind::CallValue`, which runs the call through a `Value::Func` read from a slot, a map or an argument. MLton's defunctionalization replaces every indirect call by a case, where 0CFA has cut the case down to one arm wherever it can; in cig the one arm is the common case (the census: 28 of 29 compute call sites went to one callee). cig's form: a defunctionalize pass that, where 0CFA (entry 5) has proved a `CallValue`'s target set is a singleton `{f}`, replaces it with `CallUser(f)`; where the set is up to a small `k`, lowers it to an `If`-ladder of `CallUser` arms with a fallback `CallValue` to keep the dynamic path safe.

  The `Globalize` and `LambdaFree` pre-analyses MLton runs (`mlton/closure-convert/globalize.sig`, `lambda-free.sig`) are the parts cig would need too: `Globalize` decides which free variables are top-level and can be looked up without a capture, which trims the per-site closure record; `LambdaFree` decides which variables are free in each lambda and hence are the arguments the defunctionalized call carries. In cig both are already computed by the lowering: `Func::captures` is the lambda's free set, and a top-level binding has no capture. The pass that remains is the per-call-site rewrite.
- **What would decide it.** Not measured yet: the fraction of `CallValue` sites in cigo's script that can be reduced to a `CallUser` or a small case. The census gives the compute programs' baseline (`data/census/README.md`): 28 of 29 `call` sites called one function for the whole run, and every function was only ever called with one row of argument types; the other site (`dispatch`) is written to call many. The ratio does not translate to "99 percent of call executions"; what the census measures is per-site cardinality and per-function row cardinality, not an executed-call share.
- **Feeds.** cig-compile#33 (`closure-elide`), #34; decisions (e), (i).
- **Read.** `mlton-on-20241230-release/doc/guide/src/ClosureConvert.adoc`; `mlton-on-20241230-release/doc/guide/src/Closure.adoc`; `mlton-on-20241230-release/mlton/closure-convert/closure-convert.fun` (`ClosureConvert`, `Globalize`, `LambdaFree`, `Accum`); `mlton-on-20241230-release/mlton/closure-convert/abstract-value.fun` (`AbstractValue`, `Lambda`, `Lambdas`, `LambdaNode`); `papers/compilers/cejtin-2000-flow-directed-closure.ps.gz`; `cig-script/src/lower/cir/ir.rs` (`Kind`); `cig-script/src/value.rs` (`Value`).

### 5. 0CFA: the control-flow analysis that keeps the case small

- **What it does, and why.** Weeks (`weeks-2006-mlton.pdf` slide 14) names 0CFA (0th-order control-flow analysis) as the whole-program dataflow MLton runs to compute, for each call site, the set of functions that can appear there. The report states the precision: 0CFA is imprecise in theory but precise in practice, "almost no calls require case dispatch". The complexity is cubic in theory but fast in MLton: the report names "less than 2s to analyze MLton itself" through preprocessing based on types (functions of different types cannot be the same lambda), ignoring first-order values, hash-consing sets, caching binary operations, and using union-find for equality constraints. `abstract-value.fun` is the file: `Lambdas` is a `UniqueSet` with a cache size of 5 and 13 bits for the hash table. The prior code duplication from monomorphization helps 0CFA: it makes types more specific, so the type-based preprocessing eliminates more candidates.
- **For cig: adapt.** By rule 1: a per-call-site set of candidate `FuncId`s is the shape stage D (cig-compile#34) and `closure-elide` (cig-compile#33) both want; the structure in cig is already simpler than MLton's because cig does not have polymorphism, so the type-based preprocessing MLton uses is cig's by default. cig's form: a `cfa` pass over CIR that walks each function once, propagating a per-`ValueId` set of `FuncId`s through `Load`, `Store`, `Decl`, `Closure`, `Index`, `Member`, `Key`, `Interp` (strings are not callable), `CallBuiltin` (result is the builtin's declared return), `CallUser` (result is the callee's return set), `MakeList` and `MakeMap` (lose precision through aggregates unless the pass also tracks element sets). `V9` (closures' captures resolve where the closure is made) and `V10` (every user function is made at one place at most) make the analysis sound: a captured variable is read from a known slot, and the set of `FuncId`s that reach a call site is bounded by the program.

  The engineering trick MLton uses (`abstract-value.fun`'s `Lambdas` is a `UniqueSet` with a cache size of 5 and 13 bits of hash) transfers to cig as a hash-consed small-set type: a set of up to 5 `FuncId`s is represented by a hash-consed identifier, and union of two small sets is cached. The intersection and equality tests are then pointer compares. The cig analog: a `SmallFuncSet` in `cig-script/src/lower/cir/` whose `Rc` identity is the hash. Against the census's floor of one candidate per compute call site, the set is usually `|S| = 1` and the data structure is one word.
- **What would decide it.** Not measured yet: the per-site candidate set's size on the 21 compute programs and on cigo's script. The census gives a floor (1 for 28 of 29 compute sites) but does not say what the static analysis would conclude without running the program.
- **Feeds.** cig-compile#33, #34; decision (i).

### 6. Contification: a function called from one place becomes a block

- **What it does, and why.** `Contify.adoc` and `mlton/ssa/contify.fun` describe the pass that turns a function that always returns to the same place into a continuation. The implementation is based on Fluet and Weeks's ICFP 2001 paper "Contification Using Dominators" (named in the file's header comment). The transformation exposes control flow: a recursive function that is called from one place becomes a loop with a back-edge, a conditional's two branches that call the same helper become two arms sharing a join block. `SSASimplify.adoc` names the pass in `simplify.fun`'s `ssaPassesDefault` where contification runs three times (`contify1`, `contify2`, `contify3`), interleaved with other passes. The reason it is in the default pipeline is that the shrinker and many later passes expose new one-call-site functions that only become contifiable after the shrinker has run.
- **For cig: adapt.** By rule 1 and rule 5: contification is the special case of inlining where the function has one caller, which MLton's pipeline runs cheaply because it is driven by dominator information already computed. cig's form: a `contify` pass that identifies every `Func` whose callers are all `CallUser` (not `CallValue`) and whose static call-site count is one; the pass inlines the body at that one site. The invariants it must honor: no `Step(StepSite)` moves out of its block (cig's `T1`), no effect leaves its burn (`T2`, `T3`), and the single caller's `requires_burn` becomes the sum of its own and the callee's. The trick MLton draws from its paper is that a mutually recursive group of two functions where only one is called from outside can still contify the inner one into the outer, which `contify.fun` handles through a dominator analysis; cig would need the same dominator tree over CIR's block graph.

  The paper this pass is based on (Fluet and Weeks, ICFP 2001) is named in `contify.fun`'s header comment; the paper itself is not in the library at the pin. The `Contify.adoc` document notes that "The intermediate language described in that paper has since evolved to the SSA intermediate language; hence, the complication described in Section 6.1 is no longer relevant." So the lesson for cig is to carry the dominator-driven analysis but not the paper's Section 6.1 fix-up.

  The exposure shape (why contify runs three times in MLton's pipeline) is that inlining and `removeUnused` each take a function that previously had multiple callers to one. After `inlineLeaf`, a function that was called once inline and once by a leaf caller may now have one caller; after `inlineNonRecursive`, a different set; after `localRef` and `flatten`, yet another. cig's shape is the same: a `contify` pass runs at every slot in the pipeline where a prior pass turned a multi-caller `Func` into a single-caller one.
- **What would decide it.** Not measured yet: the fraction of `CallUser` targets whose static call-site count is one on cigo's script. MLton runs contify three times because other passes expose new opportunities; the multi-pass shape is the one to take, not a one-shot.
- **Feeds.** cig-compile#33; decision (e).

### 7. Flattening: tuples at every use site are passed flat; refs are packed into their containers

- **What it does, and why.** MLton has four flattening passes. `Flatten.adoc` and `mlton/ssa/flatten.fun` describe argument and constructor flattening: if a tuple is explicitly available at every use of a function (or block, or constructor), the formals and call sites are changed so the components are passed, and the tuple is reconstructed at the beginning of the body (or at each case target for a constructor). The pass is written with a `TwoPointLattice` over each tuple's representation: `flatten` or `don't flatten`. `LocalFlatten.adoc` and `mlton/ssa/local-flatten.fun` cover block arguments inside a function: a block argument is flattened as long as it only flows to selects and some tuple constructed in the function flows to it. `DeepFlatten.adoc` and `mlton/ssa/deep-flatten.fun` cover mutable fields and vector elements: an `(int * int) ref` becomes a two-word mutable object; an `(int * int) array` becomes an array of pairs of ints instead of pointers to pairs. `RefFlatten.adoc` and `mlton/ssa/ref-flatten.fun` flatten a `ref` cell into its containing object: `(int ref * real)` becomes `(int[m] * real)` with a mutable `int` field, saving one heap object and two pointer loads.
- **For cig: adapt.** By rule 1 (cleanup is deterministic) and rule 5: tuple flattening maps onto cig's shaped records (cig-compile#35: a map with fixed keys becomes a struct with fixed offsets), and the "tuple available at every use" condition is the same shape the lattice at cig-compile#34 draws for a record. cig has no mutable `ref` cell; the equivalent is `VarInfo::captured` on a slot in `cig-script/src/lower/cir/ir.rs`, which is true when another function captures the variable. `RefFlatten`'s safety argument (the containing object is live while the ref is live) is cig's by `V9` whenever a captured slot does not escape its creator's dynamic extent. cig's form: a `flatten` pass over `MakeMap(static keys only)` and `Member`/`SetMember` that lowers the map to a shape (cig-compile#35) and passes each field as its own value through a `CallUser`'s argument list where every call site passes a static map literal.

  `DeepFlatten.adoc`'s known hazard is memory: the standard benchmark suite measured "no significant impact" (`http://www.mlton.org/pipermail/mlton/2004-August/025760.html`), and `A number of applications require compilation with -disable-pass deepFlatten to avoid exceeding available memory`. The lesson cig should take with the pass is the user's escape hatch: a `--disable-pass` by name in `cig-compile`, with `--remarks` naming the pass that ran out so the user knows which one to disable. The companion `-keep-pass` and `-diag-pass` options MLton has are what cig's `--remarks` already covers.
- **What would decide it.** Not measured yet: the count of `MakeMap` sites in cigo's script and the 21 compute programs whose keys are all static and whose readers only use `Member` with a static name. The census records every field site saw one shape in compute code; cigo's script sees two shapes at 66% to 100% of field sites, so a `flatten` that fires only on the single-shape case is already right.
- **Feeds.** cig-compile#35, #33, #34; decisions (a), (h).
- **Read.** `mlton-on-20241230-release/doc/guide/src/Flatten.adoc`; `mlton-on-20241230-release/doc/guide/src/LocalFlatten.adoc`; `mlton-on-20241230-release/doc/guide/src/DeepFlatten.adoc`; `mlton-on-20241230-release/doc/guide/src/RefFlatten.adoc`; `mlton-on-20241230-release/mlton/ssa/flatten.fun` (`Flatten`, `Rep`, `TwoPointLattice`); `mlton-on-20241230-release/mlton/ssa/deep-flatten.fun`; `mlton-on-20241230-release/mlton/ssa/ref-flatten.fun`; `cig-script/src/lower/cir/ir.rs` (`MakeMap`, `Member`, `VarInfo`).

### 8. Useless-component removal: a dependence graph, backwards from primitives

- **What it does, and why.** `Useless.adoc` and `mlton/ssa/useless.fun` describe a backwards dataflow: a value of ground type is useful if it is an argument to a primitive, a tuple is useful if it contains a useful component, a constructor is useful if it contains a useful component or is used in a case transfer. If a useful tuple is coerced to another useful tuple, all their components must agree. Converting a useful value to useless is trivial; converting a useful tuple to one of its components is noted as "seems hard" in the file's comment. The special case the comment calls out: a `ref`, `array` or `vector` that is useful whose components are not has its components converted to type `unit` and any primitive argument likewise. The dependence graph is built per program and is one of the few passes that reads the whole program at once (as opposed to one function at a time): `useless.fun` runs the analysis, then the transform rewrites every tuple and every constructor whose components the analysis marked useless.
- **For cig: adapt.** By rule 1 and rule 5: a dead-field removal pass over CIR's `MakeMap` and `Member` sites is a direct analog, with the analysis running backwards from `Exhale`, `CallBuiltin`, `CallMethod`, `BurnOp` and `Interp` (every builtin and every effect is a "primitive" in MLton's sense). A field only written and never read is useless; a record only read at a subset of its keys has the unread keys useless. cig's form: a `useless` pass whose dependence graph has one node per `(MakeMap, key)`, one edge from a `Member` or `Interp` to each key it reads, and one edge from `Exhale` or a user function's parameter use to each field that reaches it. The pass drops a useless key by rewriting the `MakeMap` and leaving a `Kind::Const(Const::Null)` or a never-written slot where a `Member` for the key was; the error-attribution rule (rule 2) is honored because the dropped field cannot have been reached.

  The caveat MLton names on tuples ("converting a useful tuple to one of its useful components seems hard") is a reason cig's version is scoped to drop a useless *key* of a record rather than reshape a useful record into a narrower one. A record `{x, y, z}` whose `z` is useless becomes `{x, y}` in the straightforward direction; a record whose `x` is useful but used only to produce a derived `x_plus_y` that is passed on is the "narrow by one component" case cig's useless pass does not attempt.
- **What would decide it.** Not measured yet: the fraction of `MakeMap` keys that are never read by `Member` or `Interp` on cigo's script. The census lists 74 `getfield` and `setfield` sites in compute code; the useful fraction is unknown but is a natural count.
- **Feeds.** cig-compile#33, #34; decision (i).
- **Read.** `mlton-on-20241230-release/doc/guide/src/Useless.adoc`; `mlton-on-20241230-release/mlton/ssa/useless.fun` (`Useless`); `cig-script/src/lower/cir/ir.rs` (`Kind::MakeMap`, `Kind::Member`, `Kind::Interp`).

### 9. Packed representation: data layouts chosen per type at the SSA2 to RSSA boundary

- **What it does, and why.** `PackedRepresentation.adoc` and `mlton/backend/packed-representation.fun` describe an analysis of an SSA2 program that computes a packed representation for each object. The pass is invoked from `ToRSSA` and the result is used when emitting RSSA code: datatype variants are unboxed into the pointer where their bit pattern is unambiguous, integers are untagged when the type system has already excluded the overlap with a pointer, fields are reordered, and tuples are bit-packed into a word when they fit. `Closure.adoc` names the whole-program necessity: representation decisions depend on the full set of variants a type has, which separate compilation cannot see. The doc notes one special case: `true` is represented as `1` and `false` as `0`. The RSSA type system itself is subtyping-based: a singleton type `0xFFFFEEBB` is a subtype of `Word32`, so a value known to be a constant has a representation that need not carry the tag.
- **For cig: adapt.** By rule 4 (floats are IEEE-exact; maps keep insertion order), rule 8 (no memory both writable and executable; programs stay reproducible) and decision (a) (the value representation): the packed-representation idea is the same one cig-compile#35 draws between a 24-byte `Value` and a tagged 16-byte or NaN-boxed 8-byte alternative. MLton's method is "choose the layout per object from the whole program"; cig's method is "choose the layout per site from the inferred type". cig's form: a `represent` lowering between CIR's stage 2 and the bytecode (or the native code), driven by the `Ty` inferred at each `ValueId`. A `Ty::Bool` is one byte, a `Ty::Int` is eight bytes, a `Ty::Float` is eight bytes, a record (cig-compile#35) is a shape plus a flat array of its values. The invariants to honor are rule 4 (`exhale 0.1 + 0.2` prints the same digits), insertion order for every map (maps stay in order, not reordered), and rule 2 (an index out of range raises at the same span).

  The RSSA subtyping idea (a singleton type `0xFFFFEEBB` is a subtype of `Word32`) is the one cig would want for the one case stage D wants to carry: a `Ty::Int` whose range inference has proved fits in `i32` (for example a loop counter known to be in `0..n` where `n < 2^31`) is a subtype of `Ty::Int` with a 32-bit representation; the arithmetic still checks for overflow, but the storage is half. This is the shape of cig-compile#33's `range-check elim` pass, which proves `xs[i]` inside `for i in 0..xs.len()` needs no bounds check: the range information needed to drop the check is the same information needed to pick a narrower representation.
- **What would decide it.** Not measured yet: the 16-byte and NaN-boxed alternatives on the 21 compute programs and on cigo's script, each with the same differential suite. cig-compile#35 names the default bet as tagged 16-byte and the condition for NaN-boxing as "wins by ≥ 15% on the set".

### 10. GHC's worker and wrapper: a split in `WorkWrap.hs`, a safety proof in `DmdAnal.hs`

- **What it does, and why.** `compiler/GHC/Core/Opt/WorkWrap.hs` is the module that performs the split. `wwBind` takes a binding and either rewrites a `Lam` with `tryWW` or passes it through. `tryWW`'s decision is driven by three things: demand information on each argument (from `GHC.Types.Demand`), CPR information on the result (from `GHC.Types.Cpr`), and a set of `Note`s about what *not* to split: `[Don't w/w INLINE things]`, `[Worker/wrapper for INLINABLE functions]` (the solution is to split and keep the user's stable unfolding on the worker, transferring the `InlineSpec` pragma to both), `[No worker/wrapper for record selectors]`, `[Worker/wrapper for NOINLINE functions]`. The `[Which types are unboxed?]` note sets the canonical conditions: an argument is unboxed if it is (1) a strict data type argument that is an algebraic data type (not a newtype), is not recursive, has a single constructor, and may bind existentials; the pass turns `f (D @ex a b) = e` into `$wf @ex a b = e`. A CPR split (2) turns `f x y = let ... in D a b` into `$wf x y = let ... in (# a, b #)`. Both tests live in `canUnboxArg` and `canUnboxResult` (`WorkWrap/Utils.hs`). The worked example in `WorkWrap.hs`'s INLINABLE Note shows the shape: `f :: Ord a => [a] -> Int -> a; f x y = case y of I# y' -> fw d x y'; fw :: Ord a => [a] -> Int# -> a; fw d x y' = let y = I# y' in ...f...`. The wrapper `f` carries the stable unfolding and the user's INLINE pragma; the worker `fw` is marked for an inliner's later pass so a caller that already has an `Int#` reaches `fw` directly.
- **For cig: adapt.** By rule 2 (errors happen at the same place), rule 3 (step budget is exact) and rule 5: the worker-and-wrapper split in a strict language like cig takes a boxed argument and a boxed result at the wrapper boundary and an unboxed argument and result inside. cig's form: a `ww` pass that, given a `Func` whose inferred signature has a `Ty::Int` or `Ty::Float` argument or result, emits a worker `Func` with the raw value and a wrapper that unboxes on entry and boxes on return. The wrapper is inlined at every `CallUser` of the original, so a caller that already has the raw value reaches the worker directly; a caller that has `Ty::Dynamic` goes through the wrapper and the one unboxing site stays in it. The invariants: an `E503` on integer overflow is raised at the arithmetic instruction's span inside the worker, which is the original span by rule 2; the step mark at the `Call` is charged once at the wrapper, which is where the call site's statement lives.

  Because cig is strict, the `[Worker/wrapper for strict arguments]` CBV mode is cig's default, not an off-by-default flag: every argument is already evaluated at a call. The remainder of GHC's conditions carry through unchanged: `[Don't w/w INLINE things]` (do not split a `Func` the user marked for an inliner's immediate pass), `[No worker/wrapper for record selectors]` (the selector is already a one-field projection and splitting makes it longer), and the `-fmax-worker-args` cap on how many unboxed arguments a worker ends up with. cig would set the cap to the register ABI's limit for the target (entry 13).
- **What would decide it.** Not measured yet: the fraction of calls in the 21 compute programs whose argument types are the same at every site. The census (`data/census/README.md`) states two separate facts here: 28 of 29 `call` sites called one function for the whole run (the other is `dispatch`, which calls many), and "every function was only ever called with one row of argument types". The first says most sites are monomorphic in callee; the second says every function has one row of argument types across its callers. Together they give a floor for the ww split's inputs. The split's payoff is largest where the caller already has the raw value; that is the loop body of `loop`, `fib`, `mandel`, `nbody`, `sieve` and `spectral`.
- **Feeds.** cig-compile#34; decisions (a), (i).
- **Read.** `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/WorkWrap.hs` (`wwBind`, `tryWW`, `wwExpr`); `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/WorkWrap/Utils.hs` (`canUnboxArg`, `canUnboxResult`, `mkWWstr`, `mkWWstr_one`); `cig-script/src/lower/cir/ir.rs` (`Ty`, `Func`, `Kind::CallUser`); `papers/compilers/peyton-jones-1991-unboxed-values.pdf`.

### 11. Demand analysis as the safety proof: and what remains for a strict language

- **What it does, and why.** `compiler/GHC/Core/Opt/DmdAnal.hs` runs backwards over Core and computes, for each argument, a `Demand` (`GHC.Types.Demand`: cardinality `C_00` to `C_1N`, strictness, boxity, product sub-demand). The result is written on each binder's `IdInfo`. The `DmdAnalOpts` record in `DmdAnal.hs` has four knobs: `dmd_strict_dicts` (all functions implicitly strict in dictionary args, on by default), `dmd_do_boxity` (whether to update boxity signatures), `dmd_unbox_width` (`-fdmd-unbox-width`: a per-call-site cap on how many components to unbox), `dmd_max_worker_args` (`-fmax-worker-args`: refuse to unbox if the worker ends up with more than this many arguments). Note `[Worker/wrapper for strict arguments]` explains that, even for an argument whose type is not a product, knowing the argument is strict turns the worker into a CBV function whose code generator skips the eval: `f x = case x of xx { DEFAULT -> $wf xx }` and `$wf xx = case xx of ...`, flagged behind `-fworker-wrapper-cbv` (off by default). The purpose of the demand analysis is to justify the split in a lazy language: without strictness, moving the `case` into the wrapper changes the observable behavior (a thunk that would have been evaluated lazily is evaluated eagerly). Note `[WW for calling convention]` names the trade: W/W might not always be a win, badly written rule frameworks break, and the design has three strategies labelled A, B and similar. Note `[Don't change boxity without worker/wrapper]` says the boxity-update step must *not* run without worker/wrapper following it, because a boxity change not matched by a new signature changes a call site's expected ABI without updating the callee.
- **For cig: adapt.** What is adapted into what: only two of the demand analysis's four axes carry over, and the third is cig's by construction. GHC's demand analysis exists because GHC is lazy; it computes strictness, cardinality, boxity and absence, and the *strictness* axis is what makes moving an unboxing `case` into the wrapper safe (without it, a thunk is evaluated too early). cig is strict: every argument is evaluated at the call, so the strictness axis is cig's by construction and the analysis to compute it is not needed. The *cardinality* axis is partly cig's (`C_00` absent survives: a parameter never read in the body). The *boxity* axis carries over as a type-driven analog: proving that an argument is only ever used as a native `i64` (through `Unary`, `Binary`, `Index`, `SetIndex` whose idx is an `Int`), never as a `Value::Int(_)` carried around whole (through a `MakeMap` entry, a `CallBuiltin` that reads the value, a `Member` dispatch to a methods table). The *absence* axis carries over as "drop the parameter from the worker's signature". cig's form: a `boxity` sub-analysis in the inference pass (cig-compile#34), per argument and per return, with two values: `Boxed` (uses the `Value`) and `Unboxed` (uses only the primitive-operation unboxing). The worker takes the `Unboxed` arguments as raw values and reboxes them *only* where a `Boxed` use is proved to exist; the wrapper takes `Value`s and unboxes for the worker.

  The three strategies labelled A, B and similar in `WorkWrap/Utils.hs`'s `[WW for calling convention]` Note are GHC's answer to an adjacent question: when to ww-split a function whose argument is strict but not a product, trading code-size growth against the per-call eval the worker skips. Strategy A refuses to split unless unlifting is already the shape; strategy B is more aggressive. cig's strict-by-construction stance means the per-call eval is zero, so the trade-off is purely code-size against register-passing; the right strategy is somewhere around A with cig's existing `requires_burn` as a disabling flag.

  The cardinality axis GHC carries (`Card`: `C_00` absent, `C_01` at-most-once, `C_0N` any, `C_10` used-once, `C_11` strict-once, `C_1N` strict-many) is partly cig's. `C_00` (absent) in a strict language means a parameter that is passed and never read: the wrapper can pass an `absent_filler` (see `mkAbsentFiller` in `WorkWrap/Utils.hs`) instead of the real value, and the worker's version drops the parameter. cig's form: a `dead-param` sub-analysis that drops a parameter whose worker body never reads it; the wrapper still evaluates the argument because cig is strict, but the worker's signature is one shorter.
- **What would decide it.** Decided by rule 5 at the differential level; the measurement that steers it is the per-call fraction of boxed uses of a `Ty::Int` argument on the 21 compute programs. The census says 23,984,719 arithmetic executions happen; the fraction that is followed by a `MakeMap`, a `MakeList`, or a `CallBuiltin` that reads the value whole is what the sub-analysis has to catch.
- **Feeds.** cig-compile#34, #33.
- **Read.** `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/DmdAnal.hs` (`DmdAnalOpts`, `dmdAnalProgram`); `ghc-ghc-9.14.1-release/compiler/GHC/Types/Demand.hs` (`Demand`, `Boxity`, `Card`, `DmdSig`); `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/WorkWrap/Utils.hs` (`wwUseForUnlifting`, `Note [Worker/wrapper for strict arguments]`).

### 12. CPR: Constructed Product Result, the symmetric split on function results

- **What it does, and why.** Baker-Finch, Glynn and Peyton Jones's JFP 2004 paper (`papers/compilers/baker-finch-2004-cpr-analysis.pdf`) names the transformation and the property. A function has the CPR property if its body explicitly constructs a product (not just returns one that already existed, as `hdPr (x:xs) = x` would); the worker then returns the components unboxed and the wrapper boxes them at the call site, where the boxing often cancels against an immediate case-of-constructor at the caller. `compiler/GHC/Core/Opt/CprAnal.hs` implements the analysis and `GHC/Types/Cpr.hs` carries the signature. The Notes in `CprAnal.hs` include `[CPR for thunks]`, `[CPR for data structures]`, `[CPR for data structures can destroy sharing]`, `[CPR for recursive data constructors]`, `[Trimming to mAX_CPR_SIZE]`: the result is bounded in width to keep the number of return registers small.
- **For cig: adapt.** By rule 2 and rule 6 (deterministic cleanup): the CPR split in cig is the one that lets a function return `(result, status)` or `(value, overflow_flag)` in two registers rather than a boxed pair or a `MakeMap`. The invariant is that the wrapper's boxing site is where the counted value's `Rc` increment happens, which is the same place a `MakeMap` would do it today; a call site whose caller immediately reads the result through a `Member` cancels against the wrapper's boxing just as Baker-Finch describes. cig's form: the `ww` pass of entry 10 also looks at a `Func`'s returns and, when every return is a `MakeMap` with the same static keys, emits a worker that returns the flat row of values and a wrapper that reconstructs the map. The `mAX_CPR_SIZE` bound is the same shape: cig's return ABI can carry up to some fixed number of registers, past which the pass refuses.

  The paper's section on `hdPr (x:xs) = x` is the specific caution cig must honor: a function whose body does not *construct* a product but returns one that already existed (a `Member` read of a field, or a parameter passed through unchanged) does not have the CPR property. Translated to cig: a `Func` whose returns are `Member(obj, key)` or `Load(var)` for a variable the caller passed in does not get a CPR split; only a `Func` whose every return is `MakeMap(...)` with locally-made values does. The condition reads off the CIR already; no new analysis is needed beyond inspecting the return statements.
- **What would decide it.** Not measured yet: how many `Func`s in the 21 compute programs and in cigo's script return a `MakeMap` with static keys at every return. `nbody`'s records are the canonical example (seven floats). The measurement is on the test machine; the budget is the stage-D ratio against Rust (cig-compile#34).
- **Feeds.** cig-compile#34, #35; decision (i).
- **Read.** `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/CprAnal.hs`; `ghc-ghc-9.14.1-release/compiler/GHC/Types/Cpr.hs`; `papers/compilers/baker-finch-2004-cpr-analysis.pdf`; `cig-script/src/lower/cir/ir.rs` (`Kind::MakeMap`).

### 13. Unarisation: one source value becomes several machine values at STG time

- **What it does, and why.** `compiler/GHC/Stg/Unarise.hs`'s Note `[Unarisation]` describes the pass: at STG time, every unboxed-tuple and unboxed-sum binder is translated away. A variable `x :: (# t1, t2 #)` at its binding site produces fresh variables `x1 :: t1` and `x2 :: t2`, the environment maps `x -> MultiVal [x1, x2]`, the binding becomes a curried binding for `x1, x2`, and every argument occurrence is replaced by a sequence of args via the environment lookup. A tail-call occurrence becomes an unboxed tuple through the same lookup. The Note `[Translating unboxed sums to unboxed tuples]` describes the sum representation: a layout is computed per alternative, the layouts are sorted by slot type and merged for maximum overlap, and the tag is a slot at the first position; the DataCon application packs its arguments into the matching slots and fills the unused ones with rubbish. The Note states that doing unarisation at STG time rather than Core time is deliberate: it would be very hard to make this pass Core-type-preserving, because the type of a function changes. After unarisation, every identifier has at most one `PrimRep` (post-unarisation invariants, `[Post-unarisation invariants]`). `GHC/Types/RepType.hs`'s Note `[RuntimeRep and PrimRep]` names the primitive-entity model: an entity that can be stored in one register and manipulated with one machine instruction, with `PrimRep` enumerating the cases (`LiftedRep`, `UnliftedRep`, `Int8Rep`, `Int16Rep`, up to `VecRep Int PrimElemRep`); `RuntimeRep` extends this with `TupleRep` and `SumRep` so a Haskell expression `e :: ty :: TYPE rep` can talk about a value represented by several registers.
- **For cig: adapt.** By rule 1, rule 2 and rule 5: cig's `Value` is one 24-byte enum today, and stage D's "the hot loop takes raw `i64`s" (cig-compile#34) is unarisation per inferred `Ty`. cig has no unboxed tuples in the source; the idea is to arrange the ABI so that a worker's argument whose inferred `Ty` is `Ty::Int` is an `i64` register, a `Ty::Float` is an `f64` register, and a worker's result whose inferred `Ty` is a static-key record (cig-compile#35) is a flat row of values. cig's form: an `unarise` stage between CIR stage 2 and the bytecode (or Cranelift IR) that reads the inferred `Ty` at every `Func`'s parameters and return and rewrites the `CallUser` sites to pass and receive the rows. The invariant is that an error raised inside the worker (overflow on `Binary(Add, i64, i64)` returns to the wrapper's span by rule 2) stays at the original site; the step mark `Step` is where it already is.

  `Unarise.hs`'s decision to do unarisation at STG time rather than Core time, because a Core-type-preserving unarisation is hard, suggests cig should put unarisation *after* the typed CIR is settled (at stage 2 to bytecode or Cranelift), not during stage D. The `UnariseEnv` mechanism (a map from source variable to a `MultiVal` of fresh ones) matches how cig's lowering already handles multi-value returns through tuples in the parser: the worker's return of three `f64`s is read at the wrapper's three slots by position. The Note's "a case expression that scrutinises an unboxed tuple is always eliminated" is cig's equivalent of "a `Member` read of a flattened record is a direct register read, with no map".
- **What would decide it.** Not measured yet: how many registers a worker takes on the 21 compute programs, against a budget of 8 (a typical register-passing ABI). The 24-byte `Value` enum breaks into at most two machine words today; a worker whose `Ty::Int` arguments total more than 8 words falls back to the boxed path.
- **Feeds.** cig-compile#34, #35; decisions (a), (e).
- **Read.** `ghc-ghc-9.14.1-release/compiler/GHC/Stg/Unarise.hs` (`unarise`, `Note [Unarisation]`, `Note [Translating unboxed sums to unboxed tuples]`, `Note [Post-unarisation invariants]`); `ghc-ghc-9.14.1-release/compiler/GHC/Types/RepType.hs` (`PrimRep`, `RuntimeRep`, `typePrimRep`, `Note [RuntimeRep and PrimRep]`); `ghc-ghc-9.14.1-release/compiler/GHC/Builtin/Types/Prim.hs` (`intPrimTy`, `floatPrimTy`, `charPrimTy`, `wordPrimTy`).

### 14. SpecConstr: specialize a recursive loop per data constructor at its call sites

- **What it does, and why.** `compiler/GHC/Core/Opt/SpecConstr.hs`'s Notes describe the pass. `[Reboxing]` names the hazard: a specialized copy that is called with a freshly allocated constructor reboxes the same constructor at the wrapper when the caller already had the pair; the pass accepts the reboxing risk in exchange for fast loops. The Note's own example is `f p = (...(case p of (a,b) -> e)...p..., ...let t = (r,s) in ...t...(f t)...)`: at the recursive call to `f`, `t` is a known pair, but naively specializing would turn the body into `f' a b = let p = (a,b) in (..., ...)` and now `t` is allocated by the caller only for `r` and `s` to be passed to the recursive call, which allocates `(r, s)` again. The Note explicitly compares the reboxing hazard to the strictness analyser's analog (passing `a` and `b` to a strict worker also risks reboxing to reconstruct `(a, b)` for a boxed inner use) and concludes: make SpecConstr similarly aggressive and ignore the bad potential of reboxing. `[Good arguments]` sets the condition: the pass specializes a self-recursive function where some recursive call has one or more arguments as an explicit constructor application, or the argument's unfolding is a constructor. `[Limit recursive specialisation]` bounds the pass by two counters: `-fspec-constr-recursive=N` limits the number of times `go` in `specRec` loops over a recursive type, and `-fspec-constr-count=max` limits the per-function specialization count; the Note states that if `sc_count` is "no limit" the pass arbitrarily picks 10 as a last-resort ceiling. The paper is named by the file as supporting SpecConstr; the file carries the implementation.
- **For cig: adapt.** By rule 1, rule 3 and rule 5: the shape fits cig's loop-invariant and loop-specialization story (cig-compile#33's `licm`, `unswitch`). cig's analog is "specialize a `Func` per *row* of argument types whose arguments include a constant or a known-shape record", bounded by a per-`Func` count and a global budget. The invariants: a step mark inside the specialized copy charges the same as the general copy (rule 3), an `E503` fires at the same span, and the pass refuses when a recursive call's argument is `Ty::Dynamic`. cig's form: a `specconstr` pass that runs after inference (entry 11) and takes a per-site profile (the census shows 226 of 227 arithmetic-and-comparison sites in the 21 compute programs saw one operand-type pair, 97.7 percent of executions at those combined sites: the profile is already settled) and emits one specialized `Func` per row whose argument types are settled.

  The reboxing hazard the Note names has a direct cig equivalent: a specialized copy that takes the three floats of an `nbody` body and the caller still hands it a `MakeMap(x, y, z)` reboxes the record at the wrapper. The pass must therefore decide against specializing a `Func` whose only callers already have the boxed record and will use it whole after the call. The answer the Note gives (be aggressive and ignore the hazard) is not cig's answer by rule 2 (errors happen at the same place) and rule 6 (deterministic cleanup): a boxing that was not there before is an `Rc` increment and a `MakeMap` whose timing is observable. cig's `specconstr` is more conservative: specialize only when the pass can prove the caller already has the row of unboxed values, not merely hopes for it.

  The `[Good arguments]` Note distinguishes a self-recursive function from mutually recursive ones ("Ignore mutual recursion for now, because it's less common, and the code is simpler for self-recursion"). cig would take the same scope: a `specconstr` pass over `Kind::Loop` and `Kind::ForEach`, plus a self-recursive `CallUser` of the enclosing `Func`, is the first version; mutual recursion is a later pass.
- **What would decide it.** Not measured yet: the specialized-copy count on cigo's script, against cig-compile#34's `code size growth from specialisation ≤ 1.5× -O2's`. GHC's bound is per-function count and per-recursion depth; the two together cap the growth.
- **Feeds.** cig-compile#34, #33; decision (i).
- **Read.** `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/SpecConstr.hs` (`specConstrProgram`, `Note [Limit recursive specialisation]`, `Note [Reboxing]`, `Note [Good arguments]`); `cig-script/src/lower/cir/ir.rs` (`Kind::Loop`, `Kind::ForEach`).

### 15. Specialise: a copy per dictionary, the type-directed analog

- **What it does, and why.** `compiler/GHC/Core/Opt/Specialise.hs` runs at the start of the Core pipeline (`Pipeline.hs`'s `core_todo` names `CoreDoSpecialising` before full laziness). The pass creates specialized copies of overloaded functions, one per dictionary (a Haskell type class's dictionary is a record of methods), and attaches rewrite rules so later uses at the same type automatically hit the specialized copy. The late pass `CoreDoSpecialising` runs again after SpecConstr to catch opportunities the loop specializer created. The Notes include `[Specialising Calls]`, `[Avoiding loops in specImports]`, `[Specialisation modulo dictionary selectors]`, `[Specialising Must Preserve Sharing]`: the pass's correctness conditions are phrased as sharing and laziness invariants, which do not apply to a strict language.
- **For cig: adapt.** What is adapted into what: only the *pipeline-order* lesson (early specialization before inlining and a late re-run after loop specialization), not the mechanism. The mechanism specializes an overloaded function per type-class dictionary; cig has no type classes, no dictionaries and no overloading, so the dictionary-driven pass itself does not apply. The entry 3 `monomorphize` pass (keyed by a row of inferred argument types, not by a dictionary) is cig's own mechanism for the same end; what this entry contributes is *when* in the pipeline that pass runs. By rule 5 and rule 2: cig's form: the entry 3 `monomorphize` pass runs *early* at the start of the stage-D pipeline (before inlining, so the inliner sees specialized callees as smaller code), and a `late-monomorphize` runs after `specconstr` (entry 14) to pick up loops that only became monomorphic after a constant-propagation round.

  The pipeline position Pipeline.hs's `core_todo` names gives the order: `CoreDoSpecialising` (the first run, dictionary-driven), then full laziness, then the simplifier phases 2, 1, 0 (`simpl_phase`), then demand analysis and worker/wrapper (`dmd_cpr_ww = [CoreDoDemand True, CoreDoCpr, CoreDoWorkerWrapper]`), then full laziness again, then CSE, then the final simplifier, then the `-O2`-only passes (LiberateCase, SpecConstr with a simplify after it, late-Specialise). cig's shape is the same five slots: early specialization, early simplifier, demand-and-ww analog, late-constructor-specialize, late-respecialize. Rule 5 (differential suite at zero differences) is checked between every slot.

  The sharing constraint GHC's Notes on `Specialise` emphasize (`[Specialising Must Preserve Sharing]`, `[Specialisations Must Be Lifted]`) does not transfer to cig: a sharing invariant in Haskell is about a thunk's single evaluation, and cig has no thunks (values are values, and a function result is computed per call). What does transfer is the lifting constraint: a specialized copy must be a top-level binding, not nested, so its code is reachable from every call site. cig's `Func` is already top-level by lowering (the `FuncId` is a module-level index), so the invariant is cig's by construction.
- **What would decide it.** Decided by rule 5 at the differential level. The measurement that matters is the `code size growth from specialisation ≤ 1.5× -O2's` budget from cig-compile#34; the bound shared across entries 3, 14 and 15 is one global budget, not three.
- **Feeds.** cig-compile#34; decisions (e), (i).

### 16. MLton's shrinker: the small local simplifier that runs inside every pass

- **What it does, and why.** Weeks's 2006 report (`weeks-2006-mlton.pdf` slide 20) names the SSA shrinker as the largest SSA pass at 1,400 lines. The shrinker performs "obvious" local simplifications inside every other pass: constant primitive applications, case-of-variant with known tag, select-of-tuple with known tuple, and so on, applied by a depth-first search of each function's control-flow graph. It is credited as "Appel-Jim shrinker applied to SSA". `SSASimplify.adoc` lists it among the analysis and rewrite passes that augment many other optimization passes, with `Multi`, `Restore` and `Shrink` named together. The shrinker is run at the end of every other pass, so each pass only has to produce correct code; the shrinker cleans the output.

  The parallel SSA2 shrinker (`mlton/ssa/shrink2.fun`) is the same pattern for SSA2's larger grammar. The two-shrinker design says that the shrinker is kept as a dedicated pass rather than inlined into each transformation; the alternative (each pass carries its own shrinker inline) was the earlier shape and was dropped. `SSA2Simplify.adoc` names `Restore2` and `Shrink2` as the augmenting passes alongside the four SSA2 optimizers (`DeepFlatten`, `RefFlatten`, `RemoveUnused`, `Zone`).
- **For cig: adapt.** By rule 1 and rule 5: cig has `fold-consts` and `dead-pure` today (`cig-script/src/lower/cir/pass/mod.rs`'s `NAMES`), both of which are shapes of what a shrinker does. The lesson is to collect every local simplification into one named `shrink` pass that is called at the end of every other pass instead of adding a round of `fold-consts; dead-pure; sccp; dead-pure` after every bigger pass as the current pipeline does. cig's form: a `Shrink` pass that runs `fold-consts`, the case-of-constant simplification (what `sccp` catches, when the condition is known), and the select-of-constructor simplification (a `Member` of a `MakeMap` whose key is known), all in one DFS. The verifier's `T1` to `T4` run at the end, as they do today.
- **What would decide it.** Not measured yet: how many of cig's current four passes would be collapsed into the `shrink` wrapper and how often the shrinker fires per pass. On a corpus the median is MLton's 1,400 lines; cig's target is proportional to CIR's smaller language.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `mlton-on-20241230-release/doc/guide/src/SSASimplify.adoc`; `mlton-on-20241230-release/mlton/ssa/shrink.fun`; `papers/compilers/weeks-2006-mlton.pdf`; `cig-script/src/lower/cir/pass/mod.rs` (`NAMES`, `level`, `run_passes`).

### 17. GHC's multi-phase simplifier: a round of specialization, phases 2 to 0, then demand-and-ww

- **What it does, and why.** `compiler/GHC/Core/Opt/Pipeline.hs`'s `getCoreToDo` builds the pipeline from the DynFlags. The shape (named in `core_todo`) is: pre-simplify, `CoreDoSpecialising` (the first run), `CoreDoFloatOutwards` for full laziness, `simpl_phase (Phase phase) "main" max_iter` for `phase <- [phases, phases-1 .. 1]` plus one `Phase 0` round of at least 3 iterations, `CoreDoFloatInwards`, `CoreDoCallArity`, `demand_analyser` (which is `CoreDoDemand True`, `CoreDoCpr`, `CoreDoWorkerWrapper`, followed by `simplify "post-worker-wrapper"`), `CoreDoExitify`, `CoreDoFloatOutwards`, `CoreCSE`, `CoreDoFloatInwards`, `simplify "final"`, then the `-O2`-only tail: `CoreLiberateCase`, `CoreDoSpecConstr` (with a `simplify "post-spec-constr"`), `CoreCSE` again, `CoreDoSpecialising` again (late specialization), and a final `demand_analyser` if `late_dmd_anal` is on. The simplifier is run in named phases (phase 2 down to phase 0) so an inliner's rules can be gated on the current phase: an inline that is correct only after a strictness analysis has run is tagged `INLINE[1]` and will not fire until phase 1 and before.

  The `Phase 0` round runs at least 3 iterations because the simplifier has an infelicity that the comment in `Pipeline.hs` spells out: `let k = BIG in foldr k z xs ==> let k = BIG in letrec go = \xs -> ...(k x).... in go xs ==> let k = BIG in letrec go = \xs -> ...(BIG x).... in go xs`. Without the extra iterations, the simplifier leaves "huge dead expressions" that later passes have to clean. cig has no `foldr`-with-huge-k shape, so the same fix is not needed; the lesson is that the simplifier's termination condition is cheaper than the extra iterations' cost, and both GHC and cig run the simplifier until it stops making changes rather than counting iterations.
- **For cig: adapt.** By rule 1 and rule 5: cig's `level` function in `cig-script/src/lower/cir/pass/mod.rs` returns a flat vector of passes today. The shape GHC uses (phases, with pass gates per phase) is overkill for cig at four passes, but the structure to carry is the five slot shape: early specialize, simplifier phases, demand-and-ww, late specialize, final demand-and-ww. The phase gate itself can be omitted at first; the cig form of a phase is a pass's position in the vector. A pass that needs a prior one to have run (as GHC's `INLINE[1]` needs the strictness analyser) is positioned after it in cig's vector.
- **What would decide it.** Decided by rule 5 at the differential level; the measurement that steers the phase count is the iteration count per pass (how many times a simplifier round fires before fixpoint) on cig's corpus.
- **Feeds.** cig-compile#33, #34; decision (e).
- **Read.** `ghc-ghc-9.14.1-release/compiler/GHC/Core/Opt/Pipeline.hs` (`getCoreToDo`, `core_todo`, `simpl_phase`, `demand_analyser`, `CoreDoDemand`, `CoreDoCpr`, `CoreDoWorkerWrapper`, `CoreDoSpecConstr`, `CoreDoSpecialising`); `cig-script/src/lower/cir/pass/mod.rs` (`NAMES`, `level`, `run_passes`).

## What cig should carry away: stage D's "the hot loop takes raw i64s", built in CIR

The brief asks for the shape explicitly. The hot loop of `loop` (1 + 2 + ... + n) today has a `Func` with one `Ty::Int` parameter, a `Loop` whose body is a `Binary(Add, i64, i64)` into a slot, and a `Yield` of the slot. On the tree-walker every arithmetic reads and writes a 24-byte `Value::Int(i64)`; on the VM each `ADD`/`MOVE` moves 24 bytes. The analysis that justifies the raw path is in entries 10, 11 and 13; the shape is:

1. Inference (cig-compile#34): the pass walks CIR and infers a `Ty` per `ValueId`. For `loop`, every `Load` and `Store` of the accumulator is `Ty::Int`; every `Binary` is `Ty::Int -> Ty::Int`. The census (`data/census/README.md`) gives the floor for 15 of the 20 compute arithmetic sites: every arithmetic instruction ran on two integers.
2. The worker-and-wrapper split (entry 10): the `Func` is split into a wrapper that takes a `Value::Int(i64)` and a worker that takes `i64`. The wrapper is inlined at every `CallUser`; its one unboxing site is at the entry. The error-attribution rule (rule 2) is honored because `E503` is raised at the `Binary`'s span, which is the worker's span is the original's span.
3. The step budget (rule 3): a `Step(StepSite)` stays in the loop's body in both the worker and the wrapper; the wrapper carries none because the wrapper is one straight-line sequence of unboxing instructions. `E515` falls on the same statement on every engine.
4. The callback problem: a function stored in a map or passed as a callback (a `Kind::CallValue` whose target 0CFA could not settle, entry 5) does not get the split. The wrapper remains the only entry; the worker is a direct `CallUser` inlined into the wrapper only when the caller has the raw `i64` already. This preserves `V10` and the dynamic-dispatch path.
5. Record returns (entry 12): a `Func` whose every return is `MakeMap(x: Float, y: Float, z: Float)` becomes a worker returning three `f64`s and a wrapper reconstructing the map at the one call site that reads it through `Member`. `nbody`'s inner step is this shape.
6. Loop specialization (entry 14): the loop is specialized per row of argument types; the general row stays available for the one caller that does not match. The bound (entry 15) is a per-`Func` count.
7. Unarisation (entry 13): at the CIR-to-bytecode or CIR-to-Cranelift boundary, the worker's parameter list is rewritten so a `Ty::Int` is an `i64` register (not a `Value`), a `Ty::Float` is an `f64` register, and a `Ty::Bool` is a `u8`. A tuple return is a row of registers; a record return (static keys) is a row of registers for its field values. The invariant: the ABI at the boundary is identical for the tree-walker (one 24-byte `Value`), the VM (today), and the typed worker (unboxed row), and the differential suite stays at zero differences through the transition.

The error-attribution rule (rule 2) is the invariant the pass must not break. An overflow on `Binary(Add, x, y)` in the worker fires `E503` at the `Binary`'s span, which is the original source span because the lowering sets `Instr::span` once at lowering time and no pass changes it (`cig-script/src/lower/cir/verify.rs`'s `V2`: every instruction carries a span); `T4` ensures the pass only removes a raising operation when proven unable to raise, not because the worker signature says the argument is an `Int`. The step mark (`Step(StepSite)`) stays with its statement (`T1`): the worker's `Step` is the loop body's, the wrapper carries none.

The unmeasured part of this, in order of risk: how often a `CallValue` resolves to a small set under cig's 0CFA (entry 5); how often a `Func`'s returns are all `MakeMap(static_keys)` (entry 12); and whether the worker-and-wrapper split pays on cigo's script, where 72% of calls in `list` and `audit` see one row of types (`data/census/README.md`) but no loop is hot. cigo's work is in builtins and methods (3,400 builtin calls against 175 arithmetic instructions in a hook, `data/census/README.md`), so the unboxing payoff in cigo is small; the payoff in compute programs (`nbody`, `loop`, `mandel`, `sieve`, `spectral`) is where the stage-D Rust-ratio budgets of cig-compile#34 are set.

## Not settled

- Cejtin, Jagannathan and Weeks's "Flow-Directed Closure Conversion for Typed Languages" (`papers/compilers/cejtin-2000-flow-directed-closure.ps.gz`) was read in this run. It confirms entries 4 and 5: the translation "implements closures as elements of datatypes, and uses dispatches at certain call-sites to select the appropriate function to call", uses a "general flow-analysis framework which includes OCFA", and reports that "the compile-time cost of flow analysis and closure conversion is extremely small, and that the dispatches and coercions inserted by the algorithm are dynamically infrequent". One mechanism named in the paper that this study did not elaborate: *coercions* inserted at points where different flow sets merge, to keep the target language simply typed. In cig, the simply-typed target constraint does not bind because cig has no source types to preserve through closure conversion; the coercion mechanism is not needed, so entries 4 and 5 do not take it.
- The termination argument for monomorphization in SML relies on the absence of polymorphic recursion. cig has no polymorphism, so termination is trivial; the open question is whether the monomorphization-bound in the pipeline is shared with SpecConstr's and Specialise's (entries 14, 15) as one global budget or three. What would settle it: a decision in cig-compile#34 or a measurement showing the three budgets never bind.
- MLton reports that `deep-flatten` has cases where it exhausts memory and users turn it off (`DeepFlatten.adoc`). The analog in cig is unknown: a pass with quadratic behavior in the shape graph has the same shape. What would settle it: a `--max-pass-mem` option in `cig-compile` that logs the per-pass peak RSS on the test machine.
- MLton's `simplify.fun` runs contify three times; the reason is that other passes expose new one-call-site functions. The cig analog is unknown: at four passes today, the opportunity count is likely small. What would settle it: a `--count-contify-candidates` after each pass on cigo's script.
- The `deep-flatten` and `ref-flatten` safety-for-space argument (`RefFlatten.adoc`: the container is live while the ref is live) maps to cig's `V9` (captured-slot liveness) only loosely. What would settle it: a formal argument that `V9` plus `T3` proves the same invariant MLton proves by liveness approximation.
- The CPR split (entry 12) and the ww split (entry 10) are one pass in GHC (`WorkWrap.hs` performs both at once, "a single worker/wrapper transformation that deals simultaneously with unboxing both arguments and results" in Baker-Finch et al. §2.4). Whether cig splits them is open: an inferred `Ty` on a parameter lets the unboxing pass fire whether or not the function has CPR, so one combined pass is a design candidate. What would settle it: a count of `Func`s that would get one half but not the other on the 21 compute programs.
- The pipeline order of early specialization versus `monomorphize` in cig (entry 15) is set by GHC's shape but is not forced by cig's rules. Running monomorphize after inlining is the alternative: an inlined callee may expose new specialization opportunities. GHC runs `late-Specialise` after `SpecConstr` for exactly this reason. What would settle it: compile-time and specialized-copy count on both orderings, measured on cigo's script and the 21 compute programs.
- MLton's `simplify.fun` runs `removeUnused` four times. The reason is that the pipeline exposes new unused functions after inlining, specialization, and contification; a single pass misses opportunities an earlier pass hid. The cig analog is unknown; the shape is a `dead-pure` run at the end of every pass as entry 16's `Shrink` is. What would settle it: the opportunity count in each position of the pipeline, measured on cigo's script.
- GHC's `[Don't change boxity without worker/wrapper]` note binds the demand analysis and the worker-wrapper pass together: the boxity update is only run when the pass that *consumes* it is scheduled to run next. The cig analog is what pairs `boxity` sub-analysis of entry 11 with the ww pass of entry 10. What would settle it: a single pass structure that runs the sub-analysis and the split as one transaction, so the signature is never in a "boxity updated, worker not generated" state.
