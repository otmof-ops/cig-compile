## What cig should carry away

**A proposed pass order for CIR.** Each pass is marked `existing` (in `cig-script/src/lower/cir/pass/mod.rs`'s `NAMES` and `level(n)` today), `planned in #33`, or `new from this study`, with the reason for its position.

`-O1` (planned and existing passes only, fast, reads in a debugger):

1. `fold-consts` (existing). Reason: makes every later pass work on concrete terms.
2. `copy-prop` (existing). Reason: turns `stick a = b` uses into direct reads of `b`; shrinks `sccp`'s worklist.
3. `fold-consts` (existing, second time, matching `level(1)` in `cig-script/src/lower/cir/pass/mod.rs:160-164`, which returns `[&FoldConsts, &CopyProp, &FoldConsts, &Sccp, &DeadPure]`; #33's 2026-11-08 note (comment on #63) records the same order). Reason: `copy-prop` exposed new constants.
4. `sccp` (existing). Reason: cuts dead `if` arms and propagates constants through branches.
5. `dead-pure` (existing). Reason: removes the pure values nothing uses now.

`-O2` (adds the planned and new passes from this study, in the order the reasons give):

1. `fold-consts` (existing). Reason: as at `-O1`.
2. `copy-prop` (existing). Reason: as at `-O1`.
3. `scoped-cse` (new from this study, entry 7). Reason: cheap dominator-walk redundancy before heavier passes.
4. `peephole` (new from this study, entry 9; extends `fold-consts` with the "strictly simpler" rule). Reason: canonicalize so the next passes see fewer shapes.
5. `inline-small` (planned in #33, with the bottom-up walk from entries 2, 10). Reason: caller sees callee's simplified CIR before deciding. The census (`data/census/README.md`, finding 4) makes this cheap: 28 of 29 call sites in the compute programs call one function, and every function was only ever called with one row of argument types, so a trivial single-callee inliner would hit nearly all of them.
6. `scoped-cse` (new, second time). Reason: inlined callees expose more redundancy.
7. `sccp` (existing). Reason: now the branches know their constants.
8. `copy-prop` (existing, second time). Reason: `sccp` cut dead arms, phi-like merges collapse.
9. `licm` (planned in #33, with the `MayRaise` safety from entry 8). Reason: loop invariants hoisted with the two-step rule (safe first, speculate after). Note that `Step` marks must not be moved (`T3`): the census (`data/census/README.md`, finding 1) says they are 23.8% of a compute program's executed instructions (up to 50%), so the pass must divide the loop body into `Pure` (may hoist), `MayRaise` (may hoist by proof), `Effect`/`Step` (pinned).
10. `gvn` (planned in #33, with the burn barrier from entry 7). Reason: whole-function value numbering after the loop's shape has settled.
11. `peephole` (new, second time, like LLVM's second `InstCombine`). Reason: GVN's rewrites expose peephole opportunities.
12. `range-check-elim` and `overflow-check-elim` (planned in #33, with the `T4` proof from entry 8). Reason: bounded loops now visible after LICM.
13. `closure-elide` (planned in #33). Reason: direct-called closures become plain calls now that inlining has decided who stays.
14. `dead-pure` (existing). Reason: nothing is removed that a later pass could still use.

The order is the reason each pass sees what it needs: the folds come before the uses they enable, and every pass that removes work runs after the one that exposed the work. The verifier runs between each (unchanged from today).

**The findings that matter most.**

- CIR's structural shape (`Module -> Func -> Block -> Instr` with blocks owning nested blocks, from `cig-script/src/lower/cir/ir.rs`) is a closer fit to the new pass manager's IR hierarchy (`Module -> CGSCC -> Function -> Loop`, `NewPassManager.md`) than to LLVM's old CFG shape. A pass over a block in CIR is already what LLVM calls a loop pass over a rotated loop, and the two-stage simplification-then-optimization pattern maps directly (entries 1, 5).
- The function simplification pipeline runs in a fixed order and is run twice: once early on each function before the inliner's bottom-up walk shows what its callers look like, once again during that walk on each callee after inlining. LLVM's `VerifierPass` is added conditionally (one unconditional site is before `EmbedBitcodePass` in `buildFatLTODefaultPipeline`, line 1836), not between every pass; cig, by contrast, runs `verify` and `verify_transition` in its own `run_passes_inner` after every pass (`cig-script/src/lower/cir/pass/mod.rs`, lines 119 to 124). The ordering reasons carry over to CIR even though its instruction set and effect model do not (entries 1, 2, 3).
- LICM's single safety test, `isSafeToExecuteUnconditionally(..., AllowSpeculation)`, is the same test CIR owes any hoisting pass: an operation that might raise is hoisted only if it is proven to always execute or safe to speculate. CIR's `MayRaise` class in `cig-script/src/lower/cir/ir.rs` is this test already written down, and the two-LICM pattern around loop-rotate is the model (entry 8).
- InstCombine's rule, that each rewrite makes the IR strictly simpler, is why `MaxIterations = 1` is the default and a fixpoint is expected in one sweep: a fail of that fixpoint is a fatal usage error the rewrite set itself must own. CIR's fold rules would be written and measured the same way, and `fold_binary` in `cig-script/src/lower/cir/ir.rs` is the shared folder the verifier and the pass already agree on (entry 9).
- Alive2 proves refinement, not equivalence: the target may be less undefined than the source but never less defined. CIR has no undefined behavior, no undef, no poison. That removes three of the six refinement questions (1 UB, 3 poison, 4 undef) and leaves a smaller SMT encoding than LLVM has to carry; the three questions CIR still owes (return domain, value, memory-as-journal) are each small (entries 14, 15, 17).
- `-opt-bisect-limit` is one global counter incremented by the pass manager on each pass invocation, and a pass either opts in by calling `shouldRunPass` or is unskippable (an analysis, a pass required for codegen). cig's bisect can be the same shape: a per-pass counter in the existing `run_passes` in `cig-script/src/lower/cir/pass/mod.rs`, and a rule that only transform passes are skippable so the verifier always runs (entry 12).
- PGO is keyed by a `FuncHash`: a checksum of the function's CFG and its instrumented value sites. The stale-profile problem is detected by the hash mismatch, not managed out of band. cig's profile format should do the same: a CFG checksum computed over `Block::instrs` and jump targets in `cig-script/src/lower/cir/ir.rs` (entry 13).
- The census (`data/census/README.md`) measures that step marks are a quarter of a compute program's executed instructions (median 23.8%, up to 50% on `fannkuch`, `sieve`, `strbuild`) and only 1% to 13% of a cigo call. A loop pass that would move a `Step` mark fails rule 3 (step budget exact), and `T3` catches a lost or cloned mark. In compute code, the mark population a `licm` may not touch is this quarter; in cigo it is small, so a cigo-tuned `-O2` has more room (entries 8, 11).
- The `tv` plugin's biggest optimization is the trivial one: if the source and target print byte-for-byte equal, skip the solver (`alive2-v21.0/tv/tv.cpp` (`verify`)). In cig this maps onto the existing canonical printer `cig-script/src/lower/cir/` under `cir/print.rs` and would turn most pass applications into a zero-cost check (entry 17).
- The pass manager's analysis story is a `PreservedAnalyses` return type per pass with the four shapes `all()`, `none()`, a named preserve, and a set preserve such as `CFGAnalyses`. `Mem2Reg.cpp` returns `preserveSet<CFGAnalyses>()` because it does not touch the CFG, and that is what lets the dominator tree, the loop info, and the branch probabilities all survive through a pass that transforms memory into SSA (entry 11).
- The inliner's cost model is a small number of tuned constants, measured against a corpus, and a bounded walk of the callee for the cost itself. The constants that matter are `DefaultThreshold = 225`, `OptAggressiveThreshold = 250`, `OptSizeThreshold = 50`, `OptMinSizeThreshold = 5`, `HintThreshold = 325`, `ColdThreshold = 45`, `LoopPenalty = 25` (`InlineCost.cpp`, `InlineCost.h`). cig should measure its own, not copy them (entry 10).
- The late `LoopSink` is the one LLVM pass that explicitly undoes what an earlier pass did (it sinks what LICM hoisted) because the earlier shape was better for optimization and the later shape is better for code generation. The lesson for cig: a rearrangement that is right for one audience can be wrong for another, and the pipeline commits to the right one by running the rearranger late (entry 5).
- The six questions `check_refinement` asks are each short-circuiting in a specific order: check UB first (so a source that is always UB stops the rest), then return domain, then poison, then undef, then value, then memory. For CIR the order becomes: return domain, value, journal-equivalence. A failure of the first makes the next ones moot (entry 14).
- `InstCombine` runs twice in the pre-inliner-cleanup pipeline (`buildModuleSimplificationPipeline`) and at least four times in `buildFunctionSimplificationPipeline` (after `SimplifyCFG`, after loops, after the dead-code passes, at the end). LLVM pays the cost because each run finishes in one sweep and the worklist is small after each heavy transform (entry 9). cig's `peephole` should pay the same cost by the same rule.
- Alive2's `v21.0` tree reports 99 LLVM bugs and 24 Z3 bugs found so far (`alive2-v21.0/BugList.md`). The paper's §8 reports 121 refinement violations from the LLVM unit tests, of which 47 were reported upstream and 28 fixed at publication time. These numbers set the expectation for #39's planted-miscompile test (entry 17).
- `InferFunctionAttrs` runs twice in `buildModuleSimplificationPipeline`: once early (basic inference from known properties of system libraries) and `PostOrderFunctionAttrs` once inside the CGSCC pipeline (with `SkipNonRecursive=true`) and once after the simplification runs. The pattern is: attributes feed simplification feeds attributes. cig would benefit from the same loop once `requires_burn` grows into a richer attribute set (entry 2).
- The TV plugin's three-stage integration (translate source IR; run the real LLVM transformation under the pass manager; translate the optimized IR, check refinement) is reusable in cig with no new LLVM-side plumbing because cig's passes are already pure functions over `Module`. The `run_passes_inner` function in `cig-script/src/lower/cir/pass/mod.rs` takes `&mut Module` and returns the verifier's errors; a TV wrapper captures the pre and post snapshots at the same site (entry 17).
- At the `llvmorg-23.1.6` pin, the pipeline builder is `PassBuilderPipelines.cpp` at 2,580 lines, five of which are the top-level pipeline entry points (`buildPerModuleDefaultPipeline`, `buildThinLTOPreLinkDefaultPipeline`, `buildThinLTODefaultPipeline`, `buildLTOPreLinkDefaultPipeline`, `buildLTODefaultPipeline`), and the rest are the shared helpers. Short enough that cig's pass runner at 272 lines today (`cig-script/src/lower/cir/pass/mod.rs`) can grow without turning unreadable. (Entry 1.)

**Where the ideas map to cig's files.** The pipeline builder lives in `cig-script/src/lower/cir/pass/mod.rs` (`run_passes`); the analysis manager grows as a new module alongside `cig-script/src/lower/cir/verify.rs`; the bisect counter is a new argument to the existing `run_passes_inner` in `cig-script/src/lower/cir/pass/mod.rs`; the TV module is new alongside `cig-compile/src/fuzz.rs` and `cig-compile/src/reduce.rs`. Per-pass remarks for `--remarks` (planned in #33) reuse the existing `run_passes_with_remarks` entry point in the same file. The PGO counter table is a new `ProfileRecord` serialized alongside the module in `cig-script/src/lower/bc/mod.rs`, keyed by the CFG checksum of its `Func`. The CIR passes themselves live in `cig-script/src/lower/cir/pass/` (one Rust module per pass): entry 3's proposed `scoped-cse`, entry 9's `peephole` (extending `fold-consts`), entry 10's `inline-small`, entry 8's `licm`, entry 7's `gvn`, and entry 13's `profile` loader are all new modules under that directory, each shipping with a broken twin in `cig-script/src/lower/cir/pass/broken.rs` that the verifier (`cig-script/src/lower/cir/verify.rs`) must catch.

## Design points

### 1. The pipeline's shape, a module through the default build

- **What it does, and why.** `PassBuilder::buildPerModuleDefaultPipeline` at `-O1`..`-O3` builds two stages joined in order: `buildModuleSimplificationPipeline`, then `buildModuleOptimizationPipeline`. The first runs a short early function pipeline on every function (`SimplifyCFG`, `SROA`, `EarlyCSE`), does interprocedural constant propagation (`IPSCCPPass`), optimizes globals, runs `AlwaysInlinerPass`, then enters the inliner's module wrapper. The inliner walks the call graph bottom-up over strongly connected components, and inside each SCC it runs `buildFunctionSimplificationPipeline` on every function as it is visited; that is why a callee is fully simplified before a caller sees it and decides to inline it. The second stage adds loop transforms the first stage did not need yet: `LoopRotate` again, `LoopInterchange`, `LoopDistribute`, the loop and SLP vectorizers, `LoopSink`, `DivRemPairs`, `MergeICmps`, a final `SimplifyCFG` with switch-to-lookup-table turned on.
- **For cig: adapt.** Not take whole: CIR has no CGSCC walk today and no inliner (`cig-script/src/lower/cir/pass/mod.rs` (`NAMES`) lists four passes), and burns cannot cross a region boundary (rule 1: `T1`), which forces an inliner to prove that a pulled callee has no `BurnOp` before it may be inlined across one. But the two-stage shape, the function pipeline run once before and once during the inliner walk, and the late loop-and-vectorize stage after inlining are the shape to adopt: #33's `-O2` and `-O3` lists in the issue match this. cig's form: `cir/pass/mod.rs:run_passes` is already a sequence with a verifier call after each; it grows a second phase that is invoked under a bottom-up walk once cig-compile#17's self-hosted call graph is built.
- **What would decide it.** Not measured yet: at a fixed inline-threshold set, compare a one-stage pipeline (every function once) against a two-stage one (function pipeline before inlining, then again during the inliner walk) on the four corpus programs `spectral`, `nbody`, `mandel`, `dispatch`, at stage B, and report the geomean speedup and the extra compile time.
- **Feeds.** #33 (the pipeline shape), decision (e) (crate split between the lowering and the shared code generator, which the bottom-up walk needs).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Passes/PassBuilderPipelines.cpp` (`buildPerModuleDefaultPipeline`, `buildModuleSimplificationPipeline`, `buildModuleOptimizationPipeline`, `buildInlinerPipeline`, `buildFunctionSimplificationPipeline`); `llvm-project-llvmorg-23.1.6/llvm/docs/NewPassManager.md` (`createModuleToPostOrderCGSCCPassAdaptor`); `cig-script/src/lower/cir/pass/mod.rs` (`run_passes`, `NAMES`, `level`).

### 2. The bottom-up walk and the inliner's module wrapper

- **What it does, and why.** The inliner is a CGSCC pass that is wrapped in `ModuleInlinerWrapperPass`. The wrapper takes the callee set, computes strongly connected components of the call graph, and visits them post-order so a function is seen only after everything it calls has been. Inside each SCC the pipeline is: `AttributorCGSCCPass` (optionally); `PostOrderFunctionAttrsPass(SkipNonRecursive=true)` (so the simplification step sees attributes it can use); the inliner itself (part of `ModuleInlinerWrapperPass`); `createCGSCCToFunctionPassAdaptor(buildFunctionSimplificationPipeline(Level, Phase), EagerlyInvalidateAnalyses, NoRerun=true)`; `PostOrderFunctionAttrsPass` again (after simplification). `NoRerun=true` records on each function that it has been fully simplified so the SCC visitor will not simplify it twice by accident.
- **For cig: adapt.** cig has no call graph pass today, and cig's burn rule constrains what may be inlined: a pull across a region boundary is a `T1` violation unless the pulled callee has no `BurnOp` anywhere it may run. `pass/mod.rs:NAMES` has no `inline`, so this is new. Adopt the bottom-up order and the `NoRerun` marker on each `Func`; decided by rule 1 that an inliner never moves a pinned instruction across a region boundary. cig's form: a new module-level pass that walks `Module::funcs` in post-order of the static call graph, running `pass/mod.rs:run_passes` on each `Func` after it is first inlined into.
- **What would decide it.** Settled in part by the census (`data/census/README.md`, finding 4): on the compute programs 28 of 29 call sites call one function, so bottom-up and a simplistic order hit the same set in practice; what is still open is how much extra cig gains on large-cigo-scale code (cigo's script has 1,038 functions, 13 to 80 entered per call; finding 7), where bottom-up may do strictly better. Not measured yet for cigo-scale.
- **Feeds.** #33 (`inline (small)` at `-O2`), decision (e) (where the inliner lives in the lowering crate).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Passes/PassBuilderPipelines.cpp` (`buildInlinerPipeline`, `MainCGPipeline`, `NoRerun`); `llvm-project-llvmorg-23.1.6/llvm/lib/Transforms/IPO/Inliner.cpp` (`InlinerPass`); `cig-script/src/lower/cir/ir.rs` (`Module`, `Func`, `BurnOp`).

### 3. The function simplification pipeline, in order, with reasons

- **What it does, and why.** `buildFunctionSimplificationPipeline` at `-O2` and `-O3` lays down, in this order (one function, one call): `SROA(ModifyCFG)` turns aggregate allocas into promotable ones and then into SSA values, which is what makes everything after it work on registers rather than memory; `EarlyCSE(mem-ssa)` catches the trivial redundancies; optional `GVNHoist`/`GVNSink`; `SpeculativeExecution(OnlyIfDivergentTarget)`; `JumpThreading`; `CorrelatedValuePropagation`; `JumpTableToSwitch`; `SimplifyCFG(convertSwitchRangeToICmp)`; `InstCombine`; `AggressiveInstCombine`; `LibCallsShrinkWrap`; (PGO only) `PGOMemOPSizeOpt`; `TailCallElim`; `SimplifyCFG`; `Reassociate` (tree form for `LICM` and `GVN`); `ConstraintElimination`; LPM1 (`LoopInstSimplify`, `LoopSimplifyCFG`, `LICM(AllowSpeculation=false)`, `LoopRotate`, `LICM(AllowSpeculation=true)`, `SimpleLoopUnswitch(NonTrivial at O3)`); extra unswitch; LPM2 (`LoopIdiomRecognize`, `IndVarSimplify`, `LoopDeletion`, `LoopFullUnroll`); `SimplifyCFG`, `InstCombine`; `SROA` again (after unroll); `VectorCombine(TryEarlyFoldsOnly)`; `MergedLoadStoreMotion`; `GVN` (or `NewGVN`); `SCCP`; `BDCE`; `InstCombine`; `DFAJumpThreading`; `JumpThreading`; `CorrelatedValuePropagation`; `ADCE`; `MemCpyOpt`, `DSE`, `MoveAutoInit`; `LICM(AllowSpeculation=true)` on the loop, once more; `SimplifyCFG(convertSwitchToArithmetic, hoistCommonInsts, sinkCommonInsts)`; `InstCombine`. Reasons the comments give: `SROA` first because every other pass reads better in SSA; `EarlyCSE` before heavier passes because it is cheap and shortens their worklists; `Reassociate` before `LICM` so canonical trees expose invariant subtrees; `LICM(false)` before `LoopRotate` because speculative hoisting would destroy metadata the rotate may need; `LICM(true)` after rotate because now the header is a single block; `InstCombine` appears after every big transform (SROA, loops, DSE) because each opens new peephole opportunities and InstCombine is cheap on a small worklist.
- **For cig: adapt.** Not take whole: half these passes do not apply (no `SROA` because CIR has no aggregates in temporaries, no `LoopIdiomRecognize` because there is no `memset` or `memcpy`, no `GVNHoist`/`GVNSink` because CIR is structured and a block only exists as a child of an owning node). The ordering reasons do carry over: `fold-consts` before `copy-prop` so folds expose chains that copy-prop then collapses; `copy-prop` before `sccp` so the dead branch is cut; `dead-pure` last so nothing is removed that a later pass could have used. cig's form: at `-O1` the four today; at `-O2` the proposal is in the "carry away" section.
- **What would decide it.** Not measured yet: at `-O2`, time the full function pipeline with one `InstCombine` at the end against the LLVM-like layout (`InstCombine` after every heavy pass) on the benchmark corpus; the measurement is total stage B time and number of instructions removed.
- **Feeds.** #33 (pass order), decision (c) (profile-driven order of the fast paths).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Passes/PassBuilderPipelines.cpp` (`buildFunctionSimplificationPipeline`, `LPM1`, `LPM2`); `llvm-project-llvmorg-23.1.6/llvm/lib/Transforms/InstCombine/InstructionCombining.cpp` (`combineInstructionsOverFunction`, `MaxIterations`); `cig-script/src/lower/cir/pass/mod.rs` (`run_passes`, `NAMES`).

### 4. `-O0`, `-O1`, `-O2`, `-O3`, `-Os`, `-Oz`: what each changes

- **What it does, and why.** `OptimizationLevel::O0` returns `buildO0DefaultPipeline`, which runs `AlwaysInliner` and a few canonicalizations and stops; no simplification, no CGSCC walk. `O1` is a separate function pipeline, `buildO1FunctionSimplificationPipeline`: it leaves out `JumpThreading`, `CorrelatedValuePropagation`, `JumpTableToSwitch`, `TailCallElim`, `AggressiveInstCombine`, `GVN`, `DFAJumpThreading`, the late `LICM` after `DSE`, and the `switchToArithmetic`/`hoistCommonInsts`/`sinkCommonInsts` tunings. `O2` is the default and runs the full function pipeline. `O3` runs the same function pipeline with `SimpleLoopUnswitch(NonTrivial=true)`, an extra unswitch in `LPM2`, `ArgumentPromotion` in the CGSCC pipeline, and a higher inline threshold (`OptAggressiveThreshold = 250` against the default `225`). `Os` and `Oz` both reuse the function pipeline but with inline thresholds dropped to `OptSizeThreshold = 50` and `OptMinSizeThreshold = 5`, and at `Oz` loop-rotate's header duplication is turned off.
- **For cig: adapt.** cig's levels at 1.25.0 are `-O0` (lowering only) and `-O1`/`-O2` (the same four passes in a row); #33 plans five levels. Adopt LLVM's shape: `-O0` is lowering; `-O1` is the fast function pipeline (fold-consts, copy-prop, sccp, dead-pure); `-O2` adds the planned GVN-like pass, LICM-like pass, small inlining, bounds-check elimination, closure-elide; `-O3` raises the inline threshold and turns on the aggressive unswitch; `-Os` is `-O2` with inlining capped at a small threshold. Decided by rule 5 (every engine computes the same answer): the levels differ only in speed, not in what a program does. cig's form: a new `Level` enum in `cir/pass/mod.rs` with `O0`..`O3`, `Os`, and `level(n)` returning the pass list.
- **What would decide it.** Not measured yet: at each level, measure stage B's runtime geomean over the benchmark corpus and its code size; the budget in #33 is `-O2 >= 1.5x -O0`, `-O3 >= 1.1x -O2`, `-Os <= 0.8x -O2` size.
- **Feeds.** #33 (levels), #37 (compile time vs. runtime trade-off).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Passes/PassBuilderPipelines.cpp` (`buildO1FunctionSimplificationPipeline`, `buildO0DefaultPipeline`, `OptimizationLevel`); `llvm-project-llvmorg-23.1.6/llvm/include/llvm/Analysis/InlineCost.h` (`OptSizeThreshold`, `OptMinSizeThreshold`, `OptAggressiveThreshold`); `cig-script/src/lower/cir/pass/mod.rs` (`level`); `cig-script/src/lower/mod.rs` (`DEFAULT_LEVEL`).

### 5. The late module-optimization stage and why `LoopSink` is last

- **What it does, and why.** `buildModuleOptimizationPipeline` runs after `buildModuleSimplificationPipeline` has returned. It starts with `GlobalDCEPass` (optionally after `PartialInliner`) and `ReversePostOrderFunctionAttrsPass`, re-runs `GlobalsAA`, does a single `LoopRotate` to re-rotate loops that `SimplifyCFG` may have un-rotated, `LoopDeletion`, optional `LoopInterchange`, `LoopDistribute`, `InjectTLIMappings`, then the vectorizers in `addVectorPasses`: `LoopVectorize`, `InferAlignment`, `InstCombine`, extra passes gated on `ExtraVectorizerPasses`, a canonicalizing `SimplifyCFG` (with `forwardSwitchCondToPhi`, `convertSwitchToLookupTable`), `SLPVectorizer`, `VectorCombine`, `InstCombine`, `LoopUnroll`, another `SROA(aggregateToVector=true)`, `InferAlignment`, `InstCombine`, late `LICM`. Then: `LoopSink`, `InstSimplify`, `DivRemPairs`, `MergeICmps`, `ExpandMemCmp`, `TailCallElim`, final `SimplifyCFG(convertSwitchToLookupTable)`. The comment states that `LoopSink` sinks instructions that `LICM` hoisted and must be run very late so other passes cannot undo it; `DivRemPairs` after sinking so it has final positions; `SimplifyCFG` with `convertSwitchToLookupTable` only here because this is the last time the CFG will be shaped before codegen.
- **For cig: adapt.** cig has no vectorizer and no `LoopSink`, but the principle stands: a late stage that commits to a shape codegen will take, run after inlining has finished (so it sees a stable call pattern). Decided by rule 7 (verified bytecode, never rewritten): the late stage finishes before the bytecode emitter runs, which already happens in `cig-script/src/lower/bc/mod.rs`. cig's form: a second phase of `run_passes` called after the inliner walk, running `dead-pure` again and the passes #33's table names at `-O2` and `-O3` that only make sense after inlining decisions have settled (`rc elision` at stage C, `string builder`, `tail calls` at `-O3`; `string builder` and `tail calls` are #33's own spellings, table row names).
- **What would decide it.** Not measured yet: compare a one-stage pipeline (every pass once, pre-inline) to a two-stage one (post-inline late passes) at `-O2` on `orchestrate.cig`; the measurement is runtime and instruction count after the final pass.
- **Feeds.** #33 (late passes), #37 (compile time budget at `-O2`).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Passes/PassBuilderPipelines.cpp` (`buildModuleOptimizationPipeline`, `addVectorPasses`, `LoopSinkPass`); `cig-script/src/lower/bc/mod.rs` (`lower`, `compile`, `CompileError`).

### 6. SROA, then Mem2Reg: how a frontend's memory becomes SSA

- **What it does, and why.** `SROA` ("scalar replacement of aggregates") is run first in the function pipeline to split aggregate allocas (structs, arrays) into per-member allocas and then promote the promotable ones. It walks `alloca` instructions in the entry block, slices each by its use pattern, and lowers each slice to a scalar `alloca` or directly to an SSA value if its address is never taken. `Mem2Reg` (`PromoteMemToReg` in `Mem2Reg.cpp`) does the plain SSA construction: it collects promotable allocas, places phi nodes using dominator frontiers, and rewrites loads and stores into pure SSA. Both preserve the CFG (`PA.preserveSet<CFGAnalyses>()` in `Mem2Reg.cpp`): they never create or delete a block, so the dominator tree, the loop info and the branch probability information all survive. The order (SROA first, Mem2Reg second or implicit inside SROA) is there because the aggregate split must happen before promotion: a struct alloca is not promotable but a scalar is.
- **For cig: not applicable.** CIR has no aggregate allocas: `ir.rs` (`Ty`) lists `Dynamic, Null, Bool, Int, Float, Str, List, Map, Func`, and `cig-script/src/value.rs` (`Value`) carries each as a single enum variant backed by an `Rc`. A list or a map is a `Rc<RefCell<..>>` that cannot be split at the CIR level. ### 7. EarlyCSE then GVN: cheap redundancy first, exhaustive redundancy later

- **What it does, and why.** `EarlyCSE` (`EarlyCSE.cpp`) does a single dominator-tree walk with a scoped hash table keyed on each instruction's class and operands; a use that hits is replaced by the earlier value and discarded. It is called in two forms: without MemorySSA at the start of the pre-inliner pipeline (cheap), and with MemorySSA (`EarlyCSEPass(true)`) at the start of the function pipeline (still cheap, but now it folds redundant loads through may-alias sets). `GVN` (`GVN.cpp`, 4,073 lines) is value numbering: it builds equivalence classes over the whole function (not scoped to a dominator path), does partial redundancy elimination through `MemoryDependenceAnalysis`, and forwards loads from stores and from earlier loads even across block boundaries. EarlyCSE is in `-O1` and `-O2`; GVN is only in `-O2` and `-O3`. The ordering reason the comments state: EarlyCSE removes the cheap redundancies so GVN's PRE worklist is shorter, and InstCombine between them turns rewrites into forms both passes can see.
- **For cig: adapt.** cig has neither pass today. The two-step shape (cheap then global) is what to take: at `-O1`, a scoped dominator-walk CSE that only values pure instructions and reads from a slot not written in between; at `-O2`, a global VN that reaches across the structured blocks (an `if`'s two arms produce distinct value numbers, but a value number computed in the parent is seen in both arms). Decided by rule 1 (burns never move) and rule 2 (errors at the same place): a redundancy may not be eliminated across a `BurnOp` unless `effects.rs` declares the burn does not write the state the value reads; a `MayRaise` operation may only be eliminated by `T4`'s proof.
- **What would decide it.** Not measured yet: implement a scoped CSE at `-O1` and measure `spectral`'s runtime stage B before and after; separately, implement a global VN at `-O2` and report the extra instructions removed and the extra compile time per 1000 lines.
- **Feeds.** #33 (`gvn/cse` row), decision (c) (what belongs at `-O1` against `-O2`).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Transforms/Scalar/EarlyCSE.cpp` (`EarlyCSEPass`, `EarlyCSELegacyCommonPass`); `llvm-project-llvmorg-23.1.6/llvm/lib/Transforms/Scalar/GVN.cpp` (`GVNPass`, `processBlock`, `processLoad`); `cig-script/src/lower/cir/effects.rs` (`kind_of`, `Resolver`).

### 8. LICM's safety test, and why there are two LICM invocations around LoopRotate

- **What it does, and why.** `LICM.cpp` (3,064 lines) hoists loop-invariant pure code into the preheader and sinks it to exit blocks when safe. The safety test for hoisting is `isSafeToExecuteUnconditionally(Inst, DT, TLI, CurLoop, SafetyInfo, ORE, CtxI, AC, AllowSpeculation)`: if `AllowSpeculation` is on and `isSafeToSpeculativelyExecute` returns true, the hoist is allowed; otherwise the instruction must be guaranteed to execute in the loop (`SafetyInfo->isGuaranteedToExecute`). `AllowSpeculation` is passed false the first time LICM is called in the function pipeline (`LICMPass(..., AllowSpeculation=false)`) and true the second time, right after `LoopRotatePass`. The comment states the reason: speculative hoisting destroys metadata that `LoopRotate` may need, so the first pass only hoists the code it can prove is always executed, the rotate runs, and the second pass picks up the rest. The scalar-promotion side promotes must-aliased memory locations to registers by inserting a preheader load, in-loop loads and stores on the register, and exit-block stores back. `LICM.cpp:promoteLoopAccessesToScalars` runs only when there are no conflicting reads or writes to the pointer from unanalyzable instructions (`noConflictingReadWrites`).
- **For cig: take.** This is CIR's `MayRaise` rule written as code. The equivalence: LLVM's `isSafeToExecuteUnconditionally(..., AllowSpeculation=false)` is CIR's `T4` (an operation that may raise is removed only when proven unable to); LLVM's `AllowSpeculation=true` is what cig would allow once it knows a loop runs at least one iteration and knows the raise would happen then. Decided by rule 1 (burns never move) and rule 2 (errors at the same place). cig's form: a `licm` pass that uses `ir.rs:Kind::class` to divide the loop body into `Pure` (may hoist freely), `MayRaise` (may hoist only when the loop surely runs once or the raise is proven impossible), `Effect` and `Step` (never hoisted). The two-LICM pattern around a future loop-rotate pass is the model.
- **What would decide it.** Decided by rule 1 and rule 2. The census (`data/census/README.md`, finding 1) measures the floor on what cannot move: a quarter of a compute program's executed instructions are `Step` marks that `T3` pins. What is still open is the share of pure loop-invariant work in a compute program (not measured) and how much `licm` would move once the `MayRaise` safety analysis is written; not measured yet, time `spectral`'s inner loop before and after LICM is wired in, stage B.
- **Feeds.** #33 (`licm` row), decision (d) (guards and exits that keep the step count and the open burns).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Transforms/Scalar/LICM.cpp` (`isSafeToExecuteUnconditionally`, `AllowSpeculation`, `promoteLoopAccessesToScalars`, `noConflictingReadWrites`); `llvm-project-llvmorg-23.1.6/llvm/lib/Passes/PassBuilderPipelines.cpp` (`LICMPass`, `LoopRotatePass`); `cig-script/src/lower/cir/ir.rs` (`Class`, `MayRaise`); `cig-script/src/lower/cir/verify.rs` (`T4`).

### 9. InstCombine: a worklist of rewrites that strictly simplify

- **What it does, and why.** `InstructionCombining.cpp` runs a worklist-driven set of peephole rewrites over a function and, by contract, every rewrite makes the instruction graph strictly simpler. The pass guarantees a fixed set of canonicalizations (`Passes.md`): a binary operator's constant operand is on the right; shifts come before `or`s, `and`s and `xor`s in bitwise chains; `<`, `>`, `<=`, `>=` become `==` or `!=` when possible; `cmp` on booleans becomes a logical op; `add X, X` becomes `shl X, 1`; power-of-two multiplies become shifts. The default `InstCombineDefaultMaxIterations = 1`: each invocation is expected to reach a fixpoint in one sweep. If a run goes past `MaxIterations` and `VerifyFixpoint` is on, the pass raises a fatal usage error that names the function. This discipline ("every rewrite strictly simplifies") is what allows the pass to run inside the function pipeline at every joint between heavy passes without cost tracking: it will not loop.
- **For cig: adapt.** cig's `fold-consts` is the start of this: a rewrite set over pure binary and unary ops, bounded by the term becoming constant. Adopt the "strictly simpler" rule as a property of each new rewrite: write it so no sequence of rewrites loops. Decided by rule 5 (identical behavior on every engine): a rewrite that is not confluent would produce different CIR on different runs. cig's form: `cir/ir.rs:fold_binary` is the shared folder `verify.rs` and the pass both call; a new `peephole` pass adds a short rule list (identities, double-negation, concatenating interpolation) and is verified with the same `broken.rs` discipline that `pass/broken.rs` records today.
- **What would decide it.** Not measured yet: the test is a golden-file suite of 20 CIR snippets, each run through the peephole pass to a fixpoint in a single sweep; the suite fails if any snippet needs two sweeps.
- **Feeds.** #33 (`fold-consts` grown into a peephole set).

### 10. The inliner's cost model: thresholds and bonuses

- **What it does, and why.** `InlineCost.cpp` computes a per-call cost (an unsigned-ish `int` where small means more likely to inline) and compares it to a threshold that depends on the site. The default threshold is `225` (`DefaultThreshold`), `250` at `-O3` (`InlineConstants::OptAggressiveThreshold`), `50` at `-Os` (`OptSizeThreshold`), `5` at `-Oz` (`OptMinSizeThreshold`). A callee with `inlinehint` raises the threshold to `325`; a `cold` or cold-callsite callee drops it to `45` (`ColdThreshold`, `ColdCallSiteThreshold`). A loop in the callee adds a `LoopPenalty = 25`. The cost accounting walks the callee counting instruction costs, subtracting bonuses for constants that will flow in from the call site (the "call simplification" bonuses), subtracting a bonus when the call is the only call of the function (so the callee goes away after inlining). An `inline-cost-benefit-analysis` mode (`-inline-enable-cost-benefit-analysis`, off by default) measures cycles saved against bytes added and takes `InlineSavingsMultiplier = 8`, `InlineSavingsProfitableMultiplier = 4`, `InlineSizeAllowance = 100` as its scaling factors. A recursive callee is bounded by `TotalAllocaSizeRecursiveCaller = 1024` bytes of stack.
- **For cig: adapt.** cig has no inliner. Adopt the shape, not the numbers: one cost in CIR-instruction units, one threshold per level, bonuses for constants that flow in at the call site, a penalty for loops in the callee. #33 plans "small pulls (by CIR size) and single-call pulls inlined"; `cig-script/src/lower/cir/ir.rs` declares `Func` with `requires_burn` among its fields: a `requires_burn` callee may never be inlined across a region boundary (rule 1, `T1`). The thresholds are measured, not copied. cig's form: a new `inline_cost(Func, call_site) -> i32` function in `cir/pass/inline.rs`, and a `level`-dependent threshold constant named next to the `level` function in `cig-script/src/lower/cir/pass/mod.rs`. The census (`data/census/README.md`) measures that 28 of 29 call sites in the compute programs call one function for the whole run and every function was only ever called with one row of argument types: a trivial inliner that targets single-callee sites would hit nearly all of them.
- **What would decide it.** Settled in part by the census (`data/census/README.md`, finding 4): with single-callee sites dominating (28 of 29 in compute) and one argument-type row per function, a very low threshold (close to "inline if the site has one callee") captures most of the gain without a tuned cost model. What is still open is the threshold-vs-size trade-off on cigo-scale code and the right cost unit (CIR instructions vs. a weighted metric). Not measured yet.
- **Feeds.** #33 (`inline` row), decision (a) (value representation changes what a CIR instruction costs).
- **Read.** `llvm-project-llvmorg-23.1.6/llvm/lib/Analysis/InlineCost.cpp` (`getInlineParams`, `getInlineParamsFromOptLevel`, `DefaultThreshold`, `HintThreshold`, `ColdCallSiteThreshold`); `llvm-project-llvmorg-23.1.6/llvm/include/llvm/Analysis/InlineCost.h` (`OptSizeThreshold`, `OptMinSizeThreshold`, `OptAggressiveThreshold`, `LoopPenalty`, `TotalAllocaSizeRecursiveCaller`); `cig-script/src/lower/cir/ir.rs` (`Func`).

### 14. Alive2's refinement check: six questions per pair of functions

- **What it does, and why.** For a source function `src` and a target function `tgt`, Alive2 asks whether `tgt` refines `src`: for every input, every behavior of `tgt` is a behavior of `src`, but not necessarily the other way. `tools/transform.cpp` (`check_refinement`) builds the SMT formula and asks the solver six questions in order (each can short-circuit the rest): 1 UB (`fndom_a.notImplies(fndom_b)`, "Source is more defined than target"); 2 return domain (`fndom_a && fndom_b && retdom_a != retdom_b`, "Source and target don't have the same return domain"); 3 poison (`dom && !poison_cnstr`, "Target is more poisonous than source"); 4 undef (`dom && encode_undef_refinement(..., ap, bp)`, "Target's return value is more undefined"); 5 value (`dom && !value_cnstr`, "Value mismatch"); 6 memory (`src_mem.refined(tgt_mem, ...)`, "Memory does not refine"). Each `CHECK(...)` runs the SMT solver (Z3 by default); unsat means the question has no counterexample and the next one is asked, sat produces a concrete input and the counterexample value for the report. The whole shape is: axioms over the source and target states, a precondition linking their inputs, the refinement predicate. The paper formalizes the refinement with a program-state tuple `(R, M, b)` (register file, memory, UB flag) and defines `tgt` refines `src` as "for every input, every final state of `tgt` is one that `src` could also produce" (paper §3). Refinement is strictly weaker than equivalence: a target that returns a single concrete value for an input where the source may return `undef` (any value) still refines. This is the direction of the arrow a correct optimizer wants: more defined, less non-determinism.
- **For cig: adapt.** CIR has no immediate UB, no deferred UB (no `undef`, no `poison`), no `freeze` instruction; checks 1, 3 and 4 do not apply. A CIR semantic check reduces to checks 2 (both reach `Yield`/`Ret` on the same inputs), 5 (same return value when both return), and 6 (the same effects were burned in the same order, and the same journal entries). Decided by rules 1, 2 and 5. cig's form: a new `tv.rs` module in `cig-compile/src/` beside `cig-compile/src/reduce.rs` and `cig-compile/src/fuzz.rs` that encodes two CIR functions as SMT and asks the three questions; the `T1..T4` already in `cig-script/src/lower/cir/verify.rs` proves half of check 6 structurally, so TV only tests the remaining equivalence.
- **What would decide it.** Not measured yet: a small corpus of 20 CIR functions, each with a known-good target produced by `fold-consts` and `copy-prop`; the TV must say "correct" on all 20 in under 10 s each (budget consistent with #39's `equivalence check on small functions`).
- **Feeds.** #39 (`translation validation`), #33 (per-pass verification).
- **Read.** `alive2-v21.0/tools/transform.cpp` (`check_refinement`, `TransformVerify::verify`); `alive2-v21.0/ir/state.cpp` (`State`); `alive2-v21.0/README.md` (overview); `papers/compilers/lopes-2021-alive2.pdf` (Section 5); `cig-script/src/lower/cir/verify.rs` (`T1`, `T2`, `T3`, `T4`).

### 15. The IR encoding: `StateValue` and the fresh-undef-per-use rule

- **What it does, and why.** `ir/state_value.h` defines `struct StateValue { smt::expr value, non_poison; }`: every IR value becomes a pair of SMT expressions, a bit-vector (or FPA) carrying the value and a Boolean carrying whether the value is not poison. Integers are bit-vectors, floats use SMT's FPA theory, aggregates concatenate bit-vectors element-wise, pointers concatenate block-id and offset (`ir/pointer.h`). An `undef` input is represented as `ite(isundef_a, undef_1, a)` where `undef_1` is a fresh SMT variable quantified so it can take any value of its type, and the paper explains (Section 3.3) that each observation of `undef` rewrites `undef_i` with a fresh variable; the `freeze` instruction stops that rewriting by clearing the undef set. Memory (`ir/memory.cpp`) is a map from block id to a record (data, size, alignment, alive bit). Partial `undef` (one bit in an `i32` is undef, the rest are defined) is deliberately under-approximated by Alive2: it allows only "fully undef" or "fully defined" to keep the state space merely exponential rather than doubly-exponential (`2^(2^n - 1)` for an `n`-bit integer). Section 3.3 justifies this trade: "We believe the potential for missed bugs is small." This encoding is why the refinement check can be compact: the single question "is tgt's `non_poison` at least as strong as src's" replaces a case-split on every possible poison trace. For NaN bitcasts, where two readings of IEEE-754 collide (preserve the bit pattern, or allow a nondeterministic canonicalization), Alive2 chose the second (paper §3.5) to support hardware that canonicalizes.
- **For cig: adapt.** CIR values are a concrete runtime type (`Int`, `Float`, `Str`, `List`, `Map`, ...), not a pair with a poison flag. A `StateValue` for cig has one half: the value. There is no `non_poison`, no `isundef`, no `freeze`. That is a smaller SMT encoding than Alive2 carries; Lopes et al. list "about 23,000 lines of C++" for the whole tool (paper, §8.1), of which a large part is the undef/poison and memory lattice; dropping that lattice is where the simplification lives. Decided by rule 4 (floats are IEEE-exact: CIR's Float maps to SMT's FPA with no `nnan`/`nsz` flags), rule 2 (errors happen at the same place: a raise is a concrete value in the SMT model, not a nondeterministic poison).
- **What would decide it.** Not measured yet: a draft encoding of `Ty::Int`, `Ty::Float` and `Ty::Str` as SMT bit-vectors and strings, one at a time, timed on the 20-function corpus; the metric is median solver time per function.
- **Feeds.** #39 (encoding), decision (a) (value representation shapes the SMT type).
- **Read.** `alive2-v21.0/ir/state_value.h` (`StateValue`, `value`, `non_poison`); `alive2-v21.0/ir/state.h` (`class State`, `ValTy`); `alive2-v21.0/ir/state.cpp` (`SMTMemoryAccess`); `alive2-v21.0/ir/memory.cpp` (`Memory`); `alive2-v21.0/ir/instr.cpp` (`BinOp`, `ICmp`, `Phi`); `papers/compilers/lopes-2021-alive2.pdf` (Section 3); `cig-script/src/lower/cir/ir.rs` (`Ty`).

### 16. The bounds: what "bounded translation validation" bounds, and what it skips

- **What it does, and why.** Alive2 bounds the work with `src_unroll_cnt` and `tgt_unroll_cnt` (`util/config.h`): each loop is unrolled inside-out by Tarjan-Havlak's loop analysis (paper, Section 7), with every backedge of the last unroll redirected to a sink basic block. The sink's reachability is negated and added to the function's precondition, so a model that reaches the sink is excluded from refinement (that trace is "out of bounds", not a counterexample). Address space and pointer width are capped by `max_offset_bits` and `max_sizet_bits`. The default for both unroll factors is 0: `llvm_util/cmd_args_list.h:22-29` declares `opt_src_unrolling_factor`, `opt_tgt_unrolling_factor` and the single `opt_unrolling_factor` (used when not built with `ARGS_SRC_TGT`) each with `cl::init(0)`; the `tv` plugin's tests in `tests/clang-tv/` typically pass `-tv-src-unroll=2 -mllvm -tv-tgt-unroll=2` (`tests/clang-tv/issue569.cpp:1`, `tests/clang-tv/issue579.c:1`). The README states the known limit: "Alive2 does not support inter-procedural transformations. Alive2 may produce spurious counterexamples if run with such passes." The plugin handles that by skipping unsupported passes. The paper's §7 adds: for optimizations that do not manipulate loops the unroll factor should be at least 2; for loop-manipulating optimizations it may have to be 64 (a vectorizer that collapses 32 iterations into one needs 64 source unrolls to cover two target iterations).
- **For cig: adapt.** cig loops (`cir/ir.rs:Kind::Loop`, `Kind::ForEach`) have no induction variable analysis today and no planned unroller before stage D (#34). A CIR TV can pick a small fixed unroll factor (2 for simplification passes, higher only when a loop-manipulating pass lands) and use the same sink-BB trick; interprocedural passes (inlining) are skipped exactly as Alive2 does. Decided by rule 5 (every engine computes the same answer): spurious counterexamples in TV are themselves a correctness concern, so the sink-BB skip is the only sound way.
- **What would decide it.** Not measured yet: on the 20-function TV corpus, measure refinement time at unroll 2, 4, 8, 16, 32, 64, and plot wall time vs. unroll factor; the operational budget is 10 seconds per function so the CI gate stays under the PR's 10-minute wall time (#39).
- **Feeds.** #39 (TV bounds), #33 (bisect's own time budget).

### 17. The `tv` plugin, and what a CIR verifier would own that `T1..T4` do not

- **What it does, and why.** `tv/tv.cpp` installs an LLVM plugin that captures each function's Alive2 IR before each pass (via `registerBeforeNonSkippedPassCallback`), captures it again after each pass (via `registerAfterPassCallback`), and runs `TransformVerify::verify` on the pair. If the source and target print byte-for-byte equal (`src_tostr == tgt_tostr`), the plugin prints "Transformation seems to be correct! (syntactically equal)" and skips SMT entirely (the paper calls this "trivial but effective"). Repeated queries are cached in Redis if configured, keyed by the concatenation `src_tostr + "===\n" + tgt_tostr`. For parallel work the plugin `fork()`s one child per verification and limits children with a job server. `BugList.md` records 99 LLVM bugs and 24 Z3 bugs this tool has found at `v21.0`; the paper's §8 reports 121 refinement violations in the LLVM unit tests, of which 47 were reported.
- **For cig: adapt.** The plugin shape maps onto cig: `cir/pass/mod.rs:run_passes_inner` is where a `tv_mode: bool` option captures the pre-pass and post-pass CIR, asks the SMT backend about refinement, and prints a result the same way. The byte-equal shortcut carries over: cig's `cir/print.rs` produces a canonical text form today (used for golden tests), so a byte-equal pre/post can skip SMT. What `T1..T4` do not cover: they enforce *structural* equivalence under the four transition rules, not *value* equivalence. A pass that keeps every effect in place but changes a value's integer result (a wrong fold of `2 + 3` to `6` is fine, a wrong fold of `2 + 3` to `7` is not) passes `T1..T4` and fails TV. Decided by rules 2 and 5: cig needs both the structural check and a value refinement check, not either alone.
- **What would decide it.** Not measured yet: plant a wrong-arithmetic bug in `fold-consts` (e.g. `*` returns `x + y` instead of `x * y`), run both `verify.rs:verify_transition` and a planned `tv.rs:refines` on the fuzz corpus, and report how many functions each catches; the TV should catch strictly more.
- **Feeds.** #39 (per-pass TV), decision (c) (TV's budget shapes how often PGO can afford to run it).
- **Read.** `alive2-v21.0/tv/tv.cpp` (`runOnModule`, `verify`, `TVPass`, `registerBeforeNonSkippedPassCallback`, `registerAfterPassCallback`); `alive2-v21.0/README.md` (plugin usage); `alive2-v21.0/BugList.md` (99 LLVM bugs); `papers/compilers/lopes-2021-alive2.pdf` (Section 8); `cig-script/src/lower/cir/pass/mod.rs` (`run_passes_inner`, `run_passes_with_remarks`); `cig-script/src/lower/cir/verify.rs` (`verify_transition`); `cig-compile/src/fuzz.rs` (fuzz corpus).

## Not settled

- Settled on the second read (`llvm_util/cmd_args_list.h:22-29`): `-tv-src-unroll` and `-tv-tgt-unroll` both default to 0 (via `cl::init(0)`), and the standalone `-tv-unroll` (used when the build is not configured for separate source/target factors) also defaults to 0; the plugin tests that need loops pass `-tv-src-unroll=2 -mllvm -tv-tgt-unroll=2` explicitly. Figure added to entry 16.
- Whether cig's eventual TV can validate an `inline-small` pass at all: Alive2 declares interprocedural passes out of scope (`README.md` warning, entry 16). The answer depends on whether cig's inliner is modeled as a single-function rewrite (the inlined call becomes a block in the caller) or as a two-function change. If the former, TV can verify it; if the latter, TV cannot, and the inliner's correctness rides on the fuzz corpus.
- Whether `GVNHoist` and `GVNSink` (off by default in LLVM: `EnableGVNHoist` and `EnableGVNSink` both initialise to `false`) are worth building for CIR: they only help when common code lives in both arms of an `if`, and CIR's structured shape should make them cheap, but I found no measurement in the pinned tree that says what they buy.
- Whether cig's PGO format should carry the per-branch weight as a count (the `!prof` metadata LLVM uses) or as a ratio (a byte on 0-255). LLVM's `PGOInstrumentationUse` attaches the raw count; the ratio would be smaller in a `.cigprof` payload but loses information when combined across runs. Decided by a read of #33's `--profile-use` user story that was not in the issue copy I had.
- Whether cig's bottom-up walk should pick strongly connected components (LLVM's CGSCC) or a simple post-order over the call graph. SCCs matter only when there is mutual recursion; how much cig code has mutual recursion today is not read from the clones, and an SCC-aware walk is harder to get right. A post-order walk with a visited-set and a conservative "do not inline into a cycle" rule would be simpler and would lose little.
- Whether `Reassociate` (entry 3) should be a cig pass at all. It changes the shape of an expression tree so later passes see more invariants, but CIR's expression trees are smaller than LLVM's and floats are IEEE-exact (rule 4), so the main `Reassociate` move (`4 + (x + 5) -> x + (4 + 5)`) is only sound for integers; on floats it is a rule-4 violation. A cig-reassociate would have to type-check and only reassociate integer chains.
- Whether cig's `-O1` should include a scoped CSE at all (entry 7). LLVM's `-O1` runs `EarlyCSE` with MemorySSA; cig has no MemorySSA analog today and `copy-prop` already catches the simple local redundancies. The cost of a dominator walk at `-O1` against the gain was not measured.
- Whether cig's bisect counter should be per-function or global (entry 12). LLVM's is global and `FunctionPass` invocations each take one counter value, which is slower to narrow than a per-function counter but gives a simpler mental model to the user.
- The exact size of the SMT encoding of a CIR `List` or `Map` (entry 15). A `List` is a `Rc<RefCell<Vec<Value>>>`; in SMT it could be an uninterpreted array of value-encodings, but the solver's handling of its length is the hard bit. The 20-function corpus measurement (Measurements owed) will tell.
- Whether cig's SMT encoding should model the step budget (`STEPS` in the bytecode, `E515` at the budget's expiry). Including it adds one integer counter to every SMT state, which doubles the width of the state value. Leaving it out means TV cannot catch a pass that changes step counts; `verify_transition`'s `T3` already does (`T3` catches a lost or cloned step mark), so leaving it out of TV may be defensible.
- Whether the `PreservedAnalyses::preserveSet<CFGAnalyses>()` shape from `Mem2Reg.cpp` maps onto cig's structured IR. CIR has no `BasicBlock`-level CFG; its blocks nest under owning nodes. A "CFG analysis" over CIR might be the shape of its nested-block tree, which every pass structurally preserves unless it explicitly rewrites a control-flow node.
- Whether cig's `JumpThreading`-analog pass has anything to do today. LLVM's `JumpThreading` is run twice in the function pipeline because `InstCombine` and loop passes expose more threadable branches each time. CIR's structured `if` has far fewer branch chains to thread, but `short-circuit` (`Kind::Short`) in `ir.rs` is a case worth measuring.
- Whether PGO's indirect-call-site data (LLVM's `PGOIndirectCallPromotion`) applies to cig. The study set aside that cig's inline caches already track one receiver type per `callm` site (`cig-script/src/vm/mod.rs`, `Proto`, `hints: Vec<std::cell::Cell<u32>>` at line 285); whether a `.cigprof` records the top receivers across many runs, or whether per-site caches suffice, was not resolved.
- The right shape of a cig TV cache (LLVM's `ALIVECC_BATCH_OPTS` and Redis cache, `tv/tv.cpp:runOnModule`). For CI the cache would avoid re-solving refinement for pass pairs that have been seen; the cache key is the Alive2 IR text (`src_tostr + "===\n" + tgt_tostr`) at LLVM, and for cig it would be the printed CIR before and after.
