## What cig should carry away

- The compiled artifact is one ELF file, read-only on disk, with a dozen named Wasmtime sections next to the `.text`. Trap codes, stack maps, exception tables and address maps are compact binary sections that are decoded in place: no post-processing after mmap, no per-entry allocation. cig's own program-file for stage C is close to the same idea, with one more section recording the runtime ABI version and the module's signature (entries 1 to 3, 10, 13, 14, 15).

- Loading is three permission changes: read-write while bytes are placed, read-only once everything is in place, read-execute only for the `.text` range at publish time. The artifact is never both writable and executable, and a loader that has no way to make memory executable is caught by a specific check with a specific error (entry 5).

- The engine-compat header is a one-byte version, then a length-prefixed version string, then a postcard-encoded struct carrying target, compiler flags, tunables and the wasm feature set. It is the first thing read, and it is "extra hardened" against mismatched hosts: cig's own program header needs the same discipline, and should check it before any other byte is trusted (entry 6).

- Fuel is charged in a function-local register that is loaded from `VMStoreContext` at entry, incremented by the sum of a block's operator costs on exits, checked on function entry and before any instruction that leaves the function, and spilled back to the store around calls. The counter stays close to the operator but is not literally after every operator: cig's "exact step budget" would need a stricter emission (entries 7, 8).

- Calls into the runtime do not use relocations against the libcall's native symbol. They go through a `builtin_functions` array hanging off `VMContext`: load the array base, load a slot by index, call indirect. Every builtin has a `trap_sentinel` that the generated wasm-to-builtin trampoline tests and converts to a `raise` libcall. A result-convention is already what Wasmtime uses for host returns; its own unwinder handles the cross-function `throw` case (entries 12, 14).

- A trap code is a single byte, and the `.wasmtime.traps` section is a two-level table (fixed-width block index, variable-length block bodies with a per-block default code) that averages a bit over one byte per entry. The same shape covers the pc-to-source address map. cig's "errors happen at the same place" rule (rule 2) is what the byte-plus-span section is for (entries 2, 10, 13).

- The on-disk cache key is a SHA-256 over the hashed state, the compiler version and (for git builds) the compiler's mtime. Entries are zstd-compressed, and a background worker enforces LRU eviction on file count and total size. cig's `modcache.rs` already does the key-plus-MAC part under its own rules; the store layout and the worker's eviction loop are close models for cig-cherry's cache (entry 16).

- Winch is one pass over the WebAssembly bytecode: no IR, a shadow value stack whose entries are either a constant, a local, a memory slot or a typed register, and a single-pass register allocator backed by a bitset freelist. For cig-cherry's tier 2, a shadow stack over CIR values and a freelist allocator buy a baseline compiler in roughly the size of Winch itself (entry 17).

- Pulley is a portable bytecode-plus-interpreter that Cranelift targets where it has no native back end. cig does not need it (cig's VM is portable, and stage B serves 32-bit ARM already) but Pulley's macro-defined ISA and its two interpreter loops (one `match`, one tail-call) are a good cross-reference for cig-script#243's VM design (entry 18).

## Design points

### 1. The compiled artifact: an ELF with Wasmtime sections

- **What it does, and why.** `wasmtime::Module::precompile_module` produces an ELF file (even on non-ELF platforms) whose `e_ident.os_abi` is `ELFOSABI_WASMTIME = 200` and whose `e_flags` carry `EF_WASMTIME_MODULE` or `EF_WASMTIME_COMPONENT` plus, when targeting the portable interpreter, `EF_WASMTIME_PULLEY32` or `EF_WASMTIME_PULLEY64`.

Beyond `.text` and the standard `.rodata`, the file holds a set of custom sections with fixed names: `.wasmtime.addrmap` (pc-to-source map), `.wasmtime.stackmap` (gc roots per pc), `.wasmtime.traps` (trap code per pc), `.wasmtime.exceptions` (handler tables), `.wasmtime.frames` (debug frame slot tables), `.wasmtime.bti` (one byte flagging branch protection), `.wasmtime.engine` (the compatibility header), `.wasmtime.info` (bincode of `CompiledModuleInfo`), `.rodata.wasm` (concatenated data segments), `.name.wasm` (function names), `.wasmtime.dwarf` (concatenated guest DWARF), `.wasmtime.wasm_bytecode` and `.wasmtime.wasm_bytecode_ends` (optional guest-debug source copies).

The loader recognizes each by name, keeps a byte range for it, and reads it in place. A section not in the list is a load-time error, so an artifact that strays from this schema is noticed early (entry 2).
- **For cig: adapt.** By **rule 8** (no memory both writable and executable) and **rule 10** (ahead of time by default). cig's form today is the "program" built by cig-compile: the pinned `cig-runtime` binary with a payload trailer appended, each payload laid out as a sequence of program sections (`cig-compile/src/build.rs` writes the trailer; the section shape lives in `cig-script/src/program.rs`). cig-compile does not depend on the `object` crate and writes no ELF: there is no linker and no native-code emitter in cig today. Stage C grows both. Keep the per-section names and the one-section-per-concern layout for the native sidecars that stage C will add; add one cig-only section, `.cig.engine`, that records the runtime ABI version the program was built for (issue 32: `E1051` on mismatch).
- **What would decide it.** Decided by rule 8 and rule 10.
- **Feeds.** #32, #36; (e), (f).
- **Read.** `wasmtime-v50.0.1/crates/environ/src/obj.rs` (`ELFOSABI_WASMTIME`, `EF_WASMTIME_MODULE`, `EF_WASMTIME_COMPONENT`, `EF_WASMTIME_PULLEY32`, `EF_WASMTIME_PULLEY64`, `ELF_WASMTIME_ADDRMAP`, `ELF_WASMTIME_STACK_MAP`, `ELF_WASMTIME_TRAPS`, `ELF_WASMTIME_EXCEPTIONS`, `ELF_WASMTIME_FRAMES`, `ELF_WASM_BTI`, `ELF_WASM_ENGINE`, `ELF_WASM_DATA`, `ELF_WASMTIME_INFO`, `ELF_NAME_DATA`, `ELF_WASMTIME_DWARF`); `wasmtime-v50.0.1/crates/environ/src/compile/mod.rs` (`fn object`); `wasmtime-v50.0.1/docs/examples-minimal-cwasm.md`; `cig-script/src/lower/mod.rs` (`VERSION`, `module_bytes`).

### 2. Sections that are decoded in place, not parsed

- **What it does, and why.** Every Wasmtime sidecar section is encoded so that parsing is bounds-checks on offsets, not allocation. The trap section (`crate::compile::trap_encoding::TrapEncodingBuilder`) is a two-level table: a `(first_offset, data_pos)` fixed-width index per 128-entry block, followed by variable-length block bodies whose entries are `uleb((pc_delta << 1) | code_differs)` with an optional explicit code byte; lookup is a binary search on the index then a linear decode of at most 128 entries.

The address-map section has the same two-level shape (`compile::address_map::AddressMapSection`): a 128-entry block holds `(pc_delta << 1) | pos_is_none` with sleb-encoded source deltas. The stack-map section is three parallel arrays of `u32` plus a bitmap pool (`compile::stack_maps::StackMapSection`), read as `object::slice_from_bytes` with no per-entry allocation.

The shape is chosen for a specific property that the source spells out: consecutive instructions (or trap sites, or source positions) are close together, so pc-deltas usually fit in a single-byte leb128; and a block often has one dominant trap code or one short run of source positions, so an optional code byte and sleb-encoded deltas carry the rare exceptions without inflating the common case.
- **For cig: adapt.** By **rule 1** (burns never move) only indirectly: cig's own sidecars would never move an effect, and the shape here does not touch that rule. Adopt the two-level block layout for cig's compiled-program sidecars. cig's form: a `cig-script/crates/cig-bytecode` sidecar builder modeled on `TrapEncodingBuilder`, for CIR-span to text-offset.
- **What would decide it.** Not measured yet: section size per 10 kloc of lowered CIR on the test machine, in cig's stage-C pilot, against the older 5-bytes-per-entry layout.
- **Feeds.** #32, #36, #37; (e).
- **Read.** `wasmtime-v50.0.1/crates/environ/src/compile/trap_encoding.rs` (`TrapEncodingBuilder`, `TRAP_BLOCK_SIZE`, `seal_block`, `most_common_code`); `wasmtime-v50.0.1/crates/environ/src/compile/address_map.rs` (`AddressMapSection`, `ADDRMAP_BLOCK_SIZE`); `wasmtime-v50.0.1/crates/environ/src/compile/stack_maps.rs` (`StackMapSection`, `push`, `append_to`); `wasmtime-v50.0.1/crates/environ/src/trap_encoding.rs` (`lookup_trap_code`); `wasmtime-v50.0.1/crates/environ/src/address_map.rs` (`lookup_file_pos`, `ADDRMAP_BLOCK_SIZE`); `wasmtime-v50.0.1/crates/environ/src/stack_map.rs` (`StackMapSection`).

### 3. Relocations: which are resolved when the image is built

- **What it does, and why.** The code-memory loader refuses any relocation whose target is not a `.debug_*` section. That is checked explicitly inside `CodeMemory::new` (the `new` on the `impl CodeMemory` block): `reloc_section_target` returns the target of a `SHT_REL`, `SHT_RELA` or `SHT_CREL` section and the loader bails with `"section ... has unexpected relocations"` unless the target name starts with `.debug_`. To meet this, Wasmtime resolves every intra-module call at build time: `ModuleTextBuilder::append_func` iterates Cranelift's `MachBuffer` relocations and, for each, invokes a `resolve_reloc_target` closure (its parameter name) that maps a `FuncKey` to the target function's index in the text section. The resolved index is then passed to the `TextSectionBuilder::resolve_reloc` method, which patches the call instruction before the ELF is written. A compilation comment in `code_memory.rs` says that `floor`, `ceil` and similar operators are avoided in the Wasm-to-CLIF translator specifically so they do not end up as relocations against native libcalls.
- **For cig: adapt.** By **rule 8** and **rule 10**: no relocations left for load time means no part of the file needs writable pages to be patched, and the same bytes are the bytes that run. cig's form: cig-compile's embedded linker (issue 32 "linking without a system linker") takes this as a rule for its own output: all cross-pull calls resolved when the object is written; all calls into the runtime library through the builtin table (entry 12), never through a late-bound symbol.
- **What would decide it.** Decided by rule 8.
- **Feeds.** #32, #40; (e).
- **Read.** `wasmtime-v50.0.1/crates/wasmtime/src/runtime/code_memory.rs` (`reloc_section_target`, `is_reloc_section`); `wasmtime-v50.0.1/crates/cranelift/src/obj.rs` (`ModuleTextBuilder`, `append_func`, `resolve_reloc_target`, `resolve_reloc`); `cig-compile/src/build.rs`.

### 4. Reproducible builds, and the incremental Cranelift cache

- **What it does, and why.** The whole-program artifact is deterministic given the same input: `object`-crate construction sorts names and iterates in `SignatureIndex` order, and the metadata header is a `postcard` encoding of fixed fields (entry 6). Cranelift has a separate, per-function incremental cache that Wasmtime exposes through `CompilerBuilder::enable_incremental_compilation`: a `CacheStore` with `get(key) -> Option<Cow<[u8]>>` and `insert(key, Vec<u8>) -> bool`. The module-level on-disk cache (entry 15) layers on top. The function-level cache is distinct from the module-level one: it speeds up a rebuild, not a run.
- **For cig: adapt.** By **rule 8** (reproducibility is required for signing). cig's lowering carries a `VERSION` constant (`cig-script/src/lower/mod.rs`) that the module cache keys on, which is how a change in lowering invalidates old entries. cig's form: a per-function incremental cache that keys on CIR plus the target plus the compiler's version, matching the `CacheStore` shape, used only in `cig-cherry` and the stage-C compile path, never on load.
- **What would decide it.** Not measured yet: build time of `orchestrate.cig` on the test machine with and without the per-function cache enabled, against issue 37's build-speed budget of 10 s.
- **Feeds.** #32, #37; (e), (f).
- **Read.** `wasmtime-v50.0.1/crates/environ/src/compile/mod.rs` (`CacheStore`, `CompilerBuilder`, `enable_incremental_compilation`); `wasmtime-v50.0.1/crates/environ/src/compile/module_artifacts.rs` (`ObjectBuilder`, `append`, `sort_by_key`); `cig-script/src/lower/mod.rs`.

### 5. Loading without a page that is both writable and executable

- **What it does, and why.** `CodeMemory::new` (the loader's constructor on `impl CodeMemory`) parses the ELF with the `object` crate out of an `MmapVec` (a read-write mapping), walks the sections, and records byte ranges. The file is not made executable here.

`CodeMemory::publish` (the `publish` method on the same `impl`) runs the transition: first `make_readonly` over the whole mapping (every page read-only), then `make_executable` over just the `.text` range, then registering unwinding info and the GDB JIT image. At no point is any page both writable and executable; the bytes that will be executed are bytes that were frozen read-only first.

Targets whose virtual-memory support is disabled either take a `CustomCodeMemory::publish_executable` hook (a page-flip that the embedder performs) or fail with `"this target requires virtual memory to be enabled"`. A rare `unpublish` method exists for patching in place after a stop-the-world: it flips the mapping back to read-write for the whole image, and there is a safety comment at the top of it noting that any pc currently executing must be in a stopped frame before this is called.

The pre-compile docs state the W^X guarantee as a goal for embedders ("the `cranelift` and `winch` cargo features can be disabled" at build time for a runtime-only Wasmtime that can only load, never compile).
- **For cig: adapt.** By **rule 8** directly. cig's form: `cig-cherry` writes its native code into a file in the tin (cig-script#256 "Platforms and policy"), opens it read-only, maps it `PROT_READ`, then changes the text range alone to `PROT_READ|PROT_EXEC`. The `CustomCodeMemory` shape is the cig-side hook for platforms (iOS, hardened kernels) that forbid an anonymous executable mapping.
- **What would decide it.** Decided by rule 8.
- **Feeds.** #32, #40; cig-script#256; (e).
- **Read.** `wasmtime-v50.0.1/crates/wasmtime/src/runtime/code_memory.rs` (`publish`, `custom_publish`, `register_unwind_info`, `CustomCodeMemory`); `wasmtime-v50.0.1/docs/examples-pre-compiling-wasm.md`; `cig-script/src/burn/tin.rs`.

### 6. The compatibility header: what is checked before a file is trusted

- **What it does, and why.** The `.wasmtime.engine` section begins with a single-byte `VERSION`, then a length-prefixed Wasmtime version string, then a `postcard`-encoded `Metadata` struct that carries `target`, `shared_flags`, `isa_flags`, `tunables` and a `features` bitfield. `serialization::check_compatible` is the first thing the loader runs: it parses the ELF, requires that the `e_flags` match the expected kind (module vs component), finds the section by name, splits the version byte and the version string, and refuses on any mismatch. The `Metadata::check_compatible` method then field-by-field compares the target architecture, the compiler flags, every tunable (fuel, epochs, memory layout, inlining, stack-switching, GC) and the wasm feature set. The docs "once something successfully deserializes here it's assumed it's meant for this wasmtime" state the rule: this header is deliberately the first-and-most-hardened check.
- **For cig: adapt.** By **rule 5** (identical behavior on every engine) and **rule 10** (ahead of time by default). cig's form: `cig-script/src/lower/mod.rs` already carries a `VERSION`; add a `cig-compile` compat check that reads the program's header before mapping the text section, refuses a bytecode version, an operator-cost table, or a target triple that does not match. Store it as a fixed-shape struct, not an ad-hoc header, so cross-cig loading errors give the same message cig uses at the tree-walker.
- **What would decide it.** Decided by rule 5.
- **Feeds.** #32, #36, #40; cig-script#256.
- **Read.** `wasmtime-v50.0.1/crates/wasmtime/src/engine/serialization.rs` (`VERSION`, `Metadata`, `check_compatible`, `check_tunables`, `check_features`, `append_compiler_info`); `wasmtime-v50.0.1/crates/environ/src/obj.rs` (`ELF_WASM_ENGINE`); `cig-script/src/lower/mod.rs` (`VERSION`).

### 7. Fuel: an operator-cost table and a function-local counter

- **What it does, and why.** Fuel is a 64-bit signed negative counter: a program has fuel `fuel = -budget` and runs out when `fuel >= 0`. The compiler emits calls to `fuel_function_entry` at the start of every translated function; that declares `self.fuel_var`, loads the counter from `VMStoreContext::fuel_consumed` into it and calls `fuel_check` (entry 8).

Each operator carries a cost from a static table (`OperatorCost` built by `define_operator_cost!` over `wasmparser::for_each_operator!`): `Nop`, `Drop`, `Block`, `Loop`, `Unreachable`, `Return`, `Else` and `End` are 0, every other operator is 1.

`fuel_before_op` accumulates `self.fuel_consumed` and, at operators that transfer control (`Loop`, `If`, `Br`, `BrIf`, `BrTable`, `End`, `Else`), flushes the buffered cost into the local by `fuel_increment_var` (one `iadd_imm_s`). Variable-cost operators (`memory.copy`, `memory.fill`, `table.grow`, `array.copy`, and a few more) multiply by a per-byte or per-element factor from `VariableOperatorCost`.

A compilation comment in the source is explicit: the count is not exact per operator; "close to the actual amount is good enough". Trapping operators are deliberately not accounted for: the comment at the `fuel_before_op` site says a precise count would require saving the counter around every trappable op, which is not done.
- **For cig: reject.** By **rule 3** (the step budget is exact: `E515` falls on the same statement on every engine). Wasmtime's buffering is *fast* but not identical to the tree-walker's budget: across a block-exit it is behind by at most the block's buffered cost. cig's form today is `cig-script/src/lower/cir/ir.rs` `Kind::Step(StepSite)` plus the bytecode's `STEPS` opcode: one tick per statement and per loop iteration, checked at the mark's own span. For stage C, cig emits an explicit decrement-and-check at every `Step` mark that CIR records, not a buffered one; the operator-cost table is not what cig uses.
- **What would decide it.** Decided by rule 3.
- **Feeds.** #32; cig-script#256; (d).
- **Read.** `wasmtime-v50.0.1/crates/cranelift/src/func_environ.rs` (`fuel_function_entry`, `fuel_function_exit`, `fuel_before_op`, `fuel_after_op`, `fuel_increment_var`, `fuel_load_into_var`, `fuel_save_from_var`); `wasmtime-v50.0.1/crates/environ/src/tunables.rs` (`OperatorCost`, `OperatorCostStrategy`, `VariableOperatorCost`, `default_operator_cost`, `define_operator_cost`); `wasmtime-v50.0.1/docs/examples-interrupting-wasm.md`; `cig-script/src/lower/cir/ir.rs` (`StepSite`).

### 8. The fuel check, and the `out_of_gas` builtin

- **What it does, and why.** `fuel_check` emits: flush the buffered amount into the local, build an `out_of_gas_block` and a `continuation_block`, compare `self.fuel_var` against zero with `IntCC::SignedGreaterThanOrEqual`, and `brif` to the out-of-gas block on the positive side. The out-of-gas block spills `self.fuel_var` into `VMStoreContext` with `fuel_save_from_var`, calls the `out_of_gas` builtin with `vmctx`, then reloads the local with `fuel_load_into_var` and jumps to the continuation. That builtin may raise `OutOfFuel`, yield to an async runtime, or return with a fresh budget: the compiler does not assume. Checks are emitted at function entry and before any operator that leaves the function (`Call`, `CallIndirect`, `CallRef`, `Return`, `ReturnCall*`, `Throw`, `ThrowRef`, `Unreachable`). Exit uses `fuel_function_exit` to flush the final value back into the store.
- **For cig: adapt.** By **rule 3** on where to check (every `Step` mark), not on how (buffered register versus exact). cig's form: at every `Step` the compiler emits a `isub_imm` on a budget register and a `brif` to a cold block that calls into the runtime library for the identical error path the tree-walker uses. The save-around-call and reload pattern is correct and worth copying: a called function may itself charge, and the caller must see the updated budget after the return.
- **What would decide it.** Not measured yet: slowdown of an arithmetic-heavy script with and without the explicit per-statement check on the test machine (`loop`, `fib`, `nbody`), against issue 32's budget.
- **Feeds.** #32; cig-script#256; (d).
- **Read.** `wasmtime-v50.0.1/crates/cranelift/src/func_environ.rs` (`fuel_check`, `out_of_gas`, `fuel_save_from_var`, `fuel_load_into_var`); `wasmtime-v50.0.1/crates/environ/src/builtin.rs` (`out_of_gas`, `foreach_builtin_function`); `wasmtime-v50.0.1/crates/environ/src/trap_encoding.rs` (`OutOfFuel`).

### 9. Epochs: a cheap check against a cached deadline

- **What it does, and why.** Epoch interruption is the cheaper, non-deterministic alternative to fuel. The compiler declares two locals: `epoch_deadline_var` (the cached deadline) and `epoch_ptr_var` (a pointer to the engine's atomic counter). `epoch_function_entry` emits a full check on every function entry: the explanation in the source notes that a program could otherwise build a tree of calls with no backedges whose running time is exponential in its own size. `epoch_check` loads the current counter, compares it against the cached deadline (`IntCC::UnsignedGreaterThanOrEqual`), and `brif`s to a cold block that reloads the deadline from `VMStoreContext` and calls the `new_epoch` builtin, which returns the new deadline. The counter itself is an atomic integer that a host thread bumps; the docs quote around ten percent slowdown.
- **For cig: reject.** By **rule 3** (the step budget is exact). cig's budget is neither wall-time nor atomic; it is counted. Epochs are what cig would reach for only to interrupt an otherwise infinite computation outside the step budget, and that is not the step budget. Keep fuel's form; discard epochs.
- **What would decide it.** Decided by rule 3.
- **Feeds.** #32; (d).
- **Read.** `wasmtime-v50.0.1/crates/cranelift/src/func_environ.rs` (`epoch_function_entry`, `epoch_check`, `epoch_check_cached`, `epoch_check_full`, `epoch_load_current`, `epoch_ptr`); `wasmtime-v50.0.1/crates/environ/src/builtin.rs` (`new_epoch`); `wasmtime-v50.0.1/docs/examples-interrupting-wasm.md`.

### 10. Trap encoding: a native pc becomes a trap code

- **What it does, and why.** Every native instruction that can trap has a trap code set on the Cranelift `TrapCode` and preserved through to the `MachBufferFinalized`. At write time, `TrapEncodingBuilder::push` collects them into blocks of 128 entries. The code is a byte: `CompiledTrap::as_u8` maps a wasm `Trap` variant (from the `generate_trap_type!` macro enumeration in `trap_encoding.rs`: `MemoryOutOfBounds`, `IntegerOverflow`, `UnreachableCodeReached`, `OutOfFuel`, and about forty others) to its enum discriminant, with the sentinels `0xFF` (`InternalAssert`) and `0xFE` (`GcHeapCorrupt`) reserved.

At runtime a signal handler or a trampoline call lands with the trapping pc; the loader calls `lookup_trap_code(section, text_offset)` which binary-searches the block index and linearly decodes the matching block. The block's first byte is the "default code" (the most common code among that block's entries, picked by `most_common_code`), and most entries do not need to carry their own byte: they inherit the default. That drops the per-entry cost from five bytes (a u32 offset and a u8 code) to a bit over one byte in practice, and lookup is still `O(log n)` on the block index plus a single-block linear scan.
- **For cig: adapt.** By **rule 2** (errors happen at the same place, with the same code and the same span as the tree-walker's). cig's own operation-level errors are small in number (`E503` integer overflow, `E701` effect without a burn, and so on): a single-byte-per-site encoding carries them with room to spare, sorted by text offset so a `panic!` in native code maps to the tree-walker's error without parsing a side table.
- **What would decide it.** Not measured yet: the size of this section per thousand lines of CIR on the test machine, cross-checked against the "address map is the largest sidecar" note in the source.
- **Feeds.** #32, #40; (d), (e).
- **Read.** `wasmtime-v50.0.1/crates/environ/src/trap_encoding.rs` (`Trap`, `CompiledTrap`, `generate_trap_type`, `lookup_trap_code`, `TrapInformation`, `TRAP_BLOCK_SIZE`); `wasmtime-v50.0.1/crates/environ/src/compile/trap_encoding.rs` (`TrapEncodingBuilder`, `push`, `seal_block`); `wasmtime-v50.0.1/crates/cranelift/src/trap.rs` (`TranslateTrap`, `trap`, `trapz`, `trapnz`); `cig-script/crates/cig-bytecode/src/opcode.rs`.

### 11. Two ways a trap is raised: signals, or a libcall

- **What it does, and why.** `TranslateTrap::trap` chooses between a native CLIF `trap` instruction and a libcall. The decision is `clif_instruction_traps_enabled`: true if `tunables.signals_based_traps` is true, true unconditionally on a Pulley target (except with guest debug on).

If native traps are allowed and the trap has a wasm trap code, Cranelift emits `builder.ins().trap(trap)` and a segfault or `ud2`/equivalent is caught by the Wasmtime signal handler in `runtime::vm::traphandlers`. The entry trampoline sets up a per-thread `Handler` (through `catch_traps`), and the signal handler reads the trap pc and fp out of a per-platform `TrapRegisters` struct, looks up the trap code from the loaded `CodeMemory`'s trap data, and `longjmp`s back to the entry point with the code.

If signals are disabled (Pulley, embedded targets), the compiler emits a `trap` libcall (passes the code byte), then a `raise` libcall (returns to the outer catcher), then a defensive `trap TRAP_INTERNAL_ASSERT` after both calls. `trapz` and `trapnz` fan out to `conditionally_trap` when libcalls are in force so no CLIF-native trap is placed under them.
- **For cig: adapt.** By **rule 8** on hardened kernels (where signals handling of `SIGSEGV` from executable memory is fine but a `SIGILL` from a trap instruction may not be) and **rule 2** on identical errors. cig's form: a libcall-only path at first, like Wasmtime's non-signals mode, with the trap code carried as a byte so the runtime library raises the same `E` code as the tree-walker. A signals mode can be added later; its callback design (`store.signal_handler`) is a clear model.
- **What would decide it.** Not measured yet: measured slowdown of `nbody` on the test machine between a libcall-trap build and a signals-trap build, against issue 32's compute budgets.
- **Feeds.** #32, #40; cig-script#256; (d).
- **Read.** `wasmtime-v50.0.1/crates/cranelift/src/trap.rs` (`clif_instruction_traps_enabled`, `trapz`, `trapnz`, `uadd_overflow_trap`, `conditionally_trap`); `wasmtime-v50.0.1/crates/wasmtime/src/runtime/vm/traphandlers.rs` (`catch_traps`, `catch_unwind_and_record_trap`, `lazy_per_thread_init`, `TrapRegisters`, `signal_handler`); `wasmtime-v50.0.1/crates/environ/src/builtin.rs` (`trap`, `raise`).

### 12. The builtin table on vmctx: calls into the runtime without relocations

- **What it does, and why.** Every call from compiled code into the runtime goes through an array of function pointers that the engine sets up when it builds `VMContext`. `Compiler::call_builtin` loads the array base from `vmctx.builtin_functions`, loads the slot named by the builtin's `BuiltinFunctionIndex` (every builtin has a static index from the `foreach_builtin_function!` macro: `memory_grow`, `out_of_gas`, `new_epoch`, `trap`, `raise`, `drop_gc_ref`, `grow_gc_heap`, `gc_alloc_raw`, and about sixty more), imports its signature and `call_indirect`s. No relocation is left in the artifact for any of these.

The matching wasm-to-builtin trampoline in `compile_wasm_to_builtin` saves the last wasm fp/pc into `VMStoreContext` (so the host sees a consistent stack), forwards every argument, inspects the return value against the builtin's `TrapSentinel`, and on a trap calls `raise`. The enum has four variants, one per return convention: `Falsy` (zero in a `u32`: `gc_alloc_raw`, `array_new_data`, `array_new_elem`), `NegativeTwo` (`-2` in a `pointer` return from growth builtins: `memory_grow`, `table_grow`), `NegativeOne` (`-1` in a `pointer` return from `get_interned_func_ref`, and `-1` as a `u64` from `new_epoch`), and `Negative` (any negative value in a `u64` return: `memory_atomic_notify`, `memory_atomic_wait32`, `memory_atomic_wait64`). The sentinel table is computed by `BuiltinFunctionIndex::trap_sentinel` per the `trap_sentinel!` macro arms in `foreach_builtin_function`.

The `HostCall` enum in `environ/src/hostcall.rs` numbers every host transition in a 32-bit space: `ArrayCall` is 0, each `Builtin(i)` is `1 + i`, component builtins follow. Pulley uses that index at runtime as the identifier for a host-call event.
- **For cig: adapt.** By **rule 10** (ahead of time by default, nothing patched at load time) and **rule 9** (one unsafe loader crate). cig's form: an array of function pointers on the runtime context that the compiler indexes by builtin id. The `trap_sentinel` table is a clean separation that cig already needs (for the result-convention of issue 32): every runtime function returns a value whose sentinel the compiler's trampoline checks.
- **What would decide it.** Decided by rule 10.
- **Feeds.** #32; (e).
- **Read.** `wasmtime-v50.0.1/crates/cranelift/src/compiler.rs` (`call_builtin`, `compile_wasm_to_builtin`, `save_last_wasm_exit_fp_and_pc`, `raise_if_host_trapped`); `wasmtime-v50.0.1/crates/environ/src/builtin.rs` (`foreach_builtin_function`, `trap_sentinel`, `TrapSentinel`); `wasmtime-v50.0.1/crates/environ/src/hostcall.rs` (`HostCall`, `ArrayCall`, `Builtin`, `from_index`).

### 13. Address maps: a native pc becomes a source position

- **What it does, and why.** The `.wasmtime.addrmap` section maps instruction pcs to source positions in the original wasm. `AddressMapSection::push` is called per compiled function with `(code_offset, srcloc)` pairs, deduplicates consecutive mappings with the same source location, and emits blocks of 128 entries whose tokens are `uleb((pc_delta << 1) | pos_is_none)` followed by a uleb-encoded absolute position or an sleb-encoded delta. Lookup is `lookup_file_pos(section, offset)`: a binary search on the block index, then a linear scan for the last entry whose `text_offset` is less-than-or-equal to the probe pc. The docs call this the "largest of Wasmtime's metadata sections" and "roughly 2 bytes per entry in practice". Stripping it by `-Daddress-map=n` saves 52 KB on a `hello`-world cwasm (`examples-minimal-cwasm.md`).
- **For cig: take.** By **rule 2**: a native trap must report the same source position as the tree-walker. cig's form: a `cig-script/src/lower/cir/ir.rs` `Instr::span` already carries the source position; the compiler emits a parallel section with the same block-and-token shape, read by the runtime library's error path to format the error at the right line.
- **What would decide it.** Not measured yet: addrmap size per thousand compiled bytes on the test machine, against the `hello` size budget.
- **Feeds.** #32, #36, #38; (e).
- **Read.** `wasmtime-v50.0.1/crates/environ/src/address_map.rs` (`InstructionAddressMap`, `FilePos`, `lookup_file_pos`, `ADDRMAP_BLOCK_SIZE`); `wasmtime-v50.0.1/crates/environ/src/compile/address_map.rs` (`AddressMapSection`, `push`, `seal_block`); `wasmtime-v50.0.1/docs/examples-minimal-cwasm.md`; `cig-script/src/lower/cir/ir.rs` (`Instr`).

### 14. Unwinding and the exception table: handlers without stack walking

- **What it does, and why.** Wasmtime carries its own unwinder in `wasmtime-unwinder`, in a `no_std` crate. The README gives four jobs: walk the Wasm stack and visit each frame; find exception handlers using a serialized format that can be mapped and used in place from disk; provide a "throw" helper that, when called from host code invoked from Wasm code, can find a handler; and a "resume" stub that can be invoked to transfer control to the corresponding handler. The lib.rs file publishes three modules (`stackwalk`, `exception_table`, `throw`); the `throw` module is where the resume stub lives.

For unwinding without exceptions, `stackwalk.rs` defines a per-platform `Unwind` trait and a `FrameCursor` that walks `(fp, pc)` pairs using a table of frame descriptors. For exception handling, `ExceptionTable` is a side table of six parallel arrays (`callsites`, `frame_offsets`, `ranges`, `tags`, `contexts`, `handlers`) built from Cranelift's `MachCallSiteItem` records: lookup by callsite pc yields a window into the handler arrays where a tag matches a dynamic context value (fetched from an SP-relative offset) or a `-1` catch-all handler.

The format is designed to be mapped in from disk and used in place. The `wasmtime_unwinder::ExceptionTable::parse` call runs at load time in debug builds (`cfg!(debug_assertions)` in `code_memory.rs`) only as a well-formedness check; in release the on-disk bytes are trusted as the output of this version of Wasmtime.
- **For cig: adapt.** By **rule 5** (identical behavior on every engine): cig's issue 32 already plans a *result convention* for `throw` and runtime errors, "not through native stack unwinding", and the step budget plus the `try`/`finally` lowering are what make that work. Keep cig's result convention; the exception-table layout here is the clean fallback if, after measurement, the branch per call is too expensive. The unwinder is also what cig would need if it ever adds async yield or GC root scanning that needs to walk native frames.
- **What would decide it.** Not measured yet: a cost comparison on the test machine of the per-call status flag against the handler-table lookup on a `try`-heavy program (CIG scripts under 500 lines).
- **Feeds.** #32, #40; (d), (e).
- **Read.** `wasmtime-v50.0.1/crates/unwinder/src/lib.rs` (`stackwalk`, `exception_table`, `throw`); `wasmtime-v50.0.1/crates/unwinder/src/stackwalk.rs` (`Unwind`, `Frame`, `FrameCursor`, `frame_iterator`, `visit_frames`); `wasmtime-v50.0.1/crates/unwinder/src/exception_table.rs` (`ExceptionTableBuilder`, `ExceptionTable`, `MachCallSiteItem`, `MachExceptionHandler`); `wasmtime-v50.0.1/crates/unwinder/README.md`; `cig-script/src/lower/cir/ir.rs` (`Try`).

### 15. Stack maps: live roots at each callsite

- **What it does, and why.** For every pc that can suspend with live gc-managed values, the compiler records a `(frame_size, bitmap)` pair in a stack-map section. `StackMapSection::push` writes the pc into a parallel array `pcs` and the per-map data into `stack_map_data`: a `frame_size` u32, a count, and a bitmap whose bits are `stack_slot / 4` (slots are 4-byte aligned so this compresses the bitmap fourfold).

The reader `StackMap::lookup(pc)` is a binary search on `pcs`. There is no per-entry allocation: slots of the section are u32 arrays read with `object::slice_from_bytes`, and the bitmap is stored as a `CompoundBitSet<u32>` that iterates scalars on demand.

The GC uses `backtrace` plus the stack maps to turn a conservative list of possibly-live `ExternRef` values into a precise one; `Store::gc` is the API caller hook that runs that pass. The architecture doc notes that reference counts are "deferred" in generated code: the compiler leaves values on the stack without bumping the count, and the precise pass at a safepoint reconciles.
- **For cig: adapt.** cig's reference counting (rule 6) is deterministic and does not need a tracing collector, but issue 35's cycle collector needs to see values held in native frames once stage C is live. cig's form: at each callsite, emit a bitmap of which stack slots hold reference-counted objects; the cycle collector reads the section exactly as Wasmtime reads it. The precise-vs-conservative distinction is directly useful: cig's cycle collector can be precise about native frames at zero per-call cost.
- **What would decide it.** Not measured yet: the size of this section on the test machine for a script whose hot function does heavy map work, against issue 36's hello budget.
- **Feeds.** #32, #38; cig-script#256; (e).
- **Read.** `wasmtime-v50.0.1/crates/environ/src/stack_map.rs` (`StackMap`, `StackMapSection`, `lookup`); `wasmtime-v50.0.1/crates/environ/src/compile/stack_maps.rs` (`StackMapSection`, `push`, `append_to`); `wasmtime-v50.0.1/docs/contributing-architecture.md`.

### 16. The on-disk cache: a hashed key and an LRU worker

- **What it does, and why.** `ModuleCacheEntry::get_data_raw` hashes the caller-supplied state with SHA-256 (using a `Sha256Hasher` adapter over Rust's `Hasher` trait), base64-URL-encodes the hash (slashes replaced to work as a filename), then looks up `<cache_dir>/modules/<compiler_name>-<compiler_version>[-<mtime>]/<hash>`. The file is zstd-compressed with a baseline level (default 3).

A background worker thread (`crates/cache/src/worker.rs`) receives `on_cache_get_async`/`on_cache_update_async` events through a bounded queue and performs three jobs: usage-counting (a sidecar statistics file per cache entry), recompression at a higher level (default 20) past a threshold, and cleanup against soft limits on file count (default 65536) and total size (default 512 MiB).

The LRU policy uses mtime; locks are files with a tolerated clock drift (default 1 day for locks from the future). Writes are atomic: `fs_write_atomic` opens a sibling `.wip-atomic-write-mod` file with `create_new(true)`, writes, closes, and renames. A write-rename cycle survives power loss: on the next look-up the half-written file is ignored.
- **For cig: adapt.** By **rule 6** (deterministic cleanup) and **rule 9** (contained unsafe). cig's `cig-script/src/burn/modcache.rs` already keys entries by SHA-256 over `cig`'s build, the lowering's version, the optimization level and the script's SHA-256; what Wasmtime's cache adds and cig does not is the background worker with LRU eviction and compression. For cig-cherry's native cache, the worker shape is the model: the compile runs in a separate `cig-cherry` process (issue 256 "The compiler runs in its own process"), and the worker runs alongside to evict native entries on disk pressure.
- **What would decide it.** Not measured yet: hit rate of cig's modcache on a run of the differential corpus on the test machine, with and without a worker that evicts past a soft size limit.
- **Feeds.** #37; cig-script#256; (f).
- **Read.** `wasmtime-v50.0.1/crates/cache/src/lib.rs` (`ModuleCacheEntry`, `get_data`, `get_data_raw`, `fs_write_atomic`, `Sha256Hasher`); `wasmtime-v50.0.1/crates/cache/src/worker.rs` (`Worker`); `wasmtime-v50.0.1/crates/cache/src/config.rs` (`CacheConfig`); `wasmtime-v50.0.1/docs/cli-cache.md`; `cig-script/src/burn/modcache.rs`.

### 17. Winch: one pass, a shadow stack, a bitset allocator

- **What it does, and why.** Winch is a baseline compiler that walks the WebAssembly bytecode once, visitor-style (`VisitOperator` and `VisitSimdOperator` are implemented directly for `CodeGen`), and emits machine instructions. There is no IR.

The compiler keeps a shadow value stack whose entries are `Val::{I32, I64, F32, F64, V128, Reg(TypedReg), Local, Memory}`: a constant stays a constant until it needs a register, a local may be referred to by index until its value is consumed, a spilled value lives in a `StackSlot`. This lets a chain of `const; add; const; mul;` fold without ever materialising the intermediate values.

The register allocator (`regalloc.rs::RegAlloc`) is a bitset freelist per class (GPR, FPR): `reg_for_class` returns a free register or calls a caller-supplied `spill` closure. Spill moves `Local` and `Reg` values from the shadow stack to memory. Machine-code emission uses the `MacroAssembler` trait (`masm.rs`) with per-ISA implementations that call into Cranelift's assembler library.

The design principles state "no intermediate representation" and "it should be evident which machine instructions are emitted per WebAssembly operator". That is cig-cherry's tier-2 goal literally: a function that can be read by looking at the one `visit_<Op>` method that emitted it.
- **For cig: adapt.** For cig-cherry's tier 2 (issue 256 "tier 2: a hot function compiled quickly to native code, with guards on the types it saw"). cig's form: a Winch-style single pass over the bytecode of the specific function that went hot, a shadow stack whose entries carry the observed `Ty`, a freelist register allocator, and the one unsafe loader (rule 9) mapping the emitted bytes read-execute. The same code generator stays available for stage C's full pass; the baseline is a smaller front end into it, not a separate assembler.
- **What would decide it.** Not measured yet: compile time per hot function (tier 2) against the tree-walker's time saved, on `nbody` and `fib`, on the test machine.
- **Feeds.** #32; cig-script#256; (b), (d), (e).
- **Read.** `wasmtime-v50.0.1/winch/README.md`; `wasmtime-v50.0.1/winch/codegen/src/stack.rs` (`Val`, `TypedReg`, `Local`, `Memory`); `wasmtime-v50.0.1/winch/codegen/src/regalloc.rs` (`RegAlloc`, `reg_for_class`, `reg`, `free`); `wasmtime-v50.0.1/winch/codegen/src/regset.rs` (`RegSet`, `RegBitSet`); `wasmtime-v50.0.1/winch/codegen/src/visitor.rs` (`VisitOperator`, `VisitSimdOperator`); `wasmtime-v50.0.1/winch/codegen/src/masm.rs` (`MacroAssembler`).

### 18. Pulley: a bytecode interpreter for a 32-bit ARM target

- **What it does, and why.** Pulley is a portable bytecode and an interpreter for it, used as Wasmtime's execution back end where Cranelift has no native support. Cranelift lowers to Pulley bytecode through the `pulley_shared` back end (one ISA parametric on `pulley32` vs `pulley64`, little/big-endian; `cranelift/codegen/src/isa/pulley_shared/`). The bytecode is defined in one macro (`for_each_op!`) and extended through a reserved opcode byte `0xFF` to a 16-bit extended opcode. The interpreter is implemented as `OpVisitor` on an `Interpreter` struct over a `MachineState` with 32 X, 32 F and 32 V registers. There are two interpreter loops, chosen at build: a `loop { match }` and a tail-call-based loop that is enabled by a `pulley_tail_calls` cfg. Pulley is slower than native (the docs say "10x order-of-magnitude slowdown relative to native code or Cranelift"), and a `.cwasm` can be smaller than a native one (`-Daddress-map=n -Dsymbols=n -Omemory-init-cow=n --target pulley64`: 90 KB vs 129 KB in `examples-minimal-cwasm.md`).
- **For cig: not applicable.** cig's bytecode VM (`cig-script/src/vm/mod.rs`) is the portable engine. cig has no targets that need a separate portable VM beside cig-compile's stage C: issue 32 explicitly says stage B's bytecode serves 32-bit ARM. Pulley's design is useful as cross-reference: a macro-defined ISA and a two-mode interpreter loop (tail calls under a cfg) are both patterns cig's VM could reach for.
- **What would decide it.** Not measured yet: cig's VM step rate against Pulley on a comparable compute script on the test machine, for the sake of calibration only.
- **Feeds.** #32, #41.
- **Read.** `wasmtime-v50.0.1/pulley/README.md`; `wasmtime-v50.0.1/pulley/src/lib.rs` (`for_each_op`, `for_each_extended_op`); `wasmtime-v50.0.1/pulley/src/interp.rs` (`Vm`, `MachineState`, `Interpreter`, `mod match_loop`, `mod tail_loop`); `wasmtime-v50.0.1/cranelift/codegen/src/isa/pulley_shared/mod.rs` (`PulleyFlags`); `wasmtime-v50.0.1/docs/examples-pulley.md`; `cig-script/src/vm/mod.rs` (`Proto`).

### 19. Profilers and debuggers: perf jitdump and the GDB JIT interface

- **What it does, and why.** `crates/jit-debug` holds two pieces of profiler integration. The GDB JIT interface (`gdb_jit_int.rs`) defines `JITCodeEntry` and `JITDescriptor` structs and a symbol `__jit_debug_register_code` that GDB and LLDB watch: when Wasmtime publishes new code with native DWARF, it chains a new `JITCodeEntry` into the descriptor's linked list and calls the sentinel function, breaking into the debugger. The perf jitdump file (`perf_jitdump.rs::JitDumpFile`) opens a file next to the process's perf data, writes a header, and appends one record per compiled function (its address, size, and dwarf line info) so that `perf report` prints the function's name. Both are gated behind feature flags: `debug-builtins` and `perf_jitdump` (Linux only). Branch protection on aarch64 is recorded as one byte in `ELF_WASM_BTI`, read at publish and passed to `make_executable`.
- **For cig: adapt.** cig's issue 38 wants `perf` to show pull names. Both hooks are tiny and self-contained: the GDB JIT interface is ~250 lines; the jitdump file is a single-writer append-only format. cig's form: a feature-gated reporter per platform that calls into the same OS entry points, with the names coming from CIR (pull name plus module), per cig-script#256's request for `cig cherry` native code to show up by name.
- **What would decide it.** Decided by rule 7 (verified bytecode, never rewritten) only in the sense that these hooks are read-only: they record what the compiler emitted, never change it.
- **Feeds.** #32, #38, #40; cig-script#256.
- **Read.** `wasmtime-v50.0.1/crates/jit-debug/src/lib.rs` (`gdb_jit_int`, `perf_jitdump`); `wasmtime-v50.0.1/crates/jit-debug/src/gdb_jit_int.rs` (`JITCodeEntry`, `JITDescriptor`, `__jit_debug_register_code`); `wasmtime-v50.0.1/crates/jit-debug/src/perf_jitdump.rs` (`JitDumpFile`); `wasmtime-v50.0.1/crates/jit-icache-coherence/src/lib.rs` (`clear_cache`, `pipeline_flush_mt`); `wasmtime-v50.0.1/docs/examples-profiling-perf.md`.
