## What cig should carry away

- Go runs a fixed pass table of 60 entries defined once in one file, with 26 marked required and the rest gated by a single `f.Config.optimize` flag; order constraints are a separate 42-entry table re-checked at init (entry 1). cig's `cig-script/src/lower/cir/pass/mod.rs` names four passes today (`FoldConsts`, `CopyProp`, `Sccp`, `DeadPure`) and at `-O1` the pipeline from `level` has five entries, `fold-consts` running twice (`[&FoldConsts, &CopyProp, &FoldConsts, &Sccp, &DeadPure]`); the shape Go uses is the same shape cig already has, scaled up, and the single-table discipline is the first thing to carry over as cig adds passes (entries 1, 2).
- Checking after every pass is a build-time compile flag in Go (`ssa/check/on`), not a release feature; the verifier runs on every function and the pass table reseeds a PRNG per function to randomize value order so that the output of the pass does not silently depend on it (entry 2). cig verifies by default after every pass today, which is stronger than Go's position; the lesson is the deterministic value-order randomizer as a regression test, not the verifier itself (entry 2).
- Rewrites are written as s-expression patterns in `.rules` files and compiled to Go code by a generator that reads them; the machine-independent file `generic.rules` carries 2,407 lines of patterns, and each target has its own file (AMD64's is 1,926 lines) so instruction selection is written in the same language as the mid-end (entries 3, 4, 5). cig today has no rewrite layer: a fifth pass that takes a small rule file and compiles it to a verified CIR rewrite is a narrow design question with a clear answer (entry 5 names what rule shape fits CIR, entry 6 names the generator cig can reimplement in Rust).
- Go's `prove` tracks per-value integer and pointer limits, plus a partial-order set (`orderS`, `orderU`) over SSA values, and asserts conditions dominating each branch to prove unreachable branches dead; its paying use is bounds-check elimination on indexed array and slice access through the `OpIsInBounds` and `OpIsSliceInBounds` opcodes (entry 7). cig has no bounds-check elimination today: a `prove`-shaped pass needs `Ty::Int` and `Ty::Float` already in CIR, a `len` operation visible to the pass (today's `MakeList` and `Index` would need a paired length value), and a transition rule under `T4` that only lets a potentially-raising `Index` be lowered to a never-raising form when the pass proved it in bounds (entry 7).
- Escape analysis is a per-function, flow-insensitive dataflow over "locations" whose edges carry an integer deref count, with a summary (`leaks`) recorded per parameter so a caller can benefit without reading the callee's body (entries 8, 9). cig has no escape analysis today and no stack: values are `Rc`-counted on the heap. The lesson is the per-parameter summary, a design that lets a caller optimize across a call without reading the body, and the shape of the function summary (an 8-byte table indexed by parameter) is a direct candidate for cig's shared stage-C/stage-D interface (entry 8).
- Inlining is bounded by a per-function cost budget (`inlineMaxBudget = 80` nodes), with PGO adding a wider budget for a hot callee and a set of seven pragmas that make inlining impossible (`go:noinline`, `go:norace`, `go:nocheckptr`, `go:cgo_unsafe_args`, `go:uintptrkeepalive`, `go:uintptrescapes`, `go:yeswritebarrierrec`) regardless of cost (entry 10). cig has no inlining pass today and no comparable pragmas; the design candidate is a byte budget per callee counted at CIR nodes with `requires_burn` disabling inlining outright, matching Go's `no function body` and pragma gates (entry 10).
- PGO uses an ordinary sampling CPU profile (a pprof-format file from `runtime/pprof`), summarized to a weighted call-edge graph `NamedEdgeMap` keyed by caller, callee and line offset from function start, so a profile survives most source edits that do not move the call off its line (entry 12). cig's VM has per-pc caches but no profile emission today; the design candidate for decision (c) is a single counter-and-sample format shared between the VM, `--profile-use` and cig-cherry, with the edge key being not a line but a CIR span so edits that renumber lines do not invalidate the profile (entry 12).
- The build cache keys every tool invocation by a SHA-256 of a "complete description" of the action (the tool's own content ID, the sources, the compile flags and salt of the Go version), stores the output by content ID, and stamps a build ID onto the output so a later link step can read the content ID without re-hashing (entries 13, 14). cig-compile has `cache.rs` already; the payloads to hash are the source, the pins, the carton's cover file and the stage-b format version, each independently for the signed module and the stage-b payload. The method is what the design should carry (entries 13, 14).
- Linker dead-code elimination is a flood-fill from the entry symbols through relocations, with two escape hatches that keep methods alive: every method of a reachable interface type, and all exported methods of all reachable types when any function flagged `REFLECTMETHOD` is reachable (entry 16). cig's equivalent of "reflection" is `light`, a dynamic callback, a function stored in a map, or a builtin reached by a name computed at run time: any of those force the full runtime in the sense a `REFLECTMETHOD` function forces every exported method. A stage-b payload cannot drop any of cig's runtime today, because the kernel, the step counter and the burn ledger are reached unconditionally (entry 16).
- Every Go program carries a `pcHeader` plus a `pclntab` (program-counter to function, file and line table) and a per-function metadata block (`_func`, 44 bytes plus pcdata) laid down by the linker and read by the runtime's traceback and profiler; inlined frames are recorded in a `funcdata` table so a stack trace shows the source frames that were inlined away (entries 17, 18). cig's bytecode has spans per instruction but no global table from a native address to a span. The design candidate is the same table built by the lowering, kept next to the module in the tin, so that cig-cherry's native code can find the source span of any address at run time (entry 17).
- Go bootstraps through an older Go (not machine code, not C): `cmd/dist`'s `buildtool.go` copies a subset of the source into a workspace, edits imports to `bootstrap/<pkg>`, and asks the older `go` command to build it into a toolchain that then builds the current one (entry 20). cig-compile is in Rust and will stay there; the lesson is the bootstrap's clear ladder (a named older version, a single workspace, no C), and what cig's #17 should take is the same clear naming of a prior cig version that builds the current one (entry 20).

## Design points

### 1. One pass table, in order, in one file, with the required passes marked

- **What it does, and why.** `src/cmd/compile/internal/ssa/compile.go` defines `passes`, a 60-entry array of `pass` records, each with a name, the function that runs it, and flags for `required`, `disabled`, `time`, `mem`, `stats`, `debug`, `test`, and a per-function `dump` map. The driver (`Compile`) walks the array in order: it skips a pass whose `disabled` is true or whose `required` is false when `f.Config.optimize` is false, times the pass, optionally logs memory, and runs the structural checker.

  26 entries are marked `required: true` and run even at `-N` (number lines, decompose user, opt, zero arg cse, opt deadcode, gcse deadcode, divisible, divmod, middle opt, expand calls, decompose builtin, softfloat, late opt, generic deadcode, writebarrier, lower, late lower, tighten tuple selectors, lowered deadcode, checkLower, tighten, critical, layout, schedule, flagalloc, regalloc). Three entries are gated by a build-time experiment flag (`insert resched checks` on `buildcfg.Experiment.PreemptibleLoops`, `cpufeatures` and `rewrite tern` on `buildcfg.Experiment.SIMD`), so a stock build with SIMD off runs 57 of 60 and `-N` runs 26 of them; with SIMD on, `cpufeatures` becomes `required: buildcfg.Experiment.SIMD` and the required count rises to 27.

  A separate `passOrder` table lists 42 explicit "a must come before b" constraints with a one-line reason each ("prove relies on common-subexpression elimination for maximum benefits", "cse substantially improves nilcheckelim efficacy", "critical must run before regalloc because regalloc requires the removal of all critical edges"); `init` walks `passOrder` at startup and panics if any constraint is violated by the position of a pass in `passes`. The order check is cheap (it runs once per compiler invocation, before any function is lowered) and it catches a careless reorder in review: a change that moves `prove` above `generic cse` fails the panic, and the reviewer has the one-line reason in the constraint to decide whether to update the comment or revert the move.
- **For cig: adapt.** By rule 5 (identical behavior on every engine) and rule 1 (burns never move): cig already has this shape in `cig-script/src/lower/cir/pass/mod.rs` as `NAMES` and `default_passes`, but with four passes and no required/optional split. The scaling lesson is the whole file: a single array in one source file, with a re-checked order table, and an `optimize` flag per `Func`. cig's form: extend `NAMES` to include a required/optional bit and a `-O0` run that skips the optional ones; add a `pass_order.rs` table that is re-verified at module load. The verifier's `T1` to `T4` already pin what Go's `required` marks protect; the distinction Go draws between `required` and `optional` is the one cig would use to decide whether `-O0` can drop a pass at all.
- **What would decide it.** Decided by rule 5. The pass list and order are a design question, not a measurement; the measurement that matters is the differential suite at zero differences for every subset the gate allows.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/compile.go` (`passes`, `passOrder`, `pass`, `Compile`, `required`, `disabled`); `cig-script/src/lower/cir/pass/mod.rs` (`NAMES`, `default_passes`, `run_passes`).

### 2. Checking after every pass: the structural checker and the deterministic value-order randomizer

- **What it does, and why.** `Compile` reads `checkEnabled` (set by `-d=ssa/check/on`) and, when it is true, does two things between passes. First, it seeds a PRNG with `crc32(f.Name) ^ checkRandSeed` and uses it to randomize the order of values within each block before each pass runs, so that the pass's output is not silently dependent on value order; the comment names issue 18169 as the regression this guards. Second, after every pass runs, it calls `checkFunc(f)` to re-verify the function's structural invariants. The checker is in `check.go`; it runs on every function in the build and is off by default because of its cost. In the same file, `PhaseOption` turns the checker on, sets a per-pass seed, or scopes a check to one pass (`ssa/check/seed=1234`, `ssa/prove/debug=2`). `BuildDump`, `GenssaDump` and the `dump` flag on each pass redirect intermediate output to per-phase files whose names are `<func>_<seq>__<phase>.dump`.
- **For cig: adapt.** cig verifies after every pass by default, which is stronger than Go's "check on debug flag" position: the structural verifier itself is rejected as something to take, because cig's `cig-script/src/lower/cir/verify.rs` already enforces `V1` to `V11` and `T1` to `T4` on every call to `run_passes`, and the broken twin per pass (`pass/broken.rs`) is the test that catches a hand-written error. What cig takes from this entry is the second mechanism: the deterministic value-order randomizer. cig's verifier would catch a semantic regression caused by an ordering dependence, but not every ordering dependence is semantic (statement attribution and span assignment can shift). A per-function PRNG, seeded from the function's name and a global seed, that shuffles instruction order inside a block before each pass, would turn an order-dependent pass into a flaky test and is cheap to add. By rule 5 (identical behavior on every engine): the randomizer is a test of that rule, not a change to behavior.
- **What would decide it.** Not measured yet: run the differential suite with a value-order randomizer enabled, counting how many programs change output. The measurement is "how many passes does cig run that depend on value order", on cig's current four passes; the pass count at which it is worth adding decides the entry.
- **Feeds.** cig-compile#33.
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/compile.go` (`checkEnabled`, `checkFunc`, `checkRandSeed`, `PhaseOption`); `go-go1.27.4/src/cmd/compile/internal/ssa/check.go`; `cig-script/src/lower/cir/verify.rs` (`verify`, `verify_transition`).

### 3. Machine-independent rewrites: `generic.rules`

- **What it does, and why.** `src/cmd/compile/internal/ssa/_gen/generic.rules` is 2,407 lines of s-expression patterns that describe mid-end rewrites: constant folding, strength reduction, algebraic identities, canonicalization, dead-branch collapse, and a large section of patterns that turn calls to `runtime.memequal` on a constant-size string into inline loads. The syntax is `(op <type> [auxint] {aux} arg0 arg1 ...)`; a condition can follow with `&&`, and the generated right-hand side names the same opcodes. Variables bind on first use and must match on later ones. A rule like `(Mul(8|16|32|64) (Const(8|16|32|64) [1]) x) => x` carries four rules in the four width variants.

  The first matching rule wins, and the loop runs to a fixed point: `rewrite.go`'s `applyRewrite` iterates until nothing changes, with a cycle detector that turns on after `max(f.NumBlocks(), 20)` iterations. The generated code (`rewritegeneric.go`) is autogenerated into the parent package; the comment at the top of the file states the rule syntax, the block-rewrite syntax, and the convention for `...` in call rules. DeMorgan's laws, absorption laws, shift combinations, and mul-by-constant strength reductions are among the identities in the file; each is one line of pattern. A reviewer reads the rule and the rewrite together, with no helper code to chase.
- **For cig: adapt.** By rule 1 and rule 7 (verified bytecode, never rewritten at run time): a rule-driven rewrite layer over CIR is a precise fit for cig's optimizer, because CIR's `Class::Pure`, `Class::Effect`, `Class::MayRaise` and `Class::Step` already decide what a rewrite may touch and `T4` already decides what a rewrite may remove. cig's form: a `rewrite.rules` file alongside `cig-script/src/lower/cir/pass/`, a Rust generator that compiles it to a trait-driven match ladder on `Kind` plus `Ty`, and a `run_rewrites` pass that iterates to a fixed point. The constraint cig adds to Go's syntax is the class of each matched instruction, so a rule can say "pure to pure" or "effect to effect of the same kind" and the generator refuses a rule that would cross a class boundary.
- **What would decide it.** Not measured yet: the count of rules (ten? forty?) needed to carry cig's existing `fold-consts` and `copy-prop` as rules instead of Rust code, and the compile-time cost on the test suite. If the two passes together are under 200 rules the method pays by scale alone.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/_gen/generic.rules` (`Trunc16to8`, `Const8`, `Lsh64x64`, `Rsh(64|32|16|8)Ux64`, `StaticLECall`, `isSameCall`, `symIsRO`); `go-go1.27.4/src/cmd/compile/internal/ssa/rewrite.go` (`applyRewrite`, `itersLimit`).

### 4. Instruction selection written in the same rule language: `AMD64.rules`

- **What it does, and why.** The architecture file is 1,926 lines of the same rule syntax, but the right-hand side now names machine-specific opcodes (`ADDQ`, `MOVQconst`, `TZCNTQ`, `BSFQ`, `POPCNTQ`, `MULQU2`). Patterns like `(Add(64|32|16|8) ...) => (ADD(Q|L|L|L) ...)` lower a generic op to one of four target instructions by width. Conditionals name cpu-level predicates read from `buildcfg`: `(Ctz64 x) && buildcfg.GOAMD64 >= 3 => (TZCNTQ x)` selects a newer instruction when the target CPU supports it, and the `< 3` sister rule falls back to a `BSFQ`-based form. Carry-chain idioms (`ADCQ`, `SBBQ`, `MULQU`) are selected into a single multi-output pattern through `Select0`/`Select1`. The lower pass runs all the machine-specific rewrites in one go (`lower`, then a `late lower` for post-lowering patterns that depend on previous results); `lower` is the single machine-specific pass in `compile.go`'s table and the rules carry nearly all of the backend.
- **For cig: reject.** By rule 8 (no memory both writable and executable, programs reproducible and signable) and rule 10 (ahead of time by default), cig's native code generator is Cranelift for stage C; selecting instructions as rules is Cranelift's job through ISLE, not cig's. The lesson from Go is the counterfactual: a compiler can do instruction selection in rules without ISLE's egraph machinery, and the rule language is identical for mid-end and backend. cig's stage C already has a code generator; a separate rule-driven selector would duplicate Cranelift's work and widen the unsafe surface (rule 9, forbid unsafe except in one small crate).
- **What would decide it.** Decided by rule 10 and the stage-C decision.
- **Feeds.** cig-compile#32; decision (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/_gen/AMD64.rules` (`ADDQ`, `MOVQconst`, `TZCNTQ`, `BSFQ`, `SBBQ`, `SETB`); `go-go1.27.4/src/cmd/compile/internal/ssa/compile.go` (`lower`, `late lower`).

### 5. The rule generator: `rulegen.go` and `main.go`

- **What it does, and why.** `_gen/main.go` is the entry point: an `arch` struct that holds `opData` (one per opcode with its register info, type, aux, whether it rematerializes, side-effects, call flags), a `blockData` list per architecture, and an `imports` list. It builds the opcode tables (`genericOps.go`'s data converted to `opGen.go` source), the block kind tables, and then calls `rulegen.go`. `_gen/rulegen.go` reads a `.rules` file line by line, parses each rule into `(match, cond, result)` with `Rule.parse`, and emits a Go function `rewriteValue<Arch>_<Op>` that returns true if the rule fired. The emitter is a whole-program Go printer (it uses `go/ast`, `go/parser`, `go/printer` and `astutil` to format the output). The docstring names the idea's origin: "Ideas stolen from the Swift Java compiler", with a reference to a 2000 Digital WRL report. `go generate cmd/compile/internal/ssa` runs the generator and writes `rewritegeneric.go`, `rewriteAMD64.go`, and the equivalents for every target.
- **For cig: adapt.** By rule 5 and rule 9 (one unsafe crate): a rule-driven CIR rewriter wants a generator in Rust, written against CIR's `Kind` enum and `Ty`, emitting a safe match ladder. cig's form: a new `rulegen` module alongside `cig-script/src/lower/cir/pass/`, taking a `.rules` text and producing a Rust module `cir::rewrites` with one function per `Kind`. The generator itself does not touch the module at build time: `build.rs` runs it on changes to the rules file and writes the Rust source into `OUT_DIR`, so the compiler input is checked-in rules and generated Rust. The feature cig wants that Go has not kept: a generator that emits span-preserving rewrites, so a rewritten instruction inherits its span from a named sub-term and the error-attribution invariant (rule 2) survives.
- **What would decide it.** Not measured yet: the complexity of the generator itself, in Rust lines, against the lines of hand-written Rust it replaces. The generator is likely to be larger than the first few passes it replaces; the payoff is in the fifth pass and after.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/_gen/rulegen.go` (`Rule`, `parse`, `normalizeSpaces`); `go-go1.27.4/src/cmd/compile/internal/ssa/_gen/main.go` (`arch`, `opData`, `blockData`).

### 6. Applying the rules to a fixed point

- **What it does, and why.** `src/cmd/compile/internal/ssa/rewrite.go`'s `applyRewrite(f, rb, rv, deadcode)` is the loop that drives the generated functions: on every block, it calls the block-rewriter once, then for every value it walks from the bottom up and calls the value-rewriter per value, replacing uses via `OpCopy` rather than editing the original value in place (so the next iteration can see the rewrite without the slice changing shape under it). The outer loop repeats until no rule fires in a pass. `itersLimit` is `max(f.NumBlocks(), 20)`; after that limit, the loop turns on a cycle detector that hashes each pass's state to detect oscillation and names the offending rules in a panic. This is where `fold-consts`, `generic cse`, the three `opt` passes and the `lower` pass are all plugged in: each is a thin wrapper around `applyRewrite` with a different pair of generated rewriters. Deadcode removal runs opportunistically: a pass can ask `applyRewrite` to drop dead values after the rewrite succeeds, which reduces work on the next iteration.
- **For cig: adapt.** By rule 5 and the verifier's `T1` through `T4`: the fixed-point loop is a small concrete pattern that fits cig's `Pass` trait. cig's form: a `RewritePass` in `cig-script/src/lower/cir/pass/` whose `run` is a `while changed` over a generated `rewrite_kind(&mut Kind)` ladder, with the same `OpCopy`-style tombstoning that leaves a `Kind::Copy(ValueId)` behind and is swept by a late `dead-pure`. The cycle detector is worth a measurement first: at four passes it costs more than it pays.
- **What would decide it.** Not measured yet: how many iterations the loop takes on cig's current corpus, and whether any program ever exceeds `max(blocks, 20)`. If it never does, the cycle detector can be a `cfg(debug_assertions)` check rather than a release feature.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/rewrite.go` (`applyRewrite`, `itersLimit`, `deadValueChoice`); `cig-script/src/lower/cir/pass/mod.rs` (`Pass`, `run_passes`).

### 7. The `prove` pass: bounds-check and nil-check elimination from facts about ranges

- **What it does, and why.** `src/cmd/compile/internal/ssa/prove.go` is 3,177 lines of a single pass whose header comment states what it does: "prove removes redundant BlockIf branches that can be inferred from previous dominating comparisons." It walks the dominator tree, at each `BlockIf` adds the assertion of the branch's condition to a `factsTable`, descends into the branch, and before each descent checks whether the assertion has reduced the fact set to `unsat`; if so, the branch is dead and prove rewrites the terminator to jump to the live successor only.

  The `factsTable` holds three structures in parallel: a per-value `limit` struct with four fields (`min`, `max` signed, `umin`, `umax` unsigned; a limit whose `min > max` or `umin > umax` is called "unsatisfiable" and marks the owning code as unreachable), two partial-order sets `orderS` and `orderU` (signed and unsigned) over value ids that record transitive `<=` and `<` relations through the `poset` type, and an `orderings` map of explicit learned orderings by value id for relations the posets do not record (such as `==` and `!=` only). A separate `lens`/`caps` map records, for each slice value, a representative `OpSliceLen` or `OpSliceCap` value, so that different `len(s)` uses of the same slice are related to one another through the poset.

  Induction variables are detected by `findIndVar` (a `Phi` whose two arguments are `min` and `next`, with `next` being an `Add` of `ind` and a constant); when the counter is used only for the comparison and the counter's next value, prove folds the loop into a downward-counting form when possible, so the compare against zero is cheaper than a compare against the loop bound. Fence-post implications are handled as a separate step after the condition is added: a fact `i < n` on an int implies `i + 1 <= n`, which the limit machinery propagates to the counter's next value. The paying use is `OpIsInBounds` and `OpIsSliceInBounds`: each loop iteration sees `0 <= i < len(a)` as a learned fact and the second use of the same index in the body is elided. `-d=ssa/prove/debug=2` emits a per-instruction trace of the facts learned and used.
- **For cig: adapt.** By rule 1 and `T4`: `prove` is exactly the shape cig needs to remove redundant failure-raising operations, because an `Index` is `Class::MayRaise` today and must stay `MayRaise` unless the pass has proved it cannot raise. The adaptation needs three extensions of CIR. First, a `len` value kind that pairs with each `MakeList` and `MakeMap` so the pass has a term to compare against. Second, a per-value `Limit { min, max }` on `Ty::Int` values, added as a field on `ValueInfo` and initialized by lowering of integer literals and ranged inputs. Third, a `RaiseFreeIndex(list, idx)` opcode that is `Class::Pure` and is only legal where the pass left it, with the verifier's `T4` checking that the preceding facts imply `0 <= idx < len(list)` at the point of lowering. cig's existing integer-overflow raise `E503` stays untouched (its span is already pinned by `Class::MayRaise`); a prove pass that removes a subsequent in-bounds check does not change the attribution of the first.
- **What would decide it.** `data/census/README.md` (point 3): every index site in cig's 21 compute programs sees one kind of container and index (a list by an integer, or a map by a string), across 5,663,526 executions. The LuaJIT comparison in `cig-script/docs/research/luajit.md` (38 against 15 instructions per indexed list read) is the gap this closes; the census says every one of those sites is a list-by-integer, so a prove-driven cut would apply at every site.
- **Feeds.** cig-compile#33, #34; decisions (a), (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/prove.go` (`factsTable`, `limit`, `orderS`, `orderU`, `orderings`, `prove`, `OpIsInBounds`, `OpIsSliceInBounds`, `findIndVar`, `maybeRewriteLoopToDownwardCountingLoop`, `OpSliceLen`, `newFactsTable`); `go-go1.27.4/src/cmd/compile/internal/ssa/loopbce.go` (`indVar`, `parseIndVar`); `go-go1.27.4/src/cmd/compile/internal/ssa/poset.go` (`poset`); `data/census/README.md`.

### 8. Escape analysis with per-parameter summaries

- **What it does, and why.** `src/cmd/compile/internal/escape/escape.go`'s header describes the pass as a static dataflow over "locations": every variable, every expression that allocates (`new`, `make`, a composite literal), and the three well-known locations `heapLoc`, `mutatorLoc`, `calleeLoc`. Every assignment becomes a directed edge whose integer weight is (deref count minus addressing count), so `p = &q` is an edge with weight -1 and `p = **q` is weight 2 (derefs cannot go below -1, because `&x` is not itself addressable). The pass walks the AST (`stmt.go`, `expr.go`, `assign.go`, `call.go`), builds the graph (`graph.go`), then runs a fixed-point dataflow (`solve.go`'s `walkAll`): a location's `attrEscapes` bit propagates along any path whose minimum deref count is less than or equal to 0, and any variable whose `attrEscapes` is true at the end of the walk is heap-allocated.

  The pass is deliberately flow-, path- and context-insensitive and does not distinguish fields within a compound: `x.f = u[0]` is modelled as `x = *u`, so the analysis stays linear in the function size at the cost of some precision. `Funcs` sorts the functions bottom-up with `ir.VisitFuncsBottomUp`, so a callee is analyzed before its caller; `Batch` processes one strongly-connected component at a time with `reassignOracles` sharing a per-function cache. The output per function is a parameter tag ("leaks"): `leaks.go` defines an 8-byte table indexed by `leakHeap`, `leakMutator`, `leakCallee`, `leakResult0` through `leakResult0+numEscResults-1`, storing the minimum deref count on any flow from the parameter to each of those targets. A caller reads the tag at the call site and avoids walking the callee's body again.
- **For cig: adapt.** By rule 1 and rule 6 (deterministic cleanup, no tracing collector): escape analysis in Go decides stack versus heap; cig has no stack, only `Rc`-counted heap, so the same output is used differently. The question is which cig problem it answers: "can this value's reference count stay the same across this call" (a borrow summary, which turns an `Rc::clone` into nothing), rather than "can this value go on the stack". The pass shape is the same: a per-function 8-byte table of what each parameter does with its argument (consumed, borrowed, stored into a map, closed over), computed by a bottom-up dataflow, read by the caller. cig's form is a `ParamInfo` on `Func`, next to `FuncInfo::captures`, with an enum `{Borrowed, Consumed, StoredIntoOwner}` per parameter. The cig-cherry call-site shape reads this to decide whether the caller must `Rc::clone` an argument before the call.
- **What would decide it.** `data/census/README.md` (point 5): in the median compute program, half of the register moves copy a counted value (range 0% to 100%). This is a floor for the Rc traffic on moves alone, not counting clones made at argument passing or by builtins; a borrow summary would cut from this floor. The census further shows that every function in the 21 compute programs was only ever called with one row of argument types (point 4), which makes a per-parameter summary a one-row table at every call site.
- **Feeds.** cig-compile#33, #34, #35; decisions (e), (g).

### 9. The escape graph and its dataflow solver

- **What it does, and why.** `graph.go` (not shown above in isolation) and `solve.go` carry the dataflow engine. The queue in `walkAll` is sized `len(allLocs) + 3` (the three implicit locations), and each location is walked once; it is re-enqueued only on transitions `!persists -> persists` and `!escapes -> escapes`, so the total work is `Theta(len(allLocs))` walks. `attrPersists` on `heapLoc` is set at the top of `Batch` along with `attrEscapes`, `attrMutates` and `attrCalls`; those are the only sticky bits. A location that escapes is pushed to the front of the todo queue (favoring heap-bound work earlier, as the comment states), and the rest to the back. The `with` method creates a per-function `escape` struct that shares the batch's state: `curfn`, `labels`, `loopDepth`. Loops matter: a variable declared in a loop body at `loopDepth > 1` whose address outlives the iteration escapes even if the pointer never leaves the function. `rewriteWithLiterals` rewrites constant expressions, and `HeapAllocReason` returns a non-empty string for values that must be heap-allocated regardless (a slice over a certain size).
- **For cig: not applicable.** By rule 6: cig has no stack. The dataflow solver's shape is worth seeing because a cig borrow-inference pass has the same structure (a work queue over locations, a dataflow to a fixed point, re-enqueue on a sticky bit transition); but the implementation details here (the two sticky bits, the front-queue bias for escapes) are specific to the stack/heap problem.

### 10. The inliner's budget and what cannot be inlined

- **What it does, and why.** `src/cmd/compile/internal/inline/inl.go` defines `inlineMaxBudget = 80` ("80-nodes leaf functions"); a function is inlinable if it costs at most that many nodes after its body is walked by a `hairyVisitor` that adds one or two nodes per statement and more for calls (`inlineExtraCallCost = 57`, benchmarked to the point where more aggressive inlining stops paying, with the comment linking a 2017 benchmark discussion), parameters-as-functions (`inlineParamCallCost = 17`, which makes a function-valued argument cheaper because inlining may expose it as a known constant), panics (`inlineExtraPanicCost = 1`, kept small so inlining a function that may panic is not penalized), and throws (`inlineExtraThrowCost = inlineMaxBudget`, so a throw bans the inline on its own). Closures called exactly once get `inlineClosureCalledOnceCost = 10 * inlineMaxBudget`, a flat permission. Big functions get a smaller budget: `inlineBigFunctionNodes = 5000` sets the threshold ("big"), and `inlineBigFunctionMaxCost = 20` is the max cost of a callee when the caller is big, so that inlining does not blow out a function that is already large.

  `InlineImpossible` lists seven reasons that bypass the budget: `go:noinline`, `go:norace` with `-race`, `go:nocheckptr` with `-d checkptr`, `go:cgo_unsafe_args`, `go:uintptrkeepalive`, `go:uintptrescapes`, and `go:yeswritebarrierrec`; a function with an empty body and no inline body is also refused (`"no function body"`). PGO adjusts: a function reached by a hot edge in the profile gets `inlineHotMaxBudget` and an inlinee that is "hot" gets a wider budget via `inlheur.BudgetExpansion`. `inlheur/` carries the heuristic layer: `analyze.go` scores functions on their shape (many returns, loop-heavy, few callers, called from a loop), and `scoring.go` turns a score into a budget adjustment. The two passes are `CanInline` (per function, saves a copy of the body) and `InlineCalls` (per caller, expands).
- **For cig: adapt.** By rule 1 and `T3` (no effect or step mark is lost or cloned): inlining in cig has to preserve the step mark of every statement in the callee, the raise-span of every operation that may raise, and every burn in the callee's body (burns never move, rule 1). The budget as a node count is cheap to port. The pragmas map to cig concepts: `go:noinline` has no direct analogue today; `requires_burn` on the callee's `Func` is the closest signal cig has (a function that owns burns inlines its body into the caller's burn region, which the caller may not expect). A cig `no_inline` on a function declaration, honored by the pass, and an automatic ban when the callee has a nested `burn` that the caller has no matching region for.
- **What would decide it.** Not measured yet: the ratio of calls per statement in cig's benchmark set, and the depth of the median call chain, to decide where 80 nodes falls. The number is likely different from Go's because cig's CIR statement is heavier than a Go ir node.
- **Feeds.** cig-compile#33, #34; decisions (e).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/inline/inl.go` (`inlineMaxBudget`, `inlineExtraCallCost`, `inlineParamCallCost`, `inlineExtraPanicCost`, `inlineExtraThrowCost`, `inlineClosureCalledOnceCost`, `inlineBudget`, `hairyVisitor`, `tooHairy`, `InlineImpossible`, `CanInline`); `go-go1.27.4/src/cmd/compile/internal/inline/inlheur/` (`analyze.go`, `scoring.go`).

### 11. Devirtualization: static and profile-guided

- **What it does, and why.** `src/cmd/compile/internal/devirtualize/devirtualize.go` is a short pass with two paths. The static path (`StaticCall`): for each `OCALLINTER` call expression, the pass looks at the interface value's concrete type; if it is a single statically-known type (an `OITAB` whose type has been determined at compile time, usually from a type assertion or a locally-constructed struct), the call is rewritten to a direct call on the concrete type's method. The pass refuses when `call.GoDefer` is true: moving the call point of a defer or go statement is observable because a panic inside the inlined concrete would move from the defer site to the surrounding statement. `const go126ImprovedConcreteTypeAnalysis = true` enables a wider-reaching concrete-type analysis. The profile-guided path is in `pgo.go` (`src/cmd/compile/internal/devirtualize/pgo.go`): for each indirect call that the profile says has a hot concrete callee, the pass generates a conditional `if typeOf(iface) == hotType { hotCallee(...) } else { iface.M(...) }`. The hot concrete is always a fallback (the original indirect call stays), so a profile that was taken against a different workload still produces correct code.
- **For cig: reject.** By rule 1 and rule 7 (verified bytecode, never rewritten at run time): devirtualization in Go is a method-dispatch optimization; cig has no interface methods, only closures, `CallValue`, `CallMethod` on a dynamic receiver, and `CallBuiltin`. The nearest equivalent is `CallMethod` with a receiver whose `Ty` is `Ty::Dynamic`: the VM's `hints` cache already records the receiver type and the resolved method per pc, so the dispatch is cached but not rewritten. A static devirtualization of `CallMethod` would require a static receiver type, which CIR does not carry (`Ty::Dynamic` is the only option for most call sites). The right pattern for cig is the SpiderMonkey CacheIR study, where the dispatch is cached per site rather than rewritten.
- **What would decide it.** Decided by rules 1 and 7.
- **Feeds.** cig-compile#33; decisions (b).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/devirtualize/devirtualize.go` (`StaticCall`, `OCALLINTER`, `go126ImprovedConcreteTypeAnalysis`); `go-go1.27.4/src/cmd/compile/internal/devirtualize/pgo.go`.

### 12. PGO: samples from an ordinary run, matched by source-relative line offset

- **What it does, and why.** `src/cmd/internal/pgo/pgo.go` defines `Profile`: a `TotalWeight` and a `NamedEdgeMap` whose `Weight` is a `map[NamedCallEdge]int64` and whose `ByWeight` is the same keys sorted from most to least hot (so that the "top X percent" selection the inliner does is a simple prefix scan). A `NamedCallEdge` is `{CallerName string, CalleeName string, CallSiteOffset int}`, where `CallSiteOffset` is the line offset from the function's start line, as measured in the profile's own line space (adjusted by `//line` directives for the same reason pclntab uses adjusted lines). `WeightInPercentage(value, total)` converts a weight to a percent for the hot-callsite threshold in the inliner.

  `FromPProf` in `pprof.go` reads a standard pprof file (the format `runtime/pprof` writes), finds the `samples/count` or `cpu/nanoseconds` sample type, builds a call graph with `profile.NewGraph`, and turns it into the edge map. An empty profile (zero samples, zero total weight) is accepted but ignored; a file that contains no sample index of the right type is rejected. `FromSerialized` reads the compiler's preprocessed form, a 4-line-per-edge text format that is faster to parse than pprof. The compiler reads the profile once per build from the `default.pgo` file next to `main.go` (or the path given to `-pgo`); `src/cmd/compile/internal/pgoir/irgraph.go`'s header comment explains that the profile's line numbers are the ones `//line` directives see, not the raw source line numbers, so a file with no `//line` directives has `RelLine == Line` and matching is trivial, while files with such directives can match "best effort" under source changes.
- **For cig: adapt.** By rule 1: a sampling profile from an ordinary run is the right shape for cig's decision (c). The match key cannot be a line: cig's spans are byte ranges in the source, not lines, and cig does not emit `//line`-style remappings. The match key is the `(caller span, callee name)` pair, where the caller span is the span of the `Call*` instruction in the caller's CIR. A stable function name plus a stable span survives a reformatting of the file, a rename of a private helper (through the caller's span), and the whole-function moves common in cig. The design that stage C and cig-cherry both read is this edge map, keyed by `(caller name, callee name, caller CIR span)`, and the collector that produces it writes from the VM's existing `hints` cache plus a sample counter the VM would add.
- **What would decide it.** Not measured yet: on a short run of cig's benchmark suite, the percentage of edges that match between two builds whose source has been reformatted but not functionally changed. The measurement names a hard target for the "survives source edits" rule.
- **Feeds.** cig-compile#33; decisions (c).
- **Read.** `go-go1.27.4/src/cmd/internal/pgo/pgo.go` (`Profile`, `TotalWeight`, `NamedEdgeMap`, `NamedCallEdge`); `go-go1.27.4/src/cmd/internal/pgo/pprof.go` (`FromPProf`); `go-go1.27.4/src/cmd/internal/pgo/deserialize.go` (`FromSerialized`, `IsSerialized`); `go-go1.27.4/src/cmd/compile/internal/pgoir/irgraph.go`.

### 13. The build cache: hashing the inputs, storing by the output

- **What it does, and why.** `src/cmd/go/internal/cache/cache.go` defines `ActionID [HashSize]byte` (32 bytes; `HashSize = 32`) and `OutputID` of the same size. The cache has two levels: `DiskCache` with a directory of indexed files, and `ProgCache` with an out-of-process helper. `cache.go`'s `Get(ActionID)` returns an `Entry` (an `OutputID`, a size and a time), and `Put(ActionID, io.ReadSeeker)` returns the `OutputID` of the content.

  `hash.go` builds the `Hash` with a salt that is the stripped Go version string (`stripExperiment(runtime.Version())`); the comment states the salt's purpose: different Go versions address different cache entries, so a bug in one version does not read another version's output. `hash.Subkey(parent, desc)` creates a sub-key from a parent `ActionID` and a label (used for linker inputs: `parent/stdout`, `parent/link-stdout`). The content ID is a plain SHA-256 of the output bytes; the action ID is a salted SHA-256 of the complete input description (compiler flags, source files' content IDs, pin versions, the tool's own content ID). The tool's own content ID is itself an `ActionID` read out of the tool binary via the `-V=full` flag the tool prints when the `go` command asks: for release toolchains the tool prints the version string instead, so a cross-compiled release has the same tool ID on every host and produces bit-identical output.

  `src/cmd/go/internal/work/buildid.go`'s `actionID`/`contentID` functions split a stored build ID on `/`, and the comment at the top of the file explains the full build-ID shape: `actionID/[.../]contentID`, with the installed binary carrying `actionID(binary)/actionID(main.a)/contentID(main.a)/contentID(binary)` so a later up-to-date check can answer without reading `main.a`.
- **For cig: adapt.** By rule 1 and rule 8 (reproducibility): cig-compile already has `cache.rs`, `sign.rs` and `sbom.rs`. The payloads to hash are the source bytes, the pin for the target (the runtime version from `cig-compile/src/runtime.rs`), the carton's cover file, the stage-b format version, and the compiler's own content ID. The method is what Go has right: salt the hash by the compiler version so a release does not cache against a development build. `Subkey` is a small primitive that pays off in three places (signed module id, stage-b payload id, and the recorded payload-cover id in the carton). cig's form: an `ActionId([u8; 32])` in `cig-compile/src/cache.rs` with a salt from `env!("CARGO_PKG_VERSION")`, a `Subkey(parent: &ActionId, desc: &str)` helper, and the stored id written next to the output with the same `/` separator.
- **What would decide it.** Not measured yet: the fraction of `cig-compile` rebuilds that would hit the cache on the current benchmark set, and the overhead of hashing on the miss path.
- **Feeds.** cig-compile#37; decisions (f).
- **Read.** `go-go1.27.4/src/cmd/go/internal/cache/cache.go` (`ActionID`, `OutputID`, `HashSize`, `DiskCache`, `Get`, `Put`, `Entry`); `go-go1.27.4/src/cmd/go/internal/cache/hash.go` (`Hash`, `hashSalt`, `stripExperiment`, `Subkey`, `NewHash`); `go-go1.27.4/src/cmd/go/internal/work/buildid.go` (`actionID`, `contentID`, `toolID`, `buildIDSeparator`); `cig-compile/src/cache.rs`.

### 14. Concurrent function compilation and the unified export format

- **What it does, and why.** `src/cmd/compile/internal/gc/compile.go`'s `compileFunctions` fans out `base.Flag.LowerC` workers (defaulting to `runtime.NumCPU()` capped), each pulling a `*ir.Func` from `compilequeue` under one mutex and calling `ssagen.Compile(fn, workerId, profile)`. The queue is sorted shortest-first (ascending by body length: `slices.SortFunc(compilequeue, func(a, b) int { return cmp.Compare(len(a.Body), len(b.Body)) })`), and the workers pop from the end; the net effect is that the longest functions are picked first and finish last without becoming stragglers, as the comment states ("we remove from the end of the slice queue, that means shortest to longest"). When race detection is on, the queue is permuted instead of sorted, to shake out races. `types.CalcSizeDisabled` is set to true for the parallel phase because `types.CalcSize` mutates shared state; `base.Ctxt.InParallel` carries the flag down to the assembler.

  The second mechanism is the unified export format (`src/cmd/compile/internal/noder/`): one compiled package writes a serialized IR for every function body that is inlinable or generic, plus the type information for every exported declaration, plus the escape-analysis parameter tags, into a single export file that importers read directly, instead of re-parsing source. `noder/README.md` names the versioning discipline: a change to the writer gets a version flag N+1 in `internal/pkgbits/version.go`, and the writer guards the new field so readers on version N stay oblivious.
- **For cig: adapt.** By rule 5 (identical behavior on every engine): cig-compile compiles one program at a time today; the parallel-function discipline is relevant when a program's modules are compiled in parallel (one worker per module, or per function within a module). The longest-first ordering is a small win that costs nothing to adopt. The unified export format has a sharper fit: cig's stage-b payload already carries the lowered module; adding a per-module summary (parameter borrow tags from entry 8, escape-like observations, inlinable function bodies for cig-cherry) is the stage-b equivalent of Go's export file. The versioning discipline is not optional for cig either (rule 8, signable programs): a payload with a version field that a reader on an older version can skip past is what rule 8 requires.
- **What would decide it.** Not measured yet: the fraction of cig-compile time in a release build spent lowering, against the time spent in the non-parallel passes around it. The parallel discipline pays only when lowering is a majority.
- **Feeds.** cig-compile#37; decisions (e), (f).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/gc/compile.go` (`compileFunctions`, `compilequeue`, `prepareFunc`, `enqueueFunc`); `go-go1.27.4/src/cmd/compile/internal/noder/README.md` (`unified`); `go-go1.27.4/src/cmd/compile/internal/noder/` (`writer.go`, `reader.go`, `unified.go`).

### 15. The two phases of `walk`: lowering to runtime calls and respecting evaluation order

- **What it does, and why.** `src/cmd/compile/internal/walk/` runs after type checking and before SSA; `cmd/compile/README.md`'s section 5 names its two purposes. First, it decomposes complex statements (multi-assignment, type switches, range loops over maps and channels, compound literals) into simpler ones, introducing temporary variables so that the order of evaluation is explicit; this is labeled "order" in the Go documentation. Second, it desugars Go constructs into primitive operations: a `switch` on integers becomes a binary search or a jump table (`src/cmd/compile/internal/walk/switch.go`), a map read becomes a runtime call (`runtime.mapaccess1` or `mapaccess2`), channel operations become calls to `runtime.chansend` and `runtime.chanrecv`. By the end of walk the AST is still Go IR but every operation is either a primitive the SSA builder understands or a call into the runtime; this is why the Go compiler's SSA layer is small (3,500 lines of `compile.go` logic plus the rewrite rules), because walk has already dealt with the higher-level constructs.
- **For cig: reject.** By rule 1 and the CIR design: cig's lowering already does this job. `cig-script/src/lower/mod.rs` lowers AST to CIR with every effect routed through a `burn.op`, every short-circuit as its own node, and every raise explicitly placed; the "order" invariants Go's walk adds are already inherent to CIR because every operation has a `ValueId` and an explicit span. The lesson is the cleanness of the separation: the Go walk output is shallow enough that the mid-end never has to think about `switch`, `range` or map operations as special. cig's `fold-consts` and `copy-prop` already benefit from this, because CIR has no higher-level control-flow shapes to worry about.
- **What would decide it.** Decided by the CIR design (rule 1 and rule 5).
- **Feeds.** cig-compile#33; decisions (e).

### 16. Linker dead-code elimination, reflection and the interface escape

- **What it does, and why.** `src/cmd/link/internal/ld/deadcode.go`'s `deadcode(ctxt)` is the entry point; its header comment names the model. The link begins at the entry symbol (`main.main` plus the init functions; `main..inittask` for the init-task table) and floods the symbol graph through relocations, marking every reached symbol as reachable. The flood is wrapped in rules for methods: every method is referenced by a `R_METHODOFF` relocation on its receiver's `*rtype`, so the deadcode pass sees the method, decides whether to keep it, and the flood continues through the kept method's own relocations.

  Three rules decide, each stated at the top of the file: (1) direct calls are caught by the flood; a directly-called method is marked reachable like any other symbol. (2) A method called through a reachable interface is caught by decomposing every reachable interface type into method signatures and matching them against each method's name (`methodsig`); the pass walks the type's method table once per interface, records the signature set, and on every new type that reaches the flood checks whether the type's methods match any recorded signature. This is extremely conservative (the comment says so), but easy and correct: a type that has an unused method whose signature happens to match a reachable interface keeps that method. (3) `reflect.Value.Method`, `reflect.Type.Method`, and the non-constant `MethodByName` are marked with a `REFLECTMETHOD` attribute on the calling function at compile time; when any `REFLECTMETHOD` function is reachable, `d.reflectSeen` becomes true, and the pass keeps every exported method of every reachable type (and, if `d.dynlink` is also true, every method, exported or not, since a dynamic linker can reach a private method through an interface in another plugin).

  The loop in `deadcode` runs flood, then markableMethods pass, alternately, until `d.wq.empty()` is true (no new work). The one escape hatch that keeps a method out of this: `MethodByName` with a compile-time constant name, which the compiler emits as a relocation with the specific name, so only the matching method is kept rather than the whole exported set.
- **For cig: adapt.** By rule 1 and the kernel invariants: cig's equivalent of "reflection" is any reachable `light` (dynamic callback), a function stored in a `Map` whose key is computed at run time, a `CallBuiltin` by a name computed at run time, or a `CallMethod` on a receiver of `Ty::Dynamic`. Any of these is a cig `REFLECTMETHOD`: the signed payload at stage b cannot drop a builtin that might be reached by name. The three categories map one-to-one: cig's static-call flood (direct `CallUser` by resolved name), cig's "interface" flood (`CallMethod` on a receiver whose static type is known, over the receiver's method set), and cig's "reflection" fallback (any reachable `light` keeps every builtin). The payload shrink pays nowhere unless the program is proven free of the third category; a stage-b build of a "hello world" that only writes to stdout can drop every other builtin and every tin operation, but the moment the program reads a configuration key by variable the pass gives up on that builtin family.
- **What would decide it.** `data/size/README.md` names what there is to drop: the `cli` is 2.0 MB (40.1% of cigscript's 5.0 MB), the keyring 1.4 MB, `zstd` 821 KB, the regular-expression engine 617 KB, the lowering 0.3 MB; both engines plus the parser, lowering and standard library together are 1.14 MB. `data/census/README.md` names what cigo's script reaches: 3,400 builtin calls to `type_of` and others and 1,600 method calls to `.push()` and others in a hook run, against 175 arithmetic instructions; the census does not distinguish static-name builtins from dynamic-name ones. Still owed: for each of cig's 21 benchmark programs and cigo's cases, which builtin families are reachable only by static `CallBuiltin`, which only through `light`, and which not at all.
- **Feeds.** cig-compile#36, #40; decisions (e).
- **Read.** `go-go1.27.4/src/cmd/link/internal/ld/deadcode.go` (`deadcode`, `deadcodePass`, `ifaceMethod`, `genericIfaceMethod`, `reflectSeen`, `markableMethods`, `methodsig`, `flood`, `markMethod`, `mark`); `data/size/README.md`; `data/census/README.md`.

### 17. The pc-ln table: what every Go program carries for tracebacks and profiling

- **What it does, and why.** `src/cmd/link/internal/ld/pcln.go` assembles the table. A per-module `pcHeader` (`src/runtime/symtab.go`) holds the magic (`abi.PCLnTabMagic`), a min instruction size (`minLC`), a pointer size, a function count (`nfunc`), a file-count (`nfiles`), and five offsets to the four subtables and to the pclntab proper: `funcnameOffset`, `cuOffset`, `filetabOffset`, `pctabOffset`, `pclnOffset`. The `_func` object for each function is 11 four-byte fields (`funcSize = 11 * 4 = 44 bytes`).

  The `pclntab` is the per-function metadata table proper; `pctab` carries compressed pc-delta/line-delta tables (one per function) that map a program-counter offset from the function's start to the file index and line number at that pc, plus the pc-delta sequences for `funcdata` entries (frame size, local variable pointer maps, inlined call frames). The size of the table is determined by the number of reachable functions and the length of their body; `addGeneratedSym` tracks the running total in `state.size`.

  The runtime's `findfunc(pc)` returns a `funcInfo` for any pc in a loaded module, and `newInlineUnwinder(funcInfo, pc)` walks a per-function inline tree so that a traceback shows the source frames that the inliner collapsed away: `traceback.go`'s `Frames` type uses this unwinder so `runtime.Callers` returns the pc of the physical frame but iteration over the frames expands inlined calls, giving the appearance that no inlining happened. Every Go program carries this table, with no toggle to disable it; it is why Go's tracebacks work without DWARF and why a profiler sample taken inside an inlined function reports all the original callers.
- **For cig: adapt.** By rule 1 and rule 8 (signed, reproducible programs): cig's CIR already carries a span per instruction (`cig-script/src/lower/cir/ir.rs`'s `Instr::span`) and cig's bytecode carries a per-operand `span_off`/`span_len`/`line_delta` triple relative to the function's `SpanBase` (`cig-script/crates/cig-bytecode/src/module.rs`), so the data is there; what cig lacks is a single address-to-span table usable by a native code generator (cig-cherry) and by a stack walker. The shape to take is the per-function pc-delta/line-delta compression (variable-length deltas, so a long function with few line changes is small) and the inline-unwind table. cig's form, when cig-cherry lands: a `PcMap` next to each lowered function in the tin, with a compressed pc-delta/span-delta sequence and an inline tree that records the source `Func` and span of every inlined `CallUser`. The table is signed with the module (rule 8) and read by the runtime's backtrace printer.
- **What would decide it.** Not measured yet: the per-function size of the table, as a fraction of the function's own code size, on cig's benchmark set. Go's own figure is well under 20 percent for a typical function (`funcSize` is 44 bytes plus pctab deltas); the measurement decides whether the full table is worth carrying for every function, or only those the user asks for.
- **Feeds.** cig-compile#36, #38; decisions (e).
- **Read.** `go-go1.27.4/src/cmd/link/internal/ld/pcln.go` (`pclntab`, `funcSize`, `addGeneratedSym`, `makePclntab`); `go-go1.27.4/src/runtime/symtab.go` (`pcHeader`, `moduledata`, `funcInfo`, `findfunc`, `pclntable`); `go-go1.27.4/src/runtime/traceback.go` (`newInlineUnwinder`).

### 18. The built-in CPU profiler: samples the running program produces

- **What it does, and why.** `src/runtime/cpuprof.go`'s comment at the top states the shape: a SIGPROF signal (`SetCPUProfileRate` sets the rate in Hz, up to a clamp) triggers at each tick, the handler walks the current goroutine's stack with the pc-ln table, and appends the stack trace to a per-run log in a lock-free `profBuf`. A user goroutine reads from the log and turns it into pprof-format profile data.

  The buffer sizes are set as constants: `maxCPUProfStack = 64` (the maximum stack depth captured per sample), `profBufWordCount = 1 << 17` (the sample buffer, for 1,900 samples at a 100 Hz rate with 64-frame stacks, costing 1 MiB), and `profBufTagCount = 1 << 14` (the goroutine-tag buffer, 16k samples at 100 Hz for 160 seconds of thread time). Stacks from non-Go threads come through `addNonGo` into an `extra` buffer of 1,000 pointer-sized entries; the next normal goroutine on a profiling signal copies them out. The design is to produce the same pprof file as any other process-level profiler, so the whole external tooling (pprof, go tool pprof, flame graphs) works on the file unchanged.
- **For cig: adapt.** By rule 1 and decision (c): cig's VM has per-pc hints but no sampling profiler. The design to take is the signal-handler-plus-lock-free-buffer plus the external pprof format: cig emits a profile that any pprof tool reads, but the stack walker walks CIR frames by reading the frame stack the VM already maintains (`Frame::pc`). cig-cherry, when it lands, walks native frames through the pc-map from entry 17. The sample rate is a runtime flag; the buffer sizing is a design decision that scales with program length and stack depth, and Go's figures (1 MiB for 19 thread-seconds at 100 Hz, 64-frame max) are a sensible starting point. The output is a `.pprof` file, the same format Go's PGO reads (entry 12), so cig's `--profile-use` uses the same file.
- **What would decide it.** Not measured yet: the overhead of a 100 Hz signal-sampled profiler against the VM's straight-line time, on cig's benchmark set. Go's own figure is a small single-digit percentage, which is the target.
- **Feeds.** cig-compile#38; decisions (c).
- **Read.** `go-go1.27.4/src/runtime/cpuprof.go` (`cpuProfile`, `profBufWordCount`, `profBufTagCount`, `maxCPUProfStack`, `SetCPUProfileRate`, `addNonGo`); `go-go1.27.4/src/runtime/pprof/` (`pprof.go`, `proto.go`, `cpuprof`'s callers); `go-go1.27.4/src/runtime/traceback.go` (`newInlineUnwinder`).

### 19. The write barrier pass: how a tracing collector reaches into the compiler

- **What it does, and why.** `src/cmd/compile/internal/ssa/writebarrier.go` is a `required: true` pass that rewrites pointer stores into conditional calls to a runtime helper. The pass walks each block; when it finds a `Store` whose value type contains a pointer (filtered by `mightBeHeapPointer` and, for `Move`, by `mightContainHeapPointer`), it rewrites the store into the sequence the pass's header comment names: a test of the write-barrier flag which, when it is set, takes a buffer from `gcWriteBarrier2` and records in it the value being stored and the value being overwritten, followed by the plain store. The flag is `writeBarrier.enabled`, a boolean field of a package-level `writeBarrier` struct in `runtime/mgc.go` (padded so the compiler can use a 32- or 64-bit load); `setGCPhase` turns it on for `_GCmark` and `_GCmarktermination`. A batched call `runtime.gcWriteBarrier{N}` is emitted with up to eight pointers at a time, matching `runtime/mwbbuf.go:wbMaxEntriesPerCall`.

  Two optimizations prune barriers. `needWBsrc(v)` returns false for `IsGlobalAddr(v)` (a store of a global pointer needs no barrier because globals are permanent). `needWBdst(ptr, mem, zeroes)` consults a per-function `ZeroRegion` map that records which pointer-sized words of each memory state are known to be zero (a bitmask up to 64 slots); a store that overwrites a known-zero word skips the "old value" half of the barrier. The pass computes this map with `computeZeroMap` first, then rewrites. This is the deepest hook the garbage collector has into the compiler: every pointer store in the whole program becomes a two-arm branch, with the non-barrier arm picked at run time by reading the package-level `writeBarrier.enabled`.
- **For cig: not applicable.** By rule 6 (deterministic cleanup, reference counting, no tracing collector): cig has no write barrier and no tracing collector, so the pass has no analog. The lesson is twofold. First, the shape of a "pass that lives between the SSA layer and the runtime" (a required pass that materially changes code size and run-time cost; Go's figure is on the order of 20 percent of pointer-heavy code going through the branch, which is why Go treats the barrier as a central design concern). Second, the two things that would be cig's equivalent if the design ever changed: a `Store` that writes an `Rc`-counted value through a `List` or `Map` cell, and a `Clone` that increments a count. Both are already explicit in cig's bytecode (the VM's `SETFIELD` and `SETINDEX` opcodes), so the pass's shape is irrelevant to cig in the way GC's own invariants are irrelevant.
- **What would decide it.** Decided by rule 6.
- **Feeds.** cig-compile#33, #35; decisions (g).
- **Read.** `go-go1.27.4/src/cmd/compile/internal/ssa/writebarrier.go` (`writebarrier`, `ZeroRegion`, `computeZeroMap`, `mightBeHeapPointer`, `mightContainHeapPointer`, `needWBsrc`, `needWBdst`, `UseWriteBarrier`, `maxEntries`); `go-go1.27.4/src/cmd/compile/internal/ssa/compile.go` (`writebarrier`); `go-go1.27.4/src/runtime/mgc.go` (`writeBarrier`, `setGCPhase`).

### 20. The compiler compiling itself: `cmd/dist`'s bootstrap

- **What it does, and why.** `src/cmd/dist/buildtool.go` lists the packages that must be compiled with an older Go to produce the bootstrap toolchain: `cmd/asm`, `cmd/compile`, `cmd/compile/internal/...`, `cmd/cgo`, plus a small list of standard-library packages that the compiler depends on. `copyGoDir` walks the source, copies the files into a bootstrap workspace, and rewrites every import path of the form `cmd/<pkg>` into `bootstrap/<pkg>` so the older Go's `go` command treats them as fresh packages. The older Go is named by `$GOROOT_BOOTSTRAP` (today Go 1.22 or newer).

  The current Go is built in three steps: `go_bootstrap` is the older Go compiling the bootstrapped source into a toolchain; that toolchain compiles the standard library; the toolchain then compiles itself one more time, so the installed `go` binary is produced by itself and the build is self-stable. `main.go`'s `cmdbootstrap` function orchestrates it; the two-step rebuild is the convergence that `cmd/go/internal/work/buildid.go`'s comment on action IDs references ("so too do the action IDs and therefore the build IDs and the overall compiler binary converge"). Go has had this discipline since Go 1.5, when the C-written compiler was replaced by Go-written code.
- **For cig: adapt.** By rule 1 and rule 5 (the tree-walker is the oracle): cig-compile is in Rust and will remain there; a cig-on-cig bootstrap is a different problem. The two ideas worth carrying across for cig-compile#17 (self-hosting) are the naming discipline (a named older version of cig that builds the current one) and the convergence check (the current cig, built by the previous one, must reproduce itself bit for bit on a second pass). The previous-version discipline is what lets cig publish a working build at every release without a C compiler in the path. The convergence check is what rule 8 wants: a program whose signed form is reproducible from its sources on any machine.
- **What would decide it.** Not measured yet: cig has no self-hosted compiler and no bootstrap ladder today. The measurement is the cost (in disk and build time) of keeping a previous-cig binary in the tree and using it to build the current cig. Go's figure is on the order of minutes for the full three-pass bootstrap; the measurement for cig is whether a Rust-on-Rust pre-built cigcompile pays for itself as a bootstrap.
- **Feeds.** cig-compile#17.
- **Read.** `go-go1.27.4/src/cmd/dist/buildtool.go` (`bootstrapDirs`); `go-go1.27.4/src/cmd/dist/main.go` (`cmdbootstrap`); `go-go1.27.4/src/cmd/go/internal/work/buildid.go` (lines 58 to 67 "Separating action ID from content ID").

## For the issues

**cig-compile#33 (the optimizer).** The 60-pass table and its 42-constraint order check (entry 1) is the first lesson: a single file, a single `Pass` record per pass, a single boolean per Func for optimize on/off, and 26 required passes that run even at `-N`. cig's `cig-script/src/lower/cir/pass/mod.rs` already has the shape; it should scale from 4 passes to 20 with the same discipline. The rule-driven rewrite layer (entries 3, 5, 6) is what Go uses for most of its optimizations: a `.rules` file, a Rust generator, a `rewrite.go`-shaped fixed-point loop, with CIR's `Class` as the rule's safety boundary. `prove` (entry 7) is the pass that gives cig bounds-check elimination, which the comparison with LuaJIT in `cig-script/docs/research/luajit.md` (38 against 15 instructions for an indexed read) names as the gap to close; a prove-shaped pass needs `len` values in CIR, per-value integer limits, and a `T4`-protected `RaiseFreeIndex` opcode. The inliner budget (entry 10) is cheap to adopt once CIR has an inliner at all; the pragmas map to `requires_burn` and a user `no_inline`. Devirtualization (entry 11) does not apply to cig; the CacheIR study (file 04) is the right pattern. Walk's separation (entry 15) is what CIR already enjoys, and the lesson is the cleanness, not a port.

**cig-compile#36 (start-up and size).** Linker dead-code elimination (entry 16) is the biggest finding: any reachable `light`, `CallBuiltin` by dynamic name, or `CallMethod` on `Ty::Dynamic` is cig's equivalent of `REFLECTMETHOD`, and the moment one is reached the payload cannot drop any builtin by name. The design question for stage b is which of the 21 benchmark programs' reachable builtins are provably by static name, which only through a dynamic reference, and whether a payload shrink pays at all. The pc-ln table (entry 17) is the other half of start-up size: Go's figure for the table is under 20 percent of code size; for cig, the span-per-instruction already in CIR is the data, so carrying it as a pc-map for cig-cherry is close to free.

**cig-compile#37 (build speed).** The build cache (entry 13) is already in cig's `cache.rs`; the method Go has right is the salt from the compiler version so a bug in one build does not read another build's output. `Subkey(parent, desc)` is a small primitive that pays off in three places (signed module id, stage-b payload id, carton-cover id). The parallel function compilation (entry 14) with longest-first ordering is a small win that costs nothing to adopt; the unified export format and the versioning discipline on the writer is more directly relevant to cig's stage-b payload, which already carries a version field but needs the "writer writes version N+1 guarded, readers on N stay oblivious" rule written down.

**cig-compile#38 (debugging and profiling).** The built-in CPU profiler (entry 18) is the design decision (c) for cig: a sampling profiler that writes the same pprof file that `--profile-use` reads (entry 12). The buffer sizing (1 MiB for 19 seconds at 100 Hz, 64 max stack depth) is a sensible starting point. The pc-ln table (entry 17) is what the profiler's stack walker reads; cig-cherry, when it lands, also reads it.

**cig-compile#17 (self-hosting).** `cmd/dist/buildtool.go` (entry 20) is the right discipline for a self-hosted compiler: a named older version builds the current one, with a convergence pass that re-builds and checks for bit-identical output (rule 8). cig-compile is in Rust and will remain so; the lesson is the naming and the convergence, not the mechanism.
