## What cig should carry away

- **A cig exit record is the whole frame, not a translation subset.**
  `cig-script/src/vm/mod.rs` `struct Frame` holds eleven fields:
  `func` (the function index in the program),
  `pc` (where the frame is in its bytecode),
  `site` (the pc of the call this frame is waiting on, which is where an error from the callee is offered to this frame's tries),
  `base` (the frame's `R(0)` in the register stack),
  `extra` (how many registers after `R(A)` the call's result row covers),
  `held_calls` (calls this frame holds on the interpreter's depth count, its own call and each tail call that replaced a frame in it),
  `nest` (the frame's loop nesting as its last `steps` set it),
  `held_nest` (loop nesting held for frames a tail call replaced),
  `up` (the index of its closure's upvalues in `Machine::upvals`, or `NO_UPVALS`),
  `tries` (where its open tries begin in `Machine::tries`),
  `burns` (where its open burns begin in `Machine::burns`).
  Every one of these has to be rebuilt by an exit from compiled code, because the VM reads every one. V8's per-exit translation (entry 8) is a reference for the format, not the content: the content list is this one, plus the step counter, the open-try and open-burn side lists the `tries` and `burns` fields point into, and the journal's position at `cig-script/src/burn/journal.rs` (entry 11).
- **One language for inline caches and one for feedback, kept by the VM and consumed by stage C and cig-cherry alike.** V8 keeps feedback in a per-function vector with a slot kind per bytecode site and a state per slot (entry 1); JSC uses value profiles and a 50-bit speculated-type lattice (entry 3). cig today keeps only one cell per pc (`cig-script/src/vm/mod.rs`: `hints`, read at `GETFIELD`, `SETFIELD`, `CALLM`) and no counters. Decision (b) needs a format with site state (uninitialized to polymorphic to generic), shape recording, and a call-site target. The lattice as bits (entry 3) is the smallest form.
- **CFG beats sea of nodes for cig, decided by rule 1.** V8's own account of leaving the sea of nodes (entry 6) is that effect and control chains made every pass fragile. cig's "burns never move" is a stronger version of V8's effect chain, and CIR is already structured and block-ordered (`cig-script/src/lower/cir/`); the reasons V8 gives for the move all apply (entry 7).
- **A lighter back end is worth having only for a top tier, and cig does not need one.** JSC replaced LLVM with B3 because about three quarters of FTL's compile time was LLVM (entry 16); the target was "ten times faster than LLVM at comparable code quality". Cranelift is already in that range and its allocator is already modern; cig has no top tier LLVM would serve (entry 16).
- **Three register allocators for three budgets is the right shape for cig-cherry** (entry 15). JSC's Air has a greedy allocator and a graph-coloring allocator at `optLevel >= 1`, and a one-pass allocator-and-generator at `optLevel == 0`. cig-cherry tier 2 wants the one-pass path; Cranelift's `regalloc2` covers tier 3 (study 02).
- **Exits must be a first-class test target, not a path exercised only by accident** (entry 13). JSC ships `DFGOSRExitFuzz` so the suite forces exits to fire at random under compiled code. cig-cherry needs the same gate on top of the differential suite, run with cherry forced on everything (threshold 0) and with cherry-fuzz injecting a forced failure at each guard in turn.
- **The interrupt budget is scaled by function size and held after an IC update** (entry 2). V8's rule, "do not tier up until the ICs have stopped moving", is the one that makes the tier a better guess than the plain counter would give; cig needs that rule more than it needs V8's exact 500-invocation value.
- **The signed code cache's header is a sanity check, not a signature alone** (entry 17). cig's tin cache needs V8's eight-field header shape plus cig's signature (cig-script#256 section 4). A failed field is one of the nine outcomes in V8's `SerializedCodeSanityCheckResult`, and `cig tin gc` needs to tell them apart.

## Design points

### 1. Feedback as a per-function vector with a kind per site and a state per slot

- **What it does, and why.** V8 keeps the profile for a function in a `FeedbackVector` referenced by its `FeedbackCell`. `src/objects/feedback-vector.h` has one `FeedbackSlotKind` per bytecode site, 26 kinds at this pin from `kInvalid` through `kJumpLoop` (`kCall`, `kLoadProperty`, `kLoadGlobalNotInsideTypeof`, `kLoadKeyed`, `kSetNamedStrict`, `kDefineKeyedOwn`, `kBinaryOp`, `kCompareOp`, `kForIn`, `kInstanceOf`, `kCloneObject`, `kJumpLoop`, and more). A slot records up to `DEFAULT_MAX_POLYMORPHIC_MAP_COUNT` map-and-handler pairs (`MapsAndHandlers` in the same header). Its runtime state is one of nine in `src/common/globals.h` `InlineCacheState`:
  - `NO_FEEDBACK` (no profile will be collected at this site);
  - `UNINITIALIZED` (the site has not run yet);
  - `MONOMORPHIC` (one receiver type seen);
  - `RECOMPUTE_HANDLER` (the shape changed and the handler can be rebuilt);
  - `POLYMORPHIC` (several maps seen);
  - `MEGADOM` (many DOM receivers for one accessor);
  - `HOMOMORPHIC` (many maps, one handler);
  - `MEGAMORPHIC` (so many maps that keeping them is not worth it);
  - `GENERIC` (a generic handler, no further feedback).

  The brief names four states; nine is the number at the pin.
- **For cig: adapt.** cig's maps are string-keyed and insertion-ordered (`cig-script/src/value.rs`, `Map = Rc<RefCell<IndexMap<String, Value>>>`) and its `hints` today keeps one cell per pc (`cig-script/src/vm/mod.rs`, read at `GETFIELD`, `SETFIELD`, `CALLM`): a field cache at `GETFIELD`/`SETFIELD`, a method cache at `CALLM`. For decision (b), cig takes the shape of the design and leaves the DOM variants: a per-function vector sized at lower time, one slot per site, states `Uninitialized`, `Monomorphic`, `Polymorphic` (up to a small number, 4 is plausible on insertion-order maps), `Megamorphic`. The verifier's "no shapes" fact (rule 4, insertion order) is why cig can skip MEGADOM and MapsAndHandlers over DOM accessors.
- **What would decide it.** Not measured yet: how many distinct shapes a field site sees in the compute programs and in cigo. The census report says every field site saw one shape (`data/census/README.md` "In the compute programs" point 3); cig's "polymorphic" threshold is a future decision, not a present one.
- **Feeds.** cig-compile#33, cig-script#256; decision (b).
- **Read.** `v8-15.8.62.31/src/objects/feedback-vector.h` (`FeedbackSlotKind`, `MapsAndHandlers`, `DEFAULT_MAX_POLYMORPHIC_MAP_COUNT`); `v8-15.8.62.31/src/common/globals.h` (`InlineCacheState`); `cig-script/src/vm/mod.rs` (`hints`); `cig-script/src/value.rs` (`Map`).

### 2. The interrupt budget: counting scaled by code size, charged on the feedback cell

- **What it does, and why.** V8 stores the "budget until the next tiering check" in the `FeedbackCell`, not the function. `src/objects/feedback-cell.h` has `int32_t interrupt_budget_`, `inline int32_t interrupt_budget()` and `inline void set_interrupt_budget(int32_t)`. `src/execution/tiering-manager.cc` scales the budget by the function's bytecode length: `ScaleInterruptBudget(invocations, bytecode_length)` returns `invocations * bytecode_length` clamped to `INT_MAX/2`, so a bigger function reaches the next check sooner in invocation terms. Thresholds are in `src/flags/flag-definitions.h`: `invocation_count_for_feedback_allocation` 8 (when a vector is first allocated), `invocation_count_for_maglev` 400 (1000 on Android), `invocation_count_for_turbofan` 3000, `invocation_count_for_osr` 500, `minimum_invocations_before_optimization` 2, `minimum_invocations_after_ic_update` 500 (tier up only after the ICs have stopped moving).
- **For cig: adapt.** cig's VM today has no counter and no tier-up (confirmed by searching the clone: `hints` is a cache, not a count). For decision (c), cig takes the design: a per-function counter charged per call and per loop back-edge, scaled by function size, with a small set of thresholds named by flag; and the "wait for the ICs to settle" rule from `minimum_invocations_after_ic_update`, which stops cig-cherry from compiling against a profile that is still moving. Four thresholds are enough: feedback allocation, tier 2 (cherry baseline), tier 3 (cherry optimizing), and the OSR cousin of tier 3. `cig-compile/src/bench.rs` already has size-scaled budgets in the gate, which is the right side of the project to keep them.
- **What would decide it.** Not measured yet: how many of cigo's 1,038 functions reach any of the four thresholds on a typical CLI call, from `data/census/README.md`'s cigo cases. If few, cig-cherry's tier 2 threshold should be lower than V8's 400.
- **Feeds.** cig-compile#33, #37, cig-script#256, #243; decisions (c), (d).
- **Read.** `v8-15.8.62.31/src/objects/feedback-cell.h` (`interrupt_budget_`, `interrupt_budget`); `v8-15.8.62.31/src/execution/tiering-manager.cc` (`ScaleInterruptBudget`, `InterruptBudgetFor`); `v8-15.8.62.31/src/flags/flag-definitions.h` (`invocation_count_for_feedback_allocation`, `invocation_count_for_maglev`, `invocation_count_for_turbofan`, `invocation_count_for_osr`, `minimum_invocations_before_optimization`, `minimum_invocations_after_ic_update`).

### 3. JavaScriptCore's value profiles and the speculated-type lattice as bits

- **What it does, and why.** JSC collects types at the value profile, not the inline cache. `bytecode/ValueProfile.h` has `ValueProfileBase<numberOfBuckets, numberOfSpecFailBuckets>`: a small ring of `EncodedJSValue` buckets a baseline tier writes into on every value-producing site. The lattice the tiers reason over is `bytecode/SpeculatedType.h` `typedef uint64_t SpeculatedType`: 50 named kinds as single bits, from `SpecFinalObject` (bit 0) through typed arrays (bits 4 to 15), argument objects, string identifiers (`SpecStringIdent` bit 32), 32-bit integer disjoint from boolean-looking integer (`SpecBoolInt32` bit 37 and `SpecNonBoolInt32` bit 38), `SpecInt52Any`, `SpecAnyIntAsDouble`, `SpecDoublePureNaN`/`SpecDoubleImpureNaN` (NaN has two kinds so JSC can keep `NaN` canonical on the heap), `SpecBoolean`, `SpecOther` (null or undefined), `SpecEmpty`, `SpecHeapBigInt`, `SpecBigInt32`. Composite kinds (`SpecInt32Only`, `SpecBytecodeDouble`, `SpecFullNumber`, `SpecBytecodeNumber`) are ORs. `bytecode/ArrayProfile.h` is a parallel 32-bit `ArrayModes` bitfield for indexed access, one bit per `IndexingType` and one per typed array kind, so an array site records "which array shapes have I seen" as a set.
- **For cig: adapt.** Decision (b)'s format is a type set per site, kept by the VM, read by stage C and cig-cherry alike. The 50-bit lattice is more granular than cig can fill (`cig-script/src/lower/cir/ir.rs` `enum Ty` has nine variants: `Dynamic`, `Null`, `Bool`, `Int`, `Float`, `Str`, `List`, `Map`, `Func`), so cig's lattice is about eleven bits: the nine `enum Ty` variants plus "list of ints only" and "list of floats only" (the two the census showed every program needing for a numeric loop). Encoding as bits makes the "has the site stabilised" test a single compare against zero.
- **What would decide it.** Not measured yet: how many sites in the compute set see exactly one type pair and how many see two. `data/census/README.md` "Types do not move" says 226 of 227 arithmetic and comparison sites saw one pair for the whole run, 97.7% of the executions; one bit per type is enough on that evidence.
- **Feeds.** cig-compile#33, cig-script#256; decisions (b), (c), (i).
- **Read.** `webkit-wpewebkit-2.54.3/Source/JavaScriptCore/bytecode/ValueProfile.h` (`ValueProfileBase`); `webkit-wpewebkit-2.54.3/Source/JavaScriptCore/bytecode/SpeculatedType.h` (`SpecNone`, `SpecInt32Only`, `SpecBytecodeNumber`); `webkit-wpewebkit-2.54.3/Source/JavaScriptCore/bytecode/ArrayProfile.h` (`ArrayModes`); `cig-script/src/lower/cir/ir.rs` (`enum Ty`).

### 4. JavaScriptCore's execution counter: counts scaled by code size and by how often a function was thrown back

- **What it does, and why.** `bytecode/ExecutionCounter.h` `ExecutionCounter<CountingVariant>` stores a signed `m_counter` that counts up from a negative starting value toward zero and an `m_totalCount` of executions seen so far. The threshold is reset by `setNewThreshold` and compared through `checkIfThresholdCrossedAndSet`. The threshold is not the raw option: `applyMemoryUsageHeuristics` in `bytecode/ExecutionCounter.cpp` multiplies it by `ExecutableAllocator::memoryPressureMultiplier(predictedMachineCodeSize)`, so tier-up slows down when executable memory is tight. `hasCrossedThreshold` adds a second scaling: `modifiedThreshold - min(m_activeThreshold, maximumExecutionCountsBetweenCheckpoints) / 2`, so the threshold "declares victory a bit early" to avoid thrashing. Options (`runtime/OptionsList.h`): `thresholdForJITAfterWarmUp` 500, `thresholdForJITSoon` 100, `thresholdForOptimizeAfterWarmUp` 1000, `thresholdForOptimizeSoon` 1000, `thresholdForFTLOptimizeAfterWarmUp` 64000, `thresholdForFTLOptimizeSoon` 1000, `executionCounterIncrementForEntry` 15 (a call is worth 15 loop turns), `executionCounterIncrementForLoop` 1. Separate counters for baseline and upper tiers (the two `CountingVariant` values).
- **For cig: adapt.** A function that has been thrown back by cig-cherry once should wait longer before being recompiled, as JSC's `optimizationThresholdScalingFactor` does. For decision (c), cig keeps "one counter per tier target" and the "loop turn is worth less than a call" split (`executionCounterIncrementFor*`), but leaves the "executable memory is tight" scaling out: cig-cherry's design (cig-script#256) is to write signed files in the tin, not to anonymous executable pages, and its back pressure is file space, measured elsewhere.
- **What would decide it.** Not measured yet: the ratio of loop turns to calls over the compute set, from pair counts in `bench-stats`. The census tables (`data/census/report.md`) count singles, not pairs; a pair run would decide the loop/call weighting.
- **Feeds.** cig-script#256, #243 (A8), cig-compile#33; decision (c).
- **Read.** `webkit-wpewebkit-2.54.3/Source/JavaScriptCore/bytecode/ExecutionCounter.h` (`ExecutionCounter`, `CountingForBaseline`, `CountingForUpperTiers`); `webkit-wpewebkit-2.54.3/Source/JavaScriptCore/bytecode/ExecutionCounter.cpp` (`applyMemoryUsageHeuristics`, `hasCrossedThreshold`); `webkit-wpewebkit-2.54.3/Source/JavaScriptCore/runtime/OptionsList.h` (`thresholdForJITAfterWarmUp`, `thresholdForOptimizeAfterWarmUp`, `thresholdForFTLOptimizeAfterWarmUp`, `executionCounterIncrementForEntry`, `executionCounterIncrementForLoop`).

### 5. Maglev: a CFG SSA built straight from bytecode using feedback, with specialized nodes

- **What it does, and why.** Maglev (`src/maglev/`) is V8's middle tier. `maglev-graph-builder.h`/`.cc` builds an SSA control-flow graph directly from the ignition bytecode, specializing nodes as it goes: the post says "if Maglev sees `o.x` and knows from the runtime feedback that `o` always has one specific shape, it will generate an SSA node to check at runtime that `o` still has the expected shape, followed by a cheap `LoadField` node which does a simple access by offset" (`v8-maglev.html`). A prepass finds branch targets and liveness so loop phis are created before the loop body is walked (single forward pass, no fix-up). `maglev-ir.h` has about twelve thousand lines of node kinds carrying their own deoptimization information: a node that can exit records what every interpreter register holds in the node that may deopt (the `DeoptInfoVisitor` in `maglev-deopt-frame-visitor.h` walks that). `maglev-regalloc.cc` is a single forward walk with register state merged at block joins and a prepass to find linear live ranges. `maglev-concurrent-dispatcher.cc` runs Maglev on a background thread off a locked queue of compilation jobs.
- **For cig: adapt.** For cig-cherry's tier 2 (cig-script#256 phase 2 to 4), a lowering straight from the verified bytecode into a block-ordered SSA, specialized by the VM's observed types, is the model. cig's CIR is already structured and already SSA on `ValueId` (`cig-script/src/lower/cir/ir.rs`); cherry's own lowering produces a flatter form from the register bytecode (cig-script/crates/cig-bytecode/src/opcode.rs, 73 opcodes), not CIR. Decision (e)'s crate boundaries: one code generator shared with stage C, one background dispatcher borrowed from the Maglev shape (locked job queue, cig's values stay `Rc` and never cross threads, only the bytecode and the profile cross).
- **What would decide it.** Not measured yet: compile time for Maglev-shaped per-function compilation on cigo's 1,038 functions, on the test machine, against `cig run --engine vm`'s start-up today. Phase 2 of cig-script#256 names "compile time per function" as the measurement. Rule 10 decides the "no anonymous executable memory" part.
- **Feeds.** cig-compile#32 (guards that exit), #37 (compiling fast), cig-script#256; decisions (b), (d), (e).
- **Read.** `v8-15.8.62.31/src/maglev/maglev-graph-builder.h` (`MaglevGraphBuilder`, `MaglevCallerDetails`); `v8-15.8.62.31/src/maglev/maglev-ir.h` (`DeoptFrame`, `ValueNode`); `v8-15.8.62.31/src/maglev/maglev-regalloc.cc`; `v8-15.8.62.31/src/maglev/maglev-compiler.cc`; `v8-15.8.62.31/src/maglev/maglev-concurrent-dispatcher.cc` (`LocalIsolateScope`, `MaglevCompilationJob`); `v8-15.8.62.31/src/maglev/maglev-deopt-frame-visitor.h` (`DeoptInfoVisitor`); `papers/compilers/v8-maglev.html`.

### 6. Why V8 is leaving the sea of nodes

- **What it does, and why.** The sea of nodes was V8's "a node is an instruction, an edge is a true data dependency; control and effect are extra edge kinds" IR (`papers/compilers/v8-leaving-the-sea-of-nodes.html`, and `src/compiler/turboshaft/` as the replacement). The post gives the reasons for leaving it: (i) a graph is hard to read for engineers used to source and assembly, which are both ordered; (ii) almost every memory op and some pure ops (division, bounds-checked loads) needs an effect edge *and* a control edge, so the "float freely" benefit shrinks; (iii) one effect chain is error-prone and multiple chains were not attempted; (iv) lowerings have to maintain the effect and control chains explicitly, which is a cliff every pass stumbles over; (v) cache locality is worse than for an array of operations in blocks. The example graph for a nine-line function fills a page.
- **For cig: reject.** Sea of nodes is not for cig; CIR stays structured. Decided by rule 1 and rule 6: a pass that reorders an effect breaks `T1`-`T3`, and a sea-of-nodes pass is a pass that reorders by default and pins what cannot move. CIR puts the "cannot move" marks on the instructions themselves (`enum Class` in `cig-script/src/lower/cir/ir.rs`: `Pure`, `MayRaise`, `Effect`, `Step`), and the verifier enforces them after every pass (`cig-script/src/lower/cir/verify.rs`, transition rules `T1` to `T4`). That is the opposite of SoN's design and it is the one cig's rules let it have.
- **What would decide it.** Decided by rule 1.
- **Feeds.** cig-compile#33.
- **Read.** `papers/compilers/v8-leaving-the-sea-of-nodes.html`; `v8-15.8.62.31/src/compiler/turboshaft/graph.h` (the replacement); `cig-script/src/lower/cir/ir.rs` (`enum Class`); `cig-script/src/lower/cir/verify.rs` (`T1`, `T2`, `T3`).

### 7. Turboshaft: operations in blocks in fixed order, a reducer stack, one phase per copy

- **What it does, and why.** `src/compiler/turboshaft/graph.h` represents a function as blocks of `Op`s packed in an `OperationBuffer` (append-only, `OperationStorageSlot`-aligned slabs), each op at a fixed offset in a block. `operations.h` (eleven thousand lines) names every op, each a compact `struct` with inline operand storage. A pass is a stack of reducers: each reducer intercepts the ops it cares about, calls `Next::ReduceFoo(args)` for the rest. Reducers at this pin include `branch-elimination-reducer.h` (nested `if (cond)` inside `if (cond)` folded to one), `dead-code-elimination-reducer.h`, and more under `src/compiler/turboshaft/`. `copying-phase.h` is the orchestrator: a `CopyingPhase<Reducers...>` copies the graph from an input to a new output through the reducer stack, so each pass sees a fresh graph (not a mutated one), which keeps the "did the pass break an invariant" check to "does the output validate".
- **For cig: adapt.** CIR already has "blocks in fixed order" (`Block { instrs }` in `ir.rs`). The reducer stack and the copying phase are the right design for CIR's passes: today `cig-script/src/lower/cir/pass/mod.rs` has four passes (`fold-consts`, `copy-prop`, `sccp`, `dead-pure`, from `NAMES` in that file) and each produces a new module the verifier compares against a snapshot (rule T1 to T4). That matches "each phase copies the graph through its reducers"; the extension cig takes is one assembler-style helper trait so a pass can be written as a reducer, not as a hand-written traversal. Decision (e) can put the reducer trait in CIR's crate and share it with stage C.
- **What would decide it.** Not measured yet: how many of cig's current passes are easier to read as reducers than as traversals, and whether the verifier's cost rises when every pass produces a fresh module. The existing passes are small, so this is a readability decision today.
- **Feeds.** cig-compile#33.
- **Read.** `v8-15.8.62.31/src/compiler/turboshaft/graph.h` (`OperationBuffer`, `ReplaceScope`); `v8-15.8.62.31/src/compiler/turboshaft/operations.h` (`TURBOSHAFT_OPERATION_LIST`); `v8-15.8.62.31/src/compiler/turboshaft/assembler.h`; `v8-15.8.62.31/src/compiler/turboshaft/copying-phase.h` (`OutputGraphAssembler`); `v8-15.8.62.31/src/compiler/turboshaft/branch-elimination-reducer.h` (`BranchEliminationReducer`); `v8-15.8.62.31/src/compiler/turboshaft/dead-code-elimination-reducer.h`; `cig-script/src/lower/cir/pass/mod.rs` (`NAMES`, `level`, `run_passes`).

### 8. The frame translation: per exit, where each interpreter register's value now lives

- **What it does, and why.** V8's deoptimizer rebuilds interpreter frames from optimized ones by replaying a per-exit *translation*. `src/deoptimizer/translation-opcode.h` is the opcode set (44 opcodes at this pin, counted from the `V(...)` entries across `TRANSLATION_JS_FRAME_OPCODE_LIST`, `TRANSLATION_FRAME_OPCODE_LIST` and `TRANSLATION_OPCODE_LIST`): `BEGIN_WITH_FEEDBACK`/`BEGIN_WITHOUT_FEEDBACK`, then a frame start per inlined call (`INTERPRETED_FRAME_WITHOUT_RETURN`, `INTERPRETED_FRAME_WITH_RETURN`, `JAVASCRIPT_BUILTIN_CONTINUATION_FRAME`, `CONSTRUCT_CREATE_STUB_FRAME`), then per interpreter register either a `REGISTER` (its current CPU register), a `TAGGED_STACK_SLOT` (its stack offset), an `INT32_REGISTER`/`DOUBLE_REGISTER`/`FLOAT_STACK_SLOT`/… for typed values, a `LITERAL` (a constant from the pool), `OPTIMIZED_OUT` (its value was dropped), `CAPTURED_OBJECT` and `DUPLICATED_OBJECT` for allocation-sunk values (entry 9), `UPDATE_FEEDBACK` to record a failure in the vector, and `MATCH_PREVIOUS_TRANSLATION` to share a prefix with another exit point to save bytes. `src/deoptimizer/frame-translation-builder.h` builds the stream; `src/deoptimizer/translated-state.h` reads it and forms a `TranslatedFrame` per inlined call with a `TranslatedValue` per interpreter register.
- **For cig: adapt.** The idea cig takes for decision (d): an exit point is a short stream that rebuilds a `Frame` field by field, from one of a few places a value can be (a CPU register, a stack slot, a constant, or an allocation to materialise, entry 9). What cig adds for its own semantics: one more place a value can be (`Rc` to a heap value, with a reference-count convention at the exit; rule 6), and the step counter and the open-try/open-burn indices among the fields to rebuild. `MATCH_PREVIOUS_TRANSLATION` is the right compression for cig too: many exits of a hot loop share most of their state.
- **What would decide it.** Not measured yet: the average number of bytes a cig exit record takes over the compute set, once there are compiled functions to measure; the goal is that the exits do not dominate the compiled size budget (cig-compile#36).
- **Feeds.** cig-compile#32, cig-script#256; decisions (d), (e).
- **Read.** `v8-15.8.62.31/src/deoptimizer/translation-opcode.h` (`TRANSLATION_OPCODE_LIST`, `TRANSLATION_JS_FRAME_OPCODE_LIST`); `v8-15.8.62.31/src/deoptimizer/frame-translation-builder.h` (`FrameTranslationBuilder`, `BeginInterpretedFrame`); `v8-15.8.62.31/src/deoptimizer/translated-state.h` (`TranslatedValue`, `TranslatedFrame`); `cig-script/src/vm/mod.rs` (`struct Frame`).

### 9. Materializing objects whose allocation the optimizer removed

- **What it does, and why.** When Turbofan or Maglev proves that a newly allocated object never escapes its optimized region, it drops the allocation. If a guard then fails and the deoptimizer has to rebuild that object for the interpreter, it allocates it then from the translation (`CAPTURED_OBJECT` and `DUPLICATED_OBJECT` opcodes in `translation-opcode.h`, then the per-field values that follow). The deoptimizer keeps a side table of already-materialised objects per frame pointer (`src/deoptimizer/materialized-object-store.h` `MaterializedObjectStore`: `Get(Address fp)`, `Set(Address fp, DirectHandle<FixedArray>)`, `Remove(Address fp)`), so a second exit from the same frame finds its object already built and does not duplicate it.
- **For cig: adapt.** cig keeps every allocation reference-counted (`cig-script/src/value.rs`); allocation sinking is one of the rc-elision tricks that is sound only on a value that does not escape (study 05). For decision (g), the rule is: a sunk allocation may be materialised at an exit as a new `Rc`-held value of the right shape, with the reference count set to one; the compiled region that sank it must not have handed the value to anything that holds a count, which the ownership-SSA work (study 06) proves. The materialised-object side table is a per-exit need: on a side-trace-style second exit from the same compiled region, the same `Rc` is given out, not a fresh one, otherwise identity (`a is b`) changes between runs.

### 10. Lazy against eager deopt, and what stops a function from deoptimizing forever

- **What it does, and why.** V8 has three deopt kinds at this pin, not two. `src/common/globals.h` `enum class DeoptimizeKind` is `kEager`, `kLazyAfterFastCall`, `kLazy`: eager is the compiled code checking a condition and exiting itself; lazy is the runtime having invalidated the code (a dependent map changed, a prototype was swapped), so the code is patched to exit on its next return; lazy-after-fast-call is the shape of lazy that holds for a fast-API call. `src/deoptimizer/deoptimize-reason.h` names every reason the compiled code can exit for: `DEOPTIMIZE_REASON_LIST` carries 68 at this pin (counting `DEOPTIMIZE_IN_BUILTIN_REASON_LIST`'s one entry plus 67 direct entries, by `grep -cE "^\s+V\("`): `WrongMap`, `NotASmi`, `DivisionByZero`, `Hole`, `InsufficientTypeFeedbackForBinaryOperation`, `OSREarlyExit`, `LostPrecision`, `ArrayBufferWasDetached`, and more; `LAZY_DEOPTIMIZE_REASON_LIST` carries 17 more for the runtime reasons, `MapDeprecated`, `FieldTypeChange`, `PrototypeChange`, `PropertyCellChange`, and more. What stops a function from deoptimizing forever: `src/objects/feedback-vector.h` keeps `invocation_count_before_stable_` (an 8-bit field, "in case a function deoptimizes we set invocation_count_before_stable to … and wait for that many invocations without further deopts before re-optimizing"), and the tiering manager's `minimum_invocations_after_ic_update` of 500 holds the next tier-up until the ICs have stopped changing. A function that keeps deopting past a bound is left on the baseline tier (JSC's analogue is in entry 13).
- **For cig: adapt.** cig-cherry needs both kinds: an eager exit (a guard inside compiled code), and a lazy exit (the module's bytecode or a dependency was changed between runs, which rule 7 forbids anyway, but `cig tin gc` can remove a cache entry, which is the cig-side lazy case). The reason list is cig's own: the exit reasons from `WrongType`, `WrongShape`, `WrongReceiver`, `IntegerOverflow` (rule 4 means integer overflow is a visible error, not a tier-dropped guess), `TooManyCallees`, `StepBudgetBoundary` (the step budget charged a step and rule 3 says the point is exact). The counter cig takes is one byte of "exits since last recompile" per function, resetting on a run; past a bound, cig-cherry blacklists the function for that cig version (`E2383` in cig-script#256).
- **What would decide it.** Not measured yet: the cigo cases in the census that would exit a cherry-compiled function would show how many reasons are hot. The census does not measure exits; a cherry build would.
- **Feeds.** cig-compile#32, cig-script#256; decision (d).
- **Read.** `v8-15.8.62.31/src/common/globals.h` (`DeoptimizeKind`, `kEager`, `kLazy`, `kLazyAfterFastCall`); `v8-15.8.62.31/src/deoptimizer/deoptimize-reason.h` (`DEOPTIMIZE_REASON_LIST`, `LAZY_DEOPTIMIZE_REASON_LIST`); `v8-15.8.62.31/src/deoptimizer/deoptimizer.cc` (`MaterializeHeapObjects`); `v8-15.8.62.31/src/objects/feedback-vector.h` (`invocation_count_before_stable_`).

### 11. JavaScriptCore's OSR exit: recover the bytecode's variables from a stream of value sources

- **What it does, and why.** JSC's `dfg/DFGOSREntry.cpp` is the path in the other direction: a long-running loop in the baseline tier is replaced by its compiled version while the loop is still running, by rebuilding the compiled stack frame from the interpreter's values and jumping into the compiled loop at the matching back-edge. `dfg/DFGTierUpCheckInjectionPhase.cpp` inserts the check that calls into the OSR entry routine when the loop's counter crosses the threshold. ### 14. Liftoff: a single pass over the Wasm bytecode with a virtual operand stack

- **What it does, and why.** `src/wasm/baseline/liftoff-compiler.cc` (about 11,700 lines at this pin) decodes a Wasm function body once, generating machine code as it goes. The decoder calls back into the compiler per instruction; there is no IR. `src/wasm/baseline/liftoff-varstate.h` keeps a per-value `LiftoffVarState` with a `Location` of `kStack`, `kRegister` or `kIntConst`, plus a `kind` (`kI32`, `kI64`, `kF32`, `kF64`) and a spill offset: at every point the compiler knows where every stack value lives (a register, a spilled stack slot, or a known small constant). `src/wasm/baseline/liftoff-assembler.h` is the arch-targeted assembler. `src/wasm/baseline/parallel-move.h` encodes moves between locations as a batch that can handle cycles (a swap of two registers), so a merge at a branch target that needs values in different places from the fall-through is a single `Transfer` call. The Liftoff post says: "it performs only one pass over the opcodes of a function, generating code for each opcode, one at a time"; a small integer `i32.const` is not emitted, only recorded on the virtual stack, and combined with its first use.

The Wasm advantage Liftoff has (statically typed, structured control flow) cig partly shares: CIR is already structured and ordered (the bytecode is produced from a verified, structured source), and type profiles (entry 3) give cig enough to pick register kinds. Rules 6, 7 and 8 all hold for a one-pass compiler that writes to a file: no SSA mutation, no self-modifying code.
- **What would decide it.** Not measured yet: compile time per cig function in a one-pass tier 2, against Maglev's per-function compile time at the same code size on the test machine, for the compute set and cigo's 1,038 functions.
- **Feeds.** cig-compile#37, cig-script#256 (phase 2).

### 15. B3 and Air: a small SSA IR and a machine-level IR, three register allocators for three budgets

- **What it does, and why.** JSC's top tier compiles DFG output through two JSC-written IRs: B3 (a small SSA IR; `b3/B3Value.h` `class Value`, `b3/B3Procedure.h` `class Procedure`, `b3/B3Opcode.h` `enum Opcode`, 190 opcodes at this pin counted with a pattern that matches both bare and trailing-comment lines, polymorphic `Add`/`Sub`/`Mul` taking any value type) and Air ("Assembly IR", `b3/air/AirCode.h` `class Code`). The post ("Introducing the B3 JIT Compiler") spells out the design: reduce IR object sizes, so passes that walk the whole function cache well; drop "replace all uses with" from the API and fold its work into a traversal (`Value::replaceWithIdentity()` then `performSubstitution()`); fold common pairs into one opcode in B3 (`Check` for "branch and exit", `CheckAdd`/`CheckSub`/`CheckMul` for overflow-checked arithmetic), and in Air (`BranchAdd32`/`BranchAdd64`) for the machine form. `b3/B3Generate.cpp` runs the pipeline: at `optLevel >= 2` it runs `reduceDoubleToFloat`, `reduceStrength` (`b3/B3ReduceStrength.cpp`, over five thousand lines), optional `hoistLoopInvariantValues`, `eliminateCommonSubexpressions`, `eliminateDeadCode`, `fixSSA`, `foldPathConstants`, then lowering macros, then another `reduceStrength`, then `lowerToAir`; at `optLevel == 1` only the initial `reduceStrength`. Register allocation: `b3/air/AirGenerate.cpp` picks one of three paths, `allocateRegistersByGreedy` (`b3/air/AirAllocateRegistersByGreedy.cpp`, selected by `Options::airUseGreedyRegAlloc`), `allocateRegistersByGraphColoring` (`b3/air/AirAllocateRegistersByGraphColoring.cpp`, the default at `optLevel >= 1`), or `allocateRegistersAndStackAndGenerateCode` (`b3/air/AirAllocateRegistersAndStackAndGenerateCode.cpp`, `optLevel == 0`, which allocates, assigns stack and emits code in the same pass).
- **For cig: adapt.** For cig-script#256's phase 6 (the optimizing tier), not for the baseline tier. cig's planned baseline tier is the Liftoff-shaped design of entry 14; cig's planned top tier is Cranelift, named in `cig-compile/docs/decisions/0001-backend.md` (study 01), with `regalloc2` as its allocator (study 02); the clones hold no native code generator today. What cig takes from B3 for stage C's and cig-cherry's shared code generator: the "`Check` as one op" compression (an exit point is one opcode, not a block), the polymorphic math opcodes, and the "fold replace-all-uses-with into a traversal" pattern. The three-allocator shape is right for a tiered design: cig-cherry tier 2 uses a Liftoff-style one-pass allocator (the analogue of Air's `optLevel == 0`), tier 3 uses `regalloc2`'s backtracking allocator, and no third mode is needed.
- **What would decide it.** Not measured yet: a compile-time budget per cherry tier on the test machine, measured on the compute set and cigo.
- **Feeds.** cig-compile#32, #37, cig-script#256 (phases 2, 6); decisions (e), (f).

### 16. Why JavaScriptCore replaced LLVM in its top tier, and what the figures were

- **What it does, and why.** The post ("Introducing the B3 JIT Compiler", `webkit-introducing-the-b3-jit-compiler.html`): "the overwhelming majority — often three quarters or more — of the FTL compile time is LLVM". The goal was "about ten times faster than LLVM while still generating comparable code". The design they describe to meet it: a compact, JS-aware IR (B3), a machine-level IR that passes all walk linearly (Air), a tightly scoped opcode set (190 in `b3/B3Opcode.h` at this pin), `Check`/`CheckAdd`/`CheckSub`/`CheckMul` B3 opcodes and Air's `BranchAdd32`/`BranchAdd64` so a "branch and exit" is one op not three, and JS-specific optimizations (may-points-to analysis to sink allocations, algebraic integer-range analysis for bounds-check removal) that LLVM did not have.
- **For cig: reject.** Adding LLVM for a cig peak tier is not called for. Decided by rule 10 and by the figure above: cig-compile's planned stage C compiles ahead of time, with Cranelift (`cig-compile/docs/decisions/0001-backend.md`), to signed files mapped read-and-execute (rule 8); the problem JSC had was JIT compile time, which cig's ahead-of-time design does not have in the same shape. JSC's figure says Cranelift's compile time per function is in the range B3 targets; JSC chose its own back end because LLVM was too slow for a JIT, not because LLVM made bad code. The B3 lessons cig takes are in entry 15 (its IR shape and the three-allocator idea), not the backend itself. For cig-compile#98 area 6's question ("whether a heavier back end than Cranelift is ever worth having"): no, unless and until cig has a workload Cranelift cannot keep up with. At the pin, cig has no such workload: stage C is not built in the clones and cig-cherry is not built in the clones.
- **What would decide it.** Decided by rule 10. The figure from the post (three quarters of FTL time was LLVM, target of ten times faster at comparable quality) stands as the shape of the trade-off and is cited as the source; cig does not re-run it.
- **Feeds.** cig-compile#32 (area 6 of #98).

### 17. Code kept between runs: a header of hashes, a sanity check before anything is used

- **What it does, and why.** V8's code cache is a stream of serialized compiled code keyed by source text and checked against the runtime's own version. `src/snapshot/code-serializer.h` lays out the header:
  - a four-byte magic number (`kMagicNumberOffset`);
  - a four-byte version hash (`kVersionHashOffset`, from `Version::Hash()`);
  - a 32-byte source hash (`kSourceHashOffset`, SHA-256 of the script source and its wrapped arguments, built from `SerializedCodeData::SourceHash`);
  - a four-byte flags hash (`kFlagHashOffset`, from `FlagList::Hash()`);
  - a four-byte read-only snapshot checksum (`kReadOnlySnapshotChecksumOffset`);
  - a four-byte payload length (`kPayloadLengthOffset`);
  - a four-byte trusted payload length (`kTrustedPayloadLengthOffset`);
  - a four-byte checksum over everything after the header (`kChecksumOffset`).

  `SanityCheckWithoutSource` and `SanityCheckJustSource` in `src/snapshot/code-serializer.cc` compare each one against the running engine's current values; the possible outcomes are the nine-value `SerializedCodeSanityCheckResult` (a typedef for `v8::ScriptCompiler::CachedData::CompatibilityCheckResult` at `v8-15.8.62.31/include/v8-script.h` lines 515 to 530): `kSuccess` = 0, `kMagicNumberMismatch` = 1, `kVersionMismatch` = 2, `kSourceMismatch` = 3, `kFlagsMismatch` = 5, `kChecksumMismatch` = 6, `kInvalidHeader` = 7, `kLengthMismatch` = 8, `kReadOnlySnapshotChecksumMismatch` = 9 (value 4 is skipped, per the enum's own append-only histogram comment; `kLast == 9` is the numeric value of the last kind, not the count of kinds). The code cache is not used unless every one passes.
- **For cig: take.** The sanity-check shape for cig-cherry's tin cache (cig-script#256 section 4, "The cache: native code in the tin"). cig's key is already more conservative than V8's: "the function's bytecode hash, its type profile, the cig and cherry versions, the CPU features targeted, and the tier". The fields and outcomes map directly: V8's magic number is cig's "the cache is well-formed", V8's version hash is cig's cig and cherry versions, V8's source hash is cig's bytecode hash, V8's flags hash is cig's CPU features and tier, V8's RO-snapshot checksum is cig's "the kernel ABI version" (runtime calls into `cig_rt_*` must match). The outcome list is the error set `cig tin gc` and the loader report.
- **What would decide it.** Decided by rule 7 and rule 8: the module's bytes never change at run time, and the compiled code must be verified against its source before it runs.
- **Feeds.** cig-compile#36 (start-up and size), cig-script#256 (section 4); decisions (f).
- **Read.** `v8-15.8.62.31/src/snapshot/code-serializer.h` (`SerializedCodeData::SourceHash`, `kVersionHashOffset`, `kFlagHashOffset`, `kChecksumOffset`, `kHeaderSize`); `v8-15.8.62.31/src/snapshot/code-serializer.cc` (`SanityCheck`, `SanityCheckWithoutSource`, `SanityCheckJustSource`, `SerializedCodeSanityCheckResult`); `v8-15.8.62.31/include/v8-script.h` (`CompatibilityCheckResult`); `cig-script/src/burn/tin.rs`.

### 18. Sparkplug: a non-optimizing baseline that walks the bytecode once

- **What it does, and why.** `src/baseline/baseline-compiler.h` `class BaselineCompiler` has a two-method body (`PreVisitSingleBytecode`, `VisitSingleBytecode`), each called once per bytecode in the function. Sparkplug's measured gain ("+45% over Ignition" on JetStream, per `papers/v8-sparkplug.html`) is the shape of the gain cig-cherry tier 2 aims for against the VM.

### 19. JavaScriptCore's inline cache compiler: a per-shape handler, patched in place

- **What it does, and why.** JSC's inline caches are compiled on demand from a small number of handler shapes. `bytecode/PropertyInlineCache.h` declares the handler record for a property access site; `bytecode/InlineCacheCompiler.cpp` builds the machine code for each case the site sees (a property at a known offset, a property found on the prototype, a property that needs a getter call), and `bytecode/InlineAccess.cpp` patches the baseline's access instruction in place to point at the handler. `bytecode/CallLinkInfo.h` is the parallel record for call sites: a per-site slot of "this is the function I resolved to", with a slow-path fallback. The handlers share a `bytecode/InlineCacheHandler.h` representation that the DFG can inline when it decides the site is stable.
- **For cig: adapt.** Against CacheIR, which study 04 covers. The alternative JSC's `InlineCacheCompiler` presents is "one C++ builder per handler shape, patched in place". For cig, the trade-off is: one C++-style builder per shape is simpler to audit (fewer moving parts, no interpreter for a cache language), but CacheIR is one language shared with the optimiser (which is decision (b)'s whole point). The study's recommendation is CacheIR (per study 04), and this entry is the record of the alternative so cig-cherry can fall back to per-shape handlers if the one-language design misses a case.
- **What would decide it.** Decided by decision (b): cig picks one format, and the alternative is kept named in case the picked one cannot cover a case the measurement names.
- **Feeds.** cig-compile#33, cig-script#256; decision (b).

### 20. The code-cache's two-step deserialize: a sanity check without the source, then with it

- **What it does, and why.** V8's code serializer supports off-thread deserialization through `StartDeserializeOffThread` and `FinishOffThreadDeserialize` in `src/snapshot/code-serializer.h`. The first step reads the cached bytes and runs `SerializedCodeData::FromCachedDataWithoutSource`: it accepts every header check that does not need the script source (magic number, version hash, flags hash, read-only snapshot checksum, payload length, trusted payload length, and the checksum over the payload bytes). `NotifySourceTextAvailable` is called later with the source, and `FinishOffThreadDeserialize` passes the stored `SerializedCodeSanityCheckResult` forward so the second step only has to run `SanityCheckJustSource` (the source hash against the stored 32-byte SHA-256). The two-step shape lets the engine decode the code in parallel with fetching the source.
- **For cig: adapt.** cig-cherry's loader opens a cache entry before `cig run` has finished reading the script bytes: the signed file in the tin is for a known program (the start has already checked the module's BLAKE3 at `cig-script/src/burn/modcache.rs`), so the "source" check is a hash comparison and the structural checks (ABI version, CPU features, cherry version, tier) can run at once. Two-step deserialize is the model: structure first, source identity second.
- **What would decide it.** Decided by rule 7 (verified bytecode, never rewritten) and rule 8 (no memory both writable and executable): the cache entry is a file mapped read-and-execute, and its contents are verified against the bytecode hash the start computed. Both checks happen before the first byte of native code runs.
- **Feeds.** cig-compile#36, cig-script#256 (section 4); decisions (f).
- **Read.** `v8-15.8.62.31/src/snapshot/code-serializer.h` (`StartDeserializeOffThread`, `FinishOffThreadDeserialize`, `NotifySourceTextAvailable`, `OffThreadDeserializeData`); `v8-15.8.62.31/src/snapshot/code-serializer.cc` (`SanityCheckJustSource`); `cig-script/src/burn/modcache.rs`.

## Not settled

- Whether cig's "wait after the ICs settle" counter (entry 10) is one byte per function or per site. V8 keeps `invocation_count_before_stable_` per vector; a per-site byte is more accurate for cig-cherry's "this specific guard keeps failing", but it costs one byte per site in the vector. Settled by whether a cig site can recompile independently of the whole function, which is a stage C design decision not yet made.
- Whether cig's exit record (entry 11) is a stream of V8-style translation opcodes (entry 8) or a flat struct. The translation-opcode form is denser (`MATCH_PREVIOUS_TRANSLATION` saves bytes across adjacent exits); the flat-struct form is easier to verify (every exit is one struct of known size). Settled by which cost dominates: compiled-size (cig-compile#36) or exit-time (cig-script#256 phase 3). Both would be measured at the first cherry build.
- Whether cig-cherry tier 3's allocator is `regalloc2` as-shipped or a configured `regalloc2` with a budget flag (JSC's `airUseGreedyRegAlloc` is the shape of a per-build knob). Settled by `regalloc2`'s current knobs, which study 02 names, and by whether tier 3 ever has a compile-time budget it has to meet.
- Whether JSC's `MinifiedGraph` style (entry 11) is a better exit-time recovery format for cig than V8's translation stream (entry 8). The two are not equivalent: a minified graph can recover a constant that no translation slot stored, which may be useful for cig's dead-pure pass elisions; V8's stream cannot. Settled by how many exits need a value no CPU register or stack slot holds, measured at the first cherry build.
- Whether cig's lattice (entry 3) carries "mostly A, sometimes B" states, as V8's `RECOMPUTE_HANDLER` and `HOMOMORPHIC` do. The census shows one program (`trees`, one site, 2.3% of arithmetic executions) saw two pairs; the two-state refinement is for that case and no other today. Settled by whether a second site ever turns up in cigo or in a further benchmark.
- Whether cig-cherry's background compile dispatcher (entry 5) uses locked queues (Maglev's `LockedQueue`) or a lock-free shape. cig's values stay `Rc`, which never cross threads; only the bytecode and the profile cross. Settled by the dispatcher's own measured contention under the compute set; if there is none, a locked queue is enough.
- Whether cig records the "fast-API call" kind of lazy deopt V8 has (entry 10, `kLazyAfterFastCall`). cig has no fast-API path today (`cig-script/src/stdlib/` dispatches through the builtin catalogue, not direct calls), so the third kind has no analogue at the pin. Settled by whether cig-compile ever grows a direct-builtin path, which cig-compile#32's current design does not propose.
