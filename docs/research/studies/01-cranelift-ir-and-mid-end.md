## What cig should carry away

- The IR Cranelift exposes to a front end is a CFG with block parameters, not phi nodes, and the data-flow graph lives apart from the block-and-instruction layout: when cig lowers structured CIR into it, the lowering may change layout without rewriting values (entry 1, entry 2).
- Cranelift's mid-end divides instructions into a "skeleton" (side-effecting, kept in layout order) and "pure" nodes (freely moved, merged, re-placed). cig's `Class { Pure, MayRaise, Effect, Step }` maps onto this almost exactly; the only mismatch is `MayRaise`, which Cranelift calls pure when the trap is removable and skeleton otherwise (entry 6).
- GVN, LICM and rematerialization in Cranelift are not three passes: they fall out of a single scoped elaboration pass walking the dominator tree, with a 5-enode-per-eclass bound, a 5-rewrite-match limit, a 5-deep recursion limit and 500 units of extractor fuel per top-level rewrite (entries 7, 8, 9).
- ISLE rules are directional ("never rewrite to worse code"), must use `subsume` whenever they drop a value-use, and are checked at compile time for overlap and unreachable shadowing; cig's four passes today are a good fit to rewrite as rules once the lowering has a stable shape (entries 11, 12).
- A load or store is never a pure node: alias analysis is a separate "last-store + memory-values" fused pass that does redundant-load elimination, store-to-load forwarding, idempotent-store elimination and dead-store elimination in one walk (entry 13).
- The inliner is a library, not a policy: Cranelift gives the embedder a trait and the mechanics; the embedder names the callee and decides whether to inline. cig makes that decision, in the lowering, not in the back end (entry 14).
- `opt_level=none` skips the egraph pass entirely; everything else (NaN canonicalization, unreachable-code elimination, constant-phi removal, alias analysis, and the egraph pass that fuses GVN/LICM/remat and the rewrites) runs at `speed` and `speed_and_size`. There is no `-O1` middle tier (entry 15).
- The e-graphs are *acyclic* by construction: a rewrite builds new nodes bottom-up on fresh `Value`s, unions them on to the original, and never saturates to a fixed point. This is the trade-off against classical equality saturation (Willsey et al., POPL 2021): bounded work, directional rules, no need for a scheduler (entry 19). A chaos-mode `ControlPlane` shuffles equally-good rewrite outputs so the fuzzer catches heuristics whose default order hides a correctness bug; cig's differential suite can run the same shape at CIR (entry 20).

## Design points

### 1. Block parameters in place of phi nodes

- **What it does, and why.** Cranelift's SSA has no `phi` instruction: a block declares typed parameters and every branch that lands on it passes a matching argument list, as if calling a function. The register allocator assigns parameters to registers or stack locations in the same way it assigns call arguments. The IR document gives the loop induction variable as the worked example: three SSA values for the one source variable, one of them the block's parameter on the loop header. The design note argues the form is "better suited to handle BBs that may contain multiple branches to the same destination block with different arguments" than LLVM's phi.
- **For cig: take.** By rule 5 (identical behavior): block parameters move the fan-in explicitly into the control-flow edge, which is what cig already does in CIR for loops and `if` (CIR is structured SSA; a loop's back-edge carries the iteration's values). Lowering from CIR to CLIF therefore drops the structure down to blocks and parameters; nothing about the semantics changes. cig's form: `cig-script/src/lower/cir/ir.rs` (`Block`, `Instr`, `ValueId`, `VarId`) is already SSA with explicit scoped names; stage C's lowering emits one CLIF block per CIR block and passes the live SSA values on every branch.
- **What would decide it.** Decided by rule 5.

- **Read.** `wasmtime-v50.0.1/cranelift/docs/ir.md` (`BB parameter`, `basic block`); `wasmtime-v50.0.1/cranelift/docs/compare-llvm.md` (`phi instructions`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/dfg.rs` (`BlockData`, `BlockArg`); `cig-script/src/lower/cir/ir.rs` (`Block`, `ValueId`, `VarId`).

### 2. Data-flow graph kept apart from layout

- **What it does, and why.** The DFG stores instructions and their operand and result values, their types, source locations, memory flags and so on; the `Layout` stores two doubly-linked lists (blocks in program order, instructions per block) and a per-instruction sequence number assigned "like line numbers in BASIC: 10, 20, 30" so a new instruction can be inserted between two neighbors without renumbering. The egraph pass removes every pure instruction from the layout while leaving it in the DFG, then elaboration puts a (possibly new or cloned) instance back into the layout at the chosen point. The two structures are independent: an instruction may exist in the DFG without a layout position, and the layout may order instructions whose data-flow is unchanged.
- **For cig: adapt.** By rule 1 (burns never move) and rule 6 (deterministic cleanup): the separation is exactly what cig needs for pure passes that re-place computations while leaving `Step`, `Effect` and `MayRaise` instructions pinned. CIR today has no such separation (`Block::instrs` is one `Vec<Instr>` in `cig-script/src/lower/cir/ir.rs`, and `verify.rs`'s `T1` and `T2` police placement by comparing to a snapshot): if cig grows GVN or LICM on CIR, a layout structure of this shape, scoped to pinned instructions, keeps `T1` and `T2` honest without a separate snapshot pass.
- **What would decide it.** Not measured yet: whether CIR's per-pass verifier snapshot takes less than an explicit layout data structure, on `orchestrate.cig`, at `-O2`.
- **Feeds.** cig-compile#33, #37; decisions (e), (i).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/ir/layout.rs` (`Layout`, `SequenceNumber`, `MAJOR_STRIDE`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/dfg.rs` (`DataFlowGraph`, `Insts`, `Blocks`); `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`EgraphPass`); `cig-script/src/lower/cir/ir.rs` (`Block`, `Instr`); `cig-script/src/lower/cir/verify.rs`.

### 3. Side-data rides on an instruction: source locations, memory flags, trap codes, exception tables, stack maps, debug tags

- **What it does, and why.** An instruction carries an opaque 31-bit `SourceLoc` that Cranelift preserves across transforms without interpreting; memory flags (`notrap`, `aligned`, `readonly`, `can_move`, an alias region) ride on every load and store and are what alias analysis and the egraph's `is_pure_for_egraph` consult; a `TrapCode` names the reason for an instruction that may trap, and an exception table holds the catch destinations of a `try_call`. Stack maps are user-defined: the CLIF producer names the GC-live values, and Cranelift records where they land in the spill frame. Debug tags are embedder-supplied sequences attached to an instruction, interleaved correctly under inlining (the inliner prepends the call-site's tags to tags on every inlined instruction).
- **For cig: adapt.** By rule 2 (errors happen at the same place): CIR's `Span` on every `Instr` already does what `SourceLoc` does, and stage C must preserve it through lowering so `E503`, `E515` and the rest raise at the same file:line:col the tree-walker does. For `MayRaise`, cig's trap codes map onto Cranelift's `TrapCode` the same way, and the lowering records which cig error each trap stands for. For `Try`, the exception-table shape (normal destination + tag-indexed catches with block-call arguments) is what stage C emits for `try`/`finally`. cig has no GC, so stack maps are not used; debug tags are the right place to carry cig's inline-frame table for backtraces (#38).
- **What would decide it.** Decided by rule 2 (the spans must survive) and rule 6 (cleanup never moves, which the exception table respects by binding handlers to the single `try_call` that owns the table).
- **Feeds.** cig-compile#32, #38; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/ir/sourceloc.rs` (`SourceLoc`, `MaybeRelSourceLoc`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/memflags.rs` (`MemFlags`, `notrap`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/trapcode.rs` (`TrapCode`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/exception_table.rs` (`ExceptionTableData`, `BlockCall`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/user_stack_maps.rs` (`UserStackMapEntry`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/debug_tags.rs` (`DebugTag`); `cig-script/src/lower/cir/ir.rs` (`Instr`, `span`).

### 4. Variables to SSA at the front end (Braun et al. 2013)

- **What it does, and why.** `SSABuilder` in `cranelift-frontend` lets the front end `def_var` and `use_var` on a mutable variable while it is building the CFG. Each block's definitions are recorded per-variable; when a variable is used from a block whose predecessors have not all been sealed, the builder inserts a provisional block parameter and resolves it to the real value when `seal_block` is called. The algorithm is named in the file: Braun, Buchwald, Hack, Leißa, Mallon, Zwinkau, "Simple and Efficient Construction of Static Single Assignment Form" (CC 2013). `FunctionBuilder` sits over it and wires in a `srcloc`, a per-block `BlockStatus { Empty, Partial, Filled }` and the call to the safepoint spiller.
- **For cig: adapt.** By rule 5 (identical behavior) and rule 6 (cleanup never moves): cig's `roll` and `stick` slots (`VarId` in `cig-script/src/lower/cir/ir.rs`, with `VarInfo::captured` saying whether a closure shares the cell) are the problem this builder solves. Stage C's lowering does not need to re-derive SSA on the CIR side (CIR is already SSA for temporaries and makes slots explicit); it hands each slot to `SSABuilder::def_var`/`use_var` and lets the builder insert the block parameters. A closure-captured slot stays boxed (one cell, loaded and stored); the non-captured slot is a plain variable and becomes block parameters. This reuses a measured, well-studied construction instead of rederiving one.
- **What would decide it.** Not measured yet: lowering time of `orchestrate.cig` through `SSABuilder` against a hand-rolled parameter inserter, on the test machine, at `-O2`.
- **Feeds.** cig-compile#32; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/frontend/src/ssa.rs` (`SSABuilder`, `def_var`, `use_var`, `seal_block`); `wasmtime-v50.0.1/cranelift/frontend/src/frontend.rs` (`FunctionBuilder`, `BlockStatus`); `cig-script/src/lower/cir/ir.rs` (`VarId`, `VarInfo`).

### 5. The verifier: the invariant checker between passes

- **What it does, and why.** `verify_context` runs a battery of structural checks after each stage of the pipeline: every block ends in a terminator and no other instruction is one; every value is either a block parameter or an instruction result in a block; dominator and CFG agree; branch and jump argument types match the destination block's parameters; the entry block's parameters match the signature; globals form no cycles; memory types have their fields in order and in bounds. The verifier is always enabled by default (`settings.add_bool("enable_verifier", ..., true)`), and `Context::optimize` calls `verify_if` before and after every pass.
- **For cig: take.** By rule 5 and rule 1: cig's own `V1` to `V11` (structure) and `T1` to `T4` (transition) in `cig-script/src/lower/cir/verify.rs` (1,182 lines) do this for CIR already, and more: `T1` to `T4` compare a snapshot before and after a pass so that `burns never move` is checkable at pass boundaries, which Cranelift does not need because it has no `Step` or `MayRaise` class. cig keeps its verifier, and the Cranelift verifier runs for stage C's CLIF inside `Context::compile`.
- **What would decide it.** Decided by rule 5.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/verifier/mod.rs` (`verify_context`, `VerifierErrors`); `wasmtime-v50.0.1/cranelift/codegen/src/context.rs` (`verify_if`, `optimize`); `wasmtime-v50.0.1/cranelift/codegen/meta/src/shared/settings.rs` (`enable_verifier`); `cig-script/src/lower/cir/verify.rs`.

### 6. Pure nodes against the skeleton

- **What it does, and why.** Every instruction is sorted at pass time into "pure" (fit for the e-graph) and "skeleton" (stays in the layout). The predicate, `is_pure_for_egraph` in `inst_predicates.rs`, decides:

    ```
    pure = one result
         && not a call, branch, terminator, return
         && not (can_trap || other_side_effects || can_store)
         && (!can_load || load.flags: readonly && notrap && can_move)
    ```

    A skeleton instruction can still be merged with an earlier identical copy if `is_mergeable_for_egraph` holds (zero or one result, no load, no store, side-effects idempotent), which is what deduplicates `trapz`/`trapnz` across branches. Pure nodes leave the layout at the start of the egraph pass; the skeleton stays, and alias analysis works on it in the same walk. The comment on `EgraphPass` says the input and output both pass the verifier and have no `Union` nodes; `Union`s exist only during the pass.
- **For cig: adapt.** By rule 1 (burns never move) and rule 2 (errors happen at the same place): cig's `Class { Pure, MayRaise, Effect, Step }` maps on to this directly. `Pure` is Cranelift's pure, `Effect` and `Step` are skeleton, and `MayRaise` is skeleton unless cig proves the raise is impossible (CIR's `T4` is this proof-of-removability rule). The one thing cig keeps that Cranelift does not is `Step`: CIR's step-budget mark is not a side effect Cranelift models, it is a block-attached counter cig charges, so stage C's lowering emits `cig_rt_budget_exhausted(span)` calls that are opaque skeleton calls to Cranelift. cig's form: `cig-script/src/lower/cir/ir.rs` (`Class`), `cig-script/src/lower/cir/verify.rs` (`T1`, `T4`).
- **What would decide it.** Decided by rules 1 and 2.
- **Feeds.** cig-compile#33; decisions (e), (i).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/inst_predicates.rs` (`is_pure_for_egraph`, `is_mergeable_for_egraph`, `trivially_has_side_effects`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/memflags.rs` (`readonly`, `notrap`, `can_move`); `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`EgraphPass`); `cig-script/src/lower/cir/ir.rs` (`Class`); `cig-script/src/lower/cir/verify.rs`.

### 7. The rewrite loop, its bounds and its cost function

- **What it does, and why.** For each pure instruction encountered during the dominator-tree walk, `insert_pure_enode` looks it up in a scoped GVN hash map: a hit returns the earlier value; a miss calls `optimize_pure_enode`, which invokes the ISLE-generated `constructor_simplify`. ISLE returns up to five replacement values (`MATCHES_LIMIT = 5`); each one unions into the eclass of the original up to the eclass-size cap (`ECLASS_ENODE_LIMIT = 5`); recursion is capped at depth 5 (`REWRITE_LIMIT = 5`) so a rule that creates a new node that triggers more rules bottoms out. Every top-level rewrite spends from a 500-unit extractor fuel budget (`EXTRACTOR_FUEL = 500`), one unit per yielded enode from a multi-extractor iterator. The cost function in `egraph/cost.rs` is a saturating 32-bit integer: `iconst` 1, simple arithmetic 3, `imul` 10, otherwise 4 with +10 for `can_trap`/`other_side_effects`, +20 for a load, +50 for a store; `Cost::of_pure_op` sums an opcode cost with the sum of its operand costs. Two statements the doc comment on `Cost` makes do not match the code at this pin. First, the comment says costs are "multipl(ied) by 1024" per loop-nest level and capped at two levels, but `grep -n '1024\|loop_nest\|loop_level'` in `egraph/mod.rs`, `egraph/elaborate.rs` and `egraph/cost.rs` finds nothing, and `Cost::of_pure_op` and `Cost::of_skeleton_op` do not scale by anything but the operands; the effective loop-level knob is instead `loop_hoist_level` in `elaborate.rs`, which decides placement, not cost. Second, the comment says `u32::MAX` is reserved as infinity and is "never reachable by doing arithmetic on them (even when overflowing)" through a `finite()` method; no `finite()` method is defined in `cost.rs`, and the test `op_cost_saturates_to_infinity` asserts `Cost::new(u32::MAX - 10) + Cost::new(11) == Cost::infinity()` under the saturating `Add` impl, so a finite cost of `u32::MAX` is in fact reachable. The elaboration pass acknowledges this at `elaborate.rs:423-432`: "our cost function doesn't know about any shared structure in the dataflow graph, it only sums operand costs ... we can make cost grow exponentially with a linear sequence of operations."
- **For cig: adapt.** By rule 1 (burns never move) and rule 4 (floats are IEEE-exact): the limits are good defaults for a mid-end that must not pay for runaway rewriting. cig's form: if cig moves its passes onto an e-graph on CIR, these constants are the knobs the regression gate measures. cig's cost is a count of instructions and allocations in terms a measurement can compare to; because Cranelift at this pin does not apply a loop-level cost scaling, cig would decide placement by the loop-stack mechanism of entry 8, not by a cost multiplier.
- **What would decide it.** Not measured yet: the egraph pass's share of `Context::optimize` on `orchestrate.cig` after stage C is built, on the test machine, at `opt_level=speed`.
- **Feeds.** cig-compile#33, #37; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`optimize_pure_enode`, `insert_pure_enode`, `MATCHES_LIMIT`, `ECLASS_ENODE_LIMIT`, `EXTRACTOR_FUEL`, `REWRITE_LIMIT`); `wasmtime-v50.0.1/cranelift/codegen/src/egraph/cost.rs` (`Cost`, `of_pure_op`, `of_opcode`); `wasmtime-v50.0.1/cranelift/codegen/src/opts.rs` (`IsleContext`).

### 8. GVN and LICM are not passes, they are elaboration

- **What it does, and why.** The egraph pass walks the dominator tree in pre-order with a `ScopedHashMap` whose scope stack mirrors the path from the root to the current block; GVN is what the map does. A pure instruction is placed where all its arguments are available (`get_available_block`): the block deepest in the dominator tree among its operands' available blocks, which can be shallower than where the use sits. On the elaboration walk, `Elaborator` carries a `loop_stack` of loops dominating the current path and an `active_loop_depth`; if all of an instruction's arguments are available above the current loop level, it is hoisted to `loop_stack[loop_hoist_level].hoist_block` (the loop's immediate dominator) and the `elaborate_licm_hoist` counter is bumped. The comment names the reason the `active_loop_depth` cap exists: without it, hoisting from a loop-exit block into the header could move cold code into a hot block that previously executed zero times, and move trap-adjacent code into a loop header. Stats emitted into `pass.stats`: `elaborate_licm_hoist`, `elaborate_memoize_hit`, `elaborate_remat`.
- **For cig: adapt.** By rule 1 (burns never move): cig cannot hoist anything that is not `Pure`, and the mechanism of "hoist only if all arguments are available above the loop, and only out of a block actually inside the loop" is the one that keeps `T1` honest. If cig writes LICM at CIR level, this is the shape: walk blocks in dominator order with a scoped map, hoist a `Pure` value to the loop's `hoist_block` only when every operand is already available there, pin everything else. cig's form: an `hoist` pass under `cig-script/src/lower/cir/pass/` with `T1`/`T2` run after it, as `broken.rs` already models for the existing four.
- **What would decide it.** Not measured yet: `nbody`'s `dx * dx` and `mandel`'s outer-constant hoist, at `-O2` stage B then stage C, on the test machine.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/egraph/elaborate.rs` (`Elaborator`, `loop_stack`, `active_loop_depth`, `hoist_block`, `elaborate_licm_hoist`); `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`get_available_block`, `gvn_map`, `ScopedHashMap`); `wasmtime-v50.0.1/cranelift/codegen/src/loop_analysis.rs` (`LoopAnalysis`); `cig-script/src/lower/cir/pass/mod.rs` (`run_passes`).

### 9. Rematerialization: the cheap op computed where it is used

- **What it does, and why.** A rule in `opts/remat.isle` marks a value for rematerialization by returning `(remat x)`. The elaboration pass watches `remat_values`: when an argument to a placed instruction is marked and the argument's instruction is in another block, `maybe_remat_arg` clones the producing instruction into the current insert block (storing one clone per `(Block, Value)` in `remat_copies`), bumps `elaborate_remat`, and rewires the argument to the clone. The rules that mark values are: every `iconst`, `f32const`, `f64const`, and `bnot`; and every `iadd`, `isub`, `band`, `bor`, `bxor` where one operand is an `iconst`. The `opts/README.md` warns that rematerialization is register-pressure-positive for constants and neutral for add-with-immediate: the computation is cheap, keeping the live range short wins over sharing one register across a function.
- **For cig: adapt.** By rule 6 (deterministic cleanup): rematerialization moves a `Pure` computation, which cig allows for `Pure` by `T1`'s definition (pinned instructions do not change place; non-pinned may). cig has no analogue today; it would land at stage C and in the VM only after stage D (the type lattice) names the "cheap" ops. Stage B does not need it: its register bytecode already encodes constants in the immediate form of each opcode (`ADDK`, `cig-script/crates/cig-bytecode/src/opcode.rs`).
- **What would decide it.** Not measured yet: `loop.cig` and `fib.cig` at stage C with and without the remat rules in the egraph pass, on the test machine.
- **Feeds.** cig-compile#32, #33; decisions (e), (i).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/opts/remat.isle` (`remat`); `wasmtime-v50.0.1/cranelift/codegen/src/egraph/elaborate.rs` (`maybe_remat_arg`, `remat_values`, `remat_copies`); `wasmtime-v50.0.1/cranelift/codegen/src/opts/README.md`; `cig-script/crates/cig-bytecode/src/opcode.rs`.

### 10. `subsume`: a rewrite that drops a use

- **What it does, and why.** A rule's right-hand side may wrap the replacement in `subsume`: this tells the egraph that the other e-nodes in the eclass, which may still mention operands the rewrite dropped, must not be chosen by extraction. The README rule 2 states the invariant: "Any rule that removes value-uses in its right-hand side that previously existed in its left-hand side MUST use `subsume`." The example given is `(select 1 x y) => x`: if the eclass still allowed extracting `(select 1 x y)`, a later use in a scope where `y` is not defined would be a fault. Constants are exempt (a constant can be rematerialized anywhere, so dropping a constant use does not introduce a new definition point). In the Rust side, `optimize_pure_enode` scans the ISLE-returned values for a member of `subsume_values` and, when it finds one, returns that value alone and bumps `pure_inst_subsume` in the stats; the usual union-then-chain path is skipped, so the subsumed side cannot be extracted later.
- **For cig: adapt.** By rule 2 (errors happen at the same place) and rule 1 (burns never move): if cig moves its rewrites on to an e-graph, this invariant is what keeps a rule that drops `y` from accidentally re-introducing `y` on a path where `y` would raise or execute an effect. cig's `T3` is close kin (an effect may not be dropped), but `subsume` is the dual: when a pure rewrite drops a pure use, the dropped side must be unreachable through any later extraction. cig's form: a `subsume` marker on a rewrite's right-hand side, read by the aegraph if cig writes one, matched by the verifier against the snapshot so a pass that `subsume`s a `MayRaise` is caught.
- **What would decide it.** Decided by rules 1 and 2.
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/opts/README.md`; `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`subsume_values`, `pure_inst_subsume`); `wasmtime-v50.0.1/cranelift/codegen/src/opts/icmp.isle` (`subsume`); `cig-script/src/lower/cir/verify.rs`.

### 11. ISLE: a rule language compiled to Rust, with overlap and priority checked

- **What it does, and why.** ISLE is a typed term-rewriting language. A rule `(rule pat expr)` matches a pattern (optionally with a numeric priority) and emits a right-hand-side term; the compiler turns the full rule set into a single generated Rust file (`target/.../out/clif_opt.isle`'s compiled form, or `generated_code.rs` under `opts/`). A typical rule, from `arithmetic.isle`:

    ```
    (rule iadd_x_plus_zero (simplify (iadd ty x (all_zero ty)))
          (subsume x))
    ```

    The language reference states the priority semantics: "an applicable rule with a higher priority will always match before a rule with a lower priority"; default priority is 0; within a priority the specific tie-break is "more specific first", which is a heuristic and not part of the language's correctness contract. Overlap is a compile-time check (`cranelift/isle/isle/src/overlap.rs`) that reports pairs of rules that could apply to the same input at the same priority and warns about rules the check proves are shadowed and never reachable. The compiler lowers rules through a trie-of-cases representation in `trie_again.rs`. Extractors (left-hand-side matchers) must never have side effects, because match is speculative; constructors on the right-hand side may be side-effecting and run only once the rule has been committed.
- **For cig: adapt.** By rule 5 (identical behavior) and rule 1 (burns never move): rules make the "what changes" smaller than hand-written code and the overlap check moves class of pass bugs to compile time. cig's four passes today are `fold-consts`, `copy-prop`, `sccp`, `dead-pure` (`cig-script/src/lower/cir/pass/mod.rs`); `fold-consts` is arithmetic over `Pure` only, and is a near-drop-in for ISLE's `cprop.isle` patterns at CIR scale; `copy-prop` and `dead-pure` are small enough as code that the rule framework does not earn its cost yet. ### 13. Alias analysis: one walk, four optimizations on the skeleton

- **What it does, and why.** A memory region (`AliasRegion`) is a label put on every load and store by the front end; it is a may-alias partition that the alias analysis consults. `AliasAnalysis` fuses two passes into one: "last store" (at each program point, the last instruction that may have written each region) and "memory values" (a table from (last-store, address, type, byte order) to the SSA `Value` known to be in that location). On the walk it does: redundant-load elimination (a load for a key already in the table becomes the earlier value); store-to-load forwarding (a load fed by a dominating store becomes the stored value); idempotent-store elimination (a store writing the value already in the table is removed); and dead-store elimination (a post-dominating store with no "observing" instruction between, where observation includes any trap-adjacent instruction because post-trap memory is observable). Atomic RMW, atomic CAS, atomic load, atomic store and fence opcodes act as memory barriers (`has_memory_fence_semantics`). The analysis is called from `Context::egraph_pass` as part of the same walk that does GVN and the ISLE rewrites.
- **For cig: adapt.** By rule 1 (burns never move) and rule 6 (deterministic cleanup): CIR has no raw loads and stores: `Load`, `Store`, `GetField`, `SetField`, `GetIndex`, `SetIndex` are typed and refer to a named slot, field, or element. "Store to load forwarding" at CIR is a `stick` write followed by a `stick` read in the same block, which the lowering already turns into a temporary. Aliasing at CIR is: two field names on the same object alias themselves and nothing else; two map keys alias themselves (because strings may be equal). At stage C, Cranelift's alias analysis does the work on the lowered representation, where field and index accesses have been turned into loads and stores with alias-region tags. cig's own passes do not need an alias analyzer at CIR; the work pays once stage C writes out loads and stores.
- **What would decide it.** Not measured yet: alias analysis's share of `egraph_pass` time on `orchestrate.cig` at stage C, on the test machine.
- **Feeds.** cig-compile#32, #33, #35; decisions (e), (g).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/alias_analysis.rs` (`AliasAnalysis`, `LastStores`, `MemoryState`, `has_memory_fence_semantics`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/memflags.rs` (`AliasRegion`); `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`alias_analysis`); `cig-script/src/lower/cir/ir.rs` (`Load`, `Store`, `Member`, `Index`).

### 17. Lowering structured SSA with slots into CFG with block parameters

- **What it does, and why.** CIR is nested blocks under `Burn`, `Try`, `If`, `Loop`, `ForEach`, and the short-circuit operators, plus temporaries (`ValueId`) and shared slots (`VarId`). CLIF is a flat CFG: one entry block, block parameters on each block, branches that pass argument lists. The lowering has two independent jobs: flatten the nesting into a CFG with explicit branches (one block per CIR block, plus the tail blocks a nested `Try` or `Loop` needs), and translate slots into block parameters (`cranelift-frontend`'s `SSABuilder` through `def_var`/`use_var` and sealing). A simple CIR `Loop { body, cond }` with slot `i` becomes:

    ```
    header(i_param: i64): ... brif cond, body_block(i_param), exit
    body_block(i: i64): ... v_next = iadd_imm i, 1 ... jump header(v_next)
    exit: ...
    ```

    A loop's back-edge becomes a branch to the header; a `Try` becomes a `try_call` with an exception table whose normal destination is the continuation and whose tag catches are the handler blocks; a `Burn` region becomes two calls, `cig_rt_burn_enter` and `cig_rt_burn_leave`, with a `try_call` inside when the region is also a `Try`. A captured slot stays a heap cell (one `Load`/`Store` pair per access) as `VarInfo::captured` already records. A non-captured slot that outlives one block becomes a block parameter; one that lives within a block is a temporary. This is the standard Braun-et-al. construction for languages with mutable locals.
- **For cig: adapt.** By rule 5 (identical behavior), rule 1 (burns never move) and rule 10 (ahead of time by default): cig hands slots and spans to the builder, lets it derive the block parameters, and keeps exceptions on the result-convention path for stage C (as cig-compile#32 names) so native unwinding is not needed. cig's form: `cig-script/src/lower/cir/lower.rs` already lowers AST to CIR; stage C adds a `clif_lower` step beside it that walks the CIR module and emits CLIF through `FunctionBuilder`, with `requires_burn` on `Func` keeping the `try_call` and the burn-op calls where CIR places them.
- **What would decide it.** Not measured yet: the LOC and compile-time cost of CIR-to-CLIF on `orchestrate.cig`, on the test machine, with golden tests fixing the CLIF shape.
- **Feeds.** cig-compile#32; decisions (e), (i).
- **Read.** `wasmtime-v50.0.1/cranelift/frontend/src/ssa.rs` (`SSABuilder`, `use_var`); `wasmtime-v50.0.1/cranelift/frontend/src/frontend.rs` (`FunctionBuilder`); `wasmtime-v50.0.1/cranelift/codegen/src/ir/exception_table.rs` (`ExceptionTableData`); `cig-script/src/lower/cir/ir.rs` (`Burn`, `Try`, `Loop`, `VarInfo`); `cig-script/src/lower/cir/lower.rs`.

### 19. The "a" in aegraph: an acyclic e-graph that never saturates

- **What it does, and why.** An ordinary e-graph (`egg`, Willsey et al., POPL 2021) carries two data structures together: an equivalence of e-classes and a congruence closure that keeps classes equal when their nodes become equal. A scheduler runs rules until a fixed point, which may not exist unless the ruleset is confluent and terminating, and extraction picks one node per class at the end. Cranelift's acyclic e-graph does less: it walks the function once in dominator order, and every rewrite is a bottom-up build of a new expression on fresh `Value` nodes that is `union`-ed into the original value's class. The rules are directional (README rule 1: "right-hand side should be at least as good as the left-hand side or better"), there is no scheduler, and the rewrite recursion is bounded by `REWRITE_LIMIT`. Because nothing is added below an existing node, the resulting graph is acyclic; because the walk is one pass, there is no saturation step. The egg paper's framework serves as background: Cranelift borrows the e-class/extraction vocabulary and the "extract by cost" step, but not the scheduler.
- **For cig: adapt.** By rule 1 (burns never move) and rule 7 (verified bytecode, never rewritten at run time): what cig takes is the acyclic shape. A one-pass directional rewrite is compatible with cig's verifier because `T1` to `T4` compare a snapshot to the result of one pass, and the "no worse" invariant lets cig's regression gate measure by the same cost function the extraction uses. A full equality-saturation engine on CIR is over-powered: cig's rule set is small, its programs are small, and the compile-time budget is tight. cig's form: if cig moves rewrites on to an e-graph, it uses an aegraph of this shape, not a full `egg::EGraph` with a scheduler.
- **What would decide it.** Decided by rule 1 and the time budget (an equality-saturation run would have to finish in the build-time gate, which it will not for anything more than `fold-consts` scale).
- **Feeds.** cig-compile#33; decision (e).
- **Read.** `wasmtime-v50.0.1/cranelift/codegen/src/egraph/mod.rs` (`EgraphPass`, `union`, `insert_pure_enode`); `wasmtime-v50.0.1/cranelift/codegen/src/opts/README.md`; `papers/compilers/willsey-2021-egg.pdf`.

### 20. Chaos mode: a pseudo-randomness tap for proving that heuristics are only heuristics

- **What it does, and why.** The `cranelift-control` crate's `ControlPlane` is passed through every compile call. With the `chaos` feature off (the default) it is a zero-sized type that is optimized away. The incremental cache cuts rebuilds of unchanged functions to a byte-blob read (entry 16): a cache key covers the `FunctionStencil` and the ISA, and `apply_params` patches the per-call-site data on a hit, so the output bytes stay reproducible. cig's own build cache in `cig-compile/src/cache.rs` wraps this on the module side.
- **cig-compile#39 (correctness at scale).** Chaos-mode shuffling (entry 20) is the shape cig's differential suite adopts to prove pass correctness does not accidentally depend on the default ordering of equally-good rewrites. The filecheck test convention (entry 12) composes with cig's existing goldens and the broken-twin negative tests under `cig-script/src/lower/cir/pass/broken.rs`. For large-scale correctness, Cranelift's fuzzgen (`cranelift/fuzzgen`) is a model for `cig-smith`; stage C can be plumbed into it once the lowering has a stable shape.
- **cig-compile#35 (values and memory).** Alias analysis (entry 13) is the Cranelift mechanism that depends on the memory-region tagging cig attaches to lowered loads and stores. cig's own value representation (24 bytes today, moving towards 16 or an 8-byte NaN-box at decision (a)) decides what the alias regions look like, because an `Rc<RefCell<...>>` list and a refcounted string are not the same region. The stage C writer picks regions when the runtime library's ABI stabilizes in #4.

## Not settled

- Whether stage C emits `try_call` at all or routes every raise through the result convention (entry 17 names both options; the choice is cig-compile#32's, and the trade-off depends on a measurement of a representative try-heavy program against the simplicity of one path on every target).
- Whether cig uses `enable_nan_canonicalization` or does the canonicalization at CIR before stage C (entry 15; rule 4 says floats are IEEE-exact on every engine, which can be satisfied by either side, and the one that costs less wins: Cranelift's canonicalizer only patches floating-point arithmetic instructions, so CIR's own canonicalization would still need to handle arithmetic emitted by rewrites).
- The exact overlap between `arithmetic.isle`'s strength reductions and cig's planned `strength reduction` pass on CIR (entry 18); which half of the work stays at CIR after stage C is built is a measurement the differential suite settles, because cig's rule that `i * 8` shifts for non-negative ints only is finer than Cranelift's unconditional rule and must execute first.
- Whether stage C makes any use of `cranelift-frontend`'s `switch.rs` for `ForEach` dispatch, or lowers `ForEach` directly to the iteration protocol's calls (entry 17 does not settle this; the choice depends on the iteration shape the runtime library picks in #4).
- Whether cig uses debug tags to carry inline-frame identifiers through to the backtrace table in #38, or carries them in a side table keyed by instruction (entry 3; both are consistent with Cranelift's design, and the one that reads out with less fuss during an error landing wins).
- The alias-region tagging cig attaches to loads and stores emitted by the lowering (entry 13 names the invariant: an address in one region never appears in two different region-tagged instructions). Rings cig can carve its stdlib into (strings, lists, maps, closures, each a separate region; the burn kernel's own data a further region) are a decision the stage C writer settles when the runtime library's C ABI stabilizes in #4.
- Whether cig invokes the `clif-util souper-harvest` CLI subcommand (gated behind the `souper-harvest` feature of `cranelift/codegen`) on cig-shaped CLIF inputs to feed cig's rule set; the library function is `wasmtime-v50.0.1/cranelift/codegen/src/souper_harvest.rs`, the mechanism is ready, the rules it would output are cig's.
- How cig's version of the `broken.rs` negative-test pattern (`cig-script/src/lower/cir/pass/broken.rs`) carries over to a rules-based rewrite, where "break the pass" is "corrupt the right-hand side of a rule" rather than "swap two burn ops" (entry 11, entry 12).
