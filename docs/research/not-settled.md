# What the studies could not establish

Made from the studies by `join.py`: each study's own list, in its words.

## Cranelift: its IR and its acyclic e-graph mid-end

[studies/01-cranelift-ir-and-mid-end.md](studies/01-cranelift-ir-and-mid-end.md)

- Whether stage C emits `try_call` at all or routes every raise through the result convention (entry 17 names both options; the choice is cig-compile#32's, and the trade-off depends on a measurement of a representative try-heavy program against the simplicity of one path on every target).
- Whether cig uses `enable_nan_canonicalization` or does the canonicalization at CIR before stage C (entry 15; rule 4 says floats are IEEE-exact on every engine, which can be satisfied by either side, and the one that costs less wins: Cranelift's canonicalizer only patches floating-point arithmetic instructions, so CIR's own canonicalization would still need to handle arithmetic emitted by rewrites).
- The exact overlap between `arithmetic.isle`'s strength reductions and cig's planned `strength reduction` pass on CIR (entry 18); which half of the work stays at CIR after stage C is built is a measurement the differential suite settles, because cig's rule that `i * 8` shifts for non-negative ints only is finer than Cranelift's unconditional rule and must execute first.
- Whether stage C makes any use of `cranelift-frontend`'s `switch.rs` for `ForEach` dispatch, or lowers `ForEach` directly to the iteration protocol's calls (entry 17 does not settle this; the choice depends on the iteration shape the runtime library picks in #4).
- Whether cig uses debug tags to carry inline-frame identifiers through to the backtrace table in #38, or carries them in a side table keyed by instruction (entry 3; both are consistent with Cranelift's design, and the one that reads out with less fuss during an error landing wins).
- The alias-region tagging cig attaches to loads and stores emitted by the lowering (entry 13 names the invariant: an address in one region never appears in two different region-tagged instructions). Rings cig can carve its stdlib into (strings, lists, maps, closures, each a separate region; the burn kernel's own data a further region) are a decision the stage C writer settles when the runtime library's C ABI stabilizes in #4.
- Whether cig invokes the `clif-util souper-harvest` CLI subcommand (gated behind the `souper-harvest` feature of `cranelift/codegen`) on cig-shaped CLIF inputs to feed cig's rule set; the library function is `wasmtime-v50.0.1/cranelift/codegen/src/souper_harvest.rs`, the mechanism is ready, the rules it would output are cig's.
- How cig's version of the `broken.rs` negative-test pattern (`cig-script/src/lower/cir/pass/broken.rs`) carries over to a rules-based rewrite, where "break the pass" is "corrupt the right-hand side of a rule" rather than "swap two burn ops" (entry 11, entry 12).

- Whether cig-cherry would use `ArenaMemoryProvider` or `SystemMemoryProvider`: the first is larger-reservation and avoids per-call `mmap`, the second is simpler. Settled by cig-cherry's own perf study, which is not this one.

## SpiderMonkey's CacheIR and Warp: one inline-cache language for four tiers

[studies/04-spidermonkey-cacheir-and-warp.md](studies/04-spidermonkey-cacheir-and-warp.md)

- The cost of an off-thread compile in cig terms. `Rc` cannot cross threads, so the snapshot contains no live cig values; whether the `cig-cherry` executable can nevertheless re-materialise constants without them is a small design item for entry 16.
- The fold's realm/compartment check (`StubFolding.cpp` only folds same-realm shapes, since cross-realm shape pointers would complicate tracing). cig has no realms today; this constraint does not translate, but if cig grows modules with separate loaders (ADR 0004 payload) the question returns.
- The interpreter's register lifetime: PBL's virtual registers are `uint64_t` and no register allocator reclaims them; a cig interpreter that stores `Value` (24 bytes) per operand id will pay more. Decided by measurement, not by rule.
- Shapes for records: the census settles that two shapes a site cover cigo's field accesses and one shape covers every compute site, so decision (h) is to adopt shapes; what remains open is the per-write cost and the `IndexMap`-grow interaction (entry 6).
- Whether cig's per-op `cost_estimate` should be read in machine instructions (the cig unit, by rule 3) or in abstract score (the SpiderMonkey choice). The two scale differently as hardware moves; a cig-specific table is likely, with the thresholds in entry 13 recomputed from measurement.
- Whether every cig stub should terminate in a single "result" op as SpiderMonkey's does. cig's effect boundary (rule 1: burns never move) means a stub must never contain a `burn.op`; the one-result-op rule is a stricter version of that constraint, and the interaction with cig's `MayRaise` instruction class (CIR §2) is a design item for the first entry's measurement.
- Whether the AOT corpus (entry 10) belongs in `cig-script` (the runtime) or `cig-compile` (the program-build tool). SpiderMonkey keeps it in the runtime because the browser ships one runtime for many pages; cig ships one runtime per program (per `cigcompile build`), so either location would work. The location also decides whether the training run is `cig cherry warm` (runtime) or an invocation of `cigcompile` (build-time).
- Whether cig's `callm` cache (receiver kind + method row) should become a full CacheIR site right away or stay as a specialized two-field cache alongside new CacheIR sites for `getfield` and `setfield`. The question is whether to keep the existing hot path during the migration or replace it in one change.

## Lean 4, Koka and Lobster: reference counting made cheap

[studies/05-reference-counting-lean-koka-lobster.md](studies/05-reference-counting-lean-koka-lobster.md)

- Whether cig's `MayRaise` instructions on a value path (`Index`, `Member`) force the dec-placement pass to fence like Lean's `cases` prolog does, or whether a backward walk alone suffices: Lean's immutable arrays raise on out-of-range in a way that does not re-emit the exact prior state, so the two-phase placement is a conservatism Koka also adopts; cig's semantic rule 2 (errors happen at the same place) may demand the same two-phase structure, but the source at the pin does not say what it costs.
- Whether a `Chain`'s step list should be treated as shape-bound (entry 8's mechanism becomes relevant) or as a plain `Vec<ChainStep>`: `cig-script/src/value.rs`'s `Chain` is a `struct` with a fixed `steps: Vec<ChainStep>`, not a constructor, so the shape-bound interpretation has no direct Perceus analogue; the question is open until the stage D record design lands.
- Whether `FBIP` could ever apply to a `pack` (cig's pure function kind), given cig values are untyped at compile time: the source is clear that Koka's check is static and per-signature, which cig cannot reproduce without a lattice (cig-compile#34); outside the type lattice, the check has nothing to anchor to.
- Whether Lean's and Koka's `thread-shared` transition (promotion of a block from single-threaded to atomically counted) is worth any cost on cig today: cig is single-threaded by design, and `Rc` (not `Arc`) is the primitive in the VM; the thread-shared machinery in both runtimes is a design cross-reference, not a design cig takes. The question returns if cig ever ships a work-stealing scheduler.
- Whether entry 15's uniqueness-write should be opt-in per builtin or on by default: a surprising case is `list.push` under iteration (a user iterates a list and pushes to it in the loop), where the uniqueness check still correctly distinguishes a borrowed (read-only) iteration from an owning one, but the behavior should be measured first against the differential suite at zero differences before it is turned on everywhere.
- Whether entry 20's four-point lattice should be the pass's output on its own or a late reconciliation of entry 4's and entry 17's results: the two previous passes already compute a two-point (owned/borrow) decision; `top` from entry 20 only arises when control flow merges disagreeing decisions. A design that merges the three passes into one is tempting but gives up the modular test surface each pass currently affords.

## Swift's SIL and its ARC optimizer, and Roc's reference counting: ownership written into the IR

[studies/06-swift-ownership-and-arc-roc.md](studies/06-swift-ownership-and-arc-roc.md)

- Whether cig's `Ty::Dynamic` (the type of a value whose compile-time kind is unknown) plays the role of Swift's `OwnershipKind::Any` (the empty constraint) or needs its own class: Swift's `Any` is a constraint, never a value's kind, and cig's `Dynamic` is a value's kind. The two are not aligned, and a mechanical port would conflate them. A run-time branch on the value's tag is the only sound way to pick between the Owned and Borrowed paths for a `Dynamic` value; whether the branch is worth the two code paths is a measurement, not a design.
- Whether the `DecRef` distinction (entry 11) is worth a separate bytecode opcode in cig or should be an inline branch in the single `DEC` path: Roc has three distinct cases at IR level, but the bytecode is one path with a shallow/deep flag in Rust's `Drop`. The source does not say which is faster on cig's test machine.
- Whether a weak-reference primitive is needed for `Chain` steps that reference each other (a step naming a label of an earlier step by weak reference): cig today has no weak reference and no cycle collector; the only cycle-forming pattern the source shows is a self-referential chain, which rule 6 does not resolve. The question returns when the cycle collector lands (cig-compile#35's "cycles_are_freed" test).
- Whether the elision pass should run before or after cig's existing `dead-pure`: a clone whose result is never read is already removed by `dead-pure`, but the drop that pairs it is not (it is `Class::Effect`); the elision pass should run first so the drop pairing is seen. Not settled against the pass-order measurement in cig-compile#33's level table.
- Whether `move_value`'s cig analogue (a `Move` instruction with no reference-count change) is useful at cig's pin: cig has no move-only types and no eager-move annotations, so a `Move` kind has nothing to say that `Clone`+`Drop` cannot. The question returns if cig ever ships a move-only kind for a file handle or a chain.
- Whether the alias-analysis mechanism in Roc's `morphic_lib` (entry 13) is implementable within cig's single-crate rule 9: `morphic_lib` is a separate Rust crate with its own build; cig would have to either depend on a new crate (adding build time and binary size) or reimplement a local alias analysis for the one-block case. The source at the pin does not say which Roc chose for its Zig rewrite; at this pin the Zig side has no RC pass at all (entry 13). Measurement decides which approach is cheaper for cig.
- Whether cig's `Burn` regions should be treated as a single lifetime-ending use for every value they consume, or whether the destroy's position inside a burn can move. The current reading of rule 1 says they cannot move inside a burn (every effect is pinned), but a value that is dropped on the burn's exit is a slightly different case: the drop could in principle move to the burn's compensation block without crossing a burn op. The study does not settle this; a design review of `cig-script/src/lower/cir/ir.rs`'s `BurnNode` is owed.

## LLVM's optimization pipeline, and Alive2's translation validation

[studies/07-llvm-pipeline-and-alive2.md](studies/07-llvm-pipeline-and-alive2.md)

- Settled on the second read (`llvm_util/cmd_args_list.h:22-29`): `-tv-src-unroll` and `-tv-tgt-unroll` both default to 0 (via `cl::init(0)`), and the standalone `-tv-unroll` (used when the build is not configured for separate source/target factors) also defaults to 0; the plugin tests that need loops pass `-tv-src-unroll=2 -mllvm -tv-tgt-unroll=2` explicitly. Figure added to entry 16.
- Whether cig's eventual TV can validate an `inline-small` pass at all: Alive2 declares interprocedural passes out of scope (`README.md` warning, entry 16). The answer depends on whether cig's inliner is modeled as a single-function rewrite (the inlined call becomes a block in the caller) or as a two-function change. If the former, TV can verify it; if the latter, TV cannot, and the inliner's correctness rides on the fuzz corpus.
- Whether `GVNHoist` and `GVNSink` (off by default in LLVM: `EnableGVNHoist` and `EnableGVNSink` both initialise to `false`) are worth building for CIR: they only help when common code lives in both arms of an `if`, and CIR's structured shape should make them cheap, but I found no measurement in the pinned tree that says what they buy.
- Whether cig's PGO format should carry the per-branch weight as a count (the `!prof` metadata LLVM uses) or as a ratio (a byte on 0-255). LLVM's `PGOInstrumentationUse` attaches the raw count; the ratio would be smaller in a `.cigprof` payload but loses information when combined across runs. Decided by a read of #33's `--profile-use` user story that was not in the issue copy I had.
- Whether cig's bottom-up walk should pick strongly connected components (LLVM's CGSCC) or a simple post-order over the call graph. SCCs matter only when there is mutual recursion; how much cig code has mutual recursion today is not read from the clones, and an SCC-aware walk is harder to get right. A post-order walk with a visited-set and a conservative "do not inline into a cycle" rule would be simpler and would lose little.
- Whether `Reassociate` (entry 3) should be a cig pass at all. It changes the shape of an expression tree so later passes see more invariants, but CIR's expression trees are smaller than LLVM's and floats are IEEE-exact (rule 4), so the main `Reassociate` move (`4 + (x + 5) -> x + (4 + 5)`) is only sound for integers; on floats it is a rule-4 violation. A cig-reassociate would have to type-check and only reassociate integer chains.
- Whether cig's `-O1` should include a scoped CSE at all (entry 7). LLVM's `-O1` runs `EarlyCSE` with MemorySSA; cig has no MemorySSA analog today and `copy-prop` already catches the simple local redundancies. The cost of a dominator walk at `-O1` against the gain was not measured.
- Whether cig's bisect counter should be per-function or global (entry 12). LLVM's is global and `FunctionPass` invocations each take one counter value, which is slower to narrow than a per-function counter but gives a simpler mental model to the user.
- The exact size of the SMT encoding of a CIR `List` or `Map` (entry 15). A `List` is a `Rc<RefCell<Vec<Value>>>`; in SMT it could be an uninterpreted array of value-encodings, but the solver's handling of its length is the hard bit. The 20-function corpus measurement (Measurements owed) will tell.
- Whether cig's SMT encoding should model the step budget (`STEPS` in the bytecode, `E515` at the budget's expiry). Including it adds one integer counter to every SMT state, which doubles the width of the state value. Leaving it out means TV cannot catch a pass that changes step counts; `verify_transition`'s `T3` already does (`T3` catches a lost or cloned step mark), so leaving it out of TV may be defensible.
- Whether the `PreservedAnalyses::preserveSet<CFGAnalyses>()` shape from `Mem2Reg.cpp` maps onto cig's structured IR. CIR has no `BasicBlock`-level CFG; its blocks nest under owning nodes. A "CFG analysis" over CIR might be the shape of its nested-block tree, which every pass structurally preserves unless it explicitly rewrites a control-flow node.
- Whether cig's `JumpThreading`-analog pass has anything to do today. LLVM's `JumpThreading` is run twice in the function pipeline because `InstCombine` and loop passes expose more threadable branches each time. CIR's structured `if` has far fewer branch chains to thread, but `short-circuit` (`Kind::Short`) in `ir.rs` is a case worth measuring.
- Whether PGO's indirect-call-site data (LLVM's `PGOIndirectCallPromotion`) applies to cig. The study set aside that cig's inline caches already track one receiver type per `callm` site (`cig-script/src/vm/mod.rs`, `Proto`, `hints: Vec<std::cell::Cell<u32>>` at line 285); whether a `.cigprof` records the top receivers across many runs, or whether per-site caches suffice, was not resolved.
- The right shape of a cig TV cache (LLVM's `ALIVECC_BATCH_OPTS` and Redis cache, `tv/tv.cpp:runOnModule`). For CI the cache would avoid re-solving refinement for pass pairs that have been seen; the cache key is the Alive2 IR text (`src_tostr + "===\n" + tgt_tostr`) at LLVM, and for cig it would be the printed CIR before and after.

## Types for speed: Julia's abstract interpretation, .NET's shared generics and guarded devirtualization, and rustc's monomorphization

[studies/09-types-julia-dotnet-rustc.md](studies/09-types-julia-dotnet-rustc.md)

- The right value for cig's monomorphization cap: Julia uses 3 for `max_methods` and 3 for the tuple-complexity limit; rustc uses 128 for recursion and 2**24 for type length (a different axis). The census justifies a cap of 2 to 3, but the choice is a stage-D decision pending the measurements in entry 3.
- Whether cig's `Union2` layer should be bounded at two elements or at three. Julia uses four (`max_union_splitting`); the census says up to two shapes at a cigo field site and never more. A measured answer waits on entry 8.
- The exact `cost` to assign to a cig builtin that "calls back". Julia uses `inline_nonleaf_penalty = 1000`, a signal rather than a real cycle estimate. cig has no inliner yet, so the field can be added and populated with the same signal, then tuned when an inliner lands.
- Whether cig-cherry's cached native blob should match Julia's four-flag reject (level, debug info, bounds, inline) or a smaller set. Entry 10 suggests the same four; the final list has to wait on cig-cherry's actual flags (decision (f)).
- Whether a `Ty::Union2(A, B)` layer has to be ordered (`A` then `B` is different from `B` then `A`): Julia's `tmerge` is commutative on the lattice; a `Union2` in cig could be stored as a sorted pair without losing precision, which simplifies the equality test at a call cache. Pending the choice of union representation (entry 2).
- Whether cig's specialization cache should have a world axis at all. Rule 7 (verified bytecode, never rewritten) says no, but a module reloaded from a different source has a different hash and so lives in a different cache entry already. Pending a decision on (f).
- Whether cig should adopt Julia's `nortcall` effect (a method that does not call `Core.Compiler.return_type`). cig has no equivalent of `return_type`; the effect would always be true, so it does not need to be tracked. The general question is which of Julia's nine effects collapse to a constant in cig: `notaskstate` (no tasks), `noub` (`forbid(unsafe_code)`), `nonoverlayed` (no overlay tables) and `nortcall` all do. The five that remain are `consistent`, `effect_free`, `nothrow`, `terminates`, `inaccessiblememonly`.
- Whether cig's cig-cherry guards should test one type at a time (the .NET design) or fail over to a two-type polymorphic inline cache (SpiderMonkey's design, another study). The census says one type is enough in the compute programs and two in cigo; either shape matches. Pending the study on CacheIR.

## MLton's whole-program path and GHC's worker and wrapper: monomorphization, defunctionalization and unboxing, and what the "hot loop takes raw i64s" would be in CIR

[studies/10-whole-program-mlton-and-unboxing-ghc.md](studies/10-whole-program-mlton-and-unboxing-ghc.md)

- Cejtin, Jagannathan and Weeks's "Flow-Directed Closure Conversion for Typed Languages" (`papers/compilers/cejtin-2000-flow-directed-closure.ps.gz`) was read in this run. It confirms entries 4 and 5: the translation "implements closures as elements of datatypes, and uses dispatches at certain call-sites to select the appropriate function to call", uses a "general flow-analysis framework which includes OCFA", and reports that "the compile-time cost of flow analysis and closure conversion is extremely small, and that the dispatches and coercions inserted by the algorithm are dynamically infrequent". One mechanism named in the paper that this study did not elaborate: *coercions* inserted at points where different flow sets merge, to keep the target language simply typed. In cig, the simply-typed target constraint does not bind because cig has no source types to preserve through closure conversion; the coercion mechanism is not needed, so entries 4 and 5 do not take it.
- The termination argument for monomorphization in SML relies on the absence of polymorphic recursion. cig has no polymorphism, so termination is trivial; the open question is whether the monomorphization-bound in the pipeline is shared with SpecConstr's and Specialise's (entries 14, 15) as one global budget or three. What would settle it: a decision in cig-compile#34 or a measurement showing the three budgets never bind.
- MLton reports that `deep-flatten` has cases where it exhausts memory and users turn it off (`DeepFlatten.adoc`). The analog in cig is unknown: a pass with quadratic behavior in the shape graph has the same shape. What would settle it: a `--max-pass-mem` option in `cig-compile` that logs the per-pass peak RSS on the test machine.
- MLton's `simplify.fun` runs contify three times; the reason is that other passes expose new one-call-site functions. The cig analog is unknown: at four passes today, the opportunity count is likely small. What would settle it: a `--count-contify-candidates` after each pass on cigo's script.
- The `deep-flatten` and `ref-flatten` safety-for-space argument (`RefFlatten.adoc`: the container is live while the ref is live) maps to cig's `V9` (captured-slot liveness) only loosely. What would settle it: a formal argument that `V9` plus `T3` proves the same invariant MLton proves by liveness approximation.
- The CPR split (entry 12) and the ww split (entry 10) are one pass in GHC (`WorkWrap.hs` performs both at once, "a single worker/wrapper transformation that deals simultaneously with unboxing both arguments and results" in Baker-Finch et al. §2.4). Whether cig splits them is open: an inferred `Ty` on a parameter lets the unboxing pass fire whether or not the function has CPR, so one combined pass is a design candidate. What would settle it: a count of `Func`s that would get one half but not the other on the 21 compute programs.
- The pipeline order of early specialization versus `monomorphize` in cig (entry 15) is set by GHC's shape but is not forced by cig's rules. Running monomorphize after inlining is the alternative: an inlined callee may expose new specialization opportunities. GHC runs `late-Specialise` after `SpecConstr` for exactly this reason. What would settle it: compile-time and specialized-copy count on both orderings, measured on cigo's script and the 21 compute programs.
- MLton's `simplify.fun` runs `removeUnused` four times. The reason is that the pipeline exposes new unused functions after inlining, specialization, and contification; a single pass misses opportunities an earlier pass hid. The cig analog is unknown; the shape is a `dead-pure` run at the end of every pass as entry 16's `Shrink` is. What would settle it: the opportunity count in each position of the pipeline, measured on cigo's script.
- GHC's `[Don't change boxity without worker/wrapper]` note binds the demand analysis and the worker-wrapper pass together: the boxity update is only run when the pass that *consumes* it is scheduled to run next. The cig analog is what pairs `boxity` sub-analysis of entry 11 with the ww pass of entry 10. What would settle it: a single pass structure that runs the sub-analysis and the split as one transaction, so the signature is never in a "boxity updated, worker not generated" state.

## V8 and JavaScriptCore: feedback, tiers, leaving optimized code, and a lighter back end

[studies/12-v8-and-javascriptcore-tiers.md](studies/12-v8-and-javascriptcore-tiers.md)

- Whether cig's "wait after the ICs settle" counter (entry 10) is one byte per function or per site. V8 keeps `invocation_count_before_stable_` per vector; a per-site byte is more accurate for cig-cherry's "this specific guard keeps failing", but it costs one byte per site in the vector. Settled by whether a cig site can recompile independently of the whole function, which is a stage C design decision not yet made.
- Whether cig's exit record (entry 11) is a stream of V8-style translation opcodes (entry 8) or a flat struct. The translation-opcode form is denser (`MATCH_PREVIOUS_TRANSLATION` saves bytes across adjacent exits); the flat-struct form is easier to verify (every exit is one struct of known size). Settled by which cost dominates: compiled-size (cig-compile#36) or exit-time (cig-script#256 phase 3). Both would be measured at the first cherry build.
- Whether cig-cherry tier 3's allocator is `regalloc2` as-shipped or a configured `regalloc2` with a budget flag (JSC's `airUseGreedyRegAlloc` is the shape of a per-build knob). Settled by `regalloc2`'s current knobs, which study 02 names, and by whether tier 3 ever has a compile-time budget it has to meet.
- Whether JSC's `MinifiedGraph` style (entry 11) is a better exit-time recovery format for cig than V8's translation stream (entry 8). The two are not equivalent: a minified graph can recover a constant that no translation slot stored, which may be useful for cig's dead-pure pass elisions; V8's stream cannot. Settled by how many exits need a value no CPU register or stack slot holds, measured at the first cherry build.
- Whether cig's lattice (entry 3) carries "mostly A, sometimes B" states, as V8's `RECOMPUTE_HANDLER` and `HOMOMORPHIC` do. The census shows one program (`trees`, one site, 2.3% of arithmetic executions) saw two pairs; the two-state refinement is for that case and no other today. Settled by whether a second site ever turns up in cigo or in a further benchmark.
- Whether cig-cherry's background compile dispatcher (entry 5) uses locked queues (Maglev's `LockedQueue`) or a lock-free shape. cig's values stay `Rc`, which never cross threads; only the bytecode and the profile cross. Settled by the dispatcher's own measured contention under the compute set; if there is none, a locked queue is enough.
- Whether cig records the "fast-API call" kind of lazy deopt V8 has (entry 10, `kLazyAfterFastCall`). cig has no fast-API path today (`cig-script/src/stdlib/` dispatches through the builtin catalogue, not direct calls), so the third kind has no analogue at the pin. Settled by whether cig-compile ever grows a direct-builtin path, which cig-compile#32's current design does not propose.

## Compiling fast: QBE, TinyCC, CPython's copy-and-patch, Zig, rustc and Cranelift's per-function cache

[studies/14-compiling-fast.md](studies/14-compiling-fast.md)

- **Whether a file-backed template cache can be reproducible across machines.** `cpython-v3.15.2/Tools/jit/_targets.py: _compute_digest` hashes the triple and a few flags to decide a stencil's identity, but the stencil bytes are per clang build. For cig, the bytes would be per `rustc` build; `cig-compile/docs/decisions/0001-backend.md`'s reproducibility rule asks that a specific Rust compiler version is pinned, which would be part of the per-function cache key and the signed artifact. The pin confirms cig's reproducibility statement; the exact composition of the key is not fixed in the clones.
- **How wide the type lattice at entry 9 has to be for cigo's case.** The census (`data/census/README.md`) shows cigo's functions see 2 or 3 argument-type rows and 20% to 34% of field accesses see a second shape. A lattice with a known-class state plus two guarded paths would cover cigo; a narrower lattice would underfit. The exact threshold needs the stage-D build measured.
- **Whether lazy lowering fits rule 7 at reasonable cost.** The lowering's verifier (`cig-script/src/lower/cir/verify.rs: verify`) takes a whole `Module`; a per-function lazy path would verify a function at its first call, which puts verifier time on the critical path and asks a per-function variant of the verifier. The first run of cigo on the VM is 305.9 ms (`cig-script/docs/ENGINES-FIRST-RUNS-1.25.0.md`); the share of module **instructions** that have to be lowered on the first call is the share of instructions in entered functions, bounded below by the share of instructions actually executed, which `data/census/report.md` reports as 30.3% to 32.6% across the seven cigo cases. The top level alone is about 30% of the module (34,841 to 34,911 instructions on 115,268 total) and runs first on every call. The budget for a lazy scheme is that the sum of lowering plus verifying per entered function, totalled over entered functions, is less than the whole-module lowering and verifying time; the saving is at most two thirds, not more than nine tenths.
- **How the per-function cache invalidates on a callee signature change at stage D.** With cig-compile#34's types, a function's compiled bytes depend on each callee's signature; entry 11's `nav_ty_deps` is the model, but cig's own "signature" at stage D is not yet named. The brief's expected set was "callee signatures, captured slots, the runtime ABI version, the level": the pin confirms level, the captured slots are `cig-script/src/lower/cir/ir.rs: VarInfo.captured`, and `cig-compile/docs/decisions/0001-backend.md` names the runtime ABI version. Callee signatures are not yet named.

## The shape of an IR: nanopass and Chez Scheme, Zig's two IRs, the sea of nodes and leaving it, flambda at a distance

[studies/16-ir-shapes-nanopass-zig-sea-of-nodes.md](studies/16-ir-shapes-nanopass-zig-sea-of-nodes.md)

- The number of `define-language` forms in Chez's chain is 27 as counted (`np-languages.ss`), but some of them are intermediate and only differ by one or two productions; a "how many languages between `Lsrc` and `L16` would a redesign need" answer for cig needs a draft, not a count.
- Flambda's exact count of inlining rounds and reports is set by the `-O2`, `-O3`, `-Oclassic` defaults in `flambda.etex` section "Default settings of parameters" (lines 637 to 700), which would need its own entry at the level a paper describes, not covered here.
- Zig's incremental compilation pipeline between ZIR, AIR and codegen is covered in study 14 (compiling fast); this study takes the IR shape, not the cache.
- The sea of nodes is covered here from one paper (Click 1995), one V8 engineering post, and one Graal paper (Duboscq 2013). HotSpot's C2 has no tree in the library; a deeper account of C2's choices and their trade-offs is not available at this pin.
- Keep 2013's "compile time is a factor of 1.75" is on the hardware of 2013, the compilers of 2013, and the benchmarks of that year; it is a number to cite, not a budget cig should plan around.
- The cost to migrate today's four CIR passes (`fold-consts`, `copy-prop`, `sccp`, `dead-pure` in `cig-script/src/lower/cir/pass/`) from a hand-walked `Kind` match to an autogenerated walk over a declared grammar is unknown without a prototype in Rust that mimics `define-pass`'s clause generation. Rust's procedural macros can emit the same shape, but at a build-time cost that the Chez framework pays in Scheme's syntax expansion rather than in a separate crate: whether the trade is worth it for cig's four-passes-growing-to-fourteen depends on which passes are hand-coded by the time the second CIR is drafted.
- The V8 team's numbers for Load Elimination (up to 190 times faster on the CFG) and for cache misses (3x more on SoN) are from their own measurement on their own workloads, cited from the post, not independently reproduced here; a cig-side measurement is only possible once cig has an optimizer worth measuring (cig-compile#33's levels).
- Chez's number "15-27%" faster generated code (Keep 2013, abstract) and "1.75 times" compile time are for the 2013 benchmarks, not for a cig redesign; they say the chain shape is not a priori slow to compile, which is the only use they serve here.
- Whether the autogenerated-walk cost in Rust is paid by a procedural macro that reads a grammar declaration, or by a custom build step that generates Rust source into `target/`, or by a `derive` on each `Kind` enum, is an implementation question left for the prototype. The three options have different debug stories; a `derive` is the one that keeps the generated code visible in `cargo expand`.
- The three-language chain proposed in entry 5 (CIR-0, CIR-1, typed CIR-1) is a floor on the chain cig needs; a worked redesign may want a fourth language where closures are lifted but reference counts are not yet explicit, so `rc elision` has a cleaner input. The number of languages is set by the number of things the passes can read simpler if separated; four is a plausible ceiling.
- The OCaml flambda chapter cites `-O2`, `-O3`, `-Oclassic` levels, and the interface files name `inline_and_simplify`, `inlining_decision`, `inlining_cost`, `inlining_transforms`. The split cig would make differs: cig's optimizer has one level today (cig-compile#33), and the "classic" versus "aggressive" axis maps to cig's `-O1` and `-O3`. The levels are the issue's concern, not this study's.
- The cost of a verifier with auto-generated structural rules against a language declaration is not measured here. Chez pays the cost in Scheme's macro expansion; cig would pay it in a Rust macro. A verifier of the size `cig-script/src/lower/cir/verify.rs` (1,182 lines) would shrink by some amount in a redesign; the amount is not known without the redesign.
- The reference material for a chain-style CIR in Rust has one other reference point worth naming for the prototype: the `rustc_middle` crate already uses `derive` on its `TypeFoldable` and `TypeVisitable` traits to autogenerate walks over Rust's type tree. The pattern (derive a walk for every variant of an enum) is the same shape a cig redesign would need; whether cig's prototype uses `rustc_middle`'s approach, `syn`-and-`quote` directly, or a bespoke `build.rs` is a choice for the prototype, not for this study.
- The division of reference-counting work between `insert-rc` (a pass that places `Inc`/`Dec` in CIR-1) and `rc elision` (a later pass over CIR-1 that cancels adjacent pairs) is not fully settled by the entries above. Lean's `reset`/`reuse` and Koka's Perceus are the two shapes to study (study 5); this study's position is only that both passes belong in CIR-1, not CIR-0, so the oracle CIR has no RC machinery.
- The exact interaction between stage D's speculative narrowing (cig-compile#34's guards and side exits) and the framestate design (entry 14) is not fully laid out here: specifically, whether a guard carries a region pointer or merely an `InstrId` to the pin above it, and whether a merge in CIR-1's CFG unifies two guards' pins or keeps them separate. The answer depends on where the stage C pass to Cranelift traps and how it recovers; the entry says "a pointer back to a pinned instruction" and leaves the shape for the prototype.
- The "Read with" of this study did not open `cig-script/docs/BYTECODE.md` to verify the 73-opcode count, taking the fact sheet's number (section 3) as given. The opcode set is the one cig has today; the count may drift as cig-compile#213 and successors land.
- The shape of Chez's `L15a..L15e` sub-chain between the register allocator's substeps is described as named languages, but their differences are small (`L15a` adds frame-source annotations, `L15b` finalizes frame locations, `L15c` and `L15d` select instructions, `L15e` finalizes register locations). Whether cig needs a sub-chain of that granularity at all is unlikely, since cig's register allocation sits in Cranelift's `regalloc2`; this study leaves it as "the register allocator's chain is Cranelift's", not cig's.
